# Database migration safety

Database schema changes are production releases because application versions overlap, tables may be large, and a DDL statement can hold locks or rewrite data. Safe migration design starts by asking which old and new binaries will run at the same time, what locks the database takes, and how long a backfill competes with live traffic. A migration that succeeds quickly on a small staging table can block production writers for minutes or hours.

## Expand, migrate, contract

For a rename or type change, avoid a one-step destructive edit. Add a new nullable field or compatible structure first. Deploy code that can read the old and new forms, and initially continue writing the old form if necessary. Then dual-write or switch writes in a controlled phase, backfill existing rows in batches, compare values, and move reads to the new representation. Only after all binaries, jobs, and clients stop using the old field should a later release remove it. This lets rolling deploys, delayed workers, and rollback coexist with the schema transition.

Backfills should be restartable and idempotent. Process bounded primary-key ranges, persist a checkpoint, throttle based on replica lag and database load, and expose rows completed and remaining. Avoid one huge transaction that holds locks, bloats the write-ahead log, or makes rollback expensive. Define how concurrent updates are handled: the backfill must not overwrite a value written by new code. A condition on the old value or change-data capture can close the race, followed by a reconciliation query.

## Understand lock and rewrite behavior

Read the database engine's documentation for the exact version in production. A statement that appears metadata-only may still need a strong lock briefly; adding a constraint can scan the whole table; changing a type can rewrite it; and creating an index can block writes unless an online option is used. In PostgreSQL, `CREATE INDEX CONCURRENTLY` reduces write blocking but performs additional work, can fail and leave an invalid index, and cannot run inside a transaction block. Some migration frameworks wrap every migration in a transaction, so the framework and DDL behavior must be considered together. Use short lock and statement timeouts so a migration fails rather than queueing behind a busy transaction and blocking subsequent traffic.

Split schema declaration, data movement, and cleanup into separate operations with observable checkpoints. For constraints, some databases allow adding the constraint without immediate validation and validating separately, reducing impact on concurrent updates. Monitor locks, waiters, query latency, replication lag, disk use, and progress while the migration runs. Ensure free disk can accommodate temporary indexes or table copies.

Before running a migration, rehearse it on production-shaped data and record expected duration and lock behavior. Have a stop rule and a forward recovery plan. Rolling back application code may be simple; reversing transformed or deleted data may not be. Keep backups and verify restore procedures, but do not confuse a backup with a fast migration rollback. The safest schema change is one that can pause at every phase while old and new code continue to function.

## Design review

Which application versions are compatible at each phase? Does the DDL scan, rewrite, or lock the table? Can the backfill pause, resume, and avoid overwriting concurrent writes? How is completion validated before removing the old schema? What is the recovery plan if cleanup has already started?
