A realtime application keeps many clients informed when shared state changes. A WebSocket connection offers a bidirectional channel, but opening sockets is only the first problem. The system must authenticate and track subscriptions, route updates to the right gateways, recover after disconnects, and keep the database authoritative. A live screen should be a projection of durable state, not the only place where an update exists.

## Separate state from connections

Store accepted writes in an authoritative database with versions or sequence numbers. Publish a change event after the write commits, using an outbox or equivalent reliable path when loss matters. WebSocket gateways hold client connections and local subscription maps, but they should be replaceable. A gateway restart drops connections; clients reconnect, fetch a snapshot, and resume updates from a known version. Do not depend on an in-memory gateway map to preserve the only copy of an action.

RFC 6455 defines the WebSocket protocol and its bidirectional frames. The application still needs its own message contract: subscribe, unsubscribe, snapshot version, change event, acknowledgment, error, and heartbeat. Authenticate during connection setup and authorize each subscription, because a user may have access to one room but not another. Recheck or revoke authorization when membership changes; a long-lived connection does not make yesterday's permission permanent.

## Route updates to interested gateways

Partition events by document, room, or topic. A gateway subscribes to backend channels only for topics with local clients, then fans each update to those clients. Broadcasting every database change to every gateway wastes bandwidth. A large room may have clients across many gateways; coalesce rapid state updates or publish deltas under a bounded rate. Discord's engineering account of a million-user server illustrates the scale of one hot subscription and the need to control fanout.

Plan capacity from concurrent sockets, messages per second, bytes per message, and hot-topic fanout. A socket consumes memory, file descriptors, heartbeat traffic, and load-balancer state even when idle. Autoscaling gateways should account for connection draining and reconnection storms. Sticky routing can reduce resubscription work, but correctness should survive a client landing on another gateway.

## Handle gaps and slow clients

Attach a monotonically increasing version to each topic update. If a client sees version 105 after 103, it knows a gap may exist and can fetch a fresh snapshot or request replay from a retained log. Do not assume a WebSocket delivery is durable merely because a send call succeeded; the client may disconnect before applying it. A slow client should receive a bounded queue, a coalesced latest state, or a disconnect-and-resync instruction rather than exhaust gateway memory.

Measure active connections, subscriptions per gateway, publish-to-visible delay, dropped or coalesced messages, reconnect rate, snapshot fetch load, and version-gap repairs. Test database outage, broker outage, gateway restart, and a single room with extreme fanout. The system's promise should specify whether every intermediate event must be delivered or whether the latest correct state is sufficient.

## Design review

Which store owns the state? How does a client resume after a gap? Are subscriptions authorized for the whole connection lifetime? What happens when one room is much hotter than average? How is a slow client prevented from consuming unbounded memory?
