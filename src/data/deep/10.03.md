An impression is an opportunity for a person to see an item. In feeds and advertising, a server returning an item is not necessarily the same as the item becoming visible on screen. The product must specify the visibility threshold, duration, and measurement method. Counting the wrong point in the pipeline can make an experiment or billing report look precise while measuring delivery rather than exposure.

## Place the event at the right boundary

The server can log a served impression when it includes an item in a response. A client can log a viewable impression when the item enters the viewport for a required interval. Both are useful, but label them separately. Client observations can be lost when a tab closes, blocked by network conditions, or fabricated by automated clients. Include a server-issued request ID, placement ID, item ID, position, experiment assignment, and a unique impression ID so the server can validate context and deduplicate retries.

Virtualized lists and infinite scroll complicate measurement. An item may be prefetched but never rendered, rendered offscreen, or seen twice after scrolling away and back. Decide whether repeated exposure in one session counts again and enforce that rule in the event identity. Keep a version of the visibility logic because a change from “one pixel visible” to “half visible for one second” changes the metric even if the data pipeline is unchanged.

## Aggregate without losing auditability

Send accepted events to a durable log and partition them for processing. Count by item, placement, campaign, and time bucket as needed. High-cardinality dimensions can explode storage, so choose a small set of materialized aggregates and query raw events for less common breakdowns. Use event IDs to avoid duplicate counts after worker retries. A windowed stream processor can update minute and hour buckets; late arrivals require correction or a declared cutoff.

For advertising, keep an immutable accepted-event record and a reconciliation trail from served to viewable to billable impressions. A dropped client event should not be converted silently into a billable exposure. Billing rules may require additional fraud filtering and contractual definitions outside the counter itself. Public dashboards can be eventual, while financial reports need a reproducible close process with revisions recorded.

## Use the metric carefully

Impressions are often the denominator for click-through rate. If a UI change alters which impressions are reported, CTR can move without any change in user interest. Track served, rendered, and viewable counts, plus client event delivery rate, by platform and app version. Compare experiment groups on the same instrumentation. A ranker trained on clicks without impression and position data will learn exposure bias from the current ranking.

Monitor event lag, duplicate rate, client-to-server delivery loss, bot filtering, and impossible ratios such as more clicks than validated impressions. Test scroll, rapid navigation, offline replay, and browser backgrounding. A metric definition should include examples of what counts and what does not so engineering, analytics, and product teams share the same meaning.

## Design review

Is the metric served, rendered, viewable, or billable? Which ID deduplicates transport retries? How do repeated exposures count? Can a client fabricate the event? How are late events and instrumentation changes reflected in reports?
