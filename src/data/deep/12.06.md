Ray casting is a classic point-in-polygon test. Cast a ray from the query point in a fixed direction and count how many polygon edges it crosses: an odd count means inside and an even count means outside. The idea is simple and works well for many planar polygons, but an implementation needs deliberate rules for vertices, horizontal edges, boundaries, holes, and floating-point precision.

## Apply the crossing test

For each edge from `(x1,y1)` to `(x2,y2)`, first check whether the edge straddles the horizontal ray's y-coordinate: one endpoint is at or below `y`, the other above. If so, compute the x-coordinate where the segment crosses that horizontal line. Toggle the inside flag when the intersection lies to the right of the point. Half-open comparisons avoid counting a polygon vertex twice when two adjacent edges meet exactly on the ray.

Do not divide by `(y2-y1)` for a horizontal edge without checking the straddle condition; horizontal edges do not cross a horizontal ray under the half-open rule. A point exactly on an edge or vertex needs a separate boundary test if the product requires a deterministic inside/outside answer. Franklin's PNPOLY notes explain a compact crossing implementation and its careful handling of edge cases. For a production GIS operation, a robust library is usually safer than copying a small snippet without its assumptions.

## Respect polygon structure

A simple ring can use parity directly. A polygon with holes uses even-odd parity across all rings, provided the rings are valid and the intended fill rule is defined. Multipolygons test each component. Self-intersecting rings may have ambiguous interior semantics and should be rejected or repaired by a geometry library at ingestion. Coordinate systems matter: longitude/latitude is not a flat uniform plane over the entire globe. Project small local regions to a suitable planar CRS or use a spherical geometry implementation for broad geography.

Before ray casting, use a bounding box or spatial index to avoid scanning every polygon edge for every point. A large polygon can have thousands of edges; edge indexing or prepared geometry speeds repeated tests. The bounding box is only a necessary condition, then the exact point-in-polygon predicate decides.

## Test degeneracies explicitly

Create test cases for a point well inside, outside, on an edge, on each vertex orientation, aligned with a horizontal edge, inside a hole, and near the antimeridian if geographic. Use integer or robust orientation predicates where practical. Floating-point rounding can change whether an intersection lies just left or right of a boundary. Compare your implementation with PostGIS or another geometry library on generated random polygons and boundary-focused tests.

Document the boundary rule in the API. If a geofence treats boundary points as inside, select a predicate such as `ST_Covers`; if it follows OGC `Contains` semantics, boundary-only points are excluded. The ray algorithm is a building block, not a license to leave semantics implicit.

## Design review

How are vertex intersections counted once? What is the boundary policy? Are holes and multipolygons supported? Is the chosen coordinate system planar enough? What robust library or reference implementation validates the result?
