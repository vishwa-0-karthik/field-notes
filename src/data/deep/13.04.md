# Video upload: signed URLs and multipart

Video uploads are large enough that the API should coordinate the transfer, while object storage receives the media bytes. A robust flow starts with an upload session: authenticate the user, check plan quota and expected size, reserve an opaque staging key, and return either a scoped single PUT URL or multipart instructions. Store the session state server-side so a client cannot complete an upload belonging to another account or publish an arbitrary storage key.

## Choose single-part or multipart

A single signed PUT is easy to reason about, but a failed transfer may require sending the entire file again. Multipart upload divides the object into numbered parts that can be sent concurrently and retried independently. The backend initiates the multipart operation and retains its storage upload ID. It can then issue short-lived part URLs in batches, or validate part requests through an upload gateway. The client reports each part's number, ETag, and checksum. The backend validates that every part belongs to the session and that the total is within policy before asking storage to complete the object. S3 assembles parts in ascending part-number order; its ETag for the combined object is not necessarily an MD5 of the full file. Use explicit checksums when integrity verification is needed.

Part size is a tradeoff: small parts increase request overhead and metadata; large parts waste more bandwidth when retried. Concurrency should be tuned to the client network and constrained so many simultaneous users do not overload storage request quotas or their own connection. Provide resumability by persisting the session identifier and completed parts, but make resume authorization expire and bind to the authenticated user. A refreshed client should query server-side parts rather than trusting a local list that may be stale.

## Complete through a state machine

Completion should be idempotent. A client may time out after storage completed the object and retry; the API should return the same accepted asset rather than create a second one. Model states such as `initiated`, `uploading`, `completing`, `received`, `validating`, `ready`, `rejected`, and `aborted`. Use a conditional state transition or transaction to prevent two completion calls racing. After completion, inspect the actual object size and metadata, verify checksums where supported, and run media probing before enqueueing transcoding. Do not trust client MIME type, filename, declared duration, or reported dimensions.

Incomplete multipart sessions retain uploaded parts and can incur storage charges. Abort on user cancellation or terminal errors, and configure lifecycle cleanup as a backstop. If part uploads are still in flight when abort starts, reconcile afterward because a late part may succeed. Keep originals private, use unique keys, and make the staging bucket inaccessible to playback clients. The signed URL is a limited bearer credential: avoid access logs that expose it, keep expiry reasonable, and scope it to expected headers and one upload session.

Monitor upload completion percentage, bytes, part retry rate, session age, abandoned storage, checksum failures, and time from completion to playback-ready. Test network loss mid-part, expiry during upload, repeated completion, part replacement, oversize objects, and stale resume state. The user-visible promise should clarify that transfer completion and playable video availability are separate milestones.

## Design review

When does a file use multipart? Who owns the multipart ID and completion list? Are checksums verified independently of ETags? Can completion be safely retried? How are orphaned parts cleaned up, and what does the client see while transcoding is pending?
