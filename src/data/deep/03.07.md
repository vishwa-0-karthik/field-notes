Multi-version concurrency control, or MVCC, lets readers see a consistent snapshot while writers create newer row versions. In PostgreSQL, ordinary reads generally do not block ordinary writes, and ordinary writes do not block reads. The tradeoff is that old row versions must be tracked and eventually reclaimed, and a snapshot does not automatically make every multi-row business rule safe.

## Follow a row through an update

Imagine an account row with `status = 'ACTIVE'`. Transaction A starts a read. Transaction B changes the status to `SUSPENDED` and commits. A's visible value depends on its isolation level and when its snapshot was taken. The database keeps enough version information for A to see the appropriate state while newer transactions may see B's change. This avoids forcing B to wait for every reader before it can write.

In PostgreSQL, Read Committed takes a new snapshot per statement, so A's second statement may see the new status. Repeatable Read uses a stable transaction snapshot. This is a visibility rule, not a promise that a business workflow can ignore conflicts. If two transactions read different rows and then update them based on each other's old values, both may commit under snapshot isolation and violate a cross-row invariant. Serializable isolation or an explicit coordination point may be needed.

| Concern | MVCC effect | Remaining obligation |
| --- | --- | --- |
| Reader versus writer | Read sees a consistent version | Choose needed freshness/isolation |
| Writer versus writer | Conflicts still occur | Handle waits and retries |
| Old versions | Retained while potentially visible | Vacuum and transaction hygiene |
| Long snapshot | Keeps older state accessible | Can delay cleanup and cause bloat |

## Understand cleanup cost

Updating or deleting rows leaves versions that cannot be reclaimed while an old transaction may still need them. PostgreSQL's vacuum machinery eventually reclaims dead tuples and maintains visibility information. A long-running transaction can pin an old snapshot and make cleanup less effective, increasing table and index size. That can turn a read-heavy workload into an I/O problem over time. Monitor transaction age, dead tuples, vacuum progress, and relation growth.

MVCC also interacts with indexes. An index may point to a tuple that is no longer visible to the current snapshot, so the engine may need a heap visibility check. This is one reason an index-only scan is conditional rather than guaranteed by index contents alone. Freshly updated tables may behave differently from mostly static tables.

## Do not confuse snapshots with replication

MVCC describes concurrent visibility inside a database instance. It does not by itself say how current a read replica is or whether a write survives a host failure. Replication lag and durability are separate contracts. Likewise, a snapshot does not make a distributed workflow atomic across services. Keep each promise separate in a design review.

A useful mental model is “many logical versions, each transaction reads the version allowed by its snapshot.” The actual storage engine uses transaction IDs, visibility rules, and cleanup machinery. The model predicts why reads can coexist with writes and why a forgotten open transaction can have system-wide cost.

## Design review

What snapshot does each statement see? Could two writers both make a decision from stale but internally consistent snapshots? How are conflicts detected? What operational signal shows that old versions are accumulating?
