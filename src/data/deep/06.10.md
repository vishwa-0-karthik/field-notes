Timeouts and circuit breakers limit how much an unhealthy dependency can consume of a caller's time and capacity. A timeout stops waiting for one attempt; a circuit breaker temporarily stops sending attempts after a pattern of failure. Neither proves the remote action failed. Use them with retry budgets, idempotency, and an explicit degraded response.

## Budget the whole request

Suppose an API has a 500 ms deadline and calls three downstream services in sequence. Giving each call a 500 ms timeout permits a 1.5-second response before retry overhead. Divide the end-to-end deadline among connection setup, request execution, and remaining work. Pass a deadline or cancellation signal downstream when supported, but still treat a timed-out write as an unknown outcome because the server may have committed it.

Choose timeouts from observed latency distributions and the user's deadline, leaving room for network variation. A timeout below ordinary p99 latency creates false failures; one far above the request budget ties up workers. Separate connection timeout from overall operation timeout where the client library supports both. Measure time spent queued in a connection pool as well as time on the wire.

## Open the breaker deliberately

A breaker is closed while calls flow normally. It opens after enough recent failures and rejects new attempts quickly. After a cooling period, a limited half-open probe checks whether the dependency recovered. Microsoft’s pattern guidance emphasizes keeping the recovering service from being flooded by these probes. Set thresholds over a useful window and distinguish dependency failures from client errors such as invalid input. One tenant's bad requests should not open a global breaker for all tenants.

Scope matters. A breaker for one remote cluster or endpoint may be appropriate; a single breaker across independent shards can unnecessarily hide healthy capacity. Record why it opened, how many calls it rejected, probe results, and time to close. A breaker that remains open after recovery can be as damaging as one that never opens.

## Bound retries and amplification

Retries may convert transient errors into success, but they multiply traffic precisely when a service is struggling. If three layers each retry three times, one user action can produce 27 downstream attempts. Choose one layer to own the retry policy, cap attempts and total elapsed time, and add randomized backoff to spread traffic. Retry only operations that are safe to repeat or have a stable idempotency key. Do not retry a non-idempotent write after an unknown timeout with a fresh key.

An open breaker needs an application response: stale read within an allowed age, a queued job, a reduced page, or a clear error. A default value that looks like real data can conceal an outage and corrupt decisions. Rehearse slow responses, connection refusal, partial failures, and recovery under load. Observe the database or service protected by the breaker to confirm that the mechanism actually reduces pressure.

## Design review

What is the end-to-end deadline? Could a timed-out operation still have committed? Where are retries owned and capped? Which failures open the breaker, and what does the caller receive while it is open?
