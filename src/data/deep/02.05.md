An API gateway and a load balancer both sit in front of services, but they solve different primary problems. A load balancer distributes connections or requests across healthy targets. An API gateway presents and governs an API surface: routing, authentication, quotas, versioning, transformations, and observability. Products can overlap, so design from required behavior rather than product names.

## Trace an incoming request

For a public commerce API, a client connects to an edge endpoint. The gateway may validate a token, apply a rate limit, select the `orders` route, and attach a request ID. A load balancer may then choose one healthy orders instance. In a simple application, one reverse proxy or managed load balancer may perform enough routing and TLS termination that a separate gateway is unnecessary.

The distinction becomes clearer with multiple audiences. An API gateway can expose one stable public contract while internal services change. It may aggregate responses or translate a public HTTP API to internal protocols. That power can also create a bottleneck: if all business logic is moved into the gateway, every change becomes an edge deployment and incident blast radius grows.

| Concern | Load balancer's typical job | Gateway's typical job |
| --- | --- | --- |
| Target choice | Select healthy replica | Select API or backend route |
| Authentication | Sometimes supported | Often a central policy point |
| Rate control | Sometimes basic limits | Per-client or per-route quotas |
| Contract | Forward request semantics | Publish and version external API |
| Failure | Remove unhealthy target | Return stable public errors |

These are tendencies, not strict product boundaries. AWS Application Load Balancer supports listener rules and target groups; AWS API Gateway offers authorization, traffic management, monitoring, and API versioning. Some systems use both, and some need only one.

## Decide which policy belongs at the edge

Centralize policies that should be uniform and can be checked without domain state, such as token validation, basic request-size limits, and request IDs. Keep resource authorization in the owning service: a gateway may know that a token is valid but not whether its holder may view order 42. Avoid placing the only authorization check at an edge that internal callers can bypass.

Rate limits need clear scope. A per-client limit protects fairness; a backend capacity limit protects the service. A gateway can return `429` when a caller exceeds its quota, but a downstream service still needs overload protection if internal traffic or retries bypass the gateway. Document how clients should back off and whether the rate limit is exact or best effort.

## Plan for failure and change

The gateway is on every request path it fronts. Deploy it redundantly, keep configuration reviewable, and test bad route changes. A load balancer's health check must verify readiness to serve, not merely that the process exists. A gateway can return consistent errors when a backend is unavailable, but it cannot manufacture an authoritative order state. Preserve end-to-end deadlines and tracing headers across both layers.

Before adding a gateway, list the missing capability. If the need is simply distributing requests across three identical API replicas, a load balancer is enough. If several public APIs need independent auth policies, client quotas, and versioned routing, a gateway may earn its operational cost.

## Design review

Which layer authenticates the caller, which authorizes the resource, and which selects a replica? Can internal traffic bypass a critical policy? What happens to all APIs if the gateway configuration is wrong?
