Raw events record individual facts; derived analytics summarize them for fast queries. Both have value. A materialized hourly count is cheap to read but loses detail, while a raw event log can answer new questions and repair mistakes at greater storage and processing cost. The design should state which facts are retained, which reports can be recomputed, and when a report becomes authoritative.

## Define the raw event contract

An event should have a stable ID, type, schema version, subject, event time, ingestion time, and the fields needed for approved analyses. Avoid collecting extra sensitive data merely because storage is cheap. Validate required fields at ingestion and quarantine malformed events rather than silently changing their meaning. Maintain producer ownership and a schema evolution process; a field that switches from cents to dollars without a version will corrupt historical aggregates.

Raw events may arrive twice or out of order. The pipeline needs an idempotency policy based on event ID and a rule for late event-time placement. A log's retention must be long enough for expected recovery and reprocessing. If raw events are deleted for privacy or retention reasons, derived datasets and backups need a corresponding deletion plan. “We can always replay” is false once the source history has expired.

## Materialize useful views

Compute counters, sums, sketches, and grouped rollups for frequent queries. Record the input offset or watermark, transformation version, and output window for each view. A derived table can be updated incrementally from a stream or built in batches from raw storage. Kafka Streams' table and aggregation model illustrates how a stream of changes can maintain a queryable view. Beam's windows and triggers show how early and late results can be emitted for event-time reporting.

Different reports may need different definitions. A public view count can filter bots approximately and update every minute; a financial settlement report may close once with audited rules. Do not hide that distinction under one generic `count` field. Version metric definitions and expose whether a number is preliminary or finalized.

## Recover from a bad transform

When a parser or fraud filter is wrong, create a new derived dataset from raw events using the corrected code. Validate it against the old dataset and known examples, then switch readers or publish a revision. Overwriting the only aggregate in place without provenance makes the change hard to audit. Keep enough source-to-output lineage to explain why a bucket changed. If a real-time pipeline loses a partition, a batch repair can backfill the affected range.

Storage and compute costs need explicit bounds. Keep detailed events for the period needed for audit and correction, then roll up or expire according to policy. Sampled data can support exploratory trends but not exact billing. Monitor ingestion completeness, schema errors, deduplication, consumer lag, raw-to-derived drift, and report query latency. A dashboard with fast queries but no provenance can give confident-looking wrong answers.

## Design review

Which store holds the authoritative fact? How long can raw events be replayed? What versions identify event schema and metric logic? How are late and duplicate events handled? Can an incorrect aggregate be rebuilt and switched without losing recent input?
