# Design: observability and SLOs

Design observability from user operations and service objectives. For each journey—send a message, check out, search, upload—define an SLI for success and latency, the eligible request population, and the measurement window. The SLO gives a target, and the remaining error budget gives teams a concrete way to balance product change with reliability work. Metrics, traces, and logs then explain whether the service is meeting that promise and why it is not.

## Instrument the path and the budget

Instrument request boundaries with count, outcome, latency distributions, and saturation. Histograms expose tail latency that averages hide. Add queue age and consumer lag for asynchronous workflows, replication lag for databases, and freshness for indexes. Propagate trace context across RPC and message boundaries so a request can be followed from API to worker and dependency. Link structured logs to trace and span IDs; keep unique IDs out of metric labels to control cardinality. Logs should omit secrets and unnecessary personal data.

The SLI must match user experience. A response can be HTTP 200 but still be unusable; a delayed event can make the workflow fail even if every component returns success. Count eligible traffic and exclusions carefully. Missing telemetry must not count as success. Use burn-rate alerts across a short window for urgent budget consumption and a longer window for slow degradation. Page only on signals that require action; use dashboards and tickets for lower urgency.

## Response and decision loop

When an alert fires, the runbook should show impact, relevant dashboards, dependencies, and safe mitigation. During an incident, use a clear lead, operations owner, communications owner, timeline, and reversible actions. Afterward, identify contributing system conditions and create owned, testable actions. Error-budget policy may pause risky releases when budget is exhausted, but it should guide reliability investment rather than punish the team. Correlate release events with telemetry and use canaries to limit blast radius.

Observability itself has availability, scale, privacy, and cost constraints. Export should be asynchronous and bounded; monitor dropped telemetry, collector queues, ingest delay, cardinality, and backend availability. Sampling reduces trace volume but can hide rare slow events; use tail sampling or targeted retention where appropriate. Run drills that deliberately break a dependency and verify alert coverage, trace correlation, dashboards, and on-call access.

Measure objective attainment, budget burn, time to detect, time to mitigate, telemetry loss, and recurring incident classes. Review SLOs when product expectations or architecture change. Test a telemetry gap, deployment regression, overloaded queue, and user-visible degradation that does not create server errors. Observability is complete enough when the team can ask new questions from production data without improvising high-risk instrumentation in the middle of an outage.

Keep the SLO review cross-functional: product owners clarify which failures matter, engineers validate the measurement, and on-call responders confirm that alerts lead to action. A monthly review can identify an objective that is too strict to be useful, a metric that omits an important client failure, or a budget policy that teams cannot follow. Store the query and calculation with the objective so the reported budget can be reproduced.

## Design review

Which user journey defines the SLO? Do SLIs include asynchronous delay and meaningful outcomes? Are alerts tied to budget burn and actionable symptoms? Can traces cross queue boundaries? How does the team respond when the telemetry backend itself is unavailable?
