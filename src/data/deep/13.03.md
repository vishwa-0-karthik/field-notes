# An avatar service

An avatar looks like a small image field, but it combines identity, upload, moderation, variant delivery, and cache invalidation. A useful design treats an avatar as a versioned asset attached to a user, rather than as bytes embedded in a profile row. The profile stores an asset identifier or immutable URL. The upload service owns bytes and processing; the profile service owns which accepted asset is currently selected.

## Separate asset creation from selection

The user first requests an upload intent. The server checks authentication, account status, and any product policy, then creates a private staging asset with an unpredictable identifier. The browser uploads directly to object storage using a short-lived scoped URL. A worker checks actual file type and dimensions, applies pixel and byte limits, strips metadata, scans or moderates content, and creates standardized square renditions. Until the asset is approved and fully processed, the profile continues pointing at the previous avatar. This avoids a blank avatar or unsafe upload becoming immediately visible.

When processing succeeds, a profile update atomically changes the selected avatar reference and increments an avatar version. If two browser tabs finish out of order, use a compare-and-set against an expected profile version or an explicit “latest user choice” token so a stale upload cannot unexpectedly replace a newer selection. Keep the asset lifecycle separate: an upload may be ready but not selected, and a selected asset may be replaced while the old object remains briefly for cache and rollback needs. Reference counting or delayed garbage collection is safer than deleting bytes inline with the profile update.

## Make delivery predictable

Serve a small set of rendition sizes through stable versioned URLs: for example, tiny list avatars, medium profile images, and a larger detail view. Include the avatar version in the path so the CDN can cache immutable objects aggressively. A mutable `/users/123/avatar` endpoint can redirect to that path, but it needs a short TTL or revalidation. Do not use a user-specific cookie or authorization token in a public avatar cache key unless the response truly varies by it; that fragments cache and can expose private variants if cache policy is incorrect. For private communities, issue signed delivery URLs or perform an authorization check before redirecting to a cacheable protected object.

Default avatars should be generated from a deterministic user seed or selected from a small shared catalog, not materialized as one unique image per account. A generic default has excellent cache reuse. The API should return an explicit fallback state so clients don't retry a missing image indefinitely. Include deletion and account closure semantics: remove the profile reference first, then schedule asset cleanup according to retention and legal requirements.

## Moderation, privacy, and resilience

Avatar processing is a user-generated-content pipeline. Make moderation decisions auditable, allow safe retry of transient scanning failures, and distinguish rejection from processing outage. Keep original uploads private and limit worker permissions to their required buckets. If the transform system is unavailable, keep the previous avatar and retry asynchronously. Rate-limit upload intents and cap pending assets per user to stop resource abuse. Avoid embedding sensitive identifiers in public object paths; opaque identifiers reduce casual enumeration but are not a substitute for access control.

Operationally monitor upload completion, processing age, moderation queue age, failed transforms, cache hit rate, stale-avatar reports, and garbage-collection lag. Test out-of-order uploads, rejected content, storage success with lost client callback, user deletion during processing, and CDN caching across avatar versions. A good avatar system preserves the last known-good image until its replacement has crossed the full validation boundary.

## Design review

Does the profile point only to a ready asset? How do competing uploads resolve? Are renditions versioned and safe to cache? What moderation and file limits apply? How does deletion interact with CDN TTLs and delayed cleanup?
