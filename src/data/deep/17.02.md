# Design: a video platform

A video platform is a lifecycle system: ingest original media, validate it, create renditions, publish metadata, authorize playback, and deliver segments near viewers. The key invariant is that a video becomes playable only when every required manifest and segment is available and verified. Upload acceptance and video readiness are separate user-visible states.

## Upload and processing workflow

The client requests an upload session from an authenticated API. The service checks quota and creates a private staging object key, then returns short-lived signed PUT or multipart instructions. On completion, the backend verifies the object size, checksum, detected format, and ownership. Media probe and malware/content checks run under CPU, memory, and duration limits. Only then does a job enter the transcoding queue. The original is immutable and retained according to policy.

Workers produce a versioned rendition ladder with aligned segments, supported codecs, and HLS or DASH manifests. A media record tracks state such as `uploading`, `validating`, `transcoding`, `ready`, or `rejected`. Workers use idempotent job IDs and deterministic output paths; they write to a temporary package and verify segment readability before atomically publishing the manifest pointer. A partial package must never become the current playback target. Queue priority, per-account quotas, and worker concurrency protect against large files monopolizing compute.

## Playback and delivery

The client requests playback authorization for an asset. The service checks entitlement and returns a manifest URL plus short-lived edge authorization. The player fetches the manifest and selects a rendition based on estimated bandwidth, buffer, device decode ability, and user settings. Segments are immutable and cacheable at a CDN; manifests may be immutable for VOD and short-lived for live or personalized playback. Edge token validation must happen before a cached object is served, while cache keys should avoid unnecessary per-user variation. DRM can protect premium media where the threat model requires it, but it adds key management, license infrastructure, and platform compatibility requirements.

Live ingest has a distinct path: contribution stream, low-latency packaging, live playlist updates, and playback buffering. WebRTC serves interactive real-time sessions; HLS/DASH/CDN is generally better for large one-to-many audiences where some delay is acceptable. A hybrid can let hosts use WebRTC and viewers use segmented delivery.

## Reliability and economics

Track upload success, time to ready, transcode cost per source minute, worker backlog, playback startup time, rebuffer ratio, average bitrate, CDN hit rate, origin egress, and authorization failures. Analyze errors by geography, device, codec, and network. Test multipart resume, corrupt source, worker crash, a missing segment, expired token against a cache hit, rights revocation, and popular title cold start. Keep a base rendition for broad compatibility and a fallback path when a high-quality variant fails.

The catalog should store descriptive metadata and processing provenance separately from segment objects: owner, title, visibility, source revision, rendition profile, and moderation state. This lets the product update a caption or visibility without re-encoding video. Deleting a video should revoke new playback authorization immediately, while asynchronous lifecycle work removes manifests and segments after the required retention window. Treat CDN invalidation as best effort unless the edge checks authorization on each request.

## Design review

Which state transition makes playback available? How does the system verify package completeness? Can CDN caching coexist with entitlement checks? What controls bound transcode cost? Which protocols match interactive and broadcast latency needs?
