An inverted index changes the lookup direction from “which terms are in this document?” to “which documents contain this term?” Its dictionary maps each normalized term to a postings list. A posting commonly contains a document ID and may also hold term frequency, field, and token positions. The extra information supports ranking and phrase queries, while increasing index size and update work.

## Build a small index by hand

Take three documents: `1: red bike`, `2: blue bike`, and `3: red helmet`. After lowercasing and tokenization, the dictionary contains `red → [1,3]`, `bike → [1,2]`, `blue → [2]`, and `helmet → [3]`. To answer `red AND bike`, intersect the two sorted lists and return document 1. To answer `red OR bike`, merge their union and get all three. For a phrase such as `red bike`, document membership alone is insufficient; positional postings must show that `bike` follows `red` in document 1.

Store postings in increasing document-ID order so list intersection is linear in the lengths of the lists. For an AND query with several terms, intersect the shortest lists first to reduce intermediate work. Stanford's retrieval text describes both the basic structure and this document-frequency ordering. Real systems may encode gaps between sorted IDs and compress blocks to reduce disk reads. Compression saves space and often improves speed by moving fewer bytes, at a CPU decoding cost.

## Decide what the analyzer means

The index is only as useful as its token pipeline. Unicode normalization, case folding, language-specific segmentation, stemming, and stop-word treatment determine the dictionary keys. If `running` is indexed as `run` but the query keeps `running`, the posting list appears empty. Version the analyzer or rebuild when its behavior changes. Store the original document fields separately for display; normalized tokens are not suitable as user-visible snippets.

Fields matter. A title match may deserve more weight than a body match, and a `brand` filter should not be interpreted as free text. One design keeps separate field indexes; another encodes field information in postings. Both must handle missing fields and schema changes. Positions and offsets enable exact phrase matching and highlighting, but they add storage. Choose based on query features, not by indexing every possible detail by default.

## Update without corrupting the view

A mutable document may have old postings for terms it no longer contains. Search engines commonly write new immutable segments, mark old document versions deleted, and merge segments later. Until the index refreshes, the query may see the old version. Attach a source version to each update so a delayed update cannot replace a newer one. Deletion must remove visibility promptly enough for the product's privacy and correctness requirements, even if physical segment compaction happens later.

Monitor index size, term count, postings per field, segment count, merge pressure, query reads, and update-to-searchable lag. A common term can have a huge posting list; a rare term is cheap to intersect. Protect the system from pathological queries that scan too many postings or ask for huge result windows. The inverted index is a retrieval structure, not a full answer to ranking, authorization, or freshness.

## Design review

What is stored in each posting, and which query feature needs it? Are index and query analyzers compatible? How are old document versions hidden? What is the cost of a common-term query? Can deletions and access changes become visible within the required deadline?
