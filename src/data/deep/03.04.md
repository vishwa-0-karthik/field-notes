A B-tree is a balanced, ordered index that keeps keys in pages and lets a database narrow a search through several levels. Its value is not only fast equality lookup: ordered leaves also support ranges, prefix scans, and sometimes `ORDER BY` without a separate sort. Understanding the page structure makes index choices and write costs easier to reason about.

## Follow a lookup through the tree

Imagine an index on `(customer_id, created_at)` for an orders table. A lookup for one customer's recent orders starts at the root page, follows separator keys through internal pages, and reaches a leaf page containing key entries and row references. It can then walk adjacent entries in key order until it has enough rows. Because each page contains many keys, the tree has high fanout and stays shallow even for large tables. The balance property means growth adds levels gradually rather than turning lookups into a long chain.

An equality search on `customer_id` finds a contiguous region. Adding a time range or descending order can use the second key in that region. Reversing the index to `(created_at, customer_id)` changes which entries are adjacent, so the same query may inspect far more keys. This is why composite index order follows the query shape, not the column order in a table.

| Query | B-tree fit | Reason |
| --- | --- | --- |
| `id = 42` | Strong | Direct ordered-key lookup |
| `created_at BETWEEN a AND b` | Strong | Scan a bounded key range |
| `ORDER BY created_at LIMIT 20` | Often strong | Read leading ordered entries |
| `name LIKE 'ann%'` | Conditional | Prefix can form a range with suitable collation/operator class |
| `name LIKE '%ann%'` | Poor | Leading wildcard has no narrow starting point |

PostgreSQL's index-type documentation describes B-trees as suitable for equality and range comparisons; its detailed B-tree documentation describes the multilevel balanced implementation. A database planner may still choose a full scan when most rows match, because following the index and fetching many scattered table rows can cost more.

## Account for inserts and updates

An insert finds the correct leaf page and adds an entry. If the page lacks room, the tree may split it and update parent separator information. A split is local, but it still writes pages and log records. Updating an indexed key can require a new index entry; maintaining many B-trees makes writes and storage more expensive. Duplicate values also create many entries, though PostgreSQL may compress duplicate leaf entries with deduplication in eligible cases.

An index entry typically points to a row or tuple location rather than containing every requested field. Fetching table rows can dominate a query if it returns many results. An index-only scan may avoid some table access when the database can verify visibility and the index contains needed data, but this depends on engine details and workload. Do not assume that “uses index” means “fast”; inspect actual row counts, heap fetches, and I/O.

## Keep the abstraction honest

B-tree diagrams often show one key per node; production indexes store many keys per page and manage concurrency, page splits, deleted entries, and recovery. The useful mental model is ordered pages plus a shallow search path. It predicts why a range query is natural, why a leading wildcard is not, and why random inserts can cause more page churn than an append-like key pattern. It does not predict a query plan without data statistics and cost estimates.

## Design review

For a proposed index, identify the leading equality keys, the first range key, and the rows the query must return. Can the scan stop early? How many table fetches remain? What extra work will each write create?
