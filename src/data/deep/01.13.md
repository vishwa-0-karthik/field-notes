Infrastructure is useful when it removes a concrete constraint. Every new database, queue, cache, service, or region also creates a new failure mode and a new thing to operate. The right time to add a component is when a simpler design cannot meet a stated requirement with reasonable margin.

## Identify the pressure first

Suppose a booking API slows during evening peaks. Possible causes include an unindexed query, too many round trips, lock contention, a small connection pool, or insufficient compute. Adding a cache might hide one slow read while leaving the conflicting write path untouched. Start with a trace, query plan, saturation metric, and load test. Fix a local bottleneck locally when possible.

The same principle applies to asynchronous processing. A queue helps when work can be decoupled from the request or when a burst should be absorbed. It does not create capacity by itself. If consumers process 100 jobs/s and producers send 200 jobs/s for an hour, the backlog grows by 360,000 jobs. You need a recovery plan, retention capacity, and an answer to what happens when the queue is full. For a small synchronous operation that already meets its latency target, the queue may only add delayed failure.

| Proposed component | Evidence that may justify it | Obligation it adds |
| --- | --- | --- |
| Cache | Repeated hot reads and measured DB pressure | Invalidation, stale data, warmup |
| Queue | Work can finish after response; burst exceeds steady capacity | Retries, deduplication, backlog monitoring |
| New service | Independent ownership or scaling need | Network contracts, tracing, deployments |
| New database | Existing store cannot meet a required access pattern | Data sync, backups, operational expertise |
| Second region | Recovery target exceeds one region's capability | Replication, failover drills, data residency |

## Prefer a small reversible step

If the current SQL query is slow, try a fitting index and measure its effect before copying the entire dataset into another store. If a monolith has tangled modules, enforce module boundaries before splitting the network. If one instance is near capacity, test whether a larger instance or additional replica solves the near-term problem before introducing a full orchestration platform. These are not permanent prohibitions; they are cheaper experiments.

Ask whether the team can operate the proposed system. A component needs alert thresholds, dashboards, backup or replay procedure, upgrade path, and an owner. A design that meets a synthetic load test but cannot be restored after an incident is incomplete. Fowler's microservice tradeoff analysis emphasizes that distributed boundaries bring coordination and operational costs; those costs should be paid for a visible benefit.

## Recognize the exceptions

Some infrastructure is required before it is heavily used. Regulatory isolation, disaster recovery, or an explicit availability target may demand redundancy at low traffic. Security controls are not optional merely because the product is small. The decision rule is not “always start with one server”; it is “tie every component to a requirement or measured risk.”

Record a trigger for future change: “Introduce a dedicated search index when p95 catalog query latency exceeds 200 ms at projected peak after SQL tuning,” or “move media processing to a queue when the 99th-percentile upload response exceeds the target because of transcode time.” This keeps the architecture adaptable without building speculative complexity now.

## Design review

If the proposed component were removed, which documented promise would fail? Is there a simpler change that meets that promise? Who will operate the new component, and what will they do when it fails at peak load?
