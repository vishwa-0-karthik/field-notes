Streaming percentile analytics estimates the distribution of values as events arrive. It is often used for request latency, checkout duration, or delivery time. An average hides a long tail: 99 fast requests and one very slow request can have an acceptable mean while the slow user has a poor experience. A percentile answers a rank question, such as the value below which 99% of observations fall. The pipeline must preserve the distribution well enough for the chosen decisions.

## Define the measurement population

Choose the start and end of the measured operation, units, success and failure treatment, and grouping dimensions. A p99 over all API routes can be dominated by one high-volume fast route and hide a slow low-volume checkout route. Report by route or critical journey, but avoid exploding into millions of low-sample labels. Include sample count beside every percentile. A p99 from 20 observations is unstable because one observation determines much of the tail.

Choose event-time or processing-time windows and a late-data policy. A five-minute dashboard can be provisional until delayed events arrive. Beam's windowing model makes the watermark and trigger choices explicit. Keep a revision marker if published values can change. Do not average five-minute p99 values to produce an hour's p99; merge distribution summaries or recompute from raw values, weighted by observation count.

## Pick a summary and validate it

An exact percentile sorts all values in a bucket. That can be feasible for small or closed reports but costly for continuous high-cardinality monitoring. A histogram keeps counts in value buckets and can merge by adding corresponding bins; its error depends on bucket widths. A t-digest or KLL sketch keeps a compact approximate distribution and supports merges, with different accuracy profiles. Apache DataSketches documents KLL rank error and compares it with t-digest. Choose based on the required p99 value accuracy, not only memory usage.

Build local summaries per worker and time bucket, then merge compatible summaries in a reducer. Include units, sketch parameters, schema version, partition, and input range. Duplicate partial merges can alter a distribution; missing partitions can make it look healthier than reality. A highly skewed value such as a timeout cap should be represented consistently, not dropped from one service and included by another.

## Tie percentiles to action

Alerting on p99 requires a minimum volume and a threshold sustained across enough windows to avoid noise. Pair percentile with error rate and throughput: a sudden drop in p99 may mean slow requests are timing out or never reaching the measurement point. Keep exemplars or sampled traces for high-latency observations so engineers can investigate causes; a sketch cannot identify individual requests.

Compare stream estimates with exact calculations on sampled buckets, including repeated values and extreme tails. Monitor ingestion lag, window completeness, sketch merge errors, percentile drift, and per-label cardinality. A dashboard should state whether values are exact, approximate, or provisional. The number is useful only if its population and error are understood.

## Design review

Which requests enter the population? What sample count makes p99 meaningful? Can summaries merge across workers without duplicate input? What error at the alert threshold is tolerable? How will an outlier be traced after the sketch reports it?
