A flash sale concentrates many purchase attempts on a small quantity of stock. The central correctness rule is that accepted reservations must never exceed available inventory. A fast cache or distributed lock can reduce load, but the authoritative inventory update must enforce that rule atomically. Separate admission, reservation, payment, and final sale: a user entering a waiting room has not yet bought an item.

## Reserve with a conditional write

Suppose a SKU has 100 units. A read followed by an unconditional decrement is unsafe: many requests can read 100 before any writes occur. In PostgreSQL, one transaction can execute `UPDATE inventory SET available = available - 1 WHERE sku = $1 AND available > 0 RETURNING available`. Only an update that returns a row won a unit. Insert a reservation with a unique `(sale_id, user_id)` or idempotency key in the same transaction so a client retry cannot reserve twice. DynamoDB offers conditional writes for the same underlying idea: the write succeeds only when the stated condition still holds.

If inventory is split across warehouses or seats, reserve the exact allocatable unit or shard. A single hot SKU row may serialize all successful attempts. That is acceptable for a small sale but can cap throughput. Preallocate stock into bounded shards or tokens if measurements justify it, then reconcile shard totals with the authoritative ledger. The sum of allocated tokens must equal the stock budget; otherwise sharding only hides overselling.

## Handle the reservation lifecycle

A reservation has an ID, owner, stock unit or quantity, expiry, and state. Once reserved, payment can happen asynchronously within a stated time window. On successful payment, transition the reservation to confirmed exactly once. On failure or expiry, return the unit through a conditional state transition so two cleanup workers cannot release it twice. A late payment callback needs a defined policy: honor it if the reservation still owns stock, refund it, or fulfill from a separate buffer. Do not silently turn a paid customer into an oversold order.

Maintain an append-only inventory movement or reservation audit trail to reconcile `initial_stock - confirmed - active_reservations` with `available`. Payment provider calls are outside the inventory database transaction, so use an idempotency key and a recoverable state machine. A process crash between reserving and publishing a payment job can be handled with an outbox row written in the same reservation transaction.

## Shape demand before the hot row

Rate limit clients and use an admission queue or waiting room to keep the database within measured capacity. The queue should give a clear status, expiry, and retry behavior; it should not promise stock until the authoritative reservation succeeds. Cache a rough sold-out flag to reject obviously futile attempts, but let the source of truth make the final decision because cache invalidation and concurrent updates can lag. A Redis lock can coordinate some work, yet its lease can expire while a slow client continues; Redis documentation explicitly discusses fencing tokens for correctness-sensitive locking.

Measure accepted reservations, rejected attempts, stock remaining, reservation expiry rate, payment completion, queue wait age, and reconciliation drift. Load-test the true hottest SKU and retries, not only evenly distributed products. If a sale is paused, preserve reservation state and a way to resume or refund, because dropping queued requests is different from resolving already accepted orders.

## Design review

Which atomic write prevents overselling? How are duplicate requests identified? What releases expired reservations, and can release happen twice? What occurs when payment succeeds after expiry? How much demand can admission safely pass to the authoritative store?
