Storage engines balance read cost, write cost, space, and operational complexity. B-tree style pages, log-structured merge trees, and append-only hash files make different choices about when to reorganize bytes. Select from measured access patterns and the durability contract, not from a claim that one structure is universally faster.

## Compare the data paths

A page-oriented B-tree keeps keys sorted and updates pages in place or through a copy-on-write variant. It supports point reads and ordered scans with a shallow tree, but updates may touch nonadjacent pages and require careful crash recovery. An LSM tree accepts writes into memory and a log, flushes sorted files, then compacts them in the background. Sequential writes are efficient, but reads may consult several levels unless filters and indexes narrow the search. An append-only hash file can serve point lookups through an in-memory key directory, but range scans are weak and the directory's memory grows with key count.

| Design | Strong fit | Cost to watch |
| --- | --- | --- |
| B-tree pages | Ordered reads and mixed updates | Page splits, random writes, concurrency |
| LSM tree | High write rate and sorted key space | Compaction, read and space amplification |
| Log plus hash index | Simple point lookups | RAM per key, merge and scan limits |

The surrounding cache changes the result. If 99% of reads hit memory, disk read amplification may matter less than compaction write load. If values are large, keeping only offsets in memory may help. If queries frequently scan adjacent keys, data layout and block compression can dominate point lookup speed.

## Quantify the amplification triangle

Write amplification measures how many bytes reach storage for each logical write. LSM compaction can rewrite the same key across levels; in-place updates and page splits also write extra bytes. Read amplification counts the extra blocks or files considered for a lookup. Space amplification includes stale versions and temporary compaction files. An engine can lower one factor by spending more on another or by reserving more RAM for filters and indexes.

RocksDB exposes these as tuning dimensions and warns that compaction throughput can limit sustained writes. Benchmark the steady state after filling the store and performing updates. A short benchmark may measure only memtable acceptance and miss the later compaction debt. Include delete-heavy and overwrite-heavy phases, because tombstones and old versions affect both space and reads.

## Include correctness and operations

The data path cannot be evaluated separately from its write acknowledgement. A fast non-sync write may be lost after machine failure. Synchronizing every write can increase latency, while batching syncs shares cost and changes the loss window. An engine with replication may acknowledge after a quorum rather than one local disk, but recovery and failover still need testing. Record the promise in terms the application can understand.

Consider tooling too: online backup, corruption detection, format upgrades, metrics, and safe compaction controls. A simple engine with a weaker benchmark may be preferable if it is easier to recover and meets the service objective. Benchmark p95 and p99 reads while compaction runs, not only throughput with no background work. Use a workload trace representative of production rather than uniform random keys if hot sets or scans exist.

## Design review

Which operation dominates cost at scale? What happens after the store is full and compaction is continuous? How much RAM is available for indexes and filters? Which write acknowledgement and recovery promise does the application need?
