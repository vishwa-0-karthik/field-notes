Durability means an acknowledged write survives a specified set of failures. Replication is one technique for meeting that promise, but the number and placement of copies, write acknowledgement rule, and repair process determine the real guarantee. Availability asks whether the service can respond during failure; it is related but distinct. State both as observable service behavior.

## Name the failure before counting replicas

Three copies on one disk protect against neither a disk failure nor a host failure. Three disks on one host protect against disk loss but not host loss. Copies in separate availability zones can survive more failures, at network and coordination cost. A second region may improve disaster recovery but usually changes write latency and replication lag. S3's public data-protection documentation describes durability, availability, versioning, and replication features; these are separate protections with different scopes.

An acknowledged write can mean stored on one node, synchronized to one disk, or accepted by multiple failure domains. With asynchronous replication, a leader can return success before a follower receives the write, leaving a loss window during failover. With synchronous or quorum replication, the response waits for enough copies, but a partition can make writes unavailable. Decide the allowed recovery point objective before choosing the acknowledgement path.

## Repair lost and corrupt copies

After a node fails, replicas may become under-replicated. The system should detect that state, select a replacement location, copy the correct version, and verify it. If replicas disagree, a version or authoritative log order determines which data to repair from. Blindly copying the first reachable bytes can spread corruption. Background scrubbing and checksums catch latent bit errors that do not appear until a read.

Erasure coding can reduce storage overhead compared with full replication while surviving a chosen number of fragment losses. It increases encode, rebuild, and small-read complexity. The right scheme depends on object size, failure domains, repair bandwidth, and latency objective. For hot small objects, full replicas may be simpler; cold large objects may justify coded storage. Benchmark recovery traffic, because a large failure can consume more network than steady-state use.

## Keep backup and versioning separate

Replication faithfully propagates accidental deletion and incorrect writes. Versioning can retain prior object states, but retention rules may remove them. A backup or immutable recovery copy protects against a different class of failures. Define point-in-time restore, key and metadata recovery, and how long recovery takes at single-object and whole-region scale. Test the restore rather than inferring it from the existence of copies.

Observe the number of healthy copies, placement across failure domains, time spent under-replicated, repair queue age, checksum errors, and replication lag. A nominal “three replicas” setting is not proof that each object currently has three healthy, independently placed copies. Fail closed on a write if the required durability threshold cannot be met, or explicitly return a weaker status the caller understands.

## Design review

Which failures must an acknowledged write survive? Where are copies placed? What happens when the required replica count is temporarily unavailable? How are divergent or corrupt copies repaired? What does backup cover beyond replication?
