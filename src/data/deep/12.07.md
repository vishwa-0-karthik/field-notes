A seen filter helps a service avoid returning an item a user has already viewed, received, or acted on. An exact set answers membership correctly but can be large. A Bloom filter stores a compact bit array and several hashes: it can say “definitely not seen” or “possibly seen.” It has false positives but no false negatives under its standard add-only model. That means it may hide a new item, so it is appropriate only when that error is acceptable.

## Size the filter for expected load

The false-positive probability depends on bit-array size, number of inserted elements, and number of hash functions. Configure for the expected capacity and error target. If a filter fills beyond its design capacity, false positives rise and a service may start hiding many unseen posts. Redis documents both capacity and false-positive configuration for Bloom filters. Monitor estimated insertions and observed false-positive rate; rotate or expand filters before they become saturated.

Use a stable item identity such as post ID plus feed version. If one user's “seen” state is stored in one filter, a global filter shared by all users produces incorrect results. Partition by user or by a bounded cohort, and include scope and time window in the key. A daily filter can expire after a week if the product only suppresses recent items. This keeps memory bounded and avoids an unbounded all-time history.

## Place false positives in the right stage

A Bloom filter is useful to skip a database membership lookup for items likely already seen. If it says “possibly present,” confirm against an exact store before suppressing the candidate. This preserves correctness while reducing most lookups. If the product accepts occasional omission, it can suppress directly, but expose that approximation in the design. A Bloom filter cannot enumerate seen IDs or remove one arbitrary ID; deletion needs a counting Bloom filter, a rotating generation, or exact state.

Filters used across a distributed pipeline need consistent updates. If writes are asynchronous, a newly seen item may still be returned until the filter catches up. If each region has a separate filter, users moving between regions may see duplicates. Use an event stream or exact durable table as the source and rebuild compact filters from it. Ensure filters are not used for authorization: a false positive or stale filter could deny valid access, and a false negative could reveal an item if the filter were treated as a permission gate.

## Compare with exact state

An exact set is necessary when every item must be accounted for, such as financial deduplication or strict “one impression ever” rules. A Bloom filter fits high-volume recommendation or feed suppression where one missed candidate has low cost. Hybrid designs use the filter for cheap negative checks and an exact database for positives. Test a saturated filter, duplicate additions, restart, and regional resync. Measure memory per user, false positives, exact lookup rate, and duplicate or missing item rate.

## Design review

What does “seen” mean and for how long? Are false positives allowed to hide a candidate? How is capacity chosen and saturation detected? Can an item be removed? Is the filter merely an optimization, or does it accidentally control access?
