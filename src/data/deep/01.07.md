A server handles many requests by overlapping work that spends time waiting with work that uses the CPU. The programming model varies—threads, processes, an event loop, or a mixture—but the capacity question is the same: how many requests can make progress without saturating CPU, memory, file descriptors, connections, or a downstream dependency?

## Follow one request through the machine

A connection arrives at a listening socket. The operating system accepts it and provides bytes to the server. The application parses the request, authenticates it, runs business logic, perhaps asks a database for data, serializes a response, and writes bytes back to the socket. Each step uses different resources. Parsing and compression use CPU; database calls and network writes often spend much of their time waiting. The server's concurrency model determines what it does during those waits.

A thread-per-request design blocks one thread during synchronous I/O, so many concurrent requests may need many threads and stacks. An event-loop design registers I/O work and continues serving other requests until callbacks are ready. It can handle many mostly idle connections with relatively few threads, but a long CPU-bound callback blocks progress for unrelated clients. Node.js documentation explicitly warns that both event-loop callbacks and worker-pool tasks must stay bounded.

## Distinguish concurrency from throughput

Concurrency is the number of operations in progress; throughput is completed operations per second. A server can have 10,000 open keep-alive sockets while completing only 200 expensive requests per second. Similarly, adding threads may raise concurrency without raising throughput if all requests wait on one saturated database connection pool.

Use the relationship **in-flight requests ≈ arrival rate × latency** to reason about queues. At 500 requests/s and 200 ms average response time, about 100 requests are in flight. If database latency becomes two seconds, the same arrival rate requires about 1,000 concurrent request slots. Without limits, memory and connection counts grow. With limits, new requests wait or are rejected. This is why timeouts, bounded pools, and load shedding belong in a server design.

| Workload | Main pressure | Useful response |
| --- | --- | --- |
| Many idle sockets | File descriptors and buffers | Efficient I/O and idle timeouts |
| Heavy JSON transformation | CPU and event-loop time | Bound input, optimize, offload work |
| Slow database queries | Pool and queued requests | Fix query, cap concurrency, time out |
| Large downloads | Network bandwidth and buffering | Stream with backpressure |

## Put bounds on shared resources

A production server needs limits for request body size, handler time, database connections, outbound calls, and queued work. A timeout on the inbound request is insufficient if the abandoned database query keeps consuming a connection. Cancellation should propagate where the stack supports it. A queue that accepts unlimited work is merely a delayed overload. Bound it and define what callers see when it is full.

Measure both total load and saturation: request rate, p50/p95/p99 latency, CPU, memory, event-loop delay or thread-pool queue, active connections, database pool wait, and error rate. The first metric to deteriorate often points to the real bottleneck. A high p99 with low CPU may be a slow dependency, lock contention, or a tiny connection pool rather than insufficient application servers.

## Design review

If one handler takes five seconds of CPU, what happens to other requests? If the database stalls for 30 seconds, how many requests can accumulate? Which resource limit rejects new work, and what response does the client receive? Explain these before concluding that “the server is asynchronous.”
