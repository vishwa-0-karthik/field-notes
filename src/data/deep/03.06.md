Database locks and isolation levels determine how concurrent transactions interact. The goal is to preserve business invariants without serializing unrelated work. A transaction can be individually correct in a single-user test and still fail when two users act at the same time.

## Name the race

Suppose a booking service allows one reservation per seat. Two requests read “available,” then both attempt to reserve. A read check followed by an unprotected write is not enough. A unique constraint on active seat ownership, a conditional update, or a row lock can make one writer win. The right mechanism depends on the schema and whether several rows together form the invariant.

Locks can be implicit: an `UPDATE` holds row-level locks on changed rows until its transaction completes. A `SELECT ... FOR UPDATE` can reserve rows for a planned change. Table locks may appear during schema changes or some maintenance. Long transactions extend lock hold time and can block unrelated work. Keep external network calls, user think time, and slow report queries out of a write transaction where possible.

## Know what an isolation level promises

At PostgreSQL's default **Read Committed**, each statement sees a snapshot from the start of that statement. A second query within the same transaction may see a newly committed value. **Repeatable Read** keeps a stable transaction snapshot, but it can still allow certain write-skew patterns. **Serializable** aims for an outcome equivalent to some serial order and may abort one transaction with a serialization failure; the application must retry the whole transaction safely. PostgreSQL's implementation treats Read Uncommitted like Read Committed and offers stronger phantom protection in Repeatable Read than the SQL minimum.

| Anomaly | Example | Typical protection |
| --- | --- | --- |
| Lost update | Two writers overwrite one balance | Version check or row lock |
| Nonrepeatable read | Re-read sees new committed value | Stable snapshot when required |
| Write skew | Two doctors both go off call after checking the other | Serializable transaction or explicit invariant lock |
| Deadlock | Two transactions lock rows in opposite order | Consistent lock order and retry |

The isolation label alone does not enforce every domain rule. A unique index is often the clearest protection for a uniqueness invariant. A cross-row rule may need serializable isolation or a single row representing the shared constraint. Choose a strategy that can be explained with a concrete concurrent timeline.

## Handle conflicts as normal outcomes

Deadlocks and serialization failures can be expected under contention. Retry the entire transaction with bounded attempts and backoff, after ensuring external side effects are not duplicated. A payment call inside a retried database transaction is dangerous: the database can roll back while the payment remains real. Use a durable workflow state and idempotent external API instead.

Measure lock wait time, blocked sessions, transaction age, deadlocks, and serialization failures. A spike in lock waits may indicate a hot row, an overly broad update, or a migration holding a lock. Indexes can shorten the rows a write scans, indirectly reducing lock duration, but they also add write work. Inspect the actual SQL and plan before changing isolation globally.

## Design review

Write down two concurrent requests step by step. Which statement blocks or fails? What invariant prevents both from committing? If a transaction is retried, are all its side effects safe to repeat? How long could a lock be held during a dependency timeout?
