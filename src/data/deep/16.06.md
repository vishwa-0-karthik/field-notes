# Design: chat and messaging

A chat system needs low-latency delivery, durable history, ordering within a conversation, and a clear meaning for sent, delivered, and read. Real-time sockets improve responsiveness, but the durable message store and sync cursor make reconnect safe. Separate message content from presence and typing indicators, which are ephemeral and can be dropped without losing conversation history.

## Send, persist, and fan out

The client sends a message with conversation ID, client-generated idempotency ID, and expected membership context. The service authenticates the sender, checks membership and policy, assigns a server sequence or timestamp ordering key, persists the message, then acknowledges it. A durable acknowledgment should mean the message can be recovered after process loss. A fanout worker sends it to online recipients over WebSocket and records or queues offline delivery state. Duplicate client retries with the same message ID return the existing message. Do not rely solely on a push notification to deliver text; push is a hint to fetch the authoritative history.

For small groups, write the message once and let each recipient read by conversation cursor. For very large channels, fanout-on-read avoids one write per member but makes reads more expensive; fanout-on-write makes timelines fast but increases write amplification. A hybrid can fan out to active members and let infrequent users catch up from the conversation log. Partition messages by conversation so local sequence ordering is straightforward; a global order across all conversations is unnecessary. A very hot group may require partitioned delivery and per-conversation backpressure.

## History, sync, and receipts

Store messages as an append-only conversation log with stable message IDs and sequence numbers. Clients persist the last acknowledged cursor and request messages after it when reconnecting. Pagination should use an opaque cursor rather than an offset. Edits and deletions can be new events or versioned updates; define how they appear in history, notifications, and legal retention. Membership changes need an effective time so access to old history follows product policy. Read receipts are per-user progress metadata and can be coalesced to avoid one write for every rendered message.

Presence and typing use short TTLs and should not be durable. WebSocket servers maintain connection state but can be replaced; clients reconnect with backoff and resume from their cursor. A notification service can alert offline users, but respect mute settings and collapse repeated “new messages” signals. End-to-end encryption changes search, moderation, previews, and multi-device key management; decide the security model early because it affects server-side features.

## Scale and failure handling

Use a durable message database or replicated log, a connection gateway, a membership service, and an asynchronous fanout pipeline. Bound per-conversation message size, send rate, recipient count, and history queries. Monitor send acknowledgment latency, fanout lag, reconnect storms, dropped sockets, unread count drift, and abuse reports. Test duplicate sends, out-of-order network delivery, a gateway restart, membership revoked while offline, a hot group, and unread cursor recovery. The system should never confuse a transient socket failure with loss of a committed message.

## Design review

What does “sent” guarantee? How do clients deduplicate and resume history? Which ordering scope is required? Is delivery fanout-on-write or fanout-on-read for each conversation size? How are membership changes, encryption, and offline push handled?
