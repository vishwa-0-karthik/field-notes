# Backups and restore

A backup is useful only if it can be restored within the time and data-loss limits the business accepts. Backup design should begin with recovery point objective (RPO), the maximum tolerable loss of recent writes, and recovery time objective (RTO), the maximum acceptable restoration duration. Those targets determine backup frequency, log retention, replication, storage location, and the amount of automation required. “We have snapshots” is not a recovery objective.

## Select a recovery method

Logical exports are portable and can restore selected tables or records, but may be slow for large datasets. Physical snapshots restore database files quickly but can be engine- and version-specific. Continuous log archiving or point-in-time recovery can reduce data loss between snapshots, provided logs are retained and replay order is valid. Replicas can promote quickly for some failures but may copy accidental deletion or corruption immediately, so they are not a substitute for independent backups. A tiered plan can combine frequent transaction logs with periodic full backups and isolated copies.

Backups need consistency across related state. If the service stores database metadata and object blobs separately, a database snapshot and blob inventory taken at different times may not describe the same logical moment. Use immutable object versions, snapshot coordination, or a recovery manifest that identifies the corresponding data boundary. Include configuration, encryption keys, access policies, and deployment artifacts required to make restored data usable. Protect keys independently but ensure the recovery team can access them during a regional failure.

## Protect and verify copies

Keep at least one copy outside the primary failure domain and restrict deletion permissions. Immutability or object lock can protect against compromised credentials and ransomware. Encrypt backups and audit access, but do not let key loss make the backup unrecoverable. Verify checksums after transfer and store backup catalogs in a separate, durable location. Retention policy should reflect legal and product requirements; backups can retain deleted personal data beyond the primary system's deletion window, so deletion and restore procedures must account for that.

Restore tests should be scheduled, not improvised during an outage. Restore into an isolated environment, validate database integrity and application-level invariants, replay logs to a chosen point, and measure actual time. A successful cloud snapshot operation only proves that a snapshot was created. It does not prove that the backup can be decrypted, mounted, replayed, or used by the current application. Test partial recovery for accidental row deletion as well as full-region recovery.

Track last successful backup age, log archive lag, backup size and growth, checksum failures, restore duration, and test coverage. Alert when the newest recoverable point exceeds the RPO or when a retention gap appears. Document who can declare recovery, where credentials live, and how clients reconnect after restore. Recovery targets should be tested against the whole service, including DNS, secrets, queues, and external integrations.

## Design review

What RPO and RTO are promised? Are backups consistent across database and blob state? Is a copy protected from the same account compromise as production? Can current operators restore and validate a point in time? How do deletion obligations interact with retained backups?
