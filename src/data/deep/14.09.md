# Data retention, deletion, and privacy

Retention and deletion are core data lifecycle operations. Keeping every event forever increases breach impact, storage cost, and legal exposure; deleting immediately can break billing, audit, safety, or user recovery requirements. Start by classifying data by purpose and sensitivity, assign an owner and retention window, and define what “delete” means across primary storage, indexes, caches, analytics, replicas, and backups. The architecture should make those obligations executable and observable.

## Minimize and map data

Collect only fields required for a named product or operational purpose. Avoid copying personal data into logs, traces, search indexes, exports, and support tools by default. Maintain a data inventory that maps each field to its source of truth, processors, retention period, and deletion mechanism. Data lineage is essential: a user record can fan out into denormalized tables, event streams, object blobs, derived embeddings, and backups. Without that map, a delete request can remove the obvious account row while leaving active copies elsewhere.

Define the difference between deleting an account, removing access, anonymizing a record, and expiring a temporary copy. Some systems need a durable tombstone so delayed consumers do not recreate deleted data. A tombstone should contain the minimum information needed to enforce deletion and should itself have a defined retention period. For event-sourced data, deleting the projection may not remove the source event; the system may need encryption-key destruction, redaction events, or a documented exception based on the data's purpose and obligations. These decisions are domain and jurisdiction specific, so have the accountable privacy and legal owners define the policy.

## Make deletion propagate

Represent a deletion request as a durable workflow with an idempotency key and per-system status. The workflow authenticates the request, checks identity and policy, marks the account as deleting to block new writes, emits an outbox event, and schedules downstream cleanup. Consumers should be idempotent and retryable. Track completion acknowledgements for databases, object stores, search indexes, caches, analytics, and third-party processors. A periodic reconciliation job catches missed or failed consumers. Do not report completion until the defined scope has been processed; if some copies have different expiration behavior, state that clearly in the product policy.

Backups pose a special problem because restoring them can resurrect deleted records. Common designs retain tombstones and replay deletion events after restoration, or apply a deletion ledger before restored data is exposed. Immutable backups may be retained until their scheduled expiry while access is tightly restricted; a restored environment must still process the deletion ledger. Document this behavior and test it. For derived data, deleting the source may require rebuilding a model or index rather than surgically locating every contribution.

Monitor request age, failures by downstream store, tombstone backlog, late writes after deletion, and deletion reconciliation gaps. Test duplicate requests, identity ambiguity, consumer outage, restore from an old backup, and account reactivation during cleanup. Data lifecycle decisions should be reviewed whenever a new system begins storing personal data. Retention is not just a TTL setting: it is a distributed workflow with privacy, correctness, and recovery consequences.

## Design review

Can every copy and derived dataset be discovered? Does deletion block new writes before fanout begins? How are tombstones retained and eventually removed? What happens to a deleted record after backup restore? Can the system prove completion for the defined data scope?
