A consistency model states which outcomes a client may observe when operations overlap or complete at different times. It is a contract over histories, not a synonym for “all replicas have identical bytes right now.” Define it for the operation and scope the product needs: one key, a transaction, one user's session, or an entire database.

## Compare observable guarantees

Linearizability makes each operation appear to take effect at a single point between its invocation and response, respecting real-time order. If a write finishes before a read starts, that read must see the write or a later one. Sequential consistency preserves each process's program order but need not preserve real-time order across processes. Eventual consistency says replicas converge if updates stop; it does not, by itself, promise when a read will catch up or how concurrent writes are resolved.

Database serializability is about transactions behaving like some serial order. It is not automatically a real-time guarantee. Strict serializability adds real-time ordering to serializable transactions. These distinctions matter when an application combines several reads and writes. A single-key linearizable register does not make a multi-key transfer atomic, and a serializable database transaction can still interact with external services in an unsafe order.

| User expectation | Useful guarantee to investigate |
| --- | --- |
| Read your own profile edit immediately | Read-your-writes for that session |
| Never display a balance older than a completed transfer | Real-time ordering at the ledger authority |
| Show all feed items eventually | Convergence plus a defined delay budget |
| Move funds between accounts atomically | Transaction isolation and durability |

## Design for the actual reader

A system may offer strong reads from a leader and faster, potentially stale reads from replicas. Let the API choose based on the operation, not on an undocumented default. An editor might route its immediate follow-up read to the leader or carry a version token until a replica catches up. A public feed can tolerate lag if users understand that posts appear after a delay. For a feature that depends on monotonic reads, stick a session to a replica that has reached its last observed version or carry the minimum version between requests.

Staleness should be measured in a useful unit: seconds behind, log entries behind, or minimum accepted version. “Eventually” is too vague for an operational objective. Even systems with strong storage semantics can present stale results through application caches, asynchronous materialized views, and CDN responses, so the end-to-end contract must include those layers.

## Test histories, not labels

Write small concurrent examples: a completed write followed by a read, two clients racing to update one value, and a transaction spanning two records. Capture invocation and completion times, returned versions, and errors during network faults. Jepsen's consistency-model reference explains these guarantees in terms of allowed histories. A database marketing label is insufficient evidence that a particular API path, transaction mode, and cache configuration obeys the required model.

If a request times out, record the outcome as unknown until the authority resolves it. A client retry with the same idempotency key can discover or safely complete the operation. Treat unknown separately from failed; that distinction avoids violating a consistency promise through a user interface that says “nothing happened” when the write may have committed.

## Design review

Which operation needs real-time ordering, and at what scope? Can a session read an older version than it already saw? What lag is acceptable for replicas and projections? How will concurrent and timed-out histories be tested?
