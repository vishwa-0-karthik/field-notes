Eviction chooses which entries leave a full cache so new entries can enter. It is a memory-pressure policy, distinct from expiration, which makes an entry ineligible after a time or deadline. A cache can have TTLs but no evictions, evictions but no TTLs, or both. Choose eviction from the workload's reuse pattern and measure its effect on the authoritative store.

## Compare the common policies

Least recently used (LRU) favors keys touched recently. It works well when recent access predicts the next request, but a one-time scan can push useful older entries out. Least frequently used (LFU) favors repeatedly accessed keys, making it more resistant to scans, but a historical winner can remain after demand shifts unless frequency decays. FIFO is simpler and cheap, but age alone may have little connection to value. Random eviction can be surprisingly competitive under some workloads and is easy to implement, yet it offers little protection for a very hot item.

An ideal policy also accounts for value size and refill cost. A 10 MB object used once may evict thousands of tiny, popular keys. A cache for expensive reports may need an admission rule that refuses one-off results and admits only keys observed more than once. This is different from eviction: admission asks whether a new item should enter at all, while eviction asks which resident item should leave.

| Policy | Tends to preserve | Common weakness |
| --- | --- | --- |
| LRU | Recent working set | Sequential scans can pollute it |
| LFU | Long-lived hot set | Needs aging when popularity shifts |
| FIFO | Newest arrivals | Ignores actual reuse |
| No eviction | Every stored key until expiry or delete | New writes fail at capacity |

## Read the implementation's real contract

Redis documents `allkeys` and `volatile` eviction families. A volatile policy considers only keys with an expiry; persistent keys are not candidates. If the application forgets to set TTLs, the eligible pool may be too small and writes can fail. Redis's LRU is sampled and approximate rather than a perfect global ordering; its LFU uses probabilistic frequency estimation and decay. These details matter when diagnosing misses, though an application should usually select by measured behavior rather than fine-tuning the algorithm first.

Set the memory ceiling with space for replication, persistence, client buffers, and operational overhead. “Maximum cache data memory” is not necessarily “maximum process RSS.” Test what the client sees when no key can be evicted. A failed cache write should not silently turn a successful database write into a user-visible failure unless cache population is part of the explicit contract.

## Evaluate with workload traces

Hit rate alone is incomplete. A cache that hits many cheap tiny requests but misses the expensive queries may save little database work. Track byte hit rate, source queries avoided, refill latency, evictions by reason, and top hot keys. Replay representative request traces through candidate policies, including a product launch, a batch scan, and a popularity shift. Ensure TTL and admission settings remain comparable so policy changes are measured fairly.

At high occupancy, check whether the cache churns: items are admitted, evicted, and refetched before their second use. That is a sign to improve admission, resize the cache, or change what is cached. Merely lengthening TTL may increase stale responses without solving the working-set mismatch.

## Design review

Are recent or frequent accesses more predictive for this workload? Are large or costly values weighted appropriately? Which keys are eligible for eviction? What happens when the cache cannot accept a new entry?
