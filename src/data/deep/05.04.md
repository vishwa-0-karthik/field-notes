A TTL says when a cached entry stops being usable. It is a freshness boundary, not a promise that the bytes disappear at that exact instant. A cache may check expiry when a key is read, remove expired entries in background work, or do both. Design the application's correctness around the read-time rule; treat physical cleanup as resource management.

## Pick a TTL from the product contract

If prices may be stale for at most one minute, a 60-second TTL is an upper bound only if entries are created from a current source and the cache never resets TTL on every read. Sliding expiration can keep a popular stale value alive indefinitely unless there is also an absolute deadline. If prices must change immediately after a write, use explicit invalidation or version-aware reads; merely reducing TTL to one second may overwhelm the database while still allowing a one-second stale window.

Different data merits different TTLs. Public content can often live longer than inventory or account state. A “not found” sentinel should usually expire faster than a positive result so a newly created record becomes visible. Add limited random jitter to independently expiring keys when many values are populated together. This spreads refills and cleanup work instead of creating a synchronized spike.

## Separate logical expiry from reaping

Redis supports key expiration and records an expiry time that continues to advance across a server restart. A key can be found expired when accessed, and background work can also remove expired keys. The application should see an expired key as a miss even if its allocation has not yet been reclaimed. Do not assume an expiry callback fires at the exact TTL boundary or use cache reaping as the sole scheduler for billing, legal deletion, or other required actions.

An application-owned cache reaper may scan entries, delete those past deadline, and free memory in batches. Its scan rate trades CPU for memory. A full synchronous sweep can create latency spikes; incremental cleanup smooths work but leaves expired allocations longer. If a service handles millions of keys, measure the ratio of expired-but-resident bytes, sweep duration, and allocation pressure. Include expiry metadata in memory estimates.

## Avoid expiry-driven load spikes

A hot key expiring can send many readers to the source simultaneously. Jitter helps when many independent keys share a TTL, but it does not solve a single hot key. Use per-key single-flight loading, refresh before expiry, or bounded stale serving where the product permits it. A soft expiry can trigger a background refresh while a hard expiry stops serving the old value. Document both ages clearly; otherwise “five-minute TTL” can accidentally mean much longer stale exposure.

If refresh fails, decide whether to serve stale data, return an error, or query a different source. For an informational catalog, stale-if-error may be reasonable for a short bound. For a security entitlement, old data may be unacceptable. HTTP caching has explicit freshness and stale-response semantics; use those when an HTTP intermediary is part of the path rather than inventing ambiguous headers.

## Design review

What is the maximum permitted age of a response? Does any read extend that age? What happens when many keys expire together? Are cleanup and business deletion separate? Can stale data be served during source failure, and for how long?
