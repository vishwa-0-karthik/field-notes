Distributed systems need several meanings of “order.” Wall clocks approximate when events happened, logical clocks express causal relationships, and an authoritative log can define the sequence in which commands commit. These are different tools. A timestamp attached to an event is not proof that it happened before another event in the system's business order.

## Separate physical time from causality

Two servers can have clocks that differ by milliseconds or more. Network delay can be larger and variable. If server A writes at displayed time 10:00:01 and server B writes at 10:00:00, the timestamps alone do not prove B's action was first. Clocks can also jump during correction. Use wall time for user-facing dates, retention windows, and approximate diagnostics, while defining a different authority when an exact order matters.

Lamport's happened-before relation captures causal order: events on one process are ordered, a send precedes its receive, and transitivity connects those edges. Events without a causal path are concurrent. A Lamport clock assigns numbers that respect happened-before, but the converse does not hold: a smaller number alone does not prove causation. A tie-breaker can create a deterministic total order for display or processing, yet that order may be arbitrary among concurrent events.

## Pick an ordering scope

A per-account ledger may need a total order for entries on one account, while the entire company may not need one global sequence. A partitioned log can order records within each partition but not across every partition. A database commit position can order transactions at its authority; an event's creation timestamp may precede that commit by seconds. Specify whether the product needs per-key, per-shard, per-session, or global order before paying for cross-node coordination.

Consider a message feed. Sorting by `(created_at, id)` yields a deterministic display order, but a delayed message can be inserted before items a reader already saw. If the product requires immutable traversal, capture a high-water mark or snapshot. If it only needs a live feed, accept some movement and design pagination accordingly.

## Handle clock uncertainty honestly

Google Spanner's TrueTime API exposes an uncertainty interval rather than pretending every machine knows exact time. Spanner combines this with other coordination mechanisms to provide external consistency. That design illustrates the cost of promising real-time ordering; ordinary NTP-synchronized application timestamps do not reproduce it. For most services, a version or sequence from the authoritative store is simpler and stronger for ordering writes.

Log multiple moments when debugging asynchronous work: client event time, server receipt time, durable commit time, broker enqueue time, and consumer processing time. Those fields answer different questions. Use monotonic clocks for measuring elapsed durations within a process so wall-clock correction does not produce negative latency. Monitor clock offset when TTLs, leases, or timestamp-based IDs depend on it.

For cross-service audits, retain the operation ID alongside these timestamps. It lets an investigator reconstruct the causal chain without assuming that sorting raw timestamps reconstructs the same chain. Record uncertainty or source clock when precision matters.

## Design review

What ordering scope does the user actually need? Are concurrent events allowed to appear in either order? Which component assigns the authoritative sequence? What breaks if wall clocks are wrong or an event arrives late?
