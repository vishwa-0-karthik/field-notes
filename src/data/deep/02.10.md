Batching groups several small operations into one larger operation. It can reduce fixed per-request overhead—network round trips, transaction setup, serialization headers, or broker calls—but makes each item wait for a batch and can create larger failure units. A good batch has explicit size, time, and memory bounds.

## Find the fixed cost

Suppose a worker inserts 1,000 analytics rows one at a time. Each insert pays a network round trip and database command overhead. Sending 100 rows per command reduces that overhead substantially. PostgreSQL supports multi-row `INSERT`; for very large loads, a bulk-copy path may be more suitable. The gain depends on row size, indexes, transaction log, and contention. Measure throughput and p99 latency rather than assuming the largest possible batch is best.

Kafka producers similarly accumulate records into batches per partition. A linger interval allows more records to arrive before sending, trading a little latency for fewer requests and better compression. If the application has strict per-message latency, a long linger is inappropriate even if throughput rises.

| Bound | Protects against | Tradeoff |
| --- | --- | --- |
| Maximum item count | Huge transaction or request | Small items may underfill byte budget |
| Maximum bytes | Memory and transport limits | Variable count per batch |
| Maximum wait | Unbounded low-traffic delay | More small batches |
| Maximum in-flight batches | Downstream overload | Producer may block or reject |

## Preserve per-item outcomes

A batch endpoint must define whether it is atomic. If one item is invalid, does the whole batch fail or are valid items accepted? For a database transaction, atomicity may be natural; for a notification send, partial success may be more useful. Return item-level IDs and errors so callers can retry only failed items. If a network timeout hides whether the batch committed, use idempotency keys per item or per batch with clear scope.

Ordering also matters. A batch containing updates to the same entity must preserve their intended order, or the consumer must compare versions. Sending many entities in one batch should not let one poison item stall all others forever. A repair path can split a failing batch to isolate the bad record, with limits to prevent endless retries.

## Balance throughput and latency

Imagine events arrive at 10/s and a batch holds 100. Waiting only for the count could delay the first item ten seconds. Add a maximum wait, perhaps 50 ms, so sparse traffic still moves. At 10,000/s the count fills quickly and the timer rarely matters. This count-or-time rule adapts to changing load. It must still respect memory and broker size limits.

Batching can worsen tail latency if a slow item holds the entire batch or if one large write monopolizes a connection. It can also increase lock duration and transaction log bursts. Run tests at both peak and quiet periods. Watch batch fill ratio, flush reason, item age, payload size, errors, and downstream saturation.

## Design review

Which fixed overhead is batching reducing? How long may the oldest item wait? What happens when one item fails, the response is lost, or the producer's buffer fills? Can the receiver report outcomes precisely enough for safe retry?
