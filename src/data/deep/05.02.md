A distributed cache gives many application instances a shared, fast copy of data. It helps when process-local caches duplicate too much memory or diverge too easily. It also becomes a service on the critical read path. Design it around key distribution, source-of-truth semantics, capacity, and failure behavior before choosing a cluster size.

## Choose a read and write pattern

With cache-aside, an application reads the cache, fetches the database on a miss, and then fills the cache. Writes usually update the database and invalidate the corresponding cache entry. This keeps the database authoritative and makes misses easy to reason about, but concurrent misses can stampede it. Write-through populates the cache when a write happens, which can make the next read fast, at the cost of caching data that may never be read. AWS describes the two patterns as complementary rather than universal alternatives.

Be precise about failure between database commit and invalidation. If a write commits but the cache deletion fails, readers may see the old value until expiry. A short TTL can bound staleness, but only if the product accepts that bound. A durable outbox event can improve retryability. For strict read-after-write behavior, route the writer's next read to the source or carry a version; do not claim that asynchronous invalidation is immediately consistent.

## Partition keys without losing semantics

A single cache node eventually reaches a memory, network, or CPU limit. Sharding maps keys to nodes. Redis Cluster uses 16,384 hash slots and assigns ranges of slots to masters; clients follow the slot map during normal use and migration. This is a concrete alternative to client-side consistent hashing. Multi-key operations require compatible placement, so a key naming scheme can become part of the data model. A hot key remains hot even when the rest of the keyspace is evenly distributed.

Replicas can improve availability or read scale, but they may lag the primary. Decide whether a replica read can return an older version. Failover may lose recent cache writes, which is usually acceptable for a rebuildable cache but not for authoritative state. If the cache holds sessions, locks, or counters that cannot be reconstructed, it has stopped being “just a cache” and needs stronger durability analysis.

## Keep the working set affordable

Estimate memory from serialized value bytes, key bytes, per-entry overhead, replication factor, and allocator headroom. A million 1 KB values is more than one gigabyte in practice. Set a capacity limit and choose an eviction policy based on expected access. If entries are needed for correctness, eviction is not safe. For ordinary cached copies, watch hit rate, evictions, fragmentation, network saturation, and p95/p99 latency by node and tenant.

Use bounded request timeouts and connection pools. A slow cache can be worse than a failed cache because every application worker waits. Before rollout, load-test a cold cluster and a node migration. Warm a small set of genuinely hot keys if necessary, but avoid indiscriminately loading the entire database into memory. Plan how a new serialization version rolls through old cache entries.

## Design review

Can every cached value be reconstructed? What happens after a committed write and failed invalidation? Which keys are hot, and can one shard absorb them? What is the source load if the cluster is empty or unavailable?
