# Design: a ticket booking system

Ticket booking combines a searchable event catalog with scarce inventory that must not be oversold under intense, synchronized demand. Search and seat availability can be eventually consistent; the reservation decision must be authoritative. The design separates discovery, temporary holds, payment, and final confirmation, with explicit expiration and recovery behavior for every intermediate state.

## Inventory and holds

Represent an event's seats or ticket pool with an authoritative inventory service. For assigned seating, a seat transitions through available, held, sold, and released states. A hold has an owner, booking ID, expiry, and fencing version. Creating a hold must be atomic: a conditional write changes a seat only if it is still available, or a transaction reserves a set of seats together. For general admission, use an atomic counter or allocation ledger that prevents remaining inventory from going below zero. Cache may accelerate display but cannot grant a seat. A “available” result shown before the user clicks is only an estimate.

Holds expire to release abandoned inventory, but expiry is not a simple background delete. The payment provider may still be processing when the hold timer fires. Model booking states such as `requested`, `held`, `payment_pending`, `confirmed`, `expired`, and `cancelled`. Before releasing a hold, check payment status and use a conditional transition on its version. Use a fencing token so delayed workers cannot confirm or release a seat after a newer state has won.

## Checkout and payment orchestration

When a customer selects seats, create an idempotent booking and hold inventory for a short, visible window. Initiate payment with an idempotency key tied to the booking. A successful payment authorization should lead to a conditional confirmation that consumes the hold. If authorization fails, release the hold. If the payment response times out, query the provider or retry with the same idempotency key before changing inventory. Never blindly retry a charge with a new key. If payment succeeds after the hold has expired and the seat has been resold, initiate a compensating refund or alternate fulfillment path and notify the customer.

Use an outbox or durable workflow to coordinate hold expiration, payment callbacks, confirmation messages, and ticket issuance. Webhooks can arrive late or more than once; verify signatures, store event IDs, and process idempotently. Ticket generation happens only after confirmation and produces a unique credential that can be checked at entry. Protect against screenshot reuse with rotating or server-validated QR codes if the threat model requires it, while ensuring venue scanners can function under network disruption.

## Sale-day overload and fairness

A popular on-sale creates a thundering herd. Use a waiting room or admission token to smooth traffic, rate-limit per account and IP, and allocate inventory with fair randomized or FIFO rules that users can understand. Avoid letting a single database row serialize every purchase for a huge event; partition inventory into blocks or seat groups while preserving exact uniqueness. Keep queueing outside the inventory transaction, use short transactions, and shed excess demand before expensive payment work. Bot detection and account controls protect fairness but need a process for false positives.

Measure hold conversion, expiry, oversell attempts, payment ambiguity, confirmation latency, wait-room abandonment, inventory hot spots, and compensation volume. Test simultaneous last-seat claims, callback duplication, payment after expiry, cache staleness, and database failover. Success means no oversell, bounded checkout time, and a clear recovery outcome for every paid-but-unconfirmed booking.

## Design review

Which storage operation prevents oversell? How long is a hold and what if payment is still pending at expiry? Are payment and webhook retries idempotent? Can admission control smooth a sale without promising inventory prematurely? What compensating action handles a late successful payment?
