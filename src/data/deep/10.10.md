Reservoir sampling keeps a fixed-size random sample from a stream whose final length is unknown. It is useful for inspecting events, building an approximate test set, or retaining examples without storing every item. The basic algorithm gives every item seen so far the same probability of being in the sample, provided the random choices are unbiased and every item is processed once. It does not automatically produce a sample of distinct users or a sample weighted by business importance.

## Apply Algorithm R

Keep the first `k` items in a reservoir. For the `i`th item after that, draw a random integer uniformly from `1..i`. If the number is at most `k`, replace that reservoir slot with the new item; otherwise leave the sample unchanged. The new item has inclusion probability `k/i`. An earlier item survives each later replacement with the right probability, so after `n` events every item has probability `k/n` of inclusion. Vitter's original work and Stanford's algorithm notes develop this result.

This method uses O(k) storage and a single pass, but it considers every event. For very high-rate streams, skip-based variants reduce random draws. Use a well-seeded generator and avoid modulo bias if the implementation maps random bits into `1..i`. Record the algorithm version and input count with the sample so the result can be interpreted and reproduced in tests.

## Clarify what the sample represents

If one user generates 100 events and another generates one, an event reservoir is 100 times more likely to include the first user's activity. To sample users uniformly, sample a deduplicated user stream or use a stable hash-priority scheme over user IDs. Similarly, a global reservoir over all traffic may contain almost no examples from a rare but important tenant. Stratify by tenant, geography, error class, or time bucket if those slices matter, and account for the changed inclusion probabilities when estimating population statistics.

Distributed merging needs care. Concatenating two reservoirs or picking half the slots from each biases a sample when partitions have different sizes. Carry each partition's seen count and use a correct weighted merge, or assign each event a random priority and keep the global k smallest priorities across partitions. The latter can be merged by a top-k reduction if priorities are independent and stable. Retries must not give an event a new priority or another chance to enter the sample.

## Handle time and privacy

A cumulative reservoir represents all history and adapts slowly to recent changes. For “last hour” analysis, maintain separate time buckets or use a windowed sampling algorithm. Keep sample payloads small and redact sensitive data; sampling reduces volume, not privacy obligations. If sampled events can be deleted by user request, retain enough identity and provenance to find and remove them. Do not use a reservoir as the sole evidence for a complete audit.

Validate uniformity on synthetic streams by checking inclusion frequency across early and late positions. Monitor seen count, sample size, partition balance, and duplicate IDs. A sample that is statistically correct but drawn after an upstream filter can still misrepresent the original population, so document the point in the pipeline where sampling occurs.

## Design review

Is the unit an event, user, or session? Does every unit get one unbiased chance? How are partition samples merged? Is the desired window cumulative or recent? Which downstream estimate needs inclusion probabilities or stratification weights?
