FlockDB was Twitter's distributed store for large social adjacency lists. Its public archive describes a specific workload: add and remove directed edges, list edges in either direction, page through huge lists, and perform some set operations. It was not built for arbitrary multi-hop graph traversal. That distinction is useful when designing a follow graph today: choose the data model for the queries the product actually runs.

## Store directed edges for both directions

A follow from A to B is not symmetric. The product needs “whom does A follow?” and “who follows B?” FlockDB stored a forward row keyed by source and a backward row keyed by destination, each with a sort position and state. The duplicate representation makes both lists efficient but adds write coordination and repair work. In a relational design, two indexes on an authoritative edge table can serve the same small-scale access patterns; at huge scale, separately partitioned read copies can avoid expensive cross-node scans.

Give each edge a stable identity and state such as active, removed, or archived. Follow and unfollow events may be retried or arrive out of order. A version or monotonic state transition prevents an old follow retry from reactivating a newer unfollow. FlockDB's notes explicitly mention tolerating duplicate and reordered operations. If forward and reverse projections differ temporarily, define which is authoritative and run reconciliation so counts and lists converge.

## Page lists without scanning from the start

A celebrity may have millions of followers. Offset pagination forces the database to skip ever more rows to reach a later page and can move under concurrent changes. FlockDB used a sort position as a cursor for indexed range scans. Pair the position with a unique edge ID to break ties, and define whether a client sees a stable snapshot or a changing live list. A follow that arrives while paging may appear on an earlier page and not be seen until refresh; that is a product behavior to document.

Set operations such as “people I follow who also follow B” can be built from indexed adjacency queries and intersections. Do not assume a general graph traversal engine is needed. Conversely, a product asking for recommendations across multiple hops, community detection, or path search may need a separate offline graph computation or a different store. The adjacency list answers one-hop queries very well; it does not make every graph algorithm cheap.

## Plan partitioning and recovery

Partition forward lists by source and reverse lists by destination. A hot celebrity's reverse list may still be large, so shard or bucket within that owner if a single partition cannot hold or serve it. Track edge mutation lag between directions, page latency, count drift, and repair backlog. Store durable mutation events so a failed reverse write can be retried and projections rebuilt. Privacy changes such as blocks should be checked at read time if eventual edge projection lag could expose content.

The FlockDB repository is archived and no longer maintained, so it is a design case study, not an automatic software recommendation. Its lasting lesson is to narrow the workload: an adjacency-list system can be simpler and faster than a general graph database when the main questions are one-hop lists and indexed set arithmetic.

## Design review

Which one-hop queries must be fast? Is the edge stored in both directions or served by two indexes? How are retries and out-of-order mutations resolved? Can a million-edge list be paged predictably? Which graph questions would require another system?
