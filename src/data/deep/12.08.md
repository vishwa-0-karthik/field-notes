Matching and recommendation systems select candidates that fit a user, context, or query, then rank a manageable subset. “Best match” can mean nearest by geography, similar by content, likely to be clicked, or compatible with hard constraints. Define the objective before choosing the algorithm. A recommender that ignores availability, safety, or diversity can optimize a metric while producing an unusable list.

## Separate candidate generation from ranking

Candidate generation searches a large catalog using one or several inexpensive methods: category filters, collaborative item similarity, user history, geographic proximity, or vector retrieval. A scoring stage estimates relevance for hundreds of candidates. A reranker then applies constraints and diversity to the top results. Google’s recommendation-system documentation describes this multi-stage pattern and why a small candidate set is needed for low-latency ranking. If the candidate generator misses an item, the ranker cannot recover it.

For collaborative filtering, implicit actions such as clicks or purchases are not explicit ratings. A click depends on exposure and rank, and no click may mean “not shown,” not “disliked.” Use positive and negative evidence carefully, normalize popularity, and preserve a fallback for new users and items with little interaction history. Content features and editorial or rule-based candidates help with cold start.

## Define features and freshness

A candidate score may combine user-item affinity, freshness, distance, quality, inventory, and context. Hard constraints should filter candidates, not merely contribute a small negative score. Model features need timestamps and versions: a location estimate from an hour ago or an out-of-stock cache can make a high score meaningless. Precompute stable item embeddings or neighbors, then apply fast user context at request time. Keep feature logs sufficient to explain why a result appeared.

Recommendations have feedback loops. Popular items receive more exposure and then more clicks, which can make them even more popular. Use exploration or diversity constraints where appropriate, and monitor concentration across creators or categories. A/B tests measure outcomes, but offline ranking metrics and guardrails for latency, safety, and coverage help identify regressions before rollout.

## Make the ranking useful under failure

Bound candidate count and per-stage deadlines. If personalization times out, serve a safe popularity or category fallback rather than an error page. Deduplicate candidates from several generators and avoid showing near-identical items together. Apply seen filtering with an explicit false-positive policy; one missed recommendation may be acceptable, while suppressing a transaction-required item may not be. Cache only when the cache key captures relevant user, region, and inventory context.

Measure candidate recall, ranking quality, coverage for new items, diversity, latency by stage, stale-feature rate, and fairness across relevant cohorts. Keep a small evaluation set for cold-start, sparse-history, and unusual-context users. Record ranking model version and feature snapshot so a recommendation can be reproduced later.

When a user reports an obviously wrong result, capture the candidate sources and filter decisions as well as the final score. That trace separates missing-candidate bugs from ranking mistakes.

## Design review

What is the objective and what are hard constraints? Which generators create candidates and how is recall measured? How does the system handle new users and items? Can feedback loops collapse diversity? What fallback is served when a model or feature store is slow?
