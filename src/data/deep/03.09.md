A database ticket server issues unique identifiers from a small, centralized sequence so many data shards can create records without colliding. It separates **ID allocation** from **record storage**. This is attractive when shards need compact numeric primary keys and records may move between shards, but it puts every new ID on an availability and throughput path to the allocator.

## Why shard-local counters are insufficient

Suppose a photo service stores users across ten independent databases. Each database can auto-increment a local photo ID, but all ten can produce `photo_id = 42`. That ID cannot uniquely identify a photo in a global API unless every request also carries the shard identity. If data later moves between shards, a global ID simplifies references and migration. One approach is a dedicated sequence service that returns a new number before the photo is inserted into its shard.

Flickr described a concrete ticket-server design for globally unique integer IDs across MySQL shards. A small table on a dedicated server advanced an auto-increment value, and two independent servers used disjoint odd and even ranges. The key idea is disjoint allocation: the two issuers cannot return the same number even if they do not replicate each generated ID. This trades a single global sequence order for availability and compactness.

| Option | Strength | Important cost |
| --- | --- | --- |
| One central sequence | Simple global uniqueness | Network hop and allocator dependency |
| Two disjoint sequences | Failure tolerance without per-ID replication | Gaps and no single issuance order |
| Allocate ranges to app nodes | Fewer allocator calls | Lost unused ranges on crash |
| Random UUID | No central issuer | Larger keys and index locality tradeoff |
| Time-based ID | Distributed and roughly ordered | Clock and worker-ID management |

## Define what the ID promises

Uniqueness is different from consecutiveness and time order. A database sequence may skip values after rollback, caching, or process failure. A ticket server should promise “unique within this namespace,” not “every integer appears.” If the product requires strict event order, a ticket number alone may be insufficient because an ID can be allocated before its transaction commits. A later ID may become visible first.

Scope matters. Separate sequences for photos and comments can reduce contention and allow different growth rates, but the pair `(entity_type, id)` may then be the true global key. For API exposure, use opaque IDs if clients should not infer traffic volumes or creation time. A compact internal integer can be mapped to another public representation when necessary.

## Design the failure path

If the allocator is unavailable, can writes continue with preallocated ranges? A range allocator gives each writer a block, such as 1,000 IDs, and replenishes before it runs out. That reduces request rate to the central service but means a crashed node may waste unused IDs. Prevent range overlap by committing ownership durably. If a recovered node restarts with stale local state, it must not reuse IDs from a prior lease.

Monitor issuance rate, p99 allocation latency, remaining range headroom, sequence exhaustion horizon, and collisions at the storage layer. A unique constraint on the destination table remains a valuable last line of defense. The allocator design should be load tested at the projected *write* rate, including retry storms.

## Design review

What is the exact uniqueness namespace? Are gaps acceptable? What happens when one issuer is down? Can an ID be allocated but its record fail to commit, and does that affect any caller's assumptions?
