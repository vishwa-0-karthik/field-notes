A query understanding pipeline turns a user's text into a retrieval plan. It may detect language, normalize tokens, identify an exact identifier, correct spelling, expand synonyms, extract structured filters, and classify intent. Every transformation can improve recall or silently change meaning. Keep the original query and a trace of each rewrite so search behavior remains explainable.

## Parse before rewriting

First separate syntax from content. A quoted phrase, `brand:Acme`, and a free-text word have different semantics. Validate operators and escape special characters instead of passing user text directly into a backend query language. Normalize Unicode and case according to the corpus, then tokenize with a language-aware analyzer. For languages without whitespace word boundaries, tokenization needs a different strategy from English splitting. The index analyzer and search analyzer usually need compatible terms; Elasticsearch documents this default and the deliberate exceptions for autocomplete or search-time synonyms.

Preserve exact identifiers. A query shaped like `ERR-4291`, an ISBN, or a SKU may need an exact field lookup before stemming, stop-word removal, or spell correction. Users expect exact IDs to win over fuzzy text. Similarly, a quoted phrase should not expand into unrelated synonyms without an explicit product choice. A good internal representation carries the raw text, parsed filters, normalized terms, detected intent, and optional alternatives separately.

## Expand carefully

Synonyms can bridge vocabulary gaps, such as `laptop` and `notebook computer`, but many words are ambiguous. `Apple` may be a brand or fruit. Apply expansion based on field and context, give original terms more weight, and limit the number of alternatives. Search-time synonym expansion is easier to update without a full reindex, though it may add query cost and complexity. Index-time expansion reduces some query work but requires reindexing to change mappings. Store versioned synonym sets and test both intended matches and false positives.

Spell correction is another candidate generator, not an unconditional replacement. If the original query has strong exact matches, show them. If it has none, offer a corrected query or search both with a preference for the original. Never autocorrect a proper name or product code simply because a more common word has a lower edit distance. Query logs can identify frequent misspellings, but logs may contain private text and should be handled under a retention and access policy.

## Route the plan and measure it

A navigation intent like `refund policy` may need an authoritative help page pinned above general lexical results. A transactional intent like a product search may need availability and price filters. Keep the intent classifier's confidence and fallback path; low-confidence guesses should not exclude ordinary results. Staged retrieval can run exact lookup, lexical search, and semantic search, then combine candidates under a latency budget. The pipeline should expose which stages fired for a query.

Evaluate rewrites on a labeled set containing names, multilingual terms, short ambiguous queries, codes, and quoted phrases. Track zero-result rate, reformulation rate, latency, and the fraction of queries for which the rewrite materially changed top results. A reduction in zero results can be misleading if those new results are irrelevant. Preserve the ability to disable one rewrite independently during an incident.

## Design review

Which transformations can change meaning? Are exact IDs and quoted phrases protected? Are search and index analyzers compatible? How are synonyms versioned and evaluated? Can operators explain every rewrite for a bad result?
