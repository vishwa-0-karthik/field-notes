# Design: a product listing

A product listing serves a browsable catalog with search, filters, sorting, and pagination. It combines product data that changes at different rates: names and descriptions, category membership, price, inventory, promotions, and media. A strong design assigns each field an authoritative owner, builds a read-optimized catalog view, and makes freshness tradeoffs explicit. The listing page should stay responsive even if one enrichment source is stale or unavailable.

## Separate writes from browse reads

The product service owns canonical product records and validation. Inventory and pricing often have separate write paths and freshness requirements. A change stream or transactional outbox publishes updates to a catalog index, search engine, and cache. The index is a derived read model, not the source of truth. It can denormalize category, brand, searchable text, filter fields, price ranges, and availability to avoid fanout queries at page-read time. Include a version or event sequence so stale events cannot overwrite newer documents. Rebuild the index from canonical stores and replay changes from a checkpoint.

For a small catalog, a relational database with indexes may support browse and filters adequately. At larger scale, a search engine can provide text relevance and faceted aggregations, while a relational or key-value store remains authoritative for updates. Search results can lag inventory or price updates, so the product page may recheck critical fields before checkout. If inventory accuracy is a purchase invariant, do not rely on an eventually consistent search document to guarantee stock; reserve inventory in its authoritative service during the purchase flow.

## Query, filters, and pagination

Define supported filters and sort orders before indexing. A combination of many optional facets can create expensive query shapes. Use bounded filter sets and precomputed facet counts where necessary. Facets should represent the current result set or explicitly indicate global counts; these are different semantics. Filter values must be normalized, and category hierarchy requires a clear parent-child model. Sorting by price needs stable tie-breaking so items do not jump unpredictably across pages.

Cursor pagination is usually safer than offset pagination for deep result sets. A cursor can carry the last sort tuple and index generation. Search results change while a user pages, so decide whether pagination is a live view or a snapshot. An index point-in-time snapshot gives stable pages but consumes resources; a live cursor is cheaper but may skip or repeat products after catalog updates. Cache popular category pages with a key that includes locale, currency, market, sort, filters, and catalog version as required. Do not cache user-specific price or entitlement data under a shared key.

## Availability and relevance

The listing path can degrade gracefully. If recommendation enrichment fails, return ranked catalog results; if inventory data is stale, label it or prevent a strong availability promise. Relevance can combine text match, business rules, popularity, personalization, and availability, but each component should have bounded latency and a fallback. Monitor index lag, query p95/p99, no-result rate, filter use, stale price reports, cache hit rate, and conversion by query class. Avoid using click-through alone as a quality metric because position bias can reinforce existing rankings.

Test concurrent product edits, delayed or duplicate events, zero-result filters, changing inventory between pages, locale-specific currency, and a full index rebuild. A listing design succeeds when users can find the right product quickly while critical purchase facts are revalidated by their system of record.

## Design review

Which service owns each catalog field? How does the read model recover from missed events? Are filter and sort combinations bounded? Does pagination promise a stable snapshot? Which attributes are safe to cache globally, and when are price and inventory rechecked?
