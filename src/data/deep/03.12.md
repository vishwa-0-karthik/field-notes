Schema evolution changes stored data and application contracts while old and new software versions may run at the same time. A safe migration is a sequence of compatible steps, not one large `ALTER TABLE` followed by a hope that every process updates instantly. The desired final schema matters, but the intermediate states determine whether a live rollout works.

## Use expand, migrate, contract

Suppose an orders table has `customer_name` and you want a structured `customer_id` foreign key. First **expand**: add a nullable `customer_id` column and deploy readers that can handle either representation. Then **migrate**: make new writes populate `customer_id`, backfill existing rows in bounded batches, and compare records. Finally **contract**: switch all reads to the new field, enforce a non-null or foreign-key constraint when data is ready, and remove the old column after old binaries are gone. Fowler calls this parallel change, or expand and contract.

The stages overlap with deployments. If older app instances still write only `customer_name`, the backfill can finish and immediately fall behind again. Either dual-write during the transition or route writes through one compatible version; monitor the count of rows still missing the new field. Dual writes within one database transaction are easier to reason about than cross-database dual writes, but read preference and conflict behavior still need definition.

| Change | Safer intermediate state | Common mistake |
| --- | --- | --- |
| Add field | Nullable or compatible default first | Require it before old writers know it |
| Rename field | Write/read both during migration | Drop old name in one deployment |
| Change type | New column, transform, compare | In-place rewrite at peak without estimate |
| Add constraint | Clean data, validate, then enforce | Assume existing rows already comply |
| Remove field | Wait for usage telemetry | Delete while an old worker still reads it |

## Control database work

Some DDL is metadata-only; other operations scan or rewrite large tables or take locks. The behavior depends on database version, column default, type change, and constraint. PostgreSQL documents that many table modifications are possible through `ALTER TABLE`, but operational impact must be checked for the exact statement. Test on a production-sized copy, set lock timeouts where appropriate, and monitor replication lag and WAL volume. A migration that is fast on ten thousand rows can be disruptive on a billion.

Backfill in small batches ordered by stable key, with a checkpoint so it can resume. Avoid one transaction that holds locks and retains old row versions for hours. Record transformed-row counts, errors, and reconciliation mismatches. If the transformation is ambiguous, define manual or product-level rules rather than silently inventing data.

## Make rollback realistic

Rollback is easiest during expansion because the old representation still exists. Once old data is dropped or new writes use semantics the old version cannot understand, rolling back code may be unsafe. Define the rollback point for each phase. It may be safer to roll forward a fix after contract than to restore an old binary.

## Design review

Can old and new application versions run together at every step? What writes occur during backfill? How will you prove all rows and consumers have migrated? At which point does rollback stop being a simple code revert?
