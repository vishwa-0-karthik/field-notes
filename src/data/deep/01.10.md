The repository pattern gives domain code a collection-like interface for retrieving and storing entities while keeping query construction and persistence details in one place. It is useful when the domain needs a stable vocabulary for data operations. It can become harmful when it hides important database behavior behind an overly generic API.

## Give the repository a domain shape

For an order system, a repository might expose `getById`, `findOpenForCustomer`, and `saveWithExpectedVersion`. Those names express business-relevant queries and concurrency rules. A generic `find(table, filters)` wrapper merely re-creates the database API and adds little abstraction. Fowler's original pattern describes a repository as a mediator between domain and data mapping layers, resembling a collection of domain objects.

Separate the application decision from persistence mechanics. The service decides whether an order may be cancelled. The repository loads the order and writes the new state with an optimistic version check. If two requests race, the database constraint or transaction must enforce the invariant. An in-memory domain check alone is insufficient.

```text
cancelOrder(orderId, actor)
  order = orders.getById(orderId)
  order.assertCanCancel(actor)
  order.cancel()
  orders.saveWithExpectedVersion(order, originalVersion)
```

The sketch assumes `saveWithExpectedVersion` reports a conflict if another writer changed the row. That conflict should be mapped to a deliberate API response or retry policy. The repository does not make concurrency disappear; it gives the application a place to state and enforce the contract.

## Keep transaction scope visible

If cancelling an order also releases inventory and writes an audit entry, those changes may need one transaction. A repository per table can tempt the application to call `orders.save()`, `inventory.release()`, and `audit.insert()` independently. A crash between calls breaks the invariant. Use an explicit unit of work or transaction boundary around the workflow when all records share a database. For work across independent services, use a different coordination design; a repository abstraction cannot create a distributed transaction.

| Design choice | Benefit | Risk |
| --- | --- | --- |
| Domain-specific methods | Clear intent and query ownership | More methods to maintain |
| Generic CRUD repository | Low initial boilerplate | Leaks storage model into callers |
| Return domain objects | Central business rules | Object mapping can be costly |
| Return query projections | Efficient read paths | Separate read contracts to maintain |

Read-heavy queries often deserve projections rather than loading full aggregates. A list page may need only order ID, date, and status. Materializing hundreds of complete objects and related rows wastes work and can trigger N+1 queries. A repository can expose a purpose-built read method, or the application can use a separate query layer. The important property is that performance-sensitive SQL remains understandable and observable.

## Know when not to add it

For a small application with straightforward SQL, direct query functions may be clearer than several layers of interfaces. Add the pattern when it protects a meaningful domain boundary, consolidates repeated persistence rules, or makes complex workflows easier to test. Do not promise easy database swaps as the main benefit: query semantics, transactions, indexes, and data types often differ significantly between stores.

Test repositories with the actual database behavior when constraints, isolation, or query plans matter. Unit tests using an in-memory fake can verify application decisions, but a fake may miss uniqueness races and transaction semantics. Include focused integration tests for those contracts.

## Design review

Does each repository method express a domain operation or important query? Where is the transaction boundary? Can callers accidentally bypass a critical constraint? Does the abstraction expose enough information to diagnose slow queries and conflicts?
