# Design: a URL shortener, one machine

Start with the smallest system that satisfies the behavior: accept a long URL, return a short code, and redirect code lookups to the original destination. One application process and one relational database can handle an early product. The goal is to make correctness explicit before adding scale: codes must be unique, redirects must be fast, invalid URLs must be rejected, and creation retries must not create duplicate links.

## Requirements and data model

For creation, accept a URL, validate scheme and length, apply abuse checks, allocate a code, and persist the mapping. For redirect, look up code, check expiration or disabled status, record any required analytics, and issue an HTTP redirect. A relational table can hold `code` as a primary key, `target_url`, creation time, optional expiration, owner, and status. A unique constraint on code is the final collision guard. Keep analytics separate from the critical redirect transaction if the product does not need synchronous counts; writing one analytics row per redirect can turn the hot path into a write bottleneck.

To generate codes on one machine, use a database sequence and encode the integer in a base-62 alphabet. This produces compact, unique codes within the database's sequence scope. It is predictable, so it may not suit privacy or unguessability requirements; random codes can be used instead, with collision retries protected by the unique constraint. Do not assume a random collision is impossible; catch it and generate another code. The sequence strategy also has a clear capacity: the chosen alphabet length determines the maximum code space and code size.

## Request flows

Creation runs a single transaction: validate and normalize the submitted target as needed, allocate a code, insert the mapping, and return the short URL. An idempotency key can make client retries return the same created mapping after a network timeout. Bind that key to the authenticated principal and request parameters. Redirect is a point lookup by primary key. If the code exists and is active, return a 301 or 302 based on product semantics. Permanent caching with 301 can make destination changes difficult because clients and intermediaries may retain the redirect. A 302 or 307 offers more control; document the chosen behavior.

Validate allowed schemes such as HTTP and HTTPS to avoid turning the product into a dangerous `javascript:` redirect or an internal network proxy. Preview scanners and link unfurlers can trigger redirects; track bot traffic separately if analytics matter. Apply creation quotas and abuse detection for phishing, spam, and malware, while keeping moderation out of the latency-sensitive redirect path when possible.

## First scaling limits

On one machine, the database is both persistence and index. Add a cache only after observing read load; cache immutable or rarely changed mappings with a TTL and invalidation strategy. If destination edits are allowed, stale cached redirects need explicit handling. Use access logs or an asynchronous event queue for analytics. Back up the database and test restore. Measure lookup p95/p99, DB connection saturation, cache hit rate, creation failures, and redirect error rate.

Test duplicate code insertion, expired links, malformed URLs, a lost creation response followed by retry, database restart, and redirect caching. One machine is a valid first design when its capacity and recovery limits meet requirements. Keeping code allocation and uniqueness in the database makes later movement to multiple application servers straightforward; global uniqueness and analytics are the next design problems when scale demands them.

## Design review

What is the code allocation method and collision guard? Which redirect status code matches editability and caching? Are unsafe URL schemes rejected? Can analytics fail without breaking redirects? What traffic or recovery metric would trigger a move beyond one machine?
