Hashtags turn marked phrases in user content into navigable topics. The system must parse text consistently, store a relationship between post and tag, and serve recent or ranked posts for a tag. A simple `#\w+` regular expression is fragile across languages, combining marks, emoji, punctuation, and edited posts. Define the accepted syntax as a product contract and version the parser.

## Extract from displayed text

Parse the final stored text, not an untrusted client-provided list of tags. Normalize the tag key for matching while preserving the original display spelling. Unicode Standard Annex #31 discusses hashtag identifier boundaries, and UAX #29 describes word segmentation across scripts. Decide whether underscores, digits, emoji, and combining marks are allowed; test scripts without whitespace word boundaries. A tag should not begin in the middle of a longer identifier, and a URL fragment should not accidentally become a topic if the product excludes it.

Keep character offsets or source spans so the UI can link the exact hashtag without reparsing under a different rule. A post edit may add or remove tags. Re-extract with the current agreed parser version, calculate added and removed `(post_id, tag_key)` edges, and apply them idempotently. A parser upgrade may require reindexing old posts; keep the version so old and new results do not silently disagree.

## Model the tag relationship

Store a canonical tag row and a join table keyed by `(tag_key, post_id)` with post creation time, visibility metadata, and perhaps a ranking signal. Index by tag and time for a recent-post page. A unique constraint prevents a post repeating `#design` three times from appearing three times in the tag feed, unless the product explicitly wants occurrence counts. Keep the post as the source of truth for body text and access rules; the tag join is a derived index.

Hot tags can make one tag partition enormous during an event. Partition entries by time or bucket, use cursor pagination, and cache the first page with a short freshness bound. A trending count can be built from accepted tag events in time buckets, with spam filtering. Do not let raw mention volume alone define trend quality: bots can coordinate a burst. Retain an audit or replay path so tag indexes can be rebuilt after parser bugs.

## Serve safely and measure drift

Tag pages must filter deleted, private, blocked, and moderated posts at read time or remove them promptly from the projection. A stale join row should not reveal a private post. Normalize query tags with the same policy as stored tags, and redirect variants to one canonical URL only when they are truly equivalent. Case folding may be language-sensitive, so test representative locales rather than assuming ASCII lowercase is enough.

Measure extraction errors, tag-index lag, duplicate edge attempts, hot-tag query latency, moderation-filter rejections, and drift between tags parsed from posts and stored edges. Test edits, deletion, emoji and non-Latin text, and a sudden global trend. The goal is a stable, explainable topic link, not just a token that starts with `#`.

## Design review

What exact characters and boundaries form a tag? Is extraction server-owned and versioned? Can edits and retries update tag edges safely? How are hot tags paged? Can a stale tag index expose content that is no longer visible?
