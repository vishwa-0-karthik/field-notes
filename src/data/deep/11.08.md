Reaction modeling records who reacted to what and derives counts for display. A heart, thumbs-up, or emoji may look like a counter, but a user can retry, switch type, remove a reaction, or react from multiple devices. Model the user's desired state first and compute aggregates from accepted state changes. This makes idempotency and “unlike” behavior much easier to reason about.

## Choose the uniqueness rule

If a user may select only one reaction per item, use a unique key `(item_id, user_id)` and store `reaction_type`, state, and version. A new selection updates the existing row. If multiple types are allowed simultaneously, the unique key includes `reaction_type`. State the rule clearly; otherwise an API might accidentally allow five thumbs-up entries from one user. PostgreSQL unique constraints and `INSERT ... ON CONFLICT` provide one transactional way to enforce and update the state.

Prefer an API like `PUT /items/{id}/reaction` with the desired type or `DELETE` to remove it over a blind `toggle` when retries are possible. Sending the same desired state twice has the same outcome. If a toggle is required by the UI, attach an idempotency key and a known prior version so a retry does not reverse the action again. Return the authoritative user state and a count snapshot or version after the mutation.

## Derive counts from transitions

When a new reaction is inserted, increment its type count. When a reaction changes from 👍 to ❤️, decrement one and increment the other. When removed, decrement only if an active row existed. Emit a transition event after the state transaction commits, perhaps through an outbox. A duplicate event must not apply the count delta twice, so the aggregator tracks event IDs or computes counts from the current reaction table during reconciliation. The aggregate is a projection, not the authority for whether one user reacted.

For a viral item, updating one exact count row on every reaction may become a hotspot. Shard counters or aggregate events in small batches, accepting a short display lag. Keep a per-user state lookup fast and independent of the public count. A client can show its own reaction immediately after acknowledgment while the global count catches up. If the item is deleted or made private, block further reactions and hide the count according to visibility policy.

## Handle concurrency and abuse

Two devices can set different reaction types at nearly the same time. Decide whether last committed update wins or require a version check and conflict response. A monotonically increasing row version helps clients avoid applying an older response after a newer one. Rate limit rapid changes and monitor accounts that generate unnatural patterns. Avoid counting unauthenticated or bot activity as normal user engagement without a stated policy.

Measure accepted transitions, duplicate requests, count lag, drift between aggregate and reaction rows, and top-item write contention. Test insert, duplicate insert, switch, remove, retry after timeout, simultaneous devices, and recovery from aggregator failure. A design that keeps state transitions correct can always rebuild the display count; a design that only keeps a number cannot explain who owns a reaction.

## Design review

Can one user react once or once per type? Is the API a desired-state operation or a toggle? Which transition changes each count? Can replay apply a delta twice? How is a hot item's count scaled and reconciled?
