Byte-range indexed object storage puts a large immutable data file in an object store and fetches only the ranges needed for a lookup. It can separate cheap, durable storage from query workers, but each remote range request has latency and request cost. The index design should minimize round trips while keeping reads correct when files are replaced.

## Put a navigable index in the object

Imagine a sorted file of a million records. A footer at the end contains the location of an index. The index maps key ranges to data-block offsets and lengths. A reader first fetches the small footer, then the relevant index block, then the target data block. Each block should carry a checksum and enough metadata to detect a wrong or partial response. If the index is small enough, cache it in memory so ordinary lookups need only one remote range request.

Amazon S3 supports `Range` on `GetObject`, allowing a caller to retrieve part of an object rather than transferring it all. Its documentation notes that multiple ranges are not returned in one GET request. That means a layout requiring several scattered blocks can incur several network round trips. Co-locate metadata commonly needed together, and benchmark realistic request latency and object-store request charges as well as transferred bytes.

## Keep offsets tied to one immutable version

Offsets are meaningful only for the exact object bytes used to build the index. Overwriting the same object key while readers hold cached index entries can send them to the wrong ranges. Publish each data file under a unique immutable name or version ID, then atomically update a small manifest that points to the current file. A reader pins the manifest generation for the duration of its query. Old files remain until no reader or rollback path needs them.

An HTTP ETag or object version identifier can help a reader verify it is requesting the intended version, but the application must use it consistently. The manifest itself needs a durable update rule and recovery story. If two writers race to publish, use compare-and-set in an authoritative metadata store or a single writer; “last upload wins” may lose data.

## Account for caching and failure

Range reads benefit from local block caches and prefetch for sequential scans. Cache by immutable object identity plus offset and length, not just a mutable key name. If a range response is shorter than requested or fails checksum validation, retry with bounds and surface corruption if it persists. An object store can be highly durable while a query still fails because metadata is wrong, the network is slow, or a hot block overwhelms the request path.

For scans, many small range calls can be slower than fetching a larger continuous chunk. Choose block size from the expected mix of point reads and scans. Compression can reduce transfer size, but a record inside a compressed block usually requires fetching and decompressing that whole block. Measure p95 and p99 lookups during cold-cache operation, not only after every index is warm.

## Design review

How many remote requests does a point lookup require? Are offsets tied to an immutable object identity? What happens when a manifest changes during a read? Which blocks are cached, and how are corrupt or partial range responses detected?
