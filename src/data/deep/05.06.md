A cache makes normal reads cheaper, but its failure can put the entire original workload back on the database. “Fall back to the database” is therefore a capacity decision, not a harmless line of exception handling. Decide which requests remain available, which can use bounded stale data, and which must be rejected when cache capacity disappears.

## Model the cold-cache load

Suppose an endpoint gets 20,000 reads per second with a 98% hit rate. The database sees roughly 400 reads per second in steady state. If the cache fails and every request goes to the database, demand becomes 50 times higher. A database sized for 1,000 reads per second cannot absorb it. The fallback needs a rate limit, admission policy, or reduced feature set. Load-test this mode before relying on it.

Even partial cache failure matters. A lost shard can send all keys in its range to the source, while healthy shards still appear fine in an aggregate hit-rate chart. Monitor hit rate and source load by shard, route, and tenant. A latency spike may indicate a slow cache rather than an outright outage; short cache timeouts and a circuit breaker keep request workers from waiting behind a failing node.

## Define degraded responses

For a public profile, a recently stored local copy might be acceptable for a short stale window. For an account balance, returning a stale value without labeling it may be worse than an error. For permissions, stale allow decisions may create a security issue. Classify endpoints by freshness and consequence, then choose one of four actions: use an authoritative source within a safe rate, serve bounded stale data, return a reduced response, or fail clearly.

A process-local emergency cache can soften a distributed-cache outage, but it is fragmented across instances and may carry older values. Make its expiry and scope explicit. Do not use a local cache to hide an invalidation bug. If an API serves stale data, expose its age or a clear stale marker where that helps callers make decisions.

## Recover without causing a second incident

When the cache returns, every node may rush to refill. Limit concurrent fills, jitter TTLs, and warm only truly hot keys. A restored cluster may have changed ownership or lost writes during failover; rebuildable copies should be reloaded from the authority. Redis Cluster can continue through some node failures but becomes unavailable under larger failures, so clients must handle both redirects and loss of service. Replicas improve cache availability but do not make cache contents authoritative.

Keep the source path healthy in ordinary operation. If the application only ever reads through the cache, a broken database connection may remain unnoticed until cache failure. Run controlled cache-bypass probes and rehearse failover. Record the database's safe read budget, cache timeout, fallback rate cap, and recovery procedure in the service runbook.

## Design review

What is the database load at zero cache hit rate? Which endpoints may serve stale data? How are fallback requests capped fairly across tenants? Can the system recover and warm the cache without overwhelming the source?
