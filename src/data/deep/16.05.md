# Design: a recommendation system

A recommendation system turns a user's context and a large candidate catalog into a small ranked set. Its serving path is usually two-stage: candidate generation retrieves a manageable pool from several sources, then ranking scores candidates using richer features. The system must define the product objective first—watch time, purchase relevance, discovery, safety, or a constrained blend—because the objective shapes data collection, evaluation, and ranking tradeoffs.

## Candidate generation and ranking

Candidate sources can include collaborative filtering from user-item interactions, content similarity, popularity by cohort, editorial collections, and recent items. Each source is a retriever with its own freshness, latency, and coverage. Merge and deduplicate candidates, apply hard eligibility filters, and pass a bounded set to the ranker. Eligibility includes availability, age or region restrictions, inventory, blocks, and policy. A high model score must never override a hard safety or access rule. If one retriever is unavailable, preserve a useful baseline rather than failing the entire page.

The ranker can combine user, item, and context features such as recent activity, item popularity, price, freshness, and device. Offline-trained models can be served online with precomputed user and item embeddings or features. Online features need freshness and a fallback value when the feature store is unavailable. Cache stable candidate sets for anonymous or cold-start users; personalize after identity is known. For a newly joined user, ask a small number of preference questions or use contextual popularity without pretending the model has rich history.

## Feedback and evaluation

Log impressions, positions, clicks, dismissals, purchases, and other outcomes with event IDs and model/version metadata. An event counts as a negative only when the user had a real chance to see and reject the item; unexposed candidates are not negative examples. Position affects clicks, so training and evaluation should account for exposure bias through randomized exploration, propensity weighting, or carefully designed experiments. Add diversity and novelty constraints to avoid repeating one category or popular item endlessly. Keep a controlled exploration budget and enforce safety rules first.

Offline metrics such as recall@K, NDCG, and calibration help compare models but do not prove a product improvement. Online experiments measure user outcomes with guardrails for latency, complaints, safety, and long-term diversity. Use stable experiment assignment and avoid leaking users across control and treatment through shared household or organization accounts if that matters. Record the exact model, features, and candidate sources used for every response so a surprising recommendation can be debugged.

## Serving architecture and operations

A request service fetches context and features in parallel with strict deadlines, queries retrievers, filters candidates, ranks, and returns a small explanation or reason code when product policy allows. Precompute heavy features on a stream or batch cadence, and refresh them based on data freshness needs. Keep a simple popularity or editorial fallback. Track p95/p99 latency by stage, candidate counts, feature misses, stale feature age, ranking distribution, diversity, click and conversion metrics, and safety blocks. Test cold start, missing feature store, stale inventory, a model rollout, and feedback duplication.

## Design review

Which objective and hard constraints govern ranking? How are candidates sourced and deduplicated? Are impressions distinguished from unexposed items? What fallback works when features or models are unavailable? Can a result be traced to its model and feature versions?
