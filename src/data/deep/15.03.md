# Design: a URL shortener at scale

At scale, a URL shortener is an asymmetric workload: creating a mapping is relatively rare, while redirects can be extremely frequent and geographically distributed. Keep the mapping immutable where possible, make reads cacheable, and move analytics off the redirect path. The architecture usually contains an API for creation, a durable mapping store, a distributed cache, a redirect service near users, and an asynchronous event pipeline for click analytics and abuse signals.

## Code generation and durable mapping

A relational sequence with base-62 encoding is simple but centralizes allocation. It can be partitioned into ranges or replaced by random codes as creation scales. Random allocation needs a uniqueness constraint and retry on collision. Snowflake-style IDs or preallocated ranges can reduce central calls, but reveal ordering or require clock and worker-ID coordination. Choose code length and entropy based on predictability, collision risk, and privacy. If codes are tenant-scoped or custom aliases are offered, uniqueness may be global or scoped; encode that rule in a unique index.

Persist `code → destination` as the source of truth with owner, lifecycle, policy state, and version. The redirect read path checks a hot cache first, then a replicated key-value or relational store. Cache popular mappings at the edge or regional layer. A viral code can become a hot key, so use CDN caching, request coalescing, or replicated cache entries. TTLs should respect expiration and update semantics. For immutable destinations, versioned cache entries and long TTLs are efficient. If destinations are editable or revoked, invalidation must propagate within a stated bound; high-risk revocation may require edge authorization on every hit or short-lived caching.

## Redirect correctness and abuse

A redirect request should remain minimal: parse a normalized code, retrieve a valid mapping, enforce status and expiry, and return a redirect. Keep target URLs bounded and restrict dangerous schemes. Use a status code whose cache behavior matches whether targets can change. Bot scanners and preview clients may fetch links automatically, so click analytics should distinguish likely human visits. Record click events asynchronously with a compact schema; the redirect response should not wait for analytics persistence. A durable queue or log can absorb bursts and replay events, while downstream consumers aggregate views, geography, and device classes.

Creation requires abuse controls: quotas, reputation, URL scanning, user reports, and rapid revocation. Avoid a full malware check synchronously if it makes creation unusable; place new links in a pending state or apply risk-based policy. Replicate mapping data across regions with an explicit consistency model. Creation may be strongly consistent at the home region while reads are eventually consistent elsewhere; if a brand-new link must work globally immediately, use read-through to the home region or route by code partition.

## Scale and operations

Shard by code hash or prefix for predictable lookup distribution, but popular keys may still concentrate cache traffic. Plan backup, restore, and deletion of expired links. Track redirect p99, cache hit ratio, hot-key skew, origin fallback, replication lag, event backlog, code collision retries, and unsafe-link reports. Test viral traffic, cache invalidation, a database region outage, duplicate click events, and a revoked destination still present in an edge cache.

## Design review

How are globally unique codes generated? What is the consistency contract for a new mapping? Can revocation reach cached redirects quickly? Does analytics failure affect redirect availability? How are viral hot keys and phishing reports handled?
