# Design: an object store (S3)

An object store exposes a simple API for writing and reading large immutable or versioned blobs by key. The interface may look like a key-value map, but a production service must coordinate metadata, durable bytes, authorization, multipart uploads, versioning, listing, and repair. Start with the contract: objects are addressed by bucket and key; clients can put, get, delete, list, and inspect metadata; large transfers can upload parts; and consistency rules specify when a successful write becomes visible.

## Separate metadata from data

The control plane handles authentication, bucket policy, object metadata, version IDs, and upload sessions. The data plane streams bytes between clients and storage nodes or erasure-coded object shards. A metadata record contains key, version, size, checksum, storage placement, content type, and lifecycle state. Writing an object should stage bytes, verify integrity, ensure durable replicas or fragments exist, then atomically publish metadata that points to the completed object. Readers should never see a partially committed object. If metadata is visible before all data is durable, a successful read may fail; if bytes exist but metadata does not, they are temporary orphans for cleanup.

Partition metadata by bucket and key hash or another balanced scheme. Listing by prefix and delimiter is a different query from exact key lookup and requires an ordered index or distributed merge. Large listings must paginate with continuation tokens that preserve traversal order. Object keys are opaque strings, not necessarily filesystem paths; avoid assuming directory operations are atomic. Strong read-after-write semantics for a key are easier than globally consistent multi-key transactions. State those semantics precisely, especially for concurrent overwrites and deletes.

## Durability, consistency, and versions

Replicate data across failure domains or use erasure coding to trade storage overhead for repair complexity. A write acknowledgment should state what durability condition has been met. Checksums detect transfer corruption and background scrubbing finds latent bit rot. Versioning keeps prior object generations available after overwrite or delete, which supports recovery but changes storage and lifecycle cost. Conditional writes (such as create-only or expected-version match) prevent accidental overwrite and support optimistic concurrency. Multipart upload needs a durable session ID, independent part retries, ordered assembly, and cleanup for abandoned parts.

Reads check authorization and metadata, then fetch the object from its placement, verifying checksum as data is reconstructed. A cache can serve hot objects, but object deletion or access revocation needs a defined invalidation or authorization check path. Signed URLs grant temporary capability access and must be scoped, short-lived, and redacted from logs. Bucket and object policy evaluation should be consistent across direct reads, CDN, listing, and multipart operations.

## Scale and operations

Hot keys and large objects create different bottlenecks. Cache hot reads and spread metadata, while streaming large data with bounded buffers so a single request does not consume unbounded memory. Background repair, replication, lifecycle expiration, and inventory scans need separate capacity from foreground traffic. Monitor request latency by operation, durability lag, replica health, checksum errors, orphaned bytes, multipart age, listing latency, hot partitions, and repair backlog. Test node loss during write, metadata timeout after data commit, concurrent overwrites, partial multipart failure, corrupted fragment repair, and region recovery.

## Design review

What durability condition allows PUT success? How are bytes and metadata committed consistently? What guarantees do GET and LIST provide? How do conditional writes and versions prevent lost updates? Can background repair keep up while foreground traffic remains isolated?
