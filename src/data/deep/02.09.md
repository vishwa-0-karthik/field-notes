Timeouts bound how long a caller waits. Retries give a transient failure another chance. Idempotency makes repeating an operation safe when the caller cannot tell whether the previous attempt succeeded. These mechanisms must be designed together; adding retries alone can multiply load and duplicate side effects.

## Start with the ambiguous outcome

A client sends `POST /payments` and the connection times out. The server may have charged the card and lost the response, or it may have failed before charging. A blind retry with a new operation ID risks a second charge. The client sends a stable idempotency key for the intended payment, and the server stores the key with the result or durable operation state. A retry with the same key returns the same logical result, subject to a documented retention window and parameter-mismatch policy.

Not every request should be retried. A validation error is permanent until input changes. A short network failure or `503` may be transient. A `429` can indicate a rate limit and may include guidance about when to retry. Retry behavior belongs in the API contract, especially for writes whose side effects matter. AWS's Builders' Library discusses idempotent API design as a way to make automated retries safe.

## Budget the whole call chain

Suppose an edge request has a 600 ms deadline. Its authentication step consumes 50 ms and database work 150 ms, leaving at most 400 ms for a downstream call and response overhead. Setting every nested call's timeout to 600 ms guarantees that the edge deadline may expire first. Propagate an absolute deadline or remaining budget so deeper services stop work that no longer benefits the caller.

| Mechanism | Protects against | Risk if misused |
| --- | --- | --- |
| Timeout | Waiting forever | Too short causes false failures |
| Retry | Transient failure | Amplifies overload and duplicates |
| Backoff with jitter | Synchronized retry storms | Increases completion time |
| Idempotency key | Ambiguous repeat of one intent | Wrong key scope merges distinct intents |

## Limit retry amplification

If each of three service layers retries three times, a single user request can create up to 27 attempts at the deepest dependency. Choose one layer to retry a given operation when possible. Bound attempts, elapsed time, and retryable status classes. Exponential backoff spreads attempts; random jitter prevents many clients from waking at the same moment. When a dependency is overloaded, retries may worsen it. Respect server throttling signals and consider a retry budget or circuit breaker.

The idempotency store has its own design questions. What is the key scope: per account, operation type, or globally? What if the same key is reused with different payloads? How long must the key be remembered? If the operation remains pending, should a duplicate request wait, return pending, or query status? The durable operation and key record should commit in a way that survives process crashes. A key held only in memory does not protect a distributed service.

## Test the uncomfortable timing

Inject a failure immediately before commit, immediately after commit but before response, and during response write. Verify the client's retry gets the correct outcome in each case. Test concurrent duplicate requests, not just sequential retries. Measure retry rates, attempts per original call, and completion latency; a rising retry rate may be the first sign of downstream saturation.

## Design review

After a timeout, can the caller learn whether the operation happened? Which failures are retryable, at which layer, and for how long? Does the same intent keep the same idempotency key through every retry, including after a client restart?
