Photo tagging attaches a person, object, or label to a location within an image. The coordinate must survive thumbnails, responsive layouts, crops, rotations, and image replacement. Store tags in the image's own coordinate space, then transform them for each displayed rendition. Keep tag identity, permission, and moderation separate from the geometric point.

## Choose a canonical coordinate system

After applying image orientation, record the canonical image width and height and store a normalized point such as `(x / width, y / height)` in the range `[0,1]`. A rectangular tag can store normalized bounds. Normalized coordinates scale naturally to different display sizes. Validate bounds and reject NaN or infinite values. Keep the orientation and crop transform associated with the image version; a point from an old version may no longer identify the same face or object after replacement.

When the UI displays an image with `object-fit: contain`, the full image is visible with letterboxing; the pointer position must subtract that padding before normalizing. With `cover`, parts of the image are clipped, so the mapping must account for the scaled image and crop offset. MDN documents how `object-fit` and intrinsic image dimensions affect rendering. Do not simply divide the pointer's position by the outer element width and height, or tags will drift when aspect ratios differ.

For a thumbnail derived with an explicit crop, save the crop rectangle in canonical coordinates. The client can map canonical tag points through that transform and omit tags outside the visible crop. A rotated or mirrored rendition needs the corresponding orientation transform. Test on portrait, landscape, square, high-density, and deliberately cropped images; a single desktop screenshot will not reveal the geometry bugs.

## Model the tag lifecycle

A tag row can include `photo_id`, tag ID, target user or text label, normalized position, creator, state, and image version. A person tag may require the tagged person's approval before public display. Removal or hiding must propagate to cached renditions and search indexes. Authorization should check whether the viewer may see the photo and the tag, not assume that knowing a tag URL grants access. A unique rule may prevent duplicate tags for the same person in one image, depending on the product.

Do not infer identity automatically unless the product explicitly supports that behavior and has appropriate consent and accuracy controls. False person tags can be harmful. Preserve an audit trail for edits and reports, but limit retention of sensitive identity data. Treat embedded location metadata as separate from visual tag coordinates; exposing camera GPS data is not required to place a tag on an image.

## Serve and test at scale

Query tags by photo ID with a small index, fetch photo metadata and current visibility, then render coordinates client-side. For pages with many thumbnails, avoid an extra request per image by batching tag summaries. Cache only under the photo's permission and version constraints. Measure tag placement error across renditions, moderation queue age, removal propagation, and stale-version tags. A photo replacement should either migrate tags through a known transform or invalidate them for review.

## Design review

Are coordinates relative to the oriented original image or a viewport? How are contain, cover, crop, and rotation mapped? What happens after image replacement? Can a person approve or remove their tag? Are tag permissions checked along with photo permissions?
