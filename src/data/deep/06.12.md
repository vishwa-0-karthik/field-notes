A metadata service records how to find and coordinate the parts of a distributed system. It may store service endpoints, shard ownership, feature configuration, or the current leader. These records are small compared with application data, but a wrong or unavailable record can disrupt the whole request path. Give metadata a clear authority, version, and recovery plan.

## Bootstrap without a circular dependency

A client needs an initial address to find the metadata service. That bootstrap address might come from DNS, a configuration file, or a known endpoint list. From there the client can fetch a versioned service map and discover the current owner of each shard. Avoid a cycle in which the metadata service itself requires the unavailable application service to start. Cache the last known good map locally so a brief metadata outage does not instantly stop every read, while setting a limit on how long stale ownership is safe.

Discovery records usually include service identity, address, health or lease state, and possibly a generation number. An endpoint should register only after it can serve traffic, and its record should disappear or become unhealthy after a crash. ZooKeeper's ephemeral nodes are one coordination pattern for membership; etcd supports watched key changes. Neither makes a load balancer's existing connections vanish immediately, so clients must still handle connection failures and retry against an updated view.

## Version ownership changes

Imagine moving shard 7 from node A to node B. If a client has an old map, it may send a write to A after B starts serving. A safe transfer needs an ownership generation or epoch that both storage nodes enforce, plus a defined handoff sequence. The metadata entry can say B owns generation 12, while A refuses writes for generation 11. Without enforcement at the storage layer, a perfectly consistent metadata service can still leave stale clients able to corrupt data.

Watches reduce polling but need gap handling. A client can disconnect and miss changes, or a watched revision may be compacted. On reconnect, read a fresh snapshot and resume from a known revision when supported. Apply updates atomically in the client so it does not briefly mix half of an old map with half of a new one. Keep metadata records compact; a hot watch fan-out can itself become a bottleneck.

## Keep the control plane resilient

Metadata updates are often less frequent than data reads, so a quorum-backed service can be practical. Yet every request should not require a live quorum lookup. Cache maps and use redirect or version errors to repair stale routes. Separate a control-plane outage from data-plane availability: existing routes may keep working, while moving shards or adding nodes pauses. Decide which operations are safe with a cached map and which require fresh authority.

Back up metadata and rehearse reconstructing it from storage nodes or manifests. Monitor map age at clients, lease expiry, watch reconnects, routing redirects, and conflicting ownership claims. An emergency edit of one metadata key should leave an audit trail and a way to roll back. Metadata deserves the same schema-evolution care as any other API contract.

## Design review

How does a fresh client find the service? Can requests continue from a cached map during control-plane failure? What prevents an old owner accepting writes? How do clients recover after missing watch events?
