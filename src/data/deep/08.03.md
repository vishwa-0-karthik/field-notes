An event bus lets a service announce a completed business change to multiple downstream consumers. It reduces direct calls between services, but introduces asynchronous visibility and delivery uncertainty. Treat the event as a versioned contract: consumers need a stable identity, the subject that changed, and enough context to act without guessing about the producer's private tables.

## Publish only after the fact is committed

Suppose an order service writes `status = paid` and publishes `OrderPaid`. If it publishes first and the transaction rolls back, consumers react to a payment that never became authoritative. If it commits first and the publish fails, consumers never learn about the payment. The transactional outbox pattern writes the business row and an event row in one database transaction. A relay later publishes the event and marks its progress. AWS and Debezium document this pattern and its duplicate-delivery implications.

The relay can fail after publishing but before marking the outbox row sent, so it may publish again. Give every event a stable ID and make consumers deduplicate or apply an idempotent state transition. If events for one aggregate require order, include an aggregate ID and monotonically increasing version, then route them to the same stream partition or enforce version checks at the consumer. A global event order across unrelated orders usually adds cost without useful meaning.

## Shape the event contract

An event envelope can include `event_id`, `type`, `schema_version`, `aggregate_id`, `aggregate_version`, `occurred_at`, and `trace_id`. The payload should state the business fact, not expose a raw internal database row unless that row is itself the promised public contract. Avoid sensitive fields that consumers do not need. Clarify whether the event is a notification requiring a follow-up API read or a self-contained state change suitable for building a projection.

Schema evolution needs a plan. Add optional fields compatibly, keep old readers working during rollout, and use a new event type or version for changed meaning. A consumer may replay months-old events with an older schema. Store examples and validation in contract tests, but also measure production parse failures by event type and version.

## Manage subscribers and lag

Each subscriber should own its progress and failure handling. A search indexer can lag behind the order database without holding up payment confirmation, but the product should know the resulting freshness window. A notification consumer may retry a transient provider outage, while an analytics consumer may skip malformed noncritical events after quarantining them. One poison event should not block every later event in a partition indefinitely without an operator path.

Use a dead-letter stream or quarantine store with the original event ID, reason, and replay controls. Observe publish lag from database commit to bus, consumer lag from bus to applied projection, duplicate count, and schema errors. A bus outage should leave committed outbox rows pending, not lose the business change or make the order transaction depend on broker availability.

## Design review

What transaction establishes the fact? Can a relay publish twice? Does each event carry a stable identity and per-aggregate version? How far may consumers lag, and how are failed events inspected and replayed?
