A query planner chooses an execution plan: how to find rows, join relations, sort results, and aggregate values. SQL says what result is wanted; the plan determines how much work is done. A slow query is often a poor plan for the current data distribution, a missing access path, or a query that asks for more rows than the user needs.

## Read the plan as a tree of work

Suppose a dashboard asks for a customer's last twenty paid orders. The planner may use an index scan on `orders(customer_id, created_at)`, filter `status = 'PAID'`, and stop at twenty. Or it may scan many orders, sort them, and apply a limit. `EXPLAIN` displays the chosen plan and its estimates. Read from the leaf operations upward: scans feed joins, filters, sorts, and the final result.

Pay attention to estimated rows, actual rows, loops, and timing when available. If a nested-loop join expects one row from its outer side but actually receives 100,000, the repeated inner lookup can dominate execution. If the estimate is wrong, statistics may be stale or the data may be skewed or correlated in a way ordinary column statistics do not capture. If estimates are accurate but the plan is still slow, the query may genuinely need a new index or a different shape.

| Plan symptom | Possible cause | First investigation |
| --- | --- | --- |
| Sequential scan on huge table | Predicate not selective or no usable index | Compare rows matched and index options |
| Large sort before `LIMIT` | Index cannot provide order | Check composite index order |
| Join output far above estimate | Skew or correlation | Inspect statistics and predicates |
| Many loops of inner scan | Bad join order or missing inner index | Multiply actual loops by per-loop work |
| Disk spill | Sort/hash exceeds memory | Reduce rows or adjust memory carefully |

## Distinguish cost units from time

PostgreSQL plan costs are relative estimates used to compare candidate plans; they are not milliseconds. An `EXPLAIN ANALYZE` execution reports actual timing and row counts. It executes the statement, so running it on an `UPDATE` or `DELETE` can change data unless wrapped and rolled back appropriately. For production diagnosis, consider query impact, sensitive parameters, and sampling. Compare plans with representative values because one customer with five orders may choose a very different plan from one with five million.

`ANALYZE` refreshes statistical summaries that inform estimates. It samples data, so estimates can still be wrong for rare or highly skewed values. A planner may choose a sequential scan deliberately when a filter returns a large fraction of a table. Forcing index use without understanding cost can make the query slower.

## Fix the cause, then validate

Possible remedies include a more selective predicate, a composite or partial index, a query rewrite, an updated statistic, or a read model for expensive aggregation. Limit the selected columns and rows when the user does not need everything. Avoid making a query faster in isolation while shifting huge write cost into indexes or materialization. Compare before and after with the same data volume and realistic parameter mix, then monitor p95/p99 under load.

The plan is evidence, not a verdict. It explains what the database chose under current estimates and settings. The product requirement still decides whether the response is fast enough and whether a more expensive write path is worthwhile.

## Design review

Which operation consumes most rows or time? Do estimated and actual row counts differ substantially? Does the plan change for hot customers or recent dates? What new cost would the proposed fix add to writes and storage?
