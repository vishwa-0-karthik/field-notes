Consensus lets a group of nodes agree on an ordered sequence of decisions despite some nodes failing or messages being delayed. It is used to maintain a replicated state machine: every healthy replica applies the same committed commands in the same order and reaches the same state. The useful question is which invariant needs that shared order, not whether every distributed feature needs a consensus cluster.

## See the replicated-log problem

Suppose three nodes store configuration. If one node changes `leader = A` and another changes `leader = B` without coordination, clients can receive incompatible answers. A consensus log gives entries an order and a commit rule. In Raft, a leader appends entries and replicates them; an entry is committed under the protocol's majority and term rules. Once committed, future leaders must preserve it. The application should only claim success after the required commit milestone, not after one server merely accepts the request.

Consensus separates safety from liveness. Safety means incompatible decisions are not both committed under the model. Liveness means progress resumes when the network and enough nodes cooperate. A minority partition cannot safely commit new entries in a majority-based design, so some requests become unavailable there. Increasing the number of nodes does not automatically improve performance: each write still needs coordination, and a larger quorum can add work.

## Understand a Raft term

Raft divides leadership into numbered terms. A follower starts an election after missing leader communication, and a candidate needs a majority of votes. Log freshness rules prevent a candidate missing committed history from becoming leader. The leader sends heartbeats and replicates commands. A server observing a newer term steps down. Randomized election timeouts reduce repeated split votes, though unstable networks can still delay elections.

A five-node group tolerates two unavailable nodes for majority progress; three unavailable nodes prevent new commits. This arithmetic assumes independent failures and correct membership. Putting all five on one host does not provide the intended fault tolerance. Membership changes themselves need safe sequencing so two disjoint groups cannot each believe they are the majority.

## Keep the state machine deterministic

Replicas must apply a committed command the same way. A command such as “increment account balance by 10” is deterministic if it references the same starting state and rules. “Set balance to current wall time” may differ per node unless time is part of the committed command. External side effects like sending an email should not be run blindly by every replica during log replay. Emit a durable intent and arrange idempotent delivery by a designated worker.

Snapshot and compact old log entries so storage does not grow forever, while preserving enough metadata to maintain safety. A recovering node needs a snapshot plus subsequent entries. Monitor leader changes, commit latency, replication lag, rejected proposals, and snapshot recovery. For simple application state, using an existing database's transactions is often easier than operating a new consensus service.

## Design review

Which decisions require one agreed order? At what point does the API acknowledge success? How many failures can the quorum tolerate in the real deployment? Can every replica replay commands deterministically?
