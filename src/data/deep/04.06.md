A hot partition receives much more work than its peers and reaches a per-partition limit even when the cluster has spare capacity. More nodes do not automatically help if all requests for one key still route to one partition. The fix depends on whether the hotness comes from one item, one partition key grouping many items, or a time range that concentrates current writes.

## Identify the shape of the hot spot

Imagine a live event where millions of viewers increment one `viewer_count` item. The partition holding that key sees nearly all writes. A hash function distributes *different* keys, but one key still has one hash result. In another case, `customer_id` is a partition key and one enterprise customer has far more orders than the rest. A third case is a time-ordered key where all new writes land in the latest range. Each needs a different remedy.

Measure per-key and per-partition request rate, bytes, throttles, p99 latency, and storage size. A cluster-wide average can hide a saturated shard. AWS DynamoDB guidance explicitly warns that partition keys with poor request distribution can throttle while overall capacity is underused.

| Hotness pattern | Possible response | Cost |
| --- | --- | --- |
| One read-heavy item | Cache or replicate reads | Invalidation and staleness |
| One write-heavy counter | Sharded counters | Merge reads and approximate freshness |
| Large tenant | Bucket within tenant | Queries merge buckets |
| Current time range | Hash suffix or time buckets | Range scans touch several pieces |

## Split work only when semantics allow it

For a view counter, write to `count#0` through `count#31` chosen by a request hash, then sum the shards for a read. This raises write capacity at the cost of a more expensive or delayed total. It works because increments commute and an approximate count is often acceptable. It is unsafe for an inventory balance if two purchases must atomically compete for the last unit; splitting that invariant needs a reservation allocation scheme, not a blind counter sum.

For a hot tenant, add a bucket key such as `(tenant_id, month)` or `(tenant_id, bucket_id)` while keeping the tenant ID available for authorization. A query for one tenant may need to merge several buckets. Design pagination and ordering across them; a simple local `LIMIT 20` on each bucket does not necessarily produce the correct global top twenty without a merge.

## Beware of adaptive fixes

Some managed stores can split partitions or adapt to hot traffic, but one indivisible item or key can remain a bottleneck. Do not rely on automatic scaling as the only hot-key plan. Caches can relieve reads but not high-rate writes to one authoritative record. More application replicas can worsen contention on the same database row.

Write sharding needs a deterministic or random bucket selection and a way to discover all buckets later. If random buckets are added during a live migration, old and new readers must agree on the bucket count. Monitor skew after the change: a small number of buckets can still be uneven, while too many buckets make reads expensive. Test at realistic key popularity distributions, not uniform synthetic traffic.

## Design review

Is the hot spot one key, one tenant, or one range? Which invariant requires a single writer? If work is split, how are reads merged and how fresh is the answer? What happens when bucket count changes?
