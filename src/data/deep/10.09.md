Heavy hitters are keys that contribute a large share of a stream: popular posts, top search queries, or sources of unexpected traffic. A top-K dashboard needs to discover the keys as well as estimate their counts. A count-min sketch can estimate a key you already know, but it cannot list every key it has seen. Use a frequent-items summary, a bounded candidate table, or a partitioned exact aggregation with a merge step.

## Specify the top-K question

“Top ten products today” needs a time zone, accepted-event definition, and tie rule. Decide whether the ranking is by event count, distinct users, revenue, or another weight. A product with one purchase worth a large amount ranks differently under count and revenue. Choose how late events revise the list. If the top-K is used for abuse detection, a short freshness target may matter more than perfect order among close candidates.

For an exact result, aggregate every key in a distributed map, merge partition counts, and sort or maintain a heap. That can be expensive when key cardinality is huge. A frequent-items sketch keeps a bounded set of candidate keys and approximate frequency bounds. Apache DataSketches documents frequent-items error thresholds and modes that trade false positives and negatives. Choose the mode based on whether missing a true heavy hitter is worse than showing an extra candidate.

## Discover candidates under skew

Each partition can keep local candidates, then a reducer merges compatible summaries. A globally frequent key might be only moderately frequent in every partition, so simply taking each partition's top ten can miss it. Local candidate sets must be large enough, or the algorithm must provide a merge guarantee. Once candidates are known, a second pass over retained raw events or exact per-key counters can refine their final ordering. This two-stage design is often worth the cost for an externally visible leaderboard.

Hot keys can create hot stream partitions when partitioned directly by key. Salt their event keys for ingestion, aggregate partial counts, then combine by the original key. Keep the source event IDs and partition ranges so retries do not double-merge a partial summary. A single corrupt or missing partition can distort the ranking; track completeness by input range, not only whether the final reducer ran.

## Make outputs stable and useful

Near-tied items may swap places from small count changes or sketch error. Consider a refresh interval, minimum change threshold, or displaying approximate counts instead of continuously reshuffling the UI. A top-K list should include the measurement window and data freshness. If the purpose is operations, show uncertainty and any incomplete partitions so responders do not mistake a partial stream for a real traffic shift.

Evaluate with exact counts on sampled windows and deliberately skewed synthetic streams. Measure recall of true top-K, rank stability, count error, update throughput, merge latency, and memory. Test a new key that surges suddenly, not only long-established popular keys. The sketch is an optimization for discovery; the product contract decides whether approximate ranks are enough.

## Design review

What weight and window define “top”? Can the method enumerate candidate keys? Could a global heavy hitter be absent from all local top-K lists? Which errors are acceptable? Is there a second exact pass for externally important rankings?
