Redis GEO can provide a fast in-memory path for nearby lookup when the working set and query shape fit one Redis deployment. It stores members with longitude and latitude and can search a circle or box. Treat it as a hot candidate index: validate coordinates, filter candidates, and preserve an authoritative source for location state and rebuilds. A Redis hit is not automatically the nearest eligible result after business and permission rules.

## Model the hot location set

Use a key per region or entity type, such as `drivers:city-7`, and add members with stable IDs and coordinates. Set a TTL or remove members when a moving object's location expires. Keep the observation timestamp outside the GEO score if freshness matters; Redis GEO commands represent location, not the business validity window. A driver last seen thirty minutes ago should not be offered merely because the stored point is nearby.

`GEOSEARCH` supports radius or box queries and can return distance or coordinates. Use `COUNT` to cap a broad candidate set only when the product can tolerate that bound. If you request too few nearby members before checking eligibility, stale, offline, or unavailable drivers may consume all returned slots and hide valid candidates just beyond them. Over-fetch adaptively or use an authoritative prefilter where possible.

## Keep writes and reads consistent enough

Location updates are frequent and often last-write-wins. Attach a source timestamp or sequence and reject older updates that arrive late. If a member changes city or region key, remove it from the old key and add it to the new one; an atomic script can update both when both keys share one Redis shard. If Redis Cluster key placement prevents that, make the durable location table authoritative and run reconciliation for duplicate or missing members.

Partition by city or service area to keep queries local, but support boundary searches that span keys. A query near the edge of a city region must inspect adjacent regions or use overlapping coverage. Cache a user's location for a short time only with consent and privacy controls. Redis persistence, replication, and eviction policy determine whether this hot index survives restart; plan for reload from the authoritative location feed.

## Measure candidate quality and resource use

Track query latency, result count before and after eligibility filters, member age, location update rate, key memory, eviction, and Redis hot-key pressure. Test dense downtown queries, sparse rural queries, antimeridian behavior, and a burst of location updates. Compare the chosen Redis GEO result set with an exact spatial reference sample. If radius semantics, complex polygon filters, or durable history dominate the workload, keep Redis for the hottest path and use a spatial database for broader queries.

Include cardinality limits in load tests: one city key that grows without bounds can consume memory and slow maintenance even when query times look good. Rebuild keys with an explicit cutover if the member schema or partition boundaries change.

## Design review

Which records belong in the hot set, and how long are they valid? Can one Redis key become too hot? What happens when a query crosses region boundaries? How many candidates survive eligibility filters? How is the hot set rebuilt after eviction or restart?
