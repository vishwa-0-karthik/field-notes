HyperLogLog estimates the number of distinct values in a stream using far less memory than storing every value. It is useful for questions such as “how many unique viewers saw this page today?” where a small statistical error is acceptable. It cannot list the viewers, enforce a one-per-user quota, or prove an exact billing count. Name the result an estimate and keep its error properties visible.

## Understand the sketch intuition

Hash each identifier into a uniform bit string. Rare patterns of leading zero bits become more likely as more distinct identifiers are observed. HyperLogLog divides hashes into registers, records an extremal pattern in each, and combines register values into a cardinality estimate with bias corrections. Repeating the same identifier normally does not change the sketch because it hashes to the same value. The hash quality and stable normalization of identifiers matter: `User-7` and `user-7` are distinct unless the product normalizes them first.

Redis exposes `PFADD`, `PFCOUNT`, and `PFMERGE` for its HyperLogLog implementation and documents sub-1% standard error for that implementation. A standard error is not a hard maximum error on every estimate. For a small set where exactness matters, use a set or exact table instead. Some implementations use a sparse representation for small cardinalities, but the API still returns an estimate with implementation-specific behavior.

## Merge by the right dimensions

Create one sketch per day and segment, then merge compatible sketches to estimate a week or a broader segment. Merging requires the same hash function, precision, and identifier definition. Summing daily unique-user estimates is wrong when one user appears on multiple days; merge the sketches to count the union. Similarly, summing country sketches is only valid for an event count, not for globally unique users who may appear in several countries.

Sketches are easy to add to and merge, but removing one identifier is not generally supported. If a user deletion or fraud correction must subtract past membership, rebuild the affected bucket from raw events or use a different data structure. Windowing means storing separate sketches for bounded intervals and expiring them under a retention policy. Define how late events update an already published bucket and whether a reported number can be revised.

## Validate and operate estimates

Compare HLL estimates with exact distinct counts on sampled buckets and at several cardinalities. Monitor relative error, empty and low-count behavior, hash/version mismatches, and merge failures. A broken identifier extraction step can change the count much more than the sketch's statistical error. For example, hashing a session ID instead of a user ID measures sessions, regardless of how accurate the HLL algorithm is.

Use the same input event deduplication policy across exact and approximate reports. HyperLogLog naturally ignores repeated identical identifiers within a bucket, but it does not decide whether two accounts belong to one person or whether a bot should be excluded. Keep the semantic definition of “distinct” separate from the implementation. When reports are high stakes, preserve raw data and use an exact close process.

## Design review

What identifier defines uniqueness? Is an estimate acceptable for this decision? Are sketches merged instead of summed across overlapping groups? What happens when a record must be removed? How will estimate error and identifier-pipeline errors be detected?
