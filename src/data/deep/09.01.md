An information retrieval system finds and orders useful documents for a query. It is different from a database lookup: the user may not know the exact key, and many documents may partially match. A production search system has a document source, ingestion path, index, query parser, candidate retriever, ranker, and feedback loop. Design each against a stated corpus, freshness target, latency budget, and relevance objective.

## Define the document and query contract

Decide what counts as one searchable document. A product catalog may index a product with title, description, category, price, stock, and locale. A support search may index a whole article or smaller passages. Passage indexing improves pinpoint answers but creates more entries and requires grouping results back into pages. Define which fields are searchable, filterable, sortable, and visible to the user. Access control belongs in the retrieval contract: a fast index is unacceptable if it returns private documents to unauthorized users.

Queries need a similar contract. A user may type free text, a quoted phrase, a field filter, or a prefix. Parse these into an internal query representation; do not concatenate raw input into a backend query string. Decide how tokenization, language, spelling, and synonyms work. The same analyzer must be compatible across indexing and querying, or a term that appears in a document may never match the user's form of it.

## Separate retrieval from ranking

An inverted index maps terms to documents containing them. It can retrieve a candidate set efficiently. Ranking then scores candidates using text relevance and optional business signals such as freshness or inventory. A very selective filter can be applied before ranking; an expensive personalization model may be applied only to the top few hundred candidates. This staged design keeps tail latency bounded. A document that never enters the candidate set cannot be rescued by a better final ranker, so measure retrieval recall as well as final result quality.

The source database remains authoritative for edits and deletes. The search index is a derived view that may lag. State whether a new item must be searchable immediately, within seconds, or within minutes, and whether an update can temporarily show stale data. Use document versions or sequence numbers to reject out-of-order index updates. Keep a replay or full rebuild path; an index without a reproducible source is difficult to repair.

## Budget scale and observe outcomes

Estimate documents, average indexed tokens, posting-list size, update rate, queries per second, and high-percentile query cost. Shard for corpus size or throughput only when a single index is insufficient; every extra shard increases coordination and merge work for each query. Cache popular queries carefully because filters, permissions, and freshness can change the result. Separate query latency into parsing, retrieval, ranking, and fetch phases so an optimization targets the actual bottleneck.

Offline labeled queries and metrics such as precision or NDCG show relevance changes before rollout. Online clicks and reformulations reveal user behavior, but clicks are biased by existing rank and presentation. Watch zero-result rate, result freshness, permission-filter failures, p95 and p99 latency, indexing lag, and query categories. Maintain a small set of difficult representative queries for debugging. Stanford's information retrieval text develops the index and ranking foundations; the system design adds product contracts and operational guarantees around them.

## Design review

What is the searchable unit? Which filters and permissions must always hold? How fresh must the index be? What candidate recall is needed before reranking? How will a bad index be rebuilt and a relevance change be evaluated?
