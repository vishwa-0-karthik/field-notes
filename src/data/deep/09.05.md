BM25 is a common lexical ranking function used to score how well a document's terms match a query. It builds on TF and IDF ideas while limiting the benefit of repeated term occurrences and adjusting for document length. A production ranking system usually combines BM25 candidate scores with exact-match, field, freshness, and business signals. Those extra signals should be explicit so a relevance regression can be diagnosed.

## Read the terms of the score

For each query term, BM25 uses an IDF component and a term-frequency component that saturates as occurrences increase. Parameter `k1` controls how quickly repeated occurrences stop adding much value. Parameter `b` controls how strongly document length is normalized relative to average field length. Elasticsearch documents BM25 as its default similarity and exposes these parameters. The values are not universal constants for every corpus: product titles, long articles, and code snippets have different length distributions.

A simple example shows the point. If one article uses `raft` twice and another uses it 40 times, the second should not automatically be 20 times more relevant. If the second article is also ten times longer, some extra occurrences merely reflect its length. BM25 balances those observations. However, a query for the exact product name may deserve a title phrase match above a body document with a higher BM25 value. Give exact phrase and structured-field matches their own boosts or retrieval route.

## Build a staged ranking pipeline

First retrieve candidates with lexical postings and hard filters such as tenant, visibility, and category. Apply BM25 to get an initial top set. Then add features that require more work: phrase proximity, freshness, inventory, popularity, or a learned reranker. Keep the first stage large enough to retain relevant documents; a reranker cannot recover a document excluded by candidate retrieval. Bound expensive reranking to a known number of candidates and monitor its tail latency.

Scoring across shards can be surprising if each shard uses local corpus statistics. Two equally relevant documents on different shards may receive different lexical scores. Some engines provide a global-statistics query mode at extra round trips or cost. Test whether local-statistic differences materially change top results before adding that expense. Avoid using raw scores as absolute quality thresholds across different queries: score scales can vary by term rarity and query length.

## Tune with evidence, not intuition

Create a judgment set representing head and long-tail queries. Compare parameter changes with NDCG or a similar ranked metric, and inspect individual result movements. Run online experiments for user-facing changes, while guarding latency and zero-result rate. Click data can help but is biased toward already-high results. When a result looks wrong, use score explanations to see term frequencies, field lengths, and boosts. Elastic's explain API and Lucene's BM25 similarity documentation provide visibility into these components.

Watch for gaming. A seller may repeat target terms or put irrelevant words in fields with high boosts. BM25's saturation reduces some repetition incentive, but field validation, trust signals, and spam controls remain necessary. Keep the ranking policy readable and versioned so an emergency rollback is possible. The success measure is task completion for users, not a numerically higher score.

## Design review

Which fields get BM25, and which matches need an exact boost? How large is the candidate pool before reranking? Are shard scores comparable enough? What labeled and online metrics justify a parameter change? Can operators explain and roll back a ranking shift?
