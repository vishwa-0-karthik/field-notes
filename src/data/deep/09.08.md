Search feedback turns observations about user behavior into evidence for improving retrieval and ranking. Explicit feedback, such as “relevant” or “not relevant,” is comparatively clear but rare. Implicit signals, such as clicks, dwell time, purchases, and query reformulations, are abundant but ambiguous. A click proves that a result was visible and attractive enough to open, not that it answered the need.

## Capture the exposure, not just the click

An event for a click should include the query ID, normalized query version, result ID, rank, presentation surface, experiment assignment, and time. Also record which results were shown, because an unclicked document at rank 2 is different from one never displayed. Avoid logging raw sensitive queries or personal identifiers longer than needed. Session-level joins can reveal whether a user reformulated the query or completed a downstream task, but define privacy and retention boundaries before collecting them.

Position bias is central: the top result gets more attention partly because it is top. A naive model trained on historical clicks will reinforce the current ranking. Compare results within controlled experiments, randomize a small eligible slice when appropriate, or use established bias-correction methods. Guard business-critical and safety-sensitive queries from exploration. Explicit human judgments remain valuable for queries where clicks are sparse or misleading.

## Choose signals that match the task

For a product search, an add-to-cart or purchase may be stronger than a click, but it also depends on price, stock, and checkout quality. For documentation, a long dwell time might indicate engagement or confusion; a quick return could mean an instant answer or a bad result. Combine multiple signals and inspect segments rather than declaring one action “relevance.” Keep lexical match quality, authority, freshness, and user behavior as separate features so an item with many historical clicks does not permanently crowd out new content.

Explicit relevance feedback can modify a query representation using judged relevant and nonrelevant documents. Stanford's retrieval text discusses this approach and warns that too few judgments can make it unstable. In a modern product, feedback may instead update a training set or adjust a session's query expansion. Whatever the path, preserve the original query and the feedback version; otherwise a model cannot explain why results changed.

## Close the loop without creating one

Build a pipeline that validates events, aggregates them by query and result, filters spam or bots, and makes versioned features available to the ranker. Delay or cap rapidly changing popularity features so a short burst of fake clicks does not dominate. Hold out a stable evaluation set and compare online experiments against it. A new ranking can increase click-through rate by making sensational titles more tempting while reducing task success; pair engagement with downstream success and reformulation measures.

Monitor exposure logging completeness, missing click joins, feature age, model version, and regressions by query class. Provide an operator path to remove a corrupt feedback batch and rebuild features. A feedback system should support controlled improvement, not make the ranker depend on opaque and irreversible accumulated behavior.

## Design review

Which observed behavior reflects success for this search surface? Are exposures logged with rank and experiment context? How is position bias handled? What privacy limits apply to query logs? Can bad feedback be excluded and features rebuilt?
