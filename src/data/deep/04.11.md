Clock skew means two machines disagree about wall time, or one machine's clock jumps. It matters for time-embedded IDs, TTLs, leases, event order, and “latest” queries. An ID with a timestamp prefix is not a substitute for a globally agreed commit order. Design each use of time around the accuracy it actually needs.

## See how a clock creates an ID bug

Suppose a Snowflake-style worker issued IDs at millisecond 5000 with sequences 0 through 50. Its clock is corrected backward to 4999 and later returns to 5000. If the generator reset its sequence when time changed, it can issue `(5000, worker, 0)` again. A unique constraint may catch the duplicate, but the generator has violated its contract. It should detect backward movement before resetting state, then wait, fail, or use a documented logical-time mechanism.

UUIDv7 also embeds millisecond time. RFC 9562 discusses monotonic counters and clock rollback handling. A generator can preserve per-process monotonic order by retaining the last timestamp and incrementing a counter, but persistence across restarts and behavior across nodes need separate thought. Random bits protect uniqueness probabilistically; they do not make the timestamp accurate.

| Use of time | Risk from skew | Better contract |
| --- | --- | --- |
| Sort user posts | Misordered posts | Timestamp plus stable tie-breaker, accept bounded disorder |
| Lease expiry | Old owner acts after lease | Fencing token checked by resource |
| TTL | Premature or late expiration | Authority uses one clock and clear semantics |
| Audit sequence | Wrong causality inference | Commit order or logical sequence |

## Distinguish wall time from logical order

Wall-clock timestamps answer approximate “when.” A monotonically increasing local counter answers “which came next on this process.” Lamport clocks or database commit sequences can represent causal or authoritative order under specific rules, but neither is the same as a precise wall-clock time. If a payment record needs a defensible order of commits, define it at the ledger's commit point rather than sorting application-server timestamps.

For distributed transactions, systems that require external consistency invest in stronger clock and coordination mechanisms. Google Spanner's TrueTime API reports time uncertainty and uses it in its ordering guarantee. That is more than synchronizing clocks with a standard time daemon; it is an architectural commitment with latency and operational consequences. Most applications should avoid promising global real-time order unless the product truly requires it.

## Make uncertainty visible

Monitor clock offset and synchronization status on ID-generating nodes. Alert before offset approaches the maximum tolerated skew. Log both event time and server receipt or commit time when debugging pipelines. For delayed messages, distinguish “the event occurred at” from “the broker accepted it at” and “the consumer processed it at.” A late event can have an earlier business timestamp without being a duplicate.

If pagination sorts by `(created_at, id)`, the pair gives stable ties but not necessarily causal order across servers. New late-arriving rows may appear before a cursor the user has passed. Decide whether the feed prioritizes exact snapshot traversal, approximate freshness, or a bounded delay window.

## Design review

Which machine's clock assigns the timestamp? How large can skew be before correctness breaks? Is the required order per worker, per entity, or global? What happens after a clock correction or restart?
