# Design: a collaborative editor

A collaborative editor must make local typing feel immediate while several users edit the same document, possibly from offline devices. Separate the document's durable shared content from ephemeral presence such as cursors and typing indicators. Choose a merge model that fits document semantics and product guarantees: operational transformation (OT) commonly orders and transforms operations through a central authority, while conflict-free replicated data types (CRDTs) let replicas merge concurrent updates according to defined algebraic rules. Neither choice removes the need to design persistence, authorization, history, and resource limits.

## Data and synchronization model

Represent the document as structured nodes or shared text rather than a single HTML string if users need concurrent rich-text edits. Client edits should apply locally first for low perceived latency, then send operations or CRDT updates to the collaboration service. The service authenticates the user, checks room access, validates document and update size, persists accepted updates, and broadcasts them to connected collaborators. Presence messages use a separate short-lived channel because losing a cursor update must not lose a content edit. Awareness state should expire when a client disconnects and should not be retained as document history.

With OT, a server sequences operations and transforms incoming edits against operations already accepted. It provides a natural place to order writes but creates a central sequencing dependency and requires careful version handling. With CRDTs, replicas exchange state or incremental updates that can merge despite different arrival orders; offline edits can sync later, but metadata and tombstones may grow, and garbage collection or compaction must preserve merge correctness. Pick a mature, tested implementation rather than improvising transformation logic. Define the ordering and behavior for overlapping insertions, deletion versus formatting, and rich-text structural conflicts.

## Persistence and scale

The hot collaboration path can use WebSockets to deliver updates, with a document room or shard owning in-memory state. Persist updates to an append-only log or database before acknowledging durable success, or explicitly distinguish accepted-in-memory from saved. Periodically create snapshots so reconnecting clients need not replay an unbounded history. A durable update log enables recovery after room-owner loss. Assign each room to an owner for ordering and local batching; route clients consistently, and rebalance rooms without losing acknowledged updates. Very large popular documents may require partitioning or flow control, but splitting one shared sequence can complicate ordering.

Offline clients keep local updates and submit them after reconnect. The server should validate authorization again because permissions may have changed while offline. Updates should be idempotent by operation identity or CRDT update semantics. Retain version history through snapshots plus later updates, and define restore behavior: restoring a snapshot while users are active is a new merge or branch, not simply replacing bytes. Apply quotas for document size, update rate, connected sessions, and fanout to protect shared rooms.

Measure update-to-peer latency, local-to-durable acknowledgment, reconnect recovery time, room fanout, snapshot age, rejected updates, and document growth. Test partitions, duplicate update delivery, simultaneous edits at one position, permission revocation, owner crash, and a client reconnecting from a long-offline state. The editor is correct only if visible content converges and acknowledged edits survive failure.

## Design review

Why choose OT or CRDT for these document semantics? Are content and presence separated? When is an edit considered durable? How does an offline client reauthorize and reconcile? Can a room recover from its owner without losing acknowledged changes?
