TCP and UDP are transport protocols with different contracts. TCP provides a reliable, ordered byte stream between endpoints. UDP sends individual datagrams with little built-in delivery machinery: a datagram may be lost, duplicated, or arrive out of order. Application protocols can add their own reliability on top of UDP when that gives them more control.

## Start from the application's tolerance

A payment request cannot casually lose bytes or reorder fields. A TCP-based connection is a natural foundation for HTTP/1.1 and HTTP/2 because the application receives an ordered stream. A real-time game position update may have different priorities: an update from 200 ms ago might be less useful than a newer update, so waiting to retransmit the old one can hurt perceived responsiveness. UDP lets a game protocol decide which messages to repeat and which to discard.

TCP is a **byte stream**, not a message protocol. One `send` can be received in pieces or combined with later sends. The application must frame messages using a length prefix, delimiter, or higher-level protocol. UDP preserves datagram boundaries, but large datagrams can fragment at the IP layer and become fragile; applications usually keep them within a safe path size or implement their own framing and fragmentation strategy.

| Property | TCP | UDP |
| --- | --- | --- |
| Delivery | Retransmits detected loss | No delivery guarantee by itself |
| Order | Delivers bytes in order | Datagrams may arrive out of order |
| Message boundaries | None in byte stream | One datagram per send/receive unit |
| Congestion behavior | Built-in control | Application protocol must be responsible |
| Typical use | Web APIs, database connections | DNS, some media and game protocols |

## Understand the latency tradeoff

TCP's ordering can cause head-of-line blocking within a connection: later bytes wait for a missing earlier segment. For some live media, delivering a newer frame may matter more than repairing every older one. UDP by itself does not solve congestion or security; a well-designed protocol above it must handle both. QUIC is an example of a richer reliable transport built over UDP, used by HTTP/3. It adds machinery such as encryption, connection management, stream multiplexing, and congestion control. “UDP is faster” is therefore too crude: compare the whole protocol and workload.

TCP also has connection setup, flow control, and backpressure. These protect networks and receivers but require tuning for long-lived or high-volume connections. UDP has a smaller base header and no connection handshake at the transport layer, yet an application that needs acknowledgment, retries, authentication, or ordering may rebuild much of that complexity itself.

## Pick and test with failure in mind

For an internal RPC, prefer the protocol supported by the chosen application layer unless measurements show a clear need to change. For live telemetry or voice, decide what to do with missing samples and how much reordering to tolerate. Test packet loss, jitter, reordering, NAT traversal, and rate limits rather than only a perfect local network. Include an overload policy; a sender that emits unbounded UDP traffic can harm itself and other users.

The IETF TCP specification describes its reliable in-order byte-stream service and retransmission behavior. The UDP specification explicitly does not guarantee delivery or duplicate protection. Those are starting contracts; the application still defines end-to-end correctness.

## Design review

Is old data still valuable after a newer update arrives? Does the application need ordered bytes or independent messages? Who handles loss, congestion, security, and framing? Would an existing application protocol meet the need with less custom work?
