Live reactions let many viewers add or remove an emoji while a stream or post is active. A viral item can receive a burst of writes and fan the changing count out to far more watchers. Separate the authoritative reaction state from the low-latency display count. The user should get a clear result for their own action, while aggregate counts may be slightly delayed or coalesced.

## Define the reaction state transition

For a one-reaction-per-user rule, model a row or key `(item_id, user_id, reaction_type)` with an active state or use `(item_id, user_id)` if only one type is allowed at a time. A request has an idempotency key or a desired final state such as `set 👍` or `remove 👍`. A blind “increment” request retried after a timeout can add twice. Apply a conditional insert, delete, or state transition and emit an event only when the state actually changes. If anonymous reactions are permitted, define the weaker identity and abuse controls explicitly.

The authoritative store may be a partitioned database that enforces uniqueness. A single counter row for a viral item can be too hot, so aggregate accepted transitions through a stream into sharded counters or short time buckets. A user's reaction status should be read from their authoritative state; the public count can come from the derived aggregate. Reconcile the count from reaction rows or events when the aggregator falls behind or a bug is found.

## Broadcast at a controlled rate

Do not push a network message for every reaction to every viewer. At a million watchers, one thousand reactions per second could imply a billion outgoing messages per second. Coalesce counts on the server, for example publishing the latest total a few times each second, and let gateways fan out one update per interval to subscribed clients. A WebSocket or SSE connection can carry these updates. Include a monotonically increasing version or timestamp so a delayed update does not replace a newer count in the UI.

Partition subscriptions by item and gateway. A gateway keeps local connected viewers; a pub/sub layer sends each item update to gateways that have interested clients. Avoid broadcasting every item to every gateway. A slow client should receive the latest state rather than an unbounded backlog of obsolete intermediate totals. If a connection drops, the client fetches a fresh snapshot and resumes from there. The live count is a state, not a ledger of every intermediate display frame.

## Bound abuse and prove recovery

Rate limit reaction changes per user and item, validate item visibility, and prevent unauthorized clients from subscribing to private streams. A bot can still create many accounts, so monitor distinct actors, write bursts, and reversal patterns. Keep durable events for count recovery but only for a defined retention period. A queue outage can delay the public count while the accepted user state remains valid; show or log that lag rather than inventing a number.

Measure accepted transitions, duplicate requests, aggregation delay, broadcast fanout, gateway memory and connection count, dropped updates, reconnect snapshot rate, and drift between stored reactions and displayed counts. Load-test one extremely popular item because average traffic hides the key hot spot. The design succeeds when a user's own reaction is correct and the public display remains responsive without requiring per-reaction global broadcast.

## Design review

What unique state prevents duplicate reactions? Does an unlike reverse only a prior active reaction? How often is the aggregate broadcast, and to which gateways? Can a slow or reconnecting client recover the latest version? How is count drift reconciled?
