An LSM tree stores recent writes in memory and durable log records, then flushes sorted immutable files and merges them over time. It favors sequential write throughput while retaining ordered keys for point lookups and scans. The cost is read, write, and space amplification from multiple levels and compaction. Its performance depends on the full lifecycle, not just the initial `put`.

## Trace the write path

A write enters a memtable, commonly after or alongside a write-ahead log record that supports recovery. When the memtable fills, it becomes immutable and flushes to a sorted table file. New writes continue in another memtable. Background compaction combines overlapping files, discards obsolete versions when safe, and moves data to lower levels. RocksDB describes the memtable, SST file, and log file as its basic building blocks.

This process batches many small updates into sequential writes. Yet every value may be rewritten during later compactions. Sustained throughput is limited by the rate at which background workers can keep up. If the flush or compaction backlog grows, the engine may slow or stop foreground writes to prevent unbounded disk use and read cost.

## Trace the read path

For a point read, inspect the newest memtable, pending immutable memtables, and candidate SST files from newest to oldest. A Bloom filter can reject files that definitely lack the key; an index identifies the block that may contain it. The reader must respect versions and tombstones so an old value does not reappear. A range scan merges ordered iterators across files and filters duplicate or deleted keys, which can become expensive when many files overlap.

The structure can be tuned for different workloads. Larger memtables reduce flush frequency but use more RAM and can increase recovery work. More aggressive compaction reduces file overlap and read amplification but writes more bytes. Larger blocks and compression improve transfer and storage efficiency but make individual lookups read and decompress more data. Benchmark the workload's point-read, scan, and update mix rather than optimizing one operation in isolation.

## Choose a compaction policy

Leveled compaction maintains relatively little overlap in lower levels, often improving reads and space efficiency at the expense of more rewriting. Tiered or universal compaction delays some merging, often lowering immediate write amplification while leaving more files for reads and using more temporary space. FIFO-style retention can be suitable for disposable time-series data but has different deletion semantics. RocksDB exposes several compaction styles because no one policy wins for every workload.

An LSM tree is not a transaction protocol by itself. The storage engine still needs a commit and recovery rule for batches, snapshots for concurrent readers, and a durable manifest for the current file set. Replication, if needed, sits above or alongside those mechanisms. Observe write stalls, pending compaction bytes, level sizes, cache hit rate, and read latency while compaction runs.

## Design review

What is the sustained write rate after compaction reaches steady state? How many files can a read consult? Which compaction policy matches overwrite and scan patterns? What protects acknowledged writes and prevents deleted values from resurfacing?
