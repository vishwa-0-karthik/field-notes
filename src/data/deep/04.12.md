Pagination divides a changing result set into manageable responses. Offset pagination names a position in the current result, while keyset pagination names the last item actually seen. That difference matters when a list is large or new rows arrive between requests. Choose the contract before choosing the SQL: a live feed, a stable export, and a numbered catalog need different behavior.

## See why an offset moves

Imagine posts ordered newest first. Page one returns positions 1 through 20. A new post arrives before the reader requests `OFFSET 20 LIMIT 20`; the old position 20 is now position 21, so it appears again. A deletion can cause a row to be skipped. A unique `ORDER BY` makes each individual query deterministic, but it does not freeze the result across requests. PostgreSQL also notes that skipped offset rows still need to be computed, making deep pages expensive.

Offset is fine for small administrative tables or interfaces where direct page numbers are valuable and moderate churn is acceptable. It is a poor default for an endless feed with millions of rows. Do not promise stable traversal from offset alone.

## Seek after the last key

For a descending feed ordered by creation time and unique ID, return a cursor containing the last row's two values. The next request seeks below that pair:

```sql
SELECT id, created_at, title
FROM posts
WHERE tenant_id = $1
  AND (created_at, id) < ($2, $3)
ORDER BY created_at DESC, id DESC
LIMIT 21;
```

With a page size of 20, the extra row tells the API whether another page exists. A supporting index might begin with `tenant_id`, then `(created_at DESC, id DESC)`. The unique ID breaks timestamp ties; without it, rows sharing the boundary timestamp can be missed or repeated. PostgreSQL's row comparison evaluates the pair lexicographically, matching this ordering when both keys descend. Null sort keys need an explicit policy because ordinary row comparisons involving null can yield unknown.

Keep the cursor opaque to clients, but document its meaning. Encode a version, sort values, and any fixed filter or tenant scope. Validate decoded values and apply authorization on every page. A signature can prevent clients from forging expensive or cross-scope cursors, but it does not replace server-side authorization. A cursor tied to a different filter should be rejected rather than quietly returning surprising rows.

## Define consistency across pages

Keyset pagination avoids shifting offsets and makes indexed deep traversal practical. It does not provide a snapshot by itself. A row inserted with a newer key after page one will be above the cursor and will not appear later in that traversal. A late-arriving row with an older key may appear later. An updated sort key can move a row across the boundary. For an audit export requiring exact coverage, use a consistent snapshot or a bounded high-water mark, then document how updates and deletions are handled.

Reverse navigation needs the inverse predicate and ordering before reversing the returned page for display. Arbitrary jump-to-page is not native to a keyset cursor. If product requirements demand it, consider a separate approximate position index or bounded offset rather than pretending cursors have page numbers. Treat cursor lifetime as part of the API: old cursors may be invalid after sort changes, retention cleanup, or index migrations.

## Design review

Is the list a live feed or a stable report? Does the ordering contain a unique tie-breaker? Which index supports both the filter and seek? What should happen if a cursor is stale, modified, or used with different filters?
