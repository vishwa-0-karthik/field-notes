# Fixed-block chunking and content addressing

Chunking divides a file into smaller units so clients can upload or download only the pieces that changed. In fixed-block chunking, boundaries occur at regular byte offsets. A manifest records the ordered block identifiers and total file properties. The client hashes each block, asks the server which hashes are already present, and uploads only missing blocks. The new file version is a small manifest that references its blocks. This saves bandwidth when edits preserve block alignment, but inserting bytes near the beginning shifts every later boundary and can make most blocks appear changed.

## Block size and transfer behavior

Small blocks improve deduplication for localized edits and make retries cheaper, but they create many hashes, index entries, requests, and manifest references. Large blocks reduce metadata and request overhead, but one small edit can force retransmission of more bytes. Choose a default based on file size distribution, edit patterns, network RTT, and storage economics; a tiered size policy can prevent tiny files from producing oversized metadata. The client can batch existence checks and missing-block uploads to avoid a round trip per block.

Content addressing names an immutable block by a cryptographic digest of its bytes. Equal blocks can be stored once and referenced from many manifests. Verify the digest on receipt, and use a modern collision-resistant hash for identity. A digest detects accidental corruption; it does not authorize the caller to read or reference a block. Authorization still comes from the account and manifest layer. If blocks are encrypted before hashing, deduplication is scoped to identical ciphertext, and deterministic encryption can leak equality; if the service hashes plaintext, it learns content equality. The privacy and deduplication tradeoff must be explicit.

## Publish manifests safely

Upload missing blocks to an immutable namespace first, then commit the version manifest only after every referenced block is present and verified. The metadata transaction makes the new version visible atomically. Readers should see either the old manifest or the complete new one. Keep manifests bounded and validate block count, lengths, order, and total size. A malicious client could otherwise reference the same block many times to create a huge logical file or force pathological reads. The storage service should reject unreferenced blocks from users without quota and ownership checks, even if the digest is valid.

Garbage collection is harder because blocks may be shared across versions and uploads may be in flight. Mark-and-sweep can trace retained manifests and delete unreferenced blocks only after a grace period that exceeds upload and transaction delays. Reference counts can make deletion faster, but concurrent updates, crashes, and retry duplication can corrupt counts unless operations are transactional or reconciled. Keep a background audit that recomputes reachability for a sample or partition.

Measure bytes saved, unique-block ratio, manifest size, lookup and upload round trips, hash verification failures, and orphan retention. Test an insertion at byte zero, an overwrite within one block, duplicate uploads, stale manifests, hash mismatch, and client crash before commit. Fixed boundaries are simple and predictable; use them when edit alignment is acceptable, and compare them against rolling or content-defined chunking for workloads with frequent insertions.

## Design review

What block size balances request overhead and retry cost? Which layer computes and verifies digests? Does encryption permit or prohibit cross-file deduplication? Are manifests bounded and atomically published? Can garbage collection see in-flight uploads and retained versions?
