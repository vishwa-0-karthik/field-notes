A key-value store retrieves a value by a key. A document store also keeps a structured document and can index or query fields inside it. The difference affects how you model relationships, update parts of an object, and answer queries beyond a simple lookup. The same product may use both: durable documents as authority and a key-value cache for hot responses.

## Start with the object boundary

Imagine a support ticket with subject, description, status, and a few assigned labels. Reading the whole ticket by ID is a natural document operation. Comments are trickier: if a ticket can accumulate millions of comments, embedding them all in one document makes the object huge and every update contend on it. Store comments separately, perhaps keyed by ticket ID and creation time, and keep a bounded recent-comment summary on the ticket if that helps the common read.

MongoDB's guidance favors embedding when related data is read and updated together in one atomic operation, and references when related entities grow large, change independently, or are queried on their own. The same questions apply to document modeling generally. “Schemaless” does not mean there is no contract: the application still needs field types, required values, versions, and migration rules.

| Access pattern | Key-value approach | Document approach |
| --- | --- | --- |
| Get ticket by ID | Direct key lookup | Direct document lookup |
| Filter by status and assignee | Secondary index or separate key sets | Indexed document fields |
| Update one nested field | Replace or store subkeys | Partial document update if supported |
| Read large comment history | Many keys and explicit ordering | Separate comment collection preferred |

## Make updates and indexes explicit

A key-value record may be an opaque byte string to the store. That can make point reads simple and fast, but filtering by `status` requires a separate index maintained by the application or store. If the index update and value update are not atomic, a read can see stale or missing results. A document store can maintain secondary indexes on fields, but each index adds write and storage cost, and query behavior still depends on selectivity.

Document boundaries also define atomicity. If a support ticket and its embedded labels change in one document, one write may keep them together. If ticket state and comments live in separate collections or services, a single-document guarantee does not cover both. Identify which invariants must span objects. Do not assume the word “document” implies full transaction semantics across arbitrary records.

## Plan for evolution

A new field can be added to new documents while older ones lack it. Readers need defaults or a migration. A rename can be staged: write both, read new with fallback, backfill, then remove old. Indexing a newly introduced field may require scanning existing data and additional disk. Validate query plans with old and new documents, not just fresh test data.

Choose key-value when the service truly knows the key and treats the value as a unit, such as a session or cached profile. Choose document capabilities when the product needs structured field queries and bounded aggregate objects. If both are available in one database, model from the workload rather than the product category.

## Design review

What is the maximum document or value size? Which fields must be queried without the primary key? Which related records change independently? Can the store enforce the transaction that the business rule needs?
