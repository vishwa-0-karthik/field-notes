Relational database scaling is a sequence of workload-specific decisions. A database can hit limits in CPU, memory, disk I/O, storage size, connection count, write contention, or recovery time. “Add replicas” helps some read workloads but does not make one hot row or a single primary's write path scale indefinitely.

## Locate the limiting work

Suppose an order database shows rising p99 latency. First separate query classes and inspect plans, indexes, lock waits, buffer hit rate, disk throughput, and connection-pool wait. An unindexed query can consume far more resources than the rest of the traffic; fixing it may buy more capacity than a new server. A large number of idle connections can also impose memory overhead without increasing useful throughput. Right-size pools and keep transactions short.

Vertical scaling gives more CPU, memory, or I/O to one database and may be the simplest next step. It has a ceiling and may require a failover or restart. Read replicas can serve queries that tolerate replication lag, such as a browsing page, while the primary continues accepting writes. A read-after-write path may need to stay on the primary or use a lag-aware routing policy. PostgreSQL's hot standby supports read-only queries; the application still decides which reads may be stale.

| Pressure | Candidate response | New tradeoff |
| --- | --- | --- |
| Expensive query | Rewrite/index/materialized view | Maintenance and freshness |
| CPU or memory limit | Larger instance | Larger failure domain and cost |
| Read-heavy traffic | Read replicas | Lag and routing complexity |
| Old time-series data | Partition by time | Partition management and cross-range queries |
| Write throughput by key | Shard by stable key | Cross-shard queries and migrations |

## Use partitioning for a clear access pattern

Table partitioning splits a logical table into physical pieces. Time partitions can make retention cheap—drop an old partition rather than delete millions of rows—and let the planner prune irrelevant partitions for date-bounded queries. But every query must use the partition key effectively to benefit. Too many tiny partitions increase metadata and planning overhead. A partitioned table on one machine also does not add machine-level write capacity by itself.

Sharding distributes data across independent database nodes. Choose a key aligned with common transactions, such as `tenant_id`, so most operations stay on one shard. Cross-shard joins, global uniqueness, rebalancing, and hot tenants become explicit application concerns. Use logical shards or a routing map if physical placement may change. A hash of the key may balance ordinary tenants but cannot solve a single tenant that dominates traffic.

## Keep reliability in the scaling plan

Replicas need monitored lag and tested promotion. A failover can change the last acknowledged write visible on the new primary depending on replication mode. Backups and restore drills remain necessary even with replicas because a bad delete can replicate too. As the dataset grows, restore time may become the real scaling limit before query throughput does. Estimate recovery time and data-loss bounds alongside QPS.

Scale in measured steps: remove waste, tune the hot paths, add suitable capacity, then partition where the workload proves it necessary. Each step should have a threshold and a rollback plan. “We may have millions of users” is not enough to justify distributed writes before query and traffic data exist.

## Design review

Which resource is saturated first? Which operations can read stale replicas? Does the proposed partition key keep the important transaction local? How long will backup restore and failover take at the projected data size?
