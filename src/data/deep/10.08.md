A count-min sketch estimates how often each key appears in a stream while using bounded memory. It stores several hash-indexed counter rows. For each event, it increments one cell in each row; to query a key, it takes the minimum of those cells. Hash collisions can add counts from other keys, so the estimate is normally at least the true frequency for a stream of nonnegative updates. The sketch is useful for frequent keys, not for an exact charge or a precise count of rare events.

## Size the error against total traffic

The width controls collision error and the depth controls the probability that all rows collide badly. Redis exposes initialization by error tolerance and probability, and its documentation notes that low counts beneath the error threshold can be mostly noise. A promise of “0.1% error” is relative to the total stream count, not necessarily 0.1% of each item's count. If there are a billion events, even a small fraction of total traffic can overwhelm a key with only a few true occurrences.

Use a stable, independent set of hash functions or seeds and keep them with the sketch metadata. A query made with a different hash configuration reads unrelated cells. Normalize keys consistently; `Item42` and `item42` count separately unless deliberately canonicalized. Define whether increments may be negative. The textbook nonnegative guarantee does not automatically hold when deletions or corrections are applied through negative updates, even if a particular implementation accepts them.

## Combine shards and windows safely

Workers can maintain compatible sketches for disjoint event partitions and merge corresponding cells. This supports high ingestion rate without a single hot key. Do not merge the same partition snapshot twice if the merge adds counters. Store partition, input range, sketch version, and window so a reducer can detect duplicates. Keep separate sketches for time buckets; a cumulative sketch cannot answer “last ten minutes” unless it has a supported subtraction method or the system retains narrower buckets.

For top products, the sketch can estimate candidate frequencies, but it cannot enumerate every key it has seen. Pair it with a bounded candidate set or a frequent-items algorithm. An exact counter for the top few keys can supplement the sketch and provide a quality check. Querying all possible product IDs to find the maximum defeats the memory advantage if the key universe is large.

## Validate the use case

Compare estimates with exact counts on sampled keys across low, medium, and high frequencies. Monitor total updates, collision-driven overcount, memory, merge completeness, and key distribution changes. A highly skewed hot key can contaminate cells for many rare keys. If an operation needs exact quotas, inventory, or billing, maintain authoritative per-key records and use the sketch only for detection or prioritization.

Count-min sketch is attractive because update and query work are bounded and independent of the number of distinct keys. That benefit comes with a one-sided approximation under its standard assumptions. State those assumptions and expose the estimate as an estimate, especially when a threshold decision has consequences.

## Design review

What is the expected total stream volume and acceptable absolute error for rare keys? Are updates nonnegative? How are hash seeds, partitions, and windows versioned? Can a duplicate merge inflate counts? Does the product need to enumerate heavy hitters or only query known keys?
