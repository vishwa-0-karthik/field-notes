Bucketed aggregation groups events into time intervals before computing counts, sums, or sketches. It makes dashboards and retention manageable: a query for yesterday's hourly traffic reads 24 buckets rather than every request. The hard choices are which clock defines the bucket, how late data changes a result, and whether a displayed aggregate is provisional or final.

## Choose event time or processing time

Event time is when the action occurred. Processing time is when the pipeline handled it. A phone can record a purchase at 10:02 and deliver it at 10:15 after reconnecting. Event-time aggregation puts it in the 10:00 bucket; processing-time aggregation puts it in the 10:15 bucket. For business reporting, event time often matches the question, but client timestamps must be validated. For infrastructure alerting, processing time may be more appropriate. Apache Beam distinguishes these clocks and uses watermarks as estimates of event-time completeness.

Define interval boundaries precisely: `[10:00, 10:05)` includes the start but excludes the end. Use UTC internally and convert to the report's time zone at the edge. A “day” in a local time zone can be 23 or 25 hours around daylight-saving changes. Never derive daily totals by assuming every day has 24 fixed UTC hours when the product promises a local calendar day.

## Decide when to emit and revise

A tumbling window emits disjoint buckets; a hopping window overlaps, such as a 15-minute window advancing every minute. A session window groups events separated by no more than a gap and can merge when a late event bridges two sessions. Kafka Streams documents these window types and state stores. A processing engine can emit an early provisional count, an on-time count when the watermark passes, and late corrections for an allowed period. State whether each emission replaces the previous value or is a delta; consumers that add a replacement as a delta will overcount.

Set allowed lateness from observed delivery delay and business needs. If events arrive after the deadline, quarantine them, revise a historical report through a separate path, or drop them with a measured count. No watermark is a proof that no earlier event will ever arrive. Keeping windows open forever grows state, so pair lateness with retention and a reconciliation policy.

## Scale hot keys and query rollups

Partition aggregates by dimension and time. A single global counter can be hot; partial aggregates can be combined after a short interval. Use minute buckets to construct hours and days only when the requested dimensions and semantics are compatible. Distinct users cannot be computed by summing minute distinct counts because a user may appear in several minutes; merge a distinct sketch or revisit raw IDs. Similarly, averaging minute p95 values does not yield an hourly p95.

Monitor watermark lag, late-event rate, state-store size, emitted revisions, bucket drift against raw events, and query cost. Test out-of-order events, duplicates, clock skew, and replay. A dashboard should label provisional data when later corrections are possible, especially if users make decisions from near-real-time numbers.

## Design review

Which clock and time zone define the bucket? Are windows disjoint or overlapping? What happens to late events? Does an output replace or add to prior output? Can larger intervals be derived correctly from smaller ones for this metric?
