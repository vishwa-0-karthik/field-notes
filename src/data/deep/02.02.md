Service-to-service communication is a dependency decision. A synchronous call asks another service for an answer before the current operation can finish. An asynchronous message records work or a fact for later processing. The choice affects latency, availability, data freshness, and how failures are repaired.

## Use synchronous calls for immediate decisions

Suppose checkout must know the current shipping price before the user confirms payment. A direct request to the pricing service is appropriate if a stale price is unacceptable. The caller needs a deadline, authentication, a bounded response size, and a policy for timeout or error. If the caller's own response target is 500 ms, it cannot allow three downstream calls each to wait 500 ms. Allocate a budget across the whole critical path.

Every synchronous edge links availability. If checkout requires inventory, pricing, payment, and fraud services to all respond, a failure of any required dependency can stop checkout. Parallel calls may reduce latency, but they do not remove the failure dependency. Keep the required path small, use sensible fallbacks only where product rules permit them, and measure the end-to-end success rate.

## Use messages for work that can finish later

After a confirmed order, the system may publish an `OrderPlaced` event for email, analytics, and warehouse processing. Checkout should not wait for an email provider if email is not part of the commit promise. Messaging decouples timing, but it introduces delivery semantics: consumers can see duplicates, messages may arrive late or out of order, and a backlog can grow when consumers are down.

| Pattern | Caller waits? | Main benefit | Main obligation |
| --- | --- | --- | --- |
| Request/response | Yes | Immediate answer | Timeouts and dependency failures |
| Command queue | No | Buffer work and retry | Job state and deduplication |
| Published event | No | Several independent reactions | Schema evolution and replay safety |

Distinguish a **command** from an **event**. “SendReceipt” asks a named worker to do something. “OrderPlaced” states a fact that occurred and may have several subscribers. An event should not depend on an undisclosed caller expectation that one particular consumer will finish before checkout returns. If the outcome must be observed, expose a state resource or a callback contract.

## Preserve the handoff

A common failure gap occurs when a service commits data and then publishes a message. If it crashes between those steps, the database says “order placed” while no consumer hears about it. A transactional outbox can store the event in the same database transaction as the order, then a separate publisher sends it. The publisher may send twice after a crash, so consumers still need idempotency. The outbox closes the lost-message gap; it does not grant exactly-once side effects across all systems.

Use correlation IDs across calls and messages. Log the message ID, entity ID, attempt count, and age. Monitor queue depth and oldest-message age, not only consumer CPU. A healthy producer can create a growing backlog that delays user-visible consequences for hours. Set a retry policy with exponential backoff, a dead-letter or quarantine path, and a human repair procedure for failures that will not succeed automatically.

Microsoft's architecture guidance separates synchronous request/response from asynchronous messaging and notes that asynchronous I/O in an HTTP client does not make the *business protocol* asynchronous: the caller still waits for the answer. This distinction prevents an implementation detail from masquerading as a resilience improvement.

## Design review

Which downstream answers are required before success can be returned? Which work can happen later? If a message is duplicated or never published after a process crash, what recovers the invariant? Can the caller learn the eventual outcome?
