The memtable, write-ahead log (WAL), and SSTable form an LSM engine's write pipeline. The memtable serves recent data from memory, the WAL provides a recovery record, and the SSTable stores a sorted, immutable run on disk. Their transitions determine when a write can be acknowledged, how long restart takes, and when foreground writes stall.

## Acknowledge a new write deliberately

When a client puts a key, the engine records the operation in the WAL and inserts it into the mutable memtable. A read checks that memtable before older disk files. If the process crashes, replay the WAL to reconstruct writes that had not yet been flushed to an SSTable. RocksDB's WAL documentation describes this two-place update. The order and synchronization policy must ensure an acknowledged value does not exist only in volatile memory when the API promises stronger durability.

There are several possible acknowledgements. Returning after copying to an OS buffer can survive a process crash but may lose recent data after a machine crash. Waiting for a sync to stable storage strengthens the promise and adds latency. Group commit can share one sync among concurrent writes. Disabling the WAL may be appropriate for a bulk load that can be repeated, but it changes recovery behavior and should be explicit.

## Freeze and flush a memtable

When the active memtable reaches a size threshold, mark it immutable and create a new mutable one. A background worker writes the immutable table in key order to an SSTable. The SSTable can include data blocks, an index, filters, and a footer describing where to find them. Once the new file is durable and its addition is recorded in the manifest, WAL records covered by that flush can be retired according to the engine's recovery rules.

This pipeline allows writes to continue while a flush runs, but memory is finite. If several immutable memtables wait because the disk or compaction is slow, the engine must slow or stop new writes. Increasing the number of write buffers only postpones the bottleneck and consumes more RAM. Monitor immutable-memtable count, flush duration, WAL size, and stall time.

## Keep read order and recovery aligned

A key may have versions in the active memtable, an immutable memtable, and several SSTables. The reader must choose the newest visible version, including a tombstone. A snapshot may intentionally read an older version, so compaction cannot discard every overwritten value immediately. The manifest identifies which SSTables form the current database view, while WAL replay fills the gap since the latest durable flush.

On recovery, validate WAL framing and handle a partial final record. Replaying the same logical batch twice must not create an incorrect state. Corruption in the middle of a log is different from a torn tail and may require operator action. Test crashes before WAL sync, after sync, during SSTable write, and after manifest publication. A production storage engine's behavior is defined by these boundary cases, not just by its steady-state data structures.

## Design review

At what exact point does a put return success? Which WAL bytes can be deleted after a flush? What happens when immutable memtables accumulate? How does a reader pick the right version across memory and disk?
