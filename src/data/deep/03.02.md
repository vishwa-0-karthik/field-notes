A relational database can serve a key-value API effectively when the workload is mainly point reads, conditional writes, and bounded scans. The first design is often one table with a primary key, value, version, and expiration field. The hard part is the contract around concurrency, size, TTL, and durability, not writing `SELECT ... WHERE key = ?`.

## Define the key-value contract

Suppose clients call `put(namespace, key, value)`, `get(namespace, key)`, and `delete(namespace, key)`. Is a key unique globally or only within a namespace? Does `put` overwrite unconditionally, create only if absent, or compare a version? What is the maximum value size? Does a missing key differ from an expired key? Are range scans or prefix queries required? These answers determine the primary key and indexes.

A simple SQL shape is `PRIMARY KEY (namespace, key)` with `value BYTEA`, `version BIGINT`, and `expires_at TIMESTAMPTZ`. A point read uses the composite key. If clients need optimistic concurrency, an update can include `WHERE version = expected_version` and increment the version; zero updated rows means conflict or absence, which may require a follow-up check. A create-if-absent operation can use a uniqueness constraint and `INSERT ... ON CONFLICT` behavior.

| Operation | SQL-level idea | Edge case |
| --- | --- | --- |
| Get | Primary-key lookup | Expired row still physically present |
| Put | Insert/upsert | Concurrent overwrite semantics |
| Compare-and-set | Conditional version update | Conflict versus missing key |
| Delete | Delete or tombstone | Retry and recreation race |
| Expire | Filter on `expires_at` plus cleanup | Cleanup lag and clock source |

## Treat TTL as two separate behaviors

Logical expiration means a `get` does not return a row after its deadline. Physical cleanup removes old rows to reclaim space. The cleanup job can lag without violating logical expiration if reads filter expired rows. But large numbers of expired rows still cost storage and index maintenance, so monitor cleanup lag and batch deletes. Use the database's time consistently for writes and reads if client clocks cannot be trusted.

If keys may be recreated, a delayed delete or stale worker must not remove the new value. Conditional deletion by version or expiration timestamp protects against that race. The same issue appears in cache invalidation and lease expiry: identity and version matter more than a bare key.

## Set realistic limits

SQL offers transactions and mature durability, but huge values are a poor fit for the hot row path. Put large objects in object storage and keep a pointer and metadata in SQL if necessary. Point lookups scale well with a primary-key index until working set, I/O, or write throughput becomes limiting. A hot key can still serialize many conditional writes. More application replicas will not remove contention on the same row.

For a small to moderate service, SQL may be operationally simpler than adding a dedicated distributed key-value store. If the workload later needs extremely high write rates across many independent keys, partition by a stable key and plan data movement. If it needs ordered range scans, random hash sharding can make those scans expensive. Let the required API shape guide distribution.

## Design review

Does `put` mean replace, create, or compare-and-set? Can clients safely retry after a timeout? What happens when a key expires but cleanup has not run? How do you prevent an old cleanup task from deleting a recreated key?
