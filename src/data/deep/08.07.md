A DAG workflow describes a finite set of tasks and dependency edges: a task becomes runnable only when its required predecessors have reached the appropriate state. It is useful when work has multiple steps, parallel branches, retries, and a need to inspect progress. A DAG is not just a drawing of service calls. The orchestration system must persist each run's state so it can recover when a scheduler or worker restarts.

## Model runs separately from the definition

The workflow definition says that `extract` precedes `validate`, while `validate` precedes both `index` and `notify`. A workflow run is one execution of that definition for a particular input, version, and trigger time. Give the run a stable ID and store each task instance's state, attempt number, timestamps, and output reference. Validate definitions for cycles before deployment: a cycle has no first runnable task. Keep task outputs in durable storage and pass references between tasks when payloads are large.

Versioning matters for long-running workflows. If an operator deploys a new definition while yesterday's run is paused, which graph should resume? Pin the run to the definition version it started with or implement an explicit migration. Otherwise a new dependency can leave old runs stranded or make a previously completed step appear incomplete.

## Advance the graph after durable completion

The scheduler finds task instances whose predecessors satisfy the trigger rule, then dispatches them to workers. On success, it persists the result before unlocking descendants. On failure, it applies a retry policy or marks the task terminal. Dependencies can require all upstream tasks, any one, or a more specific branch condition. Airflow documents these task relationships and trigger rules; the choice affects whether a branch's skipped task blocks the join.

A worker can complete an external effect and crash before recording success. The orchestrator then retries, so task code must be idempotent or use an idempotency key. A workflow state database cannot make a remote payment atomic. For irreversible steps, record the external operation identity and query its status on recovery before trying again. Compensation is a business action, such as issuing a refund after a later shipping failure, and is not a database rollback.

## Bound parallelism and failure scope

Parallel branches reduce latency but can overload a shared dependency. Set global, per-workflow, and per-resource concurrency limits. A failed step should stop or skip only the appropriate descendants; unrelated branches may continue if their results are useful. Define timeouts for execution and for waiting on an external signal. A task that waits for a callback should not occupy a worker process for days if the orchestrator can persist a waiting state and resume on the event.

Make retries finite and use backoff with jitter. A permanent schema error should move to a human-visible failed state, while a temporary network error may recover. Preserve failure reason, input reference, task logs, and a controlled retry action. Monitor run completion latency, queued task age, stuck running attempts, retry counts, and workflow versions with unfinished runs. A healthy scheduler heartbeat is insufficient if no run reaches completion.

## Design review

What uniquely identifies a run and each side effect? Which definition version does an in-flight run use? What do skipped and failed branches do to joins? Can a worker repeat safely after a crash? Which limits keep parallel tasks from overwhelming their dependencies?
