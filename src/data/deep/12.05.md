A geofence is a geographic region associated with an action: notify when a device enters a campus, restrict a delivery zone, or alert when equipment leaves a service area. The business question is often point-in-polygon, but the system must also handle location noise, boundary policy, changing polygons, and repeated GPS updates. A correct geometry test by itself does not determine when a user should receive one notification.

## Store polygons with explicit semantics

Represent each zone as a polygon or multipolygon with a coordinate reference system, version, and active time range. Validate rings, self-intersections, holes, and orientation at ingestion. Decide whether a point on the boundary is inside. PostGIS `ST_Contains` excludes a point lying only on a polygon boundary, while `ST_Covers` includes boundary points. Either may fit, but different services must not silently use different rules.

For a single point check, a spatial database can use an index-aware predicate such as `ST_Covers(zone.geom, point)`. For many devices and a few zones, index zones and query candidates. For many zones and a device stream, use a spatial index or cell covering to find candidate zones, then perform exact point-in-polygon on each candidate. Bounding boxes and geohashes only prune; they do not prove containment.

## Convert noisy fixes into transitions

GPS points jitter around a boundary. If every fix triggers a notification, a user parked near the edge receives repeated enter and exit messages. Keep per-device, per-zone state and require a transition rule such as two consecutive fixes inside, a minimum dwell time, or a confidence radius contained within the zone. Use hysteresis: an entry threshold slightly inside and an exit threshold slightly outside can prevent rapid toggling. Do not apply these rules when a hard legal boundary requires immediate precise evaluation; clarify the accuracy requirement.

Assign each fix an observation time and source sequence. Ignore older fixes and expire device state after a chosen silence period. A location estimate has an uncertainty radius; if the uncertainty overlaps the boundary, report an indeterminate state or wait for a better fix rather than claiming precise entry. The product can distinguish “near the zone” from “inside.”

## Make notifications idempotent and auditable

Create a transition ID from device, zone, transition type, and state version. Queue notification work after state is durably updated. A retry should not send another alert for the same transition. When a zone changes, decide whether to re-evaluate every current device or apply the new boundary only to future fixes. Version zone geometry so a transition can be explained with the polygon that was active at the time.

Measure candidate zones per fix, geometry-test latency, GPS fix age, boundary uncertainty, duplicate transition rate, and notification delay. Test holes, multipolygons, boundary points, coordinate order, and GPS jitter. Keep location retention and access limited to the geofence purpose; a zone detector should not become an indefinite movement history by accident.

## Design review

Does the boundary count as inside? How are malformed polygons rejected? Which candidate index finds zones efficiently? What rule prevents GPS jitter from generating repeated transitions? Can a queued alert be explained and deduplicated?
