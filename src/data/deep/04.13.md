A Bloom filter is a compact test for possible membership. It can say “definitely absent” or “possibly present” when its construction and updates are correct. The second answer is deliberately uncertain: some absent keys are false positives. This makes Bloom filters useful before an expensive exact lookup, but unsuitable as the only source of truth for a decision that requires proof of presence.

## Build the membership sketch

Start with an array of `m` zero bits and choose `k` hash positions for each key. Insertion sets those positions to one. A lookup returns absent if any position is zero; otherwise it returns possibly present. One key can set bits later reused by other keys. As the filter fills, more absent keys happen to find all their positions set, so false positives rise. An intact, correctly updated filter has no false negatives for inserted keys because insertion only sets bits.

The usual approximate false-positive probability after `n` insertions is `(1 - exp(-kn/m))^k`. This is a planning model, not a service-level guarantee under every workload or hash implementation. Reserve enough bits for expected cardinality and choose the hash count for the target rate. Estimate growth over the filter's lifetime, including retries and duplicate insertions. If the dataset exceeds planned capacity, measure the actual rate and rebuild or scale the filter rather than assuming its original sizing still applies.

## Put it in front of an exact store

Suppose a service checks whether an object key exists in a remote database. A local Bloom filter can reject most random misses without a network call. A “possibly present” response still goes to the database. The benefit depends on the miss fraction, filter size, false-positive rate, and cost of the exact lookup. If almost every query is a hit, the filter adds memory and CPU while saving little. If the filter is on a separate network service, that extra hop may erase the gain.

The filter's update path is the difficult part. If a write commits to the database but the filter misses the insertion, the filter can incorrectly reject a real key. Build it from a trusted snapshot and replay writes from a durable change stream, or fail open to the exact store while freshness is uncertain. Version each filter build and atomically replace it only after catch-up. A negative filter result should never deny a user access to data unless the system can prove the filter is current and the decision tolerates its failure modes.

## Handle deletion and lifecycle

Clearing an ordinary Bloom-filter bit on deletion is unsafe: another key may rely on that bit and become a false negative. Counting Bloom filters store small counters so deletions can decrement the positions, but counters add space and require careful handling of duplicates and overflow. Simpler systems leave bits set and periodically rebuild; deleted keys then remain possible false positives until the rebuild.

Place the filter near the workload that benefits from it and decide what happens on process restart. A stale or unavailable filter should usually cause extra exact lookups, not missing data. Monitor filter fill ratio, estimated false-positive rate, rebuild lag, and exact-store requests avoided. Test the negative path against known inserted keys after recovery and replays.

## Design review

What fraction of lookups are absent? Can the filter be updated after every committed write? What is the safe fallback when freshness is unknown? How are deletions, capacity growth, and rebuilds handled?
