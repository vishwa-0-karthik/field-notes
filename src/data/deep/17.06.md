# Design: a photo-sharing interview

Design a photo-sharing service by following one user action end to end: upload an image, publish it to followers, and let those followers scroll a feed. Start with requirements and scale assumptions rather than choosing databases first. Assume users can follow one another, publish photos with captions, view a ranked or chronological feed, like and comment, and upload from unreliable mobile networks. Separate large media bytes from relational social metadata.

## Core model and upload

The core entities are user, follow edge, post, media asset, like, comment, and feed entry. A post references an immutable media asset and has visibility, creation time, and lifecycle state. Upload begins with an authenticated intent and a generated private object key. The client sends bytes directly to object storage with a scoped short-lived URL, using multipart upload for large or resumable transfers. A worker validates type and dimensions, strips sensitive metadata, moderates content, and creates thumbnail and display renditions. Publish the post only after its media package is ready or clearly display a processing state.

Media delivery goes through a CDN with versioned rendition paths and long cache lifetimes. The API returns metadata and URLs; it should not proxy every image byte. Store follow edges and post metadata in a durable database. Apply idempotency to post creation so a lost mobile response does not create duplicate posts. Likes need an idempotent unique key on user and post; counters can be asynchronously aggregated if exact counts are not required on every read.

## Feed strategies

For a chronological feed, fanout-on-write places a new post ID into followers' inboxes, making reads fast but amplifying writes for a very popular account. Fanout-on-read fetches recent posts from followed users when the viewer opens the feed, reducing write work while increasing read fanout. A hybrid can precompute ordinary accounts and merge celebrity posts at read time. Build feed entries asynchronously from a durable outbox; queue retries must be idempotent. Keep the canonical post store authoritative and filter deleted, blocked, or private posts at read time so stale feed references do not leak content.

Use cursor pagination with a stable timestamp-plus-ID tie-breaker. Ranking may combine freshness, relationship, and engagement, but a chronological fallback is valuable when the ranking feature store is unavailable. Log impressions separately from clicks to improve ranking evaluation. Follow changes and privacy updates need propagation to caches and feed entries; authorization is still checked on retrieval.

## Scale and failure modes

Partition posts by user or time, and follow edges by follower or followee depending on read patterns. Object storage handles bytes; metadata sharding handles post lookups; a queue handles fanout and derived counters. Avoid synchronous multi-service fanout during publish. Monitor upload-to-publish time, feed latency, image CDN hit rate, fanout lag, duplicate entries, moderation backlog, and hot accounts. Test upload retry, missing rendition, viral post, follow/unfollow race, deletion during pagination, and object-store outage. Make visibility rules and account privacy a first-class part of every feed query.

## Design review

What is canonical for media readiness and post visibility? Which users use write fanout versus read fanout? How do retries avoid duplicate posts, likes, and feed entries? Can a stale feed reference bypass privacy or deletion? What is the useful fallback if ranking is down?
