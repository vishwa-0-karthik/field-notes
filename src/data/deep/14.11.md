# Rate limiter placement and keys

A rate limiter decides whether to admit work based on recent usage. The hard architectural questions are where that decision is enforced, which identity the quota follows, and what happens when the limiter state is unavailable. A gateway is a good place to reject obvious excess traffic early, but it may not know the true resource cost or authenticated tenant for every operation. The service that owns an expensive resource should enforce a final limit as well.

## Choose keys that match the policy

An IP-based key can limit anonymous traffic and blunt broad floods, but many legitimate users may share a corporate or mobile carrier address. Account IDs or API keys provide a more product-aligned quota after authentication, but attackers can create accounts or rotate keys. Tenant IDs protect each customer's allocation, while global service budgets protect total capacity. Endpoint or operation keys let expensive actions have stricter limits than cheap reads. A composite decision often checks several dimensions: edge IP burst, authenticated user quota, tenant concurrency, and global dependency budget.

Do not accept the rate-limit identity from an untrusted header. The gateway should remove externally supplied identity headers and insert verified context. Normalize keys consistently across services. Hash or otherwise protect identifiers in limiter telemetry if key disclosure creates privacy risk. Keep the key space bounded; raw URL paths, random tokens, or arbitrary query parameters can create unbounded limiter state. Group endpoints into stable operation classes.

## Place checks along the cost path

At the edge, reject excessive requests before authentication work and application routing. After authentication, enforce account, plan, and tenant quotas. At the service or worker pool, enforce concurrency, queue admission, and expensive-operation budgets. A per-process limiter is fast but each instance has an independent view, so traffic can multiply its effective limit across replicas. A centralized store provides a shared counter but adds network latency and can become a dependency. Local token buckets can absorb bursts while a global limiter enforces a longer-term quota; this hybrid must specify how much overshoot is acceptable.

Rate limits are not the same as concurrency limits. A request rate can stay within quota while slow requests accumulate and exhaust workers. Bound in-flight work with semaphores or queue limits and set deadlines. A queue can smooth bursts but does not remove overload; cap its depth and age, and reject or defer work with an explicit user contract. Return `429` or a domain-specific quota response with retry guidance when the client can safely try again. For service protection, shedding optional work may be preferable to delaying every request.

## Failure and policy behavior

If the shared limiter is unavailable, choose fail-open or fail-closed by operation. A low-risk cached read may allow a small local fallback budget; a costly payment or authentication attempt may fail closed. Alert on limiter errors and fallback activation. Make counter updates atomic so concurrent requests cannot all observe capacity and overshoot unpredictably. Policies should be versioned and distributed consistently; a quota change can cause a sudden client-visible shift.

Track allowed and denied counts by operation and plan, limiter latency, store errors, overshoot, cardinality, and local fallback. Test NAT users, account rotation, autoscaling, clock skew, a limiter outage, hot tenant keys, and a sudden policy reduction. A limit is only useful if the enforcement layer can identify the caller reliably and protect the actual resource at risk.

## Design review

Which limit belongs at the edge, authenticated service, and worker pool? Can a caller spoof the key? Does each instance multiply the allowed rate? What is the fail-open budget? How are concurrency and backlog constrained separately from requests per second?
