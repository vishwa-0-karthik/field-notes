“NoSQL” is a broad label for data stores with different models and tradeoffs. It is not a single alternative to relational databases. The useful question is which operations must be fast and correct: point lookups, document retrieval, ordered scans, relationship traversal, or large analytical aggregation. Choose the data model and distribution strategy from those access patterns.

## Begin with queries and invariants

Suppose a commerce system stores orders. It needs to create an order with line items, list recent orders for one customer, update fulfillment state, and produce finance reports. A relational database may handle the core transaction well because constraints and joins express important invariants. A document store could keep one order and its line items together if they are usually read and changed as one unit. A key-value store could serve a read-through copy by order ID, but it would not by itself answer a flexible finance report.

Write the required operations before evaluating products. Include key cardinality, item size, query predicates, sorting, update frequency, transactional scope, consistency target, and retention. DynamoDB's modeling guidance explicitly begins from the questions the application must answer. The model can be excellent for known key-based paths while making an ad hoc query unexpectedly expensive.

| Need | Candidate model | Design question |
| --- | --- | --- |
| One object by exact key | Key-value | How is key distributed and expired? |
| Related fields read together | Document | Does the document grow without bound? |
| Rows by partition and order | Wide-column | Is the partition key known in every query? |
| Large aggregates over few columns | Columnar analytic | How fresh must results be? |
| Multi-hop relationships | Graph | How deep and selective are traversals? |

## Count the lost conveniences

A specialized store may improve one access pattern while narrowing others. Many key-value designs do not offer arbitrary joins or full-table transactions. A document model may duplicate frequently changing data. A wide-column table often fixes query order in the primary key. A graph store can make traversals natural but may be less attractive for a simple high-volume point lookup. These are model constraints, not defects; they are useful when the workload matches.

Operational fit matters too. A second database requires expertise in backups, restore, access control, monitoring, upgrades, and data movement. If a new store is a derived read model, define the authoritative source and a rebuild procedure. If it is the system of record, test its failure, consistency, and transaction behavior against the product's invariants before migration.

## Compare a concrete alternative

For the order example, start with one relational schema and benchmark the known reads and writes. If customer order history becomes a hot path, a covering index or materialized read view may suffice. If the product later needs a flexible product catalog with deeply variable attributes, a document model may be worth evaluating. If daily analytics scans billions of events, a columnar warehouse can be added as a derived store without moving checkout state.

The decision should name the workload and measured limit: “This query needs a 200 ms p95 at 10,000 reads/s and cannot meet it under the current schema and indexing,” not “NoSQL scales better.” A relational database can partition and replicate; a NoSQL database can still have hot keys and costly cross-partition work.

## Design review

List the five most important reads and writes. Which require transactions or flexible queries? Which key drives placement? What is the authority if two stores disagree? What new operational work does the chosen store add?
