Cache concurrency appears when several readers miss the same key, or a write races with a refill. The cache can remain internally consistent while still serving an old business value. Design concurrency around the authoritative version and the exact order in which a value may enter the cache.

## Collapse simultaneous misses

Suppose a popular key expires and 500 requests arrive while its database query takes 100 milliseconds. Without coordination, all 500 may issue the same query. Single-flight loading lets one request fetch and the others wait briefly for the result. Within one process, a map of in-flight promises can be enough. Across processes, a short-lived lock or lease can coordinate, but the lock itself adds failure modes. The Redis cache-aside examples use a per-key token and atomic acquisition; release checks the token so an old owner cannot delete a newer owner's lock.

Waiters need a deadline and a fallback. A loader can crash, time out, or finish after its lease expires. After waiting, re-read the cache; if it is still empty, allow a bounded number of source reads or return a controlled error. Do not let all waiting requests spin forever. Limit concurrent refills globally as well as per key, since thousands of different cold keys can overload the database even with perfect single-flight for each one.

## Prevent stale refill after a write

Consider this order: reader A misses; A begins a slow database read and sees version 4; writer B commits version 5 and deletes the cache key; A then stores version 4 in the cache. Invalidation happened correctly, yet the cache now contains an old value until expiry. A common defense is to store a version or update timestamp with the value and conditionally replace only if the incoming version is at least the cached version. This still needs a way to know that version 5 exists after its invalidation; a per-key generation token or write-through update can supply it.

For strict read-after-write behavior, the writer can bypass the cache for its own subsequent reads, or the service can require a minimum version from the caller. If stale reads are acceptable, a short TTL and invalidation retry may be the simpler choice. State the tolerance explicitly instead of claiming that cache-aside is strongly consistent.

## Use locks only for the job they solve

A cache-fill lock protects the source from duplicate work. It is not automatically a safe distributed mutex for irreversible side effects. Time-limited locks can expire while a worker is paused; a second worker may acquire the same lock. If the protected resource must reject an old worker, use a monotonically increasing fencing token checked at the resource, or keep the operation in a transactional authority. Redis documents lock algorithms and their assumptions; choose the guarantee the operation actually needs.

Avoid locking the whole cache for unrelated keys. Use a per-key scope and short timeouts, and test the abandoned-lock path. Observe suppressed duplicate loads, lock wait time, source load, failed refills, and the age/version of values served. These metrics reveal whether a concurrency mechanism improves latency or merely shifts contention.

## Design review

How many readers can miss one key together? What if the loader dies or finishes after its lease? Can an old refill overwrite a newer write? Is the lock protecting refill cost or a correctness-critical side effect?
