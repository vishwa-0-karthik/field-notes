HTTP is a protocol with methods, headers, status codes, and representation semantics. REST is an architectural style often expressed over HTTP. gRPC is an RPC framework that describes services and messages in an interface definition and commonly uses Protocol Buffers. The choice should follow client needs, interoperability, streaming requirements, and operational constraints rather than a blanket performance claim.

## Understand the layers

An HTTP API can use `GET /orders/42`, `POST /orders`, and standard status codes. It need not be fully RESTful to be useful. A REST-oriented design treats resources and representations as central, uses method semantics consistently, and takes advantage of caching where valid. RFC 9110 defines, among other things, that GET is safe and that PUT and DELETE are idempotent by method semantics. Application side effects and retry safety still need care: a `POST` that creates an order usually needs an explicit idempotency strategy.

A gRPC service begins with a `.proto` definition of methods and messages. Tooling generates client and server code. A unary RPC resembles one request and one response; gRPC also supports client, server, and bidirectional streams. Typed generated clients can be attractive for internal services with controlled language stacks. Browser clients and public integrators may find JSON over HTTP easier to inspect and use, depending on tooling and gateway support.

| Need | HTTP/JSON often fits | gRPC often fits |
| --- | --- | --- |
| Public API across many clients | Familiar tooling and curl | Requires generated client or gateway |
| Human inspection | Plain text JSON | Binary payload tooling |
| Streaming messages | Possible with SSE/WebSocket/chunking | Built-in stream method types |
| Strong typed internal contract | OpenAPI/schema tooling | `.proto` and generated stubs |

## Compare complete systems, not wire formats alone

Binary encoding can reduce payload size and parsing cost for some workloads, but end-to-end latency may be dominated by database queries, network distance, or fanout. Benchmark representative payloads and concurrency at the target p99 before switching protocols for speed. HTTP/2 multiplexing, connection reuse, compression, and load-balancer behavior can matter as much as serialization. gRPC usually runs over HTTP/2, so it is not simply an alternative transport to HTTP.

Error semantics need a deliberate mapping. HTTP uses status codes and bodies; gRPC uses its own status model and optional details. A gateway translating between them should preserve meaning for clients, including retryable versus permanent failures. Deadlines should propagate through a call chain. A client timeout does not automatically cancel already-committed server work, so idempotency and status lookup remain necessary.

## Evolve the contract safely

For HTTP/JSON, add fields carefully and specify how clients handle unknown ones. For Protocol Buffers, preserve field numbers and avoid reusing removed numbers; old and new deployments may coexist. In either style, semantic compatibility matters more than syntax compatibility. A field named `price` cannot silently change from cents to a decimal currency amount even if its type remains numeric.

Many systems use both: an HTTP/JSON edge for browsers and partners, and gRPC for some internal call paths. That is reasonable when the translation cost and operational tooling are justified. Do not force two protocols into a small application without a concrete need.

## Design review

Who are the clients, and what tooling can they use? Is streaming genuinely needed? Can operators inspect failures? What is the migration plan when a field changes meaning? Which measured bottleneck would the chosen protocol solve?
