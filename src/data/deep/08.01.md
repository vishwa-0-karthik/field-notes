Delegating work means the request handler records an intent and another worker completes it later. This protects user latency when the work is slow, bursty, or dependent on an external service. It also changes the product contract: the response now means “accepted for processing,” not “finished.” Design the durable handoff, progress state, retries, and user-visible outcome before adding a queue.

## Decide which work can leave the request

Sending an email, generating a thumbnail, or exporting a report can usually happen after the primary transaction. Charging a payment or reserving inventory may require an authoritative decision before telling the user the operation succeeded. A request can create a durable job row and return its ID, then let the client poll or receive a notification. Make the states explicit: pending, running, completed, failed, and cancelled may have different user actions.

The queue is not necessarily the system of record. For a report export, a database job row can hold the requested parameters, owner, idempotency key, status, and output object key. The queue message can carry only the job ID. If a message is lost, a reconciler can find pending jobs and republish them. If the job record and message publish are separate writes, use a transactional outbox or equivalent durable mechanism so a database commit cannot leave a job permanently undispatched.

## Make the worker safe to repeat

A worker can perform the side effect and crash before acknowledging the message. The broker may redeliver it. RabbitMQ documents acknowledgements as the point at which the consumer takes responsibility, and Celery exposes early and late acknowledgement choices. At-least-once delivery means the task logic must recognize repeated attempts. Use a stable job ID, unique output path, or idempotency key at the external API. “Exactly once” cannot be achieved merely by setting a queue flag if the worker changes another system.

Retry transient failures with bounded attempts and backoff. Distinguish a temporary network error from invalid input that will never succeed. A poison job should move to a dead-letter state with enough context to inspect and retry after correction. Include a per-attempt timeout, total deadline, and cancellation check. A worker that runs longer than its visibility or lease timeout may overlap with a replacement worker; fence publication or make output idempotent.

## Protect capacity and visibility

Queues absorb bursts only while their backlog fits storage and the business deadline. If arrivals exceed processing capacity for hours, the queue delays work rather than solving it. Measure oldest job age, pending count, arrival rate, completion rate, retry rate, and worker saturation. Scale workers against downstream capacity, not just queue depth; more workers can overwhelm the database or a third-party API.

Preserve tracing from the request into the job. Record the original operation ID, actor, and version of the job schema. A deployed worker may consume messages written by an older application version, so evolve payloads compatibly. Define how users learn about terminal failure; a job that silently sits in a queue for days is an unfinished product action.

## Design review

What does the initial response promise? Where is the durable job intent? Can the task run twice safely? How does the user observe progress and failure? What happens if the queue or worker fleet is unavailable?
