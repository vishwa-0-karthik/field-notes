UUID, MongoDB ObjectId, and Snowflake-style IDs solve overlapping but different identifier problems. Their byte widths, time structure, and operational assumptions differ. Choose one by the guarantees your callers and storage engine actually need, then state what it does **not** promise.

## Compare the formats

A UUID is 128 bits. RFC 9562 defines several versions: version 4 uses random bits; version 7 places a millisecond Unix timestamp in the leading bits and leaves the rest for random or monotonic subfields. UUIDv7 is useful when independent generation and roughly time-ordered storage are desired. A random UUIDv4 has no embedded time order.

MongoDB ObjectId is 12 bytes: a four-byte timestamp in seconds, a five-byte process-random component, and a three-byte counter. MongoDB notes that ObjectIds are approximately ordered by creation time, but not strictly monotonic across clients or within a second. It is a convenient native document key, not an authoritative event clock.

A Snowflake-style ID is commonly a 64-bit integer composed of time, worker identity, and a local sequence. The precise bit allocation and epoch are implementation decisions. Twitter's published design emphasized compact 64-bit values and rough ordering at high issuance rates. Unique worker identity and clock behavior become part of correctness.

| Format | Typical width | Time signal | Coordination on each ID? |
| --- | --- | --- | --- |
| UUIDv4 | 128 bits | None | No |
| UUIDv7 | 128 bits | Millisecond prefix | No, with correct generator |
| ObjectId | 96 bits | Second prefix | No per ID |
| Snowflake-style | 64 bits | Configured timestamp field | No per ID, worker IDs coordinated |

## Separate order from identity

A time-structured ID can be useful for pagination or approximate chronological display, but it does not automatically provide strict creation order. Two machines have different clocks; two IDs generated in one millisecond may be ordered by random or worker bits rather than business commit time. If a feed must be correctly ordered, store a business timestamp and a stable tie-breaker, or use a commit sequence with clear semantics.

IDs can leak information. ObjectId and UUIDv7 encode time; Snowflake-like IDs can often reveal approximate creation time and worker structure. Public APIs should not assume an opaque-looking string is secret. Authorization must protect resources even when IDs are hard to guess. If unpredictable invitation tokens are required, generate a separate cryptographically random token with sufficient entropy instead of repurposing a sortable database key.

## Consider representation and indexes

Store IDs in native binary or integer types when supported rather than verbose text if index size matters. A 64-bit integer sent to JavaScript as a JSON number can lose precision above `2^53 - 1`; serialize as a string or use a format the client handles exactly. For relational foreign keys, a 128-bit UUID uses more bytes than a 64-bit integer in every referencing index. Test the real database and workload before treating that difference as decisive.

The ID format should be stable over a long product life. Migrating primary keys across APIs, caches, logs, and foreign keys is expensive. If requirements are uncertain, a standard UUIDv7 can be a reasonable independently generated default; if compact numeric IDs are a hard requirement, invest in worker and clock operations.

## Design review

Which guarantees come from the format and which from the generator implementation? Can clients store it losslessly? Does its timestamp expose information? Would sorting by the ID produce the exact business order users expect?
