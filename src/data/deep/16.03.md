# Design: a payment system

A payment system moves money through external processors while preserving a durable record of what the customer and merchant are owed. Network timeouts make outcomes ambiguous: a charge may succeed even when the caller never receives the response. The system therefore needs stable operation identity, an append-only financial ledger, explicit state transitions, reconciliation, and carefully constrained retries. A payment status is not just a boolean; authorization, capture, settlement, refund, and dispute are separate events.

## API and idempotent operations

The client creates a payment attempt with amount, currency, merchant, and an idempotency key. The server authenticates the caller, validates amount and currency against the order, and stores an operation record before calling the processor. Scope the key by account and operation and bind it to a request hash; using the same key with different parameters must fail. If the response is lost, a retry returns the stored outcome or resumes the same workflow rather than issuing a second charge. Idempotency records need retention that exceeds realistic client retry windows and processor reconciliation delays.

Model payment state as a state machine with legal transitions. For example, `created → requires_action → authorized → captured → settled`; alternate paths include `failed`, `cancelled`, `refunded`, and `disputed`. Provider callbacks can arrive out of order or more than once. Verify signatures, record provider event IDs, and apply updates with version checks. If an event refers to an older state, store it for audit but do not regress the payment. A webhook response should acknowledge durable receipt, with processing performed asynchronously if needed.

## Ledger and reconciliation

Store a double-entry ledger with immutable postings whose debits and credits balance for each transaction and currency. The payment object describes workflow state; the ledger is the accounting record. Do not update a balance as the only record of money movement. Use database transactions to create balanced entries and link them to the payment operation. Corrections are compensating entries, not edits to history. Separate pending authorization from captured funds and from settlement because a provider can later reverse or dispute a transaction.

An outbox or durable event log publishes ledger and payment state changes to orders, receipts, analytics, and fraud systems. Consumers use stable event IDs for deduplication. Reconciliation compares internal operations and ledger totals to processor reports or API state. It catches ambiguous timeouts, missed webhooks, fees, settlement delays, and manual changes. An operator workflow should allow a payment to be placed into review rather than guessed into a final state.

## Risk, security, and failure handling

Keep card data out of application logs and general databases when possible; use processor-hosted collection or tokenization to narrow the sensitive-data boundary. Enforce authentication, authorization, amount limits, velocity checks, and merchant isolation. Protect webhook secrets and audit privileged refunds. If the processor is unavailable, preserve the order intent and return a pending state; do not claim failure until the outcome is known. Circuit breakers should prevent retry storms, and queues should cap delayed payments.

Track authorization and capture rates, ambiguous outcomes, webhook lag, reconciliation differences, ledger imbalance, refund time, and duplicate prevention. Test timeout after processor success, duplicate webhook, out-of-order events, refund race, currency mismatch, and ledger transaction failure. The primary correctness invariant is that every external money movement has one internal operation identity and a balanced, auditable ledger representation.

## Design review

What does the idempotency key cover and for how long? Which state is authoritative when a callback arrives late? Are financial records append-only and balanced? How are processor reports reconciled? What response represents an ambiguous external outcome?
