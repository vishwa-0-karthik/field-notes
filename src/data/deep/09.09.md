Search evaluation asks whether users find the information they need, in the order and time they need it. No single metric covers every search surface. A legal discovery tool may prioritize recall; a homepage search may care most about the first few results; an autocomplete list has an even tighter visible window. Define the task and judgment policy before choosing a number.

## Build a representative query set

Collect common, rare, ambiguous, exact-ID, typo, multilingual, and zero-result queries. Remove private details and sample by query class so the head does not drown out the long tail. For each query, gather candidate documents from several retrieval versions and ask assessors to judge relevance. This pooling reduces the chance that an unjudged result from a new system is incorrectly treated as bad. Write a rubric: what makes a result relevant, partially useful, outdated, or unsafe? Record assessor disagreements instead of hiding them.

Judgments are tied to a corpus snapshot. If a product goes out of stock or an article changes, its old label may no longer describe the current task. Version the query set, documents, and labels. Keep a separate holdout set so tuning decisions do not overfit the same queries used for reporting.

## Match metrics to the goal

Precision@K is the share of the first K results that are relevant. Recall@K is the share of all known relevant items retrieved in the first K; it is difficult when relevance judgments are incomplete. Mean reciprocal rank rewards finding the first relevant item early, useful for navigational queries. NDCG@K discounts lower ranks and can use graded judgments, useful when several results have different degrees of value. Average precision summarizes where relevant documents occur through a ranked list. Stanford's retrieval text explains precision, recall, and ranked evaluation; NIST's TREC evaluations use NDCG and related measures in real benchmark settings.

Compute metrics per query and aggregate thoughtfully. A mean can hide a catastrophic regression for a small but important query class. Report confidence intervals or paired comparisons when a difference is small. Check the first-stage retriever separately: a reranker cannot improve an item it never receives. A model that gains NDCG while reducing recall for exact identifiers may be unacceptable for the product.

## Connect offline and online evidence

Offline evaluation is repeatable and fast, but labels are imperfect and may not reflect live intent. Online experiments expose actual behavior, including clicks, conversions, reformulations, abandonment, and latency. Random assignment must remain stable for a user or session, and the UI should be held constant if the goal is to measure ranking. Click metrics are affected by position and snippets, so pair them with downstream outcomes and guardrails such as p95 latency and zero-result rate.

Investigate individual query diffs. Record which documents entered or left top K, score explanations, index version, and query rewrite. A metric movement without examples is hard to act on. Set a rollback threshold and monitor after launch because index contents and query distribution change over time.

## Design review

What user task defines success? Do labels include relevant long-tail and permission-sensitive queries? Which metric captures the visible ranks? Are corpus and judgments versioned? What online guardrails would stop a ranking rollout?
