Start a design by turning a product idea into a small set of observable promises. “Build a notification service” is a label, not a specification. A design becomes testable when you know who sends notifications, who receives them, which channels are supported, and what a successful send means. The system boundary comes before the box diagram.

## Discover the actual workflow

Walk through one ordinary request from the user's point of view. For a notification product: a merchant creates an order, the application emits an `order_shipped` event, the customer receives an email, and the support team can see whether delivery was attempted. This story exposes four distinct actions—event creation, policy evaluation, provider dispatch, and status reporting. Each needs an owner and a contract.

Then ask about the exceptions. Can a customer opt out? Does the merchant choose a template? If the email provider returns an error, should the order operation fail? What if the same shipment event arrives twice? An answer to each question changes the data model or failure behavior. A diagram drawn before these answers may look plausible while promising the wrong service.

Separate **functional requirements** (what the system does) from **quality constraints** (how well it does it). Functional requirements might be “send transactional email” and “record every delivery attempt.” Quality constraints might be “95% of accepted events reach a provider within 30 seconds” and “support can query a seven-day history.” State the population and measurement window for each number.

## Write down the boundaries

Use a short scope table. It prevents adjacent product ideas from silently entering the design.

| Question | Example answer | Design consequence |
| --- | --- | --- |
| Who creates an event? | Authenticated internal services | Internal API and service credentials |
| What counts as accepted? | Durable queue admission | Acknowledgment follows persistence |
| What counts as delivered? | Provider confirmation | Status has a separate update path |
| How long is history kept? | Seven days | Retention job and storage estimate |
| What is outside scope? | Marketing campaign editor | No audience segmentation in this design |

Define terms carefully. “Delivered” could mean the provider accepted the message, an email server accepted it, or the person opened it. Those are different observations. If the source system needs proof that a customer saw a message, an email dispatch receipt cannot provide it. This is a product contract issue, not a queue configuration issue.

## Find the invariants and priority order

An invariant is a property that must remain true even when dependencies fail. Examples: an opted-out customer does not receive marketing mail; two retries of one event do not create two billing records; a confirmed event can be found during its retention period. Write these before choosing technology because they identify where transactions, idempotency keys, and audit data are required.

Ask which promise wins when two cannot both be met. A payment receipt might favor durable eventual delivery over low latency. An in-app typing indicator may favor freshness over guaranteed delivery. Both are “notifications,” but their failure policies differ. If requirements include incompatible priorities, make the conflict explicit rather than hiding it in architecture.

## Turn uncertainty into assumptions

At the beginning of a design exercise, many values are unknown. Record them as assumptions with a way to check them: “Assume 100 events per second at peak until traffic data is available,” or “Assume one region until compliance confirms residency.” This distinguishes a provisional estimate from a requirement. It also shows which measurements would most change the design.

A useful first design note has five parts: user journey, must-have functions, measurable quality targets, invariants, and explicit exclusions. It should be short enough that a product owner could correct it. Only then sketch the request path and storage. Google's SRE guidance likewise starts reliability work with service indicators and objectives tied to what users experience; a target without a defined signal is difficult to operate.

## Design review

Given an “accepted” notification event, can you say exactly when the caller may receive success, what survives a process crash, how duplicates are handled, and which component answers a delivery-status query? If any answer is vague, clarify the promise before scaling the system.
