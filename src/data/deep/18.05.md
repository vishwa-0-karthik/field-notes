# Case: GitLab’s database incident

GitLab’s January 31, 2017 database incident is a case study in why “we have backups and a replica” does not prove recoverability. GitLab's postmortem reports that accidental deletion of the primary database directory caused a long outage and unrecoverable loss of some database changes. The event combined a replication failure, an unsafe manual operation, broken backup automation, unclear recovery procedures, and storage performance limits. The incident illustrates how individually reasonable safeguards can share hidden failure modes.

## Failure chain

GitLab described a primary PostgreSQL database with a hot standby. Increased load caused replication to lag; WAL segments needed by the standby had already been removed, so the replica needed to be rebuilt. During manual recovery, an engineer intended to wipe the secondary's data directory but ran the command on the primary. The operation was stopped quickly, but substantial data had already been removed. A replica could not rescue the system because it was behind and later also wiped.

The team then discovered that the routine `pg_dump` backup job had not produced valid backups. It used the wrong major PostgreSQL tool version from an application server, and alert email was rejected because its mail authentication was not configured. The recovery depended on an LVM snapshot that had been copied to staging. Restoring that snapshot to production took many hours because of slow network-attached disks. GitLab reported service recovery after about 18 hours and loss of some changes made between the last usable snapshot and the incident.

## What the postmortem changed

The documented follow-up work included backup monitoring, point-in-time recovery and WAL archiving, more frequent snapshots, automated restore testing, improved runbooks, clearer environment identification, and ownership for data durability. These changes address different failure classes: detect backup failure, preserve finer recovery points, reduce restore time, and make operator actions safer. A secondary replica supports availability but is not an independent backup when it replicates destructive changes. A successful backup command is not enough; the team must prove that a current, decryptable, consistent copy can be restored within the target RTO.

## Lessons and limits

Use the incident to ask how destructive commands distinguish production from staging, whether commands require explicit confirmation, whether recovery is rehearsed, and whether backup health is monitored as a user-facing SLO. Keep copies in separate failure domains and protect their credentials. Test restoration from the exact artifacts operators would use, including binaries, keys, configuration, and storage performance. Treat a replica and backup as different safeguards. The specific details here are from GitLab's historical postmortem; the general recommendations are design inferences, not a claim about GitLab's current systems.

Another subtle lesson is that recovery depends on people and tooling under pressure. The postmortem describes unclear command behavior, insufficient environment differentiation, and runbook gaps alongside technical failures. Safer recovery workflows make the target host and environment visible, automate destructive steps, require explicit confirmation for production, and preserve an independent communications channel. Practice should include the time to copy and validate data, not only the time to start PostgreSQL.

## Design review

Was the replica a recoverable backup or only a failover copy? How was silent backup failure detected? Which safeguards could have prevented a production/staging command mix-up? What restore time was measured, and what independent copy met the recovery point objective?
