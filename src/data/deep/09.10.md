A search index is usually a derived view of a database or content store. Synchronization is the process of making creates, updates, deletes, and access changes visible in search within an agreed delay. A successful database transaction does not mean the index already reflects it. Define a freshness target and a recovery path before choosing whether updates flow through direct writes, an outbox, change data capture, or periodic rebuilds.

## Preserve a reliable change path

An application that commits a product row and then calls the search engine can crash between those operations. If it calls search first, a later database rollback can expose a product that does not exist. Write an outbox event in the same source transaction, then relay it to an indexer, or consume the database change log through CDC. The indexer should use the source record's stable ID and version. A retry may deliver the same change twice, while network delay can deliver an old update after a newer one. Reject older versions so `price = 10` cannot overwrite a later `price = 12`.

Deletes and permissions deserve priority. A stale title is inconvenient; a deleted private document remaining searchable may be a serious breach. Emit tombstones or delete events with versions, and ensure an older create cannot resurrect them. Depending on the product, apply an authorization filter at query time against authoritative permission data or make access-change propagation meet a stricter deadline than ordinary content updates.

## Distinguish accepted from searchable

Search engines may acknowledge an index write before a refresh makes it visible to queries. Elasticsearch documents periodic refresh and `refresh=wait_for` when a caller must search for its own write. For most ingestion, batch writes and accept a short visibility delay; forcing a refresh on every document can harm throughput. Expose the difference in product behavior, such as “saved, searchable shortly,” when it matters.

Keep checkpoints for the change stream and a dead-letter path for malformed records. Advancing the checkpoint before a durable index write can lose an update; replaying after a crash can duplicate it. Idempotent writes by ID and version make replay safe. Measure source-commit-to-index-write delay and index-write-to-query-visible delay separately. Queue depth alone can miss an indexer that is consuming changes but failing every write.

## Rebuild and reconcile

An analyzer or schema change often requires a full reindex. Build a new index from a source snapshot while capturing changes that occur during the scan. Replay those changes until caught up, validate document counts and representative queries, then switch a read alias to the new index. Keep the old index briefly for rollback. Elasticsearch aliases support this deployment shape, but the application still needs a correct snapshot boundary and replay procedure.

Run periodic reconciliation by comparing source IDs and versions with indexed IDs and versions, sampled or complete according to scale. Repair missing, stale, and ghost documents. Define how long deleted records remain in the change log so a slow indexer can recover. If a search cluster is unavailable, the source transaction should remain valid and indexing should catch up later, unless the product explicitly requires synchronous search visibility.

## Design review

Which store is authoritative? Can a source commit be missed between database and index? What rejects out-of-order updates and resurrected deletes? When is a write actually searchable? How is a new index built and switched without losing concurrent changes?
