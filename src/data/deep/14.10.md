# Security and abuse prevention

Security and abuse prevention work best when they are part of the system's normal request path, not a collection of emergency controls added after launch. Design for authenticated identity, least privilege, explicit authorization, bounded resource use, auditability, and safe failure. Abuse includes more than malicious account takeover: a buggy client, compromised integration, or unexpectedly popular feature can exhaust compute, storage, or paid downstream APIs.

## Enforce identity and authorization at boundaries

Authenticate users and service identities at the edge, then authorize each operation against the resource and tenant. Do not treat an opaque ID or unguessable URL as proof of access. Check ownership at the service boundary and avoid trusting a client-supplied user or tenant field when verified identity context is available. For internal calls, use explicit service identity and scoped permissions rather than one broad shared credential. Rotate secrets, keep them out of source control and telemetry, and record access to sensitive operations.

Use defense in depth: network boundaries, input validation, least-privilege storage policy, encryption, and application checks. A CDN or cache can accidentally bypass authorization if a personalized response is cached under a shared key. Verify access control for cache hits as well as origin misses. For uploads, limit size, type, parsing cost, and access to staging objects. For outbound integrations, constrain destinations and budgets to reduce SSRF and financial abuse. Validate structured inputs with maximum lengths, collection sizes, and allowed formats.

## Bound resource consumption

Every expensive operation should have an explicit budget: request rate, concurrency, payload size, query complexity, retry count, storage, CPU, and downstream spend. Rate limits should account for identity confidence. IP is useful before login and for broad attack suppression, but NAT can group legitimate users. Account or API key limits are more precise after authentication; tenant-level budgets protect shared capacity; endpoint-specific controls protect expensive actions. Layer limits instead of relying on one identifier. Return a consistent throttling response and retry guidance, and avoid revealing sensitive account existence through different error behavior.

Retries and fanout can amplify overload. Use deadlines, bounded exponential backoff with jitter, circuit breakers, and queue admission controls. A limit at the gateway can protect the public edge but does not necessarily protect an expensive internal method called by other services. Enforce a final resource budget at the service that owns the cost, with upstream controls for early rejection. Preserve emergency administrative access under strong authentication, separate from user paths, and audit changes to limits.

## Detect and respond

Log security events with stable actor, action, resource, decision, and request context while minimizing sensitive payloads. Detect unusual account, tenant, IP, or key behavior using baselines and high-confidence rules; alerting on every spike will train responders to ignore alerts. Provide controls to revoke sessions, keys, and tokens; quarantine abuse; disable a feature; and preserve evidence. Run tabletop exercises for credential compromise, data exfiltration, abusive automation, and an unexpectedly expensive endpoint.

Measure denied authorization, suspicious rate patterns, resource exhaustion, quota use, secret age, audit coverage, and time to revoke credentials. Test cross-tenant access, replayed capabilities, missing authorization on cache hits, oversized request bodies, and abusive retry loops. Security controls should degrade intentionally: decide whether an unavailable policy store means reject, queue, or allow a request, based on the sensitivity of the operation.

## Design review

Where is identity established and checked? Are limits enforced where expensive resources are consumed? Can a cache return data before authorization? What happens when policy or audit services are unavailable? Can operators rapidly revoke credentials and cap spend?
