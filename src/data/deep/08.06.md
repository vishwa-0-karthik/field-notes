PostgreSQL can be a practical work queue when jobs are tied to an existing database transaction and throughput is moderate. `FOR UPDATE SKIP LOCKED` lets concurrent workers claim different rows without waiting for a locked row. PostgreSQL explicitly describes the resulting inconsistent view as suitable for queue-like tables. It does not make a general query serializable, enforce strict FIFO, or make an external side effect atomic with a database update.

## Claim a job in one short transaction

Keep a `jobs` table with `id`, `status`, `run_at`, `priority`, `attempts`, `lease_until`, `claim_token`, and a small payload or payload reference. A worker can claim one eligible row and mark it running in one statement:

```sql
WITH candidate AS (
  SELECT id
  FROM jobs
  WHERE status = 'pending' AND run_at <= now()
  ORDER BY priority DESC, run_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs AS j
SET status = 'running',
    attempts = attempts + 1,
    lease_until = now() + interval '1 minute',
    claim_token = gen_random_uuid()
FROM candidate
WHERE j.id = candidate.id
RETURNING j.*;
```

Commit immediately after the claim. Do not keep the row lock and transaction open during network calls: that holds database resources and can block other updates. An index that supports the eligible-job predicate and ordering matters more than the syntax alone. Benchmark the real query plan with the expected mix of pending, future, and completed rows; archive old completed jobs so scans do not degrade.

## Recover a worker that disappears

A lease makes an abandoned running job eligible for reclamation after `lease_until`. The original worker may simply be slow, so it can still finish after a replacement claims the job. Increment or replace a claim token on every claim, and require the current token in the completion update. That prevents an old worker from overwriting the new worker's database result. It does not stop two workers from invoking an external API. Put an idempotency key on the business operation and pass it to the external system if supported.

Long jobs need heartbeats that extend the lease conditionally on the current token. On failure, move a job back to pending with a future `run_at` and capped exponential backoff. After a bounded number of attempts, mark it failed with a reason and an operator replay path. Make a reaper reclaim expired leases, and monitor both lease age and the oldest eligible job age. A continuously failing job should not starve healthy work.

## Know the limits of the pattern

`SKIP LOCKED` skips locked rows, so priority order is best effort under contention. Workers may repeatedly pass a hot locked row. Table-level locks can still wait even with `SKIP LOCKED`. PostgreSQL's `UPDATE ... RETURNING` returns the rows actually modified, making it useful for the claim. For a small service, this design avoids another broker and allows a transaction to create the business row and job together. At high write volume, polling, row churn, vacuum pressure, and retention management can dominate; a purpose-built broker or log may fit better.

## Design review

Does the claim commit before execution? How is an expired lease reclaimed? Can a stale worker still cause a duplicate external effect? Are job order and throughput requirements compatible with best-effort skipping? Which index and retention policy keep the due scan fast?
