A social network database stores users, relationships, posts, interactions, and visibility rules. The data model should support the main access patterns: fetch a profile, list whom a user follows, list followers, show a feed, and check whether one user may see a post. A graph label alone does not solve these queries. Most designs combine an authoritative transactional model for relationships and posts with derived indexes for feeds and recommendations.

## Model edges explicitly

A follow edge can be `(follower_id, followee_id, created_at, state)` with a unique constraint on the two IDs. Index by follower to list followed accounts and by followee to list followers. A private account may need `requested`, `accepted`, and `rejected` transitions rather than a single Boolean. Blocks and mutes have different effects: a block may revoke access, while a mute may only remove feed entries. Store them as distinct edge types or tables with documented precedence.

Follower counts can be derived, cached, or maintained transactionally depending on accuracy needs. A count should not be the sole record of relationships. Deleting an account or changing privacy must remove or hide edges in all read models. A cache of “who follows whom” needs invalidation or a versioned freshness bound, especially when used for access control.

## Keep post ownership and visibility clear

A post row needs a stable ID, author, creation time, content reference, visibility, moderation state, and version. Media belongs in object storage with metadata and permission checks. Edits and deletes should propagate to search and precomputed feeds. If a private post was copied into follower inboxes, each read must still enforce current visibility or remove stale entries promptly; fanout is a convenience index, not an authorization authority.

Use cursor pagination based on a stable ordering key such as `(created_at, post_id)` for large follower or post lists. Offset pagination becomes expensive and can skip or duplicate entries as new records arrive. For a feed, a ranking score may change, so a cursor needs a snapshot or clear best-effort semantics. Keep the authoritative post table separate from denormalized feed-entry references to avoid duplicating full content millions of times.

## Design for skew and change

Social graphs are highly skewed. An ordinary user may have 200 followers while a celebrity has millions. A write path that copies every post to every follower works for one and may overwhelm the system for the other. Choose push, pull, or hybrid feed generation based on measured follower distribution. Shard edge lists by owner or counterpart as queries demand, and plan how to count or page a very large list without loading it all into memory.

Monitor edge mutation latency, follower/following list latency, count drift, feed freshness, privacy-filter misses, and delete propagation. Test follow/unfollow races, block precedence, private-account approval, and a celebrity publish burst. Twitter's FlockDB project is an example of adjacency-list-oriented graph storage built for social edges, with an explicit focus on lookups rather than arbitrary graph traversals.

## Design review

Which relationship transitions exist? What indexes answer both edge directions? Which store enforces post visibility at read time? How do deletes reach feed and search projections? What breaks when an account has millions of edges?
