# Parallel monolith read drain

Moving a capability out of a monolith is safer when the old and new paths can run side by side and traffic can move gradually. A read drain is a useful first step: keep the monolith as the source of truth for writes, mirror or replicate the relevant data to the new service, compare responses, then route selected reads to the new service. This limits the risk because a read can usually be retried or sent back to the old implementation without creating duplicate side effects.

## Establish data parity before switching

Put a routing facade in front of the capability so callers use one stable API while the implementation changes behind it. Define ownership for each record and which database is authoritative at every stage. Use an initial snapshot followed by change-data capture or another ordered change feed to keep the new store current. Track source offsets and replication lag. A “dual read” can compare old and new results on sampled requests, but do not return both or let one path mutate state. Compare normalized semantics, not only JSON shape: ordering, null handling, access control, and freshness may differ.

Begin by shadowing a small percentage of reads to the new service while still returning the monolith response. Shadow traffic must be bounded so it does not double load a fragile database, and it must avoid side effects such as billing, notifications, or audit writes. Redact sensitive data and apply normal authorization to the shadow request. Record mismatches by category and enough identifiers to diagnose without logging full private payloads. Do not promote while differences remain unexplained.

## Shift traffic and drain dependencies

When parity and latency are acceptable, route a small percentage of real reads to the new service, keeping a fast fallback to the monolith. Increase traffic gradually by tenant, region, or percentage. Watch error rate, tail latency, stale-read complaints, database load, and fallback rate. Fallback must have a deadline and circuit breaker; otherwise a degraded new service can send all traffic back to the monolith and overload it. Keep the old path alive until the rollback window and data consistency checks are complete.

The cutover is not finished merely because requests route elsewhere. Find batch jobs, admin tools, caches, reporting queries, and background workers that still read the monolith tables. Add ownership metadata and access logging to identify clients. Drain these dependencies deliberately and remove old credentials only after they no longer have legitimate use. If the new service becomes the write owner, plan a separate write migration with idempotency, dual-write consistency, conflict resolution, and rollback semantics. Reads are often reversible; writes across two databases are not automatically safe.

Keep a tested kill switch and preserve the old binary and schema until traffic is fully drained. Record every stage and its stop condition. A migration is successful when the old service can be removed without hidden consumers, stale data, or an unplanned fallback dependency. Metrics should include shadow coverage, mismatch rate, replication lag, traffic percentage, fallback rate, and remaining monolith callers.

## Design review

Which store is authoritative during each phase? Does the shadow path avoid side effects and extra load? How is semantic parity measured? Can fallback overload the old service? What inventory proves that all reads have drained before the old path is removed?
