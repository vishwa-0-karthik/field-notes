Backpressure is the signal that a downstream stage cannot safely accept work as fast as an upstream stage produces it. Without that signal, a queue or buffer grows until latency, memory use, or failure becomes unacceptable. Backpressure is a system property: every stage needs a bounded way to slow, reject, or persist excess work.

## Follow the flow of work

Consider an upload pipeline: client → API → object store → image processor. The client may send bytes faster than the API can forward them. A streaming API can pause reads when the downstream write buffer is full, then resume as capacity returns. Node.js streams expose this pattern; ignoring the writable stream's backpressure signal can accumulate large buffers and increase garbage collection or exhaust memory.

At the job level, a queue can absorb a temporary burst. But if arrival rate remains 2,000 jobs/s while processors complete 1,000 jobs/s, backlog grows by 1,000 every second. After one hour that is 3.6 million jobs. A queue smooths *bursts*; it does not fix sustained insufficient capacity. Calculate the backlog recovery time after a spike, including the normal ongoing arrival rate.

| Signal | Meaning | Possible response |
| --- | --- | --- |
| Writable buffer full | Bytes cannot drain quickly | Pause upstream reads |
| Queue age rising | Work waits longer | Add consumers or reduce admission |
| DB pool wait rising | Too many concurrent queries | Limit in-flight requests |
| Memory near limit | Buffering too much state | Shed load before crash |

## Choose an overload policy

There are several valid responses: slow the sender, return `429` or `503`, drop low-value work, persist it for later, or degrade a feature. The right choice follows product semantics. A payment request should not be silently dropped. A live typing indicator can be skipped when stale. A report export can be accepted as a background job if status and eventual completion are visible.

Set queue limits by both item count and bytes; one giant job can exhaust memory despite a small count. Set time limits too: a request that waited in a queue for ten seconds may already be useless to its caller. Propagate deadlines and cancellation when possible. A bounded queue makes failure visible early enough for clients to back off, whereas an unbounded queue converts overload into a delayed collapse.

## Avoid pushing pressure elsewhere blindly

Adding more workers can overwhelm the database or provider they call. Put concurrency limits at the scarce dependency and measure its saturation. If the dependency is healthy but workers are too few, scale them. If it is already at capacity, admission control or priority may be the only safe immediate response. Retry storms can defeat backpressure by turning one rejected request into many attempts; use backoff and retry budgets.

Backpressure should be observable. Track incoming rate, completion rate, active work, oldest queued age, rejection count, memory, and downstream wait time. A flat queue depth can still be bad if producers and consumers are both stalled; pair depth with age and throughput.

## Design review

Where can the producer first learn the consumer is slow? What is the maximum buffered work in bytes and time? Which requests are rejected or degraded first? How long will backlog recovery take after the peak ends?
