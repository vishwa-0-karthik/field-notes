An online index build adds a new access path while a table continues serving production traffic. The challenge is that rows can change during the build. The database must capture those concurrent changes and validate that the finished index covers a consistent state. “Online” reduces blocking, but it does not mean zero resource use or zero operational risk.

## Why a normal build can hurt

On a large orders table, a standard index build scans the table and constructs index pages. In PostgreSQL, ordinary `CREATE INDEX` allows reads but blocks writes until completion. If the table is busy, a build lasting minutes or hours can create an unacceptable write outage. `CREATE INDEX CONCURRENTLY` allows inserts, updates, and deletes to proceed, making it suitable for many live changes.

The concurrent path performs more work. PostgreSQL documents two table scans and waits for relevant existing transactions. CPU, I/O, WAL, and cache pressure can raise normal query latency even though writes are not blocked by the build lock. A long-running transaction may delay progress. Schedule and monitor the migration with peak traffic and headroom in mind.

| Phase or concern | What to check |
| --- | --- |
| Before build | Query need, estimated index size, disk and WAL headroom |
| During build | Progress view, I/O, p99 latency, lock waits |
| After build | Index valid, planner uses it, query actually improves |
| Failure | Invalid index cleanup or rebuild plan |

## Treat uniqueness as a migration

A unique index cannot be built successfully if duplicates already exist. First query for duplicates and decide how to resolve them. During a concurrent unique build, new writes may begin seeing uniqueness errors before the index is fully valid. If the build later fails, an invalid index may remain and still impose write overhead; inspect catalog state and clean it up before retrying. This is more involved than adding a plain read index.

If the application also needs a new constraint or changed write logic, stage the rollout. Deploy code that tolerates the new rule, clean existing data, build the index, verify it, then make code rely on the invariant. The exact order depends on whether older application versions may still write duplicate data. A rolling deployment means old and new writers coexist for a while.

## Validate the useful result

An index can be valid yet unused. Run the target query with representative parameters and inspect `EXPLAIN` or `EXPLAIN ANALYZE`. If the planner chooses a sequential scan because the predicate matches most rows, the index may not help. Check write overhead too: an index that saves 20 ms on a rare report but slows every insert may be a poor tradeoff.

For partitioned tables, online indexing may require per-partition steps and a metadata-level parent operation rather than one concurrent command. Confirm the database version's supported behavior before writing a migration script. Keep the script idempotent and observable; restarting a failed build without checking an invalid artifact can leave the system worse off.

## Design review

What query justifies the index? Will the build block writes, and how much extra I/O can it create? What happens if duplicates or a deadlock make it fail? How will you prove the new index is valid, used, and worth its ongoing write cost?
