# Deployment and migration safety

Deployment safety is the ability to change software while limiting the size and duration of mistakes. A release should be observable, staged, and reversible at the level of traffic and behavior. “Rollback” is not always a binary operation: code can be rolled back quickly, while a schema change or emitted event may already have made data incompatible with the previous version. Plan compatibility before deployment rather than treating rollback as an afterthought.

## Reduce blast radius

Build an immutable artifact once and promote the same artifact through test, canary, and production stages. Validate configuration separately and record the exact artifact and configuration revision used by each environment. A canary receives a small representative share of traffic or a limited worker cohort. Compare error rate, latency, saturation, and business outcomes to a control group, accounting for traffic mix and time effects. Halt promotion automatically when a guardrail fails. A canary that only checks process liveness can miss incorrect responses or data corruption.

Feature flags separate deployment from activation. They can release a dark code path to production, then enable it for internal users or a percentage of traffic. Flags need owners, expiry, and a cleanup process; forgotten flags become permanent branching complexity. A flag does not protect against database writes already issued by the new code, so data compatibility remains necessary. Progressive delivery can use percentage rollout, region by region, or one service instance at a time depending on statefulness and traffic distribution.

## Make old and new versions coexist

For an API or event schema change, use an expand-and-contract sequence: first add the new field or table in a backward-compatible way; deploy readers that understand both forms; begin writing the new form; backfill existing data; validate parity; switch reads; and only later remove the old form after old clients and workers are gone. This sequence handles mixed versions during rolling deployment. A destructive rename or type change in one step can break an old binary that remains active during the rollout.

Backfills should be resumable, rate-limited, checkpointed, and observable. They compete with user traffic for database resources and can create replication lag. Run them in bounded batches, monitor lock time and query load, and make each batch idempotent. Before the cutover, define a consistency check and a stop condition. If the new path is incorrect, an explicit rollback or forward-fix plan should account for writes made during the transition.

## Verify through the full release

Pre-production tests reduce risk but cannot prove production health. Use a canary, automated health gates, and an operator-visible rollout status. Keep a kill switch for dangerous optional behavior, but verify that disabling it does not strand in-flight work. Avoid coupling multiple unrelated risky changes in one release; if metrics regress, smaller changes make attribution easier. Store release events alongside telemetry so operators can correlate regressions with exact changes.

Track deployment frequency, change failure rate, time to restore, canary aborts, migration lag, and rollback success. Test a release where one region lags, a worker runs an old schema reader, and a backfill is interrupted. The safest deployment is not necessarily the slowest: clear compatibility, small blast radius, and automatic evidence allow changes to proceed with controlled risk.

## Design review

Can old and new binaries coexist against the schema and events? Is the canary representative and tied to user outcomes? Can a backfill pause and resume safely? What irreversible writes occur before rollback? Which gate stops promotion and who can override it?
