A Snowflake-style generator packs a timestamp, a worker ID, and a per-timestamp sequence into a compact integer. It allows many workers to issue IDs locally while keeping values roughly ordered by time. The design succeeds only if worker IDs never overlap while active, clocks are handled conservatively, and sequence capacity is not exceeded.

## Choose a bit budget

For illustration, reserve one sign bit, 41 bits for milliseconds since a custom epoch, 10 bits for worker identity, and 12 bits for a sequence. That permits 1,024 worker numbers and 4,096 sequence values per worker per millisecond, while 41 timestamp bits span about 69 years. These are **example limits of this layout**, not a promise that the service can sustain 4,096 durable writes per millisecond: network, storage, and downstream systems may be much slower.

The packed value is conceptually `(timestamp << 22) | (worker << 12) | sequence`. A custom epoch reduces the bits needed for dates near deployment. Document the epoch forever; changing it or the bit allocation without a version marker can make old and new IDs decode differently. Keep the sign bit clear if clients or databases use signed 64-bit integers.

| Field | Purpose | Failure to handle |
| --- | --- | --- |
| Timestamp | Rough chronological order | Clock rollback or epoch exhaustion |
| Worker ID | Disjoint issuers | Two active workers share ID |
| Sequence | Burst within one millisecond | Counter wraps before clock advances |

## Make issuance a state machine

On each request, read the current clock. If it is later than the last issued millisecond, reset the sequence. If it is equal, increment the sequence. If the sequence is exhausted, wait until the next millisecond or return a bounded error; never wrap and reuse a value. If the clock moved backward, stop issuance, wait within a configured bound, or use a carefully persisted logical time policy. Silently resetting the sequence can create duplicates when the old millisecond recurs.

Worker assignment is another state machine. A lease or coordinator can allocate unique IDs to live workers. A new worker should not reuse an ID until the old holder is fenced and the maximum relevant time window is safe. Container restarts and network partitions make “machine number in config” risky if two instances can boot with the same value. Monitor lease renewal and fail closed on uncertainty.

## Define the order promise honestly

IDs generated by one worker with a nondecreasing clock can be monotonic. Across workers, clocks differ and sequence fields overlap, so the numeric order is only approximate. A write can allocate an ID and commit later than a record with a larger ID. Twitter's announcement described its IDs as roughly sortable rather than globally sorted. Use a separate commit-order mechanism when the product requires exact ordering.

Test the generator under frozen time, backward time, many threads, worker-ID collision, and restart. Verify uniqueness with a database constraint in an integration workload. Estimate the date when the timestamp field overflows and establish a migration strategy well before it arrives.

## Design review

What is the layout and epoch? How does the worker ID remain unique through restart and partition? What does the generator do on clock rollback and sequence exhaustion? Can every client represent the resulting integer exactly?
