# Multi-tenant design

Multi-tenant design lets one service operate for many customer organizations while preserving isolation, fair resource use, and a consistent product lifecycle. A tenant is a security and business boundary: requests, stored records, background jobs, caches, and exports must remain scoped to the right organization. The architecture also decides how much infrastructure is shared. Pooling improves utilization; siloing offers stronger resource and data separation; a bridge model combines them for selected layers or customer tiers.

## Carry tenant context end to end

Resolve the tenant from a verified identity or trusted routing domain after authentication. Do not accept an arbitrary tenant ID from the request body as the authorization source. Carry tenant context through service calls, queue messages, scheduled jobs, and audit events. Each consumer should verify that the context is present and authorized for the target object. Database queries should require tenant scope by default, and tests should attempt cross-tenant reads and writes. In pooled tables, tenant ID commonly belongs in the partition or leading index key; database row-level security can add defense in depth but does not replace safe application authorization.

Caches and object storage need equal care. Include tenant identity in cache keys whenever returned data varies by tenant, or separate cache namespaces by tenant. Ensure a CDN does not cache private responses under a shared key. Use opaque storage prefixes and policies that limit access, but do not treat the prefix as the only check. Search indexes, analytics exports, and data warehouses need tenant filters and access controls as well. A single missed path can create a cross-tenant data leak.

## Choose isolation and fairness

In a silo model, each tenant has dedicated resources or storage. This improves isolation and can simplify customer-specific recovery, but increases provisioning, upgrades, and operational cost. In a pool model, tenants share compute and data structures; onboarding and release operations are efficient, but a noisy tenant can affect others and isolation mistakes have a larger blast radius. A bridge model mixes choices—for example shared web services with dedicated databases for high-sensitivity tenants. Choose per component based on data sensitivity, noisy-neighbor risk, scale, compliance needs, and operational capacity rather than making a single all-or-nothing decision.

Enforce fairness with per-tenant rate and concurrency limits, queue partitions, storage quotas, and workload scheduling. A tenant should not monopolize a shared worker pool or hot database partition. Measure usage and capacity by tenant while restricting access to sensitive identifiers. Large-tenant migration between tiers or shards should be a planned operation with routing version, backfill, dual-read validation, and cutover controls.

## Operations and lifecycle

Provisioning, configuration, backups, deletion, and upgrades should be automated through a unified control plane. A dedicated tenant stack still benefits from one product version and one operational experience; otherwise version drift becomes a separate support burden. Track per-tenant errors, latency, usage, quota, and noisy-neighbor impact while maintaining aggregate service objectives. Tenant-aware logs must avoid exposing one tenant's data to another tenant's administrators or support users.

Test tenant context loss across asynchronous boundaries, cache key collisions, query omissions, tenant deletion, a large noisy tenant, and movement from pooled to isolated resources. Include tenant identity in synthetic tests. Review permission models and database policies before adding new storage systems. Multi-tenancy is not achieved by adding a `tenant_id` column alone; it requires consistent isolation and fair scheduling across every layer.

## Design review

Where is tenant identity established and propagated? Which layers pool or silo, and why? How do caches, jobs, search, and exports enforce tenant scope? What limits prevent a noisy tenant from harming others? Can the control plane provision, recover, and delete tenants consistently?
