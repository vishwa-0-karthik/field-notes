Relational database design starts with durable facts and the rules that connect them. Tables are not merely containers for API response objects. A useful schema identifies entities, stable keys, relationships, constraints, and the transactions that keep business invariants true under concurrent writes.

## Model facts, not screens

Consider a ticket-booking product. Core facts include an event, a seat, a customer, and a reservation. A reservation has its own identity and state; it is not just a `booked=true` flag on a seat because it must record who booked, when a hold expires, and what happened during payment. A normalized first pass might use `events`, `seats`, `customers`, and `reservations` with foreign keys between them.

Write the invariants before the columns. A seat may have at most one active reservation at a time. A reservation must point to an existing seat and customer. A confirmed reservation must preserve the price that was accepted, even if event pricing changes later. Some rules can be represented by `NOT NULL`, `CHECK`, `UNIQUE`, and foreign key constraints. Others require a transaction or carefully designed partial unique index. Database constraints protect against races and alternative write paths that bypass application checks.

| Fact | Likely key | Important constraint |
| --- | --- | --- |
| Event | `event_id` | Valid start time and owner |
| Seat | `seat_id` | Unique label within event |
| Reservation | `reservation_id` | References seat and customer |
| Payment attempt | `attempt_id` | Idempotency key unique in scope |

## Choose key and relationship semantics

Use stable identifiers that do not change when a display name changes. A seat label such as `A-12` is meaningful within an event, but may not be globally unique. A compound uniqueness rule `(event_id, seat_label)` captures that domain fact. Foreign keys prevent dangling references, but deletion policies need thought: deleting a customer record may be legally required, while a financial transaction might need retained non-personal audit data. Decide whether to restrict, cascade, anonymize, or archive rather than accepting defaults blindly.

Many-to-many relationships usually need a join table that can carry its own facts. An event may have many organizers and an organizer may manage many events; `event_organizers` can store role and assignment time. If the relationship has lifecycle or attributes, treating it as an explicit entity often clarifies the model.

## Design transactions around invariants

Two customers can click the same seat at once. The application may check availability, but both checks can observe “free.” The write must resolve the race using a lock, conditional update, exclusion or uniqueness rule, or serializable transaction appropriate to the database. Return a clear conflict to the loser. A transaction should include all local changes that must commit together, such as reservation and audit record. External payment cannot be covered by a local database transaction, so the workflow needs explicit pending states and recovery.

Normalization reduces duplication and update anomalies, but it is not a ban on derived data. A read-heavy seat map may use a materialized projection or cache while the reservation table remains authoritative. Keep derived views rebuildable. Denormalize only after identifying a query or latency need and deciding how updates propagate.

## Validate with real queries

List the important operations: available seats for one event, a customer's upcoming reservations, and one reservation by ID. Design indexes for those access paths and test representative row counts. A clean schema that needs a full scan for every common operation is not finished. Conversely, adding an index to every column increases write and storage cost. Use query plans and measurements to refine the first model.

## Design review

What facts must survive independently? Which rules are enforced by the database even when two writers race? Which data is authoritative, and which is a projection? Can you explain each deletion rule and common query path?
