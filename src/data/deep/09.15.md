Did-you-mean suggests a corrected query when the typed text may contain an error. It should preserve user intent rather than always choosing the nearest dictionary word. A proper name, product code, or new brand may look misspelled to a general dictionary. The service must generate plausible candidates, rank them in context, and decide whether to show a suggestion or search with it automatically.

## Generate candidates efficiently

Edit distance counts insertions, deletions, substitutions, and sometimes transpositions needed to change one string into another. Comparing a query token against every term in a large vocabulary is expensive. A k-gram index maps short character sequences to vocabulary terms that share them; use it to narrow candidates, then compute edit distance on that small set. Stanford's retrieval text describes both methods. Limit correction distance by token length: changing one character in a three-letter word is much riskier than in a fifteen-letter word.

Index corpus terms or a curated query vocabulary with frequencies. Corpus frequency alone can prefer a common but irrelevant word; query-log frequency can include repeated typos. Add a domain dictionary for product names, acronyms, and identifiers. A candidate should remain compatible with the user's language and keyboard layout. For multiword queries, generate only a bounded number of alternatives per token to avoid combinatorial explosion.

## Rank whole-query meaning

Context can distinguish `form` from `from` in a phrase even though both are valid words. Evaluate the likelihood of the complete corrected phrase using term co-occurrence, language-model evidence, or actual search result quality. Elasticsearch offers term and phrase suggesters for these different stages. Keep the original query's strong matches as evidence against changing it. A correction that yields many results is not automatically better; those results may all be off topic.

Choose presentation based on confidence. For a low-confidence alternative, show “Did you mean ...?” as a link and retain original results. For a high-confidence correction of a zero-result query, a product may search the corrected form but clearly say so and offer a way to return to the original. Never silently alter an exact SKU, quoted phrase, or person name. Preserve both typed and effective queries in the result context so pagination and analytics use the same interpretation.

## Evaluate and operate the feature

Create test queries with typos, valid rare terms, multilingual words, names, and identifiers. Measure correction precision, missed corrections, result quality after correction, and user acceptance. False corrections are particularly costly because they can hide the intended target. Monitor latency and candidate count; spelling work should not make every ordinary search slow. Cache frequent corrections with an analyzer and vocabulary version in the key.

When the vocabulary changes, refresh correction data alongside the search index. A new product name should not be “corrected” to an older competitor. Store only the query data needed to improve correction, with appropriate privacy controls and retention. An explainable candidate list makes it easier to diagnose an embarrassing suggestion before it becomes a repeated user experience.

## Design review

How are candidates generated and bounded? Which exact strings are protected? What evidence chooses a whole-phrase correction? When does the UI auto-search versus offer a link? How are false corrections measured and rolled back?
