Partitioning divides a dataset into smaller pieces according to a key or range. Sharding commonly means placing those pieces across independent database nodes. The purpose may be faster bounded queries, manageable retention, storage capacity, or distributed write throughput. A partition scheme is only useful when the application's important operations can find and work within the right pieces.

## Choose the key from access patterns

For a multi-tenant invoice system, `tenant_id` is a plausible shard key because most reads and writes belong to one tenant. A request can route directly to that tenant's shard. A global report across all tenants becomes a fanout or analytical pipeline. If the product frequently transfers invoices between tenants in one transaction, the key may be a poor fit. Write down the common queries and transaction boundaries before choosing placement.

Time partitioning is different. A log table divided by month makes time-bounded queries and retention easier: old partitions can be detached or dropped. But a lookup by event ID without a time hint may inspect many partitions. A hash key distributes IDs evenly but destroys natural time locality. Some systems combine levels, such as tenant then month, when both dimensions matter. Every extra dimension creates more operational metadata and routing complexity.

| Strategy | Main benefit | Main drawback |
| --- | --- | --- |
| Range by time | Efficient retention and time scans | Current range can be hot |
| Hash by tenant | Spreads many tenants | Large tenant remains hot |
| Hash by object ID | Even point lookups | Cross-object queries fan out |
| Directory/map | Flexible placement | Metadata service and map consistency |

PostgreSQL describes declarative table partitioning as splitting one logical table into physical pieces, with partition pruning for queries that constrain the partition key. That is useful even on one database server, but it does not add machine-level capacity by itself. Moving partitions to different machines introduces routing, replication, migration, and cross-shard transactions.

## Plan for rebalancing before it is urgent

A key-to-shard mapping changes when nodes are added or one node grows too large. With fixed `hash(key) mod N`, changing `N` can remap much of the data. Logical partitions decouple key assignment from physical nodes: many logical shards are mapped to machines, and a subset can move at a time. Migration needs a sequence: copy existing data, capture concurrent writes, verify counts and checksums, switch routing, then retire the old copy. Reads and writes during cutover must have one authoritative owner.

Global constraints become harder. A database unique index can enforce an email address within one shard, not necessarily across all shards. A globally unique ID generator, a directory service, or a separate uniqueness authority may be needed. Multi-shard transactions add coordination or application workflows. These costs should be justified by measured limits, not by a desire for a distributed diagram.

## Measure balance as work, not record count

Two shards with equal rows can have very different traffic. A single active tenant may dominate writes and lock contention. Track per-partition bytes, reads, writes, latency, and growth. Set thresholds for split or move operations and test them before the largest tenant reaches an emergency state.

## Design review

Can every hot operation name its partition key? Which operations fan out? What happens when one tenant or time range is much hotter than others? How does a live migration preserve one authoritative writer?
