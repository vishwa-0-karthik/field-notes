Consistent-hashing load balancing routes a key to a backend so that the same key tends to reach the same place, while adding or removing a backend moves only part of the key space. It is useful for cache locality and some partitioned state. It is not automatically the best way to spread ordinary stateless requests.

## Why ordinary modulo is disruptive

Suppose a cache has four nodes and assigns a product with `hash(product_id) mod 4`. Adding a fifth node changes the divisor. Many product keys map to different nodes, causing a broad cache miss storm even though the underlying catalog did not change. A consistent-hash scheme maps both keys and nodes into a common hash space and assigns each key to a nearby node. When a node joins, it takes over a portion of neighboring keys rather than remapping almost everything.

Karger and collaborators introduced the idea for distributed web caching. The precise movement depends on the scheme and balance, but the useful property is stability as membership changes. Implementations often use multiple virtual positions per physical node to smooth uneven ranges. More virtual positions improve balance at the cost of a larger routing table and more movement bookkeeping.

| Routing method | Membership change | Typical fit |
| --- | --- | --- |
| Round robin | No key affinity | Stateless request replicas |
| `hash(key) mod N` | Broad remapping when `N` changes | Fixed small shard count |
| Consistent hash ring | Limited key movement | Cache or partition locality |
| Rendezvous hashing | Limited movement without ring traversal | Key-to-node assignment |

## Choose a stable key

The routing key must correspond to the state you want to keep local. Hashing a client IP can put unrelated users behind one NAT on the same backend and send one user's requests to different backends as their network changes. Hashing a session ID or cache key may better reflect locality. The key must be available at the load balancer and should have high enough cardinality to distribute work.

Hot keys remain a problem. If one celebrity account receives half the traffic, every request for that key can land on one node, even if the hash space is otherwise balanced. Replication, key splitting, or an application-level hot-key strategy may be necessary. Consistent hashing balances *keys* probabilistically; it does not guarantee balanced work when key popularity is skewed.

## Handle membership and failure explicitly

All routers must agree on the active node set and hash function. If two gateways have different membership views, the same key may reach different backends during a transition. That can be acceptable for a disposable cache but dangerous for state that requires one writer. For durable shards, define rebalancing, data migration, ownership handoff, and how writes behave during a node failure. A routing algorithm alone does not move bytes or prevent split-brain writes.

In a cache, a failed node's keys move to successors and miss until warmed. Plan for that temporary backend load. In a sticky application session, a failed node may lose local state; consistent routing does not make it durable. NGINX exposes a `hash ... consistent` upstream mode, but its presence should not be mistaken for a complete data-partition protocol.

## Design review

What exact key is hashed, and why does it represent useful locality? What fraction of work moves on a node addition or failure? Are key sizes and request rates evenly distributed? Who moves or reconstructs state when ownership changes?
