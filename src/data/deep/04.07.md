Consistent hashing assigns keys to a changing set of nodes while minimizing remapping when membership changes. In a storage system, it is a placement mechanism: it tells a router or coordinator which node or token range owns a key. It does not by itself replicate data, transfer bytes, ensure one writer, or make a hot key less hot.

## Compare with modulo placement

With `hash(key) mod 4`, four nodes each own some keys. Adding a fifth node changes the divisor; many existing keys now map elsewhere. If those keys hold durable data, the system must move a large fraction of the dataset before routing is correct. Consistent hashing maps keys and node positions into one circular hash space. A key belongs to the next owner clockwise. Adding a node takes a bounded interval from an existing owner, leaving most keys where they were.

The original Karger paper introduced this idea for distributed caching. For durable storage, the placement rule becomes only one part of a larger protocol. Cassandra documents a partitioned model using a variant of consistent hashing and replication across nodes. A production design also needs a consistent membership view, replica selection, handoff, repair, and failure handling.

| Property | What consistent hashing helps | What it does not solve |
| --- | --- | --- |
| Node addition | Limits remapped key range | Copies data automatically |
| Node failure | Identifies new owner/replicas | Guarantees no lost writes |
| Balance | Distributes many random keys | Splits one extremely hot key |
| Routing | Stable key-to-node rule | Keeps all routers in sync |

## Smooth imbalance with virtual positions

A few randomly placed physical nodes can own uneven arc lengths. Assigning each node many virtual positions, often called tokens or virtual nodes, reduces variance and makes it easier to distribute a node's share across the ring. Weights can give stronger machines more positions. The tradeoff is more routing metadata and potentially more transfer streams during rebalancing. Measure work distribution, not merely key counts: a node with a popular key may be overloaded despite equal token ranges.

Rendezvous hashing and jump consistent hashing are related alternatives with different implementation properties. Jump hashing is compact when buckets are numbered in a controlled sequence; a ring may be more flexible for weighted physical nodes and token ranges. Choose an algorithm whose membership and migration behavior the team can operate. The exact formula matters less than a tested handoff protocol.

## Make ownership transitions safe

When a node joins, old and new owners may temporarily disagree. A safe transition can mark a range as moving, copy a snapshot, stream later writes, verify state, and then switch the authoritative routing version. Clients or gateways must not blindly use stale maps for writes. A lease, epoch, or fencing token can prevent an old owner from accepting writes after handoff. If the store is replicated, define which replicas acknowledge during the move and how missed writes are repaired.

For a cache, a short period of misses may be acceptable; keys can be repopulated from authority. For durable data, the same loss is unacceptable. That difference should drive how much coordination the placement change requires.

## Design review

How do all routers learn the same membership version? What data moves when a node is added? Who may accept writes during handoff? How does the system detect and repair missing replicas? What happens to a single key that owns half the traffic?
