A load balancer sends incoming work to one of several eligible backends. It helps use capacity and survive individual target failures, but it does not make a stateful application automatically redundant. Correctness depends on health checks, routing policy, connection behavior, and where the application's state lives.

## Choose a layer and a policy

A network load balancer can forward connections using transport-level information. An application load balancer can inspect HTTP properties such as host and path and route to a target group. Choose the layer from requirements: simple TCP pass-through, TLS termination, host-based routing, WebSocket support, or request-level metrics. Avoid introducing protocol inspection when the application needs only connection distribution.

Common target-selection policies include round robin, least outstanding requests, and weighted routing. Round robin is straightforward when requests cost about the same. If some requests take far longer, distributing request counts evenly can still overload one target; an outstanding-work signal may fit better. Weights allow gradual rollout or different instance sizes. No policy can fix a backend that is slow because every request hits the same saturated database.

| Policy or feature | Useful when | Watch for |
| --- | --- | --- |
| Round robin | Similar request costs | Unequal long-running work |
| Least outstanding | Variable request duration | Delayed or noisy load signal |
| Weighted targets | Canary or mixed capacity | Weight mistakes and skew |
| Sticky sessions | State tied to one target | Failover loses that affinity |

## Make health checks meaningful

A process may answer `/health` while unable to reach its required database or while warming a cache. Define separate liveness and readiness signals. Liveness asks whether the process should be restarted; readiness asks whether it should receive new work. A readiness check should reflect the dependencies needed for the operation being routed, but avoid turning a transient shared dependency glitch into a simultaneous removal of every backend.

Health transitions should have thresholds. One failed probe may be a network blip; repeated failures can mark a target unhealthy. Similarly, a recovering target may need several successes before admission. Google Cloud's load-balancing documentation describes health probes and thresholds that determine target eligibility. Test how quickly the balancer removes a failed target and whether clients retry safely during that interval.

## Account for connection and state behavior

Existing long-lived connections may remain on a target even after new requests are routed elsewhere. During deployment, use connection draining so in-flight work can finish within a deadline. For WebSockets or streaming RPCs, one connection can carry much more work than one short request; connection count alone may be a poor load metric.

If sessions are stored only in process memory, routing a user to a new target can break the session. Prefer shared or client-held state when appropriate. Sticky routing can be a temporary bridge, but it reduces balancing freedom and does not survive target loss. Files written to local disk have the same problem: another replica cannot serve them without shared storage or replication.

The load balancer itself also needs redundancy and observable failure behavior. Measure target health, request distribution, 5xx rates, connection errors, and target latency separately. A rising edge 5xx rate with healthy target processes may indicate bad listener rules, TLS issues, or an exhausted connection limit.

## Design review

What qualifies a target to receive work? How quickly is a failed target removed? Can any healthy target answer any request correctly? During a rollout, what happens to an in-flight upload or long-lived stream?
