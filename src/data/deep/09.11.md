Search index sharding divides documents and their inverted indexes across machines. A query often fans out to several shards, each returns its local top candidates, and a coordinator merges them into one result page. Sharding adds storage and throughput capacity, but each query now pays coordination, network, and tail-latency costs. Start with a measured limit on one shard and a corpus growth estimate, not a large shard count by default.

## Choose routing and replication

Hashing a stable document ID spreads ordinary documents across primary shards. Routing by tenant can keep one tenant's search on fewer shards, but a large tenant may become a hot shard. Elasticsearch's routing documentation shows that custom routing can narrow a query to selected shards; it also requires using the same routing value for updates and deletes. Decide whether the workload mostly searches within a tenant or across the whole corpus. A global query still needs to contact every relevant shard.

Replicas provide another searchable copy and help availability or read throughput. They do not split a single shard's data; increasing replicas multiplies storage and indexing work. Place copies on separate failure domains and test loss of a node during heavy query load. Watch shard size, count, disk headroom, heap use, and recovery time. Too many tiny shards consume resources even when their documents are few.

## Merge top-K without losing good results

Each shard can return its top K for a query, and the coordinator merges them by score. This works when scores are comparable and each shard provides enough candidates. Shard-local term statistics can cause lexical score differences; an optional global-statistics phase may improve comparability at extra latency. Deep pagination is costly because each shard may need to rank and return many earlier hits. Use a stable sort key and a search-after cursor or point-in-time view for long result walks rather than asking for page 10,000 by offset.

Filters and aggregations complicate the plan. A category filter may eliminate most candidates on one shard but almost none on another. A distributed count or facet may require partial aggregation from all shards and careful merging. If a shard times out, choose whether to return partial results clearly marked or fail the request; silently presenting an incomplete top K as complete misleads users.

## Plan changes and failure recovery

Changing a primary shard layout can require reindexing or a supported split/shrink operation. Model the migration before the initial index grows too large. During relocation, the cluster moves shard copies and consumes network and disk; leave headroom. A rolling node failure can increase query load on surviving replicas, so test p99 latency and recovery time under a missing node. Backups or snapshots remain necessary: replicas also replicate accidental deletions.

Measure per-shard query latency, rejected requests, indexing rate, segment and merge pressure, replica lag or health, and coordinator merge time. An average shard can look healthy while one hot tenant determines the p99. Use representative queries and distribution of document sizes to benchmark routing choices. The goal is enough parallel capacity with a bounded fanout per request.

## Design review

Why is one shard insufficient? Which key distributes writes and narrows reads? Can one tenant dominate a shard? Are cross-shard scores and aggregations correct enough? What happens to p99 and recovery time when a shard host fails?
