# Live streaming, WebRTC, and latency

“Live” describes a range of latency budgets. A broadcast where viewers can be tens of seconds behind can use segmented HTTP delivery and scale through caches; an interactive call where participants must react within a few hundred milliseconds needs a real-time media path. Picking the protocol follows the product's latency and audience shape, not the label “live.” WebRTC supports interactive media and data exchange; HLS or DASH generally serves large one-to-many audiences more efficiently, often with higher latency.

## Broadcast pipeline versus interactive path

A broadcast pipeline ingests a contribution feed, normalizes or transcodes it, packages short segments and a frequently updated playlist, then distributes those objects through a CDN. The player requests the playlist and segments over HTTP. Shorter segments and more frequent playlist updates can reduce delay, but increase request rate, encoding constraints, and sensitivity to jitter. Low-latency variants use partial segments or chunked transfer patterns and require compatible packagers, CDNs, and players. The end-to-end delay includes capture, encode, ingest, transcode, packaging, origin/CDN propagation, player buffer, and decode. Measure glass-to-glass latency rather than optimizing only segment duration.

For interactive communication, peers first exchange session descriptions and network candidates through an application signaling channel. ICE gathers candidate paths and checks connectivity; STUN helps discover reachable mapped addresses, while TURN relays traffic when direct paths fail. A relay increases bandwidth cost and can add latency, but improves connectivity across restrictive NATs and firewalls. The media path should adapt to packet loss, jitter, and available bandwidth; congestion control and pacing matter as much as codec selection. A selective forwarding unit (SFU) receives participant streams and forwards selected layers to recipients, which usually scales group calls better than every participant sending to every other participant. A mixer decodes and recombines streams but has different compute and layout tradeoffs.

## Match topology to audience

Small interactive groups can use an SFU with simulcast or scalable video coding so each recipient receives an appropriate layer. Large audiences are often better served by a broadcast pipeline and CDN, or by a hybrid where a real-time host feed is repackaged for mass delivery. A WebRTC viewer fanout tree still consumes relay and egress bandwidth and requires session-aware infrastructure; it does not gain the same static segment caching behavior as HTTP delivery. A hybrid can send low-latency WebRTC to hosts and moderators while a larger HLS audience accepts delay.

Capacity planning should include ingest bitrate, transcode profiles, egress per viewer, TURN relay percentage, regions, and failover headroom. Keep signaling separate from media transport: signaling can reconnect or move between servers while an established media path has its own state. Regional placement reduces round-trip time; however, failover can interrupt a call if media state cannot migrate. Track join success, time to first frame, glass-to-glass delay, jitter, packet loss, rebuffering, relay ratio, and bitrate by region and device.

Test UDP blocked, symmetric NAT, relay overload, packet loss, encoder slowdown, stale playlists, and CDN propagation delays. The product should define a latency target and audience size so architecture can choose between cached segments, SFU forwarding, or a deliberate hybrid.

## Design review

What is the latency budget from capture to display? Is the audience interactive or primarily watching? What share of calls require TURN? Does the broadcast pipeline have a player buffer that dominates delay? Which metrics reveal the user-perceived experience?
