A logical design describes responsibilities and information flow without committing too early to machines, cloud products, or deployment counts. It answers “which part makes this decision?” before “where does this process run?” The distinction is useful because the same logical design may begin as modules in one application and later run as several services.

## Derive components from the workflow

Consider a meeting-booking service. A person searches open slots, chooses one, pays if required, and receives confirmation. The logical components are a search/read model, booking policy, reservation writer, payment adapter, and notification worker. These are responsibilities, not necessarily separate deployables. The first version could place them in one codebase with one database.

Draw two flows. The **command flow** changes state: choose slot → verify current availability → reserve it atomically → record an event → confirm to the caller. The **query flow** reads state: find candidate slots → apply filters → return results. A query view may lag briefly, but the reservation writer must make the final conflict decision. If you only draw the happy read path, you may accidentally let two customers book the same slot.

For each arrow, name the data that crosses it. “Booking API to database” is too vague. “Create reservation with customer ID, slot ID, request ID, and expected price” exposes identity, concurrency, and replay requirements. Add a response contract: reservation ID, state, and error codes such as `SLOT_TAKEN` or `PAYMENT_PENDING`.

## Choose the source of truth

List the durable facts and the component allowed to change them. For booking, a reservation row or transactional record is authoritative for slot ownership. A search index is a derived view. A cache may speed availability queries, but it cannot alone grant the slot. This prevents a common mistake: treating every copy of data as equally authoritative.

| Data | Authority | Derived reader | Allowed lag |
| --- | --- | --- | --- |
| Slot reservation | Booking store | Search index | A few seconds, if writer rechecks |
| Payment state | Payment ledger/provider record | Booking summary | Depends on checkout promise |
| Confirmation message | Notification attempts | Customer inbox view | Usually asynchronous |

The allowed lag is a product decision. If customers can tolerate a stale search result followed by “slot just taken,” the search path can be fast and eventually updated. If the product promises every shown slot is bookable, the read path needs stronger coordination and will cost more.

## Mark synchronous and asynchronous boundaries

Keep the synchronous path to decisions required for the immediate response. The booking request must know whether it owns a slot. Sending an email can happen after commit. But “async” does not mean “forget”: the booking transaction must leave durable work for a worker, commonly by writing an outbox record with the reservation. Otherwise the process can commit a reservation, crash before publishing the message, and never send confirmation.

Failure edges belong on the diagram: payment timeout, database unavailable, duplicate request, message worker retry. For each edge, decide whether to reject, retry, compensate, or return a pending state. A simple state machine—`PENDING`, `CONFIRMED`, `CANCELLED`—is often more precise than a single boolean `booked`.

## Refine into physical architecture later

After the logical responsibilities and contracts are clear, choose deployment topology from load, fault isolation, team ownership, and operational constraints. The search reader might require many replicas while the booking writer needs serializable conflict control. That is a reason to separate scaling paths. It does not require independent services on day one. Fowler's monolith-first discussion is a useful reminder that service boundaries are expensive when the domain is still changing.

## Design review

Trace one booking through the diagram and identify the exact commit point. Then remove any one component. Can you predict whether the user receives a success, a failure, or a pending result, and whether the next retry is safe?
