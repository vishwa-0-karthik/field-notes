WebSockets, server-sent events (SSE), and long polling all deliver updates to a client, but they have different communication shapes. Choose from the traffic pattern and recovery contract. A dashboard that only receives status changes may fit SSE; a collaborative editor with frequent client and server messages may fit WebSockets; a constrained environment may need long polling. None of these transports automatically provides durable delivery or authorization.

## Compare the wire behavior

WebSocket begins with an HTTP handshake and then uses a bidirectional framed connection defined by RFC 6455. Both sides can send messages without a new HTTP request. SSE keeps an HTTP response open and streams text events from server to browser. The browser's `EventSource` API handles reconnection and can send the last event ID; client writes use ordinary HTTP requests. Long polling sends an HTTP request that the server holds until an update or timeout, then the client sends another. It works with familiar HTTP infrastructure but repeats request setup and can create a large number of held requests.

For all three, account for proxy timeouts, mobile networks, idle connections, load-balancer limits, and browser behavior. SSE is simple for one-way updates and uses standard HTTP response semantics, but browser connection limits can matter under some HTTP versions and deployment patterns. WebSockets have application-level ping/pong and require infrastructure configured for long-lived upgraded connections. Long polling often works through restrictive intermediaries, at the cost of more header traffic and repeated state coordination.

## Add a delivery protocol above transport

Give each update a topic and monotonic event ID or version. A client reconnects with its last applied ID, and the server either replays from a bounded log or instructs it to fetch a snapshot. SSE has a built-in `id` field and `Last-Event-ID` behavior described by MDN, but the server still decides whether that ID is authorized and replayable. For WebSockets, define the equivalent resume message. For long polling, include a cursor in each request and response.

Backpressure differs. A fast WebSocket producer can fill a slow client's outbound buffer; cap it and resync or disconnect. SSE writes can also block on slow clients, while long polling naturally limits outstanding responses but may accumulate server-held requests. Coalesce state updates when only the latest value matters. For a chat transcript where every message matters, retain the messages and use the transport only to notify clients that new durable records exist.

## Choose for the whole system

Estimate simultaneous clients, update rate, client write rate, average payload, and reconnect storms. SSE plus POST can be simpler than WebSockets when client writes are rare. WebSocket may reduce round trips when both sides send frequently. Long polling can be a compatibility fallback. Support one primary protocol well before adding multiple transports, because each adds reconnection and observability paths.

Measure time to first update, delivery lag, connection churn, missed-version repairs, bytes per client, and server resources per connection. Test suspend/resume on mobile, proxy idle timeout, authentication expiry, and server failover. The deciding question is what application state the client can reconstruct after interruption, not only which transport has the lowest idle overhead.

## Design review

Are updates one-way or bidirectional? How does a reconnect identify missed data? What is the behavior under a slow client? Which proxies and clients must be supported? Is the stream a notification of durable state or the sole record of events?
