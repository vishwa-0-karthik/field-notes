A custom binary file format is a contract between writers today and readers years from now. It can save space and permit fast seeks, but one ambiguous length or unvalidated offset can make a file unreadable or unsafe to parse. Design the format as carefully as a network protocol: framing, versions, checksums, bounds, and compatibility all need explicit rules.

## Make a record self-describing enough

A simple file can begin with a magic sequence, format version, byte-order marker, and optional feature flags. Each record then has a bounded length, type, payload, and checksum. The length lets a reader skip unknown record types or find the next record; the checksum detects damaged or torn data. If records are compressed, specify whether the length covers compressed bytes and whether the checksum covers the stored or decoded form. Do not rely on a compiler's native struct layout, which can change with padding and architecture.

SQLite's published database-file specification illustrates the discipline: it defines a magic header, page size, byte order for multibyte fields, page headers, and record encodings down to byte offsets. A custom format needs less complexity if the workload is simpler, but it still needs equally unambiguous decoding rules. Write example byte sequences and cross-language fixtures, not just pseudocode.

## Validate before allocating or seeking

A reader should reject an impossible record size before allocating memory. Check that offsets and lengths fit within the actual file, and check integer addition for overflow. Limit nesting depth and decompressed size so a small corrupt file cannot exhaust memory. A checksum detects accidental corruption but does not authenticate malicious input; use a cryptographic authentication mechanism when files come from untrusted producers.

If the format has an index or footer, store its location in a fixed header or at a known trailer position. Validate that it points to a complete index of the expected version. A sparse index can find a nearby block, then scan within it. If a crash happens while writing the footer, the file must remain clearly uncommitted or recoverable. One approach is to write a new file completely, sync it, then publish it through a separate manifest.

## Evolve the format without guessing

Versioning is not merely incrementing a number. Decide whether a new reader can read old files and whether an old reader can reject new files cleanly. Tagged fields let readers skip unknown optional data, while changing the meaning of an existing field may require a new record type. Keep required feature flags separate from optional flags. A migration may rewrite files in the background, so mixed generations must coexist during rollout and rollback.

Test with golden files from every supported version, truncations at every byte boundary, corrupted checksums, oversized lengths, and random malformed inputs. Fuzz the parser if untrusted or long-lived files are involved. Monitor decode errors by version and offset. Keep a small inspection tool that prints headers and records without modifying the file; it is invaluable during incident response.

## Design review

Can two independent implementations decode the same bytes? What does a partial final write look like? Are all sizes and offsets bounded before use? How will old data be read after a format upgrade?
