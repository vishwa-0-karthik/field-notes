# Case: Stripe's idempotency keys

Stripe's idempotency key pattern addresses a classic distributed-systems ambiguity: a client sends a mutating request, the server performs the side effect, and the response is lost. The client cannot distinguish “server never received it” from “server succeeded but the network failed.” Retrying with a new operation can create a duplicate charge or object. A stable client-generated key lets the server recognize that a retry refers to the same logical operation.

## The protocol boundary

The client generates a high-entropy identifier for one intended operation and sends it in an `Idempotency-Key` header with the request. The server scopes the key to the relevant account and endpoint, associates it with a fingerprint of the request parameters, and stores the first result. A retry with the same key and same parameters can return the stored result rather than performing the side effect again. Reusing the same key with different parameters should be rejected because it is likely a client bug. Keys must be unique for each intended operation; two distinct purchases should not reuse one key.

Stripe's API documentation describes storing the first status code and response body once endpoint execution begins, including failure responses, and comparing parameters on reuse. It also describes retention and concurrent-request behavior. The exact retention period and boundary are product contract details that clients must understand: after a key is pruned, a later reuse may be treated as a new operation. Validation errors before execution and concurrent conflicts have different persistence behavior from a started operation. Teams should not assume every idempotency implementation has identical semantics.

## What idempotency does not solve

The key does not create a distributed transaction with a payment processor, message broker, or database. The server still needs a durable state machine and a recovery path if it crashes between recording intent and making the external call. A robust implementation can persist an operation row with a unique key, mark it in progress, make the downstream request with an appropriate idempotency token if supported, and save the response. If downstream state is uncertain, query or reconcile rather than issuing a fresh request. Concurrent requests for one key need a single winner or a well-defined wait/replay response.

Idempotency is also not exactly-once delivery. It provides deduplication within a defined key scope, storage duration, and set of side effects. Events emitted after a successful request still need outbox semantics and consumer deduplication. Clients should retry with exponential backoff and jitter, preserving the same key across retries of the same action. They should create a new key only for a new user intent.

## Design lessons

For a mutating API, define key scope, parameter comparison, first-result behavior, concurrent request behavior, retention, and what errors are stored. Make the operation record durable before exposing an ambiguous result. Test timeout after side effect, duplicate simultaneous requests, key reuse with changed parameters, process crash, and retry after retention. Stripe's documented contract is one concrete implementation; the broader design principle is stable operation identity across unreliable networks.

## Design review

What constitutes one logical operation? How are keys scoped and retained? What happens when identical calls arrive concurrently? Is the external side effect itself idempotent? How does an operator reconcile an operation stuck in progress?
