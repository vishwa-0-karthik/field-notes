# Remote file sync design

File synchronization keeps multiple devices convergent while users edit offline, reconnect intermittently, or make concurrent changes. The service should define what “same file” means before choosing its protocol. For ordinary documents, synchronization can exchange whole-file versions or changed blocks; for collaborative structured documents, operation-based CRDT or OT semantics may be needed. A sync engine should make durable versions, conflict behavior, and deletion visible rather than silently overwriting data.

## Model identity, versions, and change feed

Assign each logical file a stable file ID independent of its path. Paths and folder membership can change without changing content identity. Maintain a monotonically increasing server revision or opaque version token, plus metadata such as size, content hash, modification time, and parent folder. Devices remember the last acknowledged cursor or revision. On reconnect, they ask for changes after that cursor; the server returns a bounded ordered change feed with tombstones for deletions and moves. Cursors need retention and expiration rules: if a client is too far behind, require a rescan or snapshot instead of returning an incomplete history.

For each local edit, the client creates an upload intent linked to the base version it edited. The server stores the new content as an immutable blob, then commits metadata using compare-and-set against that base version. If the current version still matches, publish the new revision. If not, preserve both candidates and report a conflict, or apply a domain-specific merge. Never accept “last writer wins” accidentally based on unsynchronized device clocks. A simple conflict copy is often safer than data loss; better merge semantics can be layered for formats where a merge is valid.

## Efficient, resumable transfer

Small files can transfer as whole objects. Large files benefit from chunking and content hashes so unchanged blocks can be reused. Uploads should be resumable and idempotent: each block has a stable content identity, retries do not create duplicate logical changes, and the manifest commits only after all required data exists. Download clients can ask for missing blocks and verify hashes before assembling the file. This reduces bandwidth but introduces metadata, garbage collection, and consistency work; simple whole-file transfer may be preferable when files are small or rarely edited.

Treat the change feed and blob store as separate planes. Metadata transactions decide which version is current; blobs are immutable and may arrive before they are referenced. A background collector removes unreferenced blobs after a safety interval and after accounting for in-flight upload sessions. Keep metadata durable and regionally replicated according to the product's recovery objective. If the feed is unavailable, devices can continue local edits and retry; use bounded exponential backoff and show sync state to users.

Measure sync lag, time to converge, conflict rate, bytes transferred per logical byte changed, cursor resets, failed hash verification, and unreferenced data. Test simultaneous edits, move plus edit, delete while offline, replayed upload, stale cursor, partial chunk arrival, and client clock skew. A sync contract should specify conflict outcomes and retention, since these affect user trust more than transfer speed.

## Design review

What stable identity survives a rename? How does a client resume from a durable cursor? Which concurrent edits merge, and which produce a conflict copy? Are blobs immutable and verified? How does garbage collection avoid deleting in-flight or referenced content?
