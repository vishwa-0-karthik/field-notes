# Case: how Discord stores trillions of messages

Discord's 2023 engineering post describes the evolution of its message store as data grew from billions to trillions of messages. It reports moving from MongoDB to Cassandra early in the product's history, then operating a Cassandra cluster with 177 nodes by early 2022. The team described high operational toil, unpredictable latency, hot partitions, and compaction pressure. The case is valuable because it shows that a horizontally scalable database can still become difficult when partitioning and maintenance no longer match workload shape.

## Access pattern drove the partitioning pain

Discord's described message key used channel plus a fixed time bucket as the partition, with chronologically sortable Snowflake IDs. This supports fetching a channel's messages within a time range. But channels differ enormously in activity. A very large community can concentrate read and write load on one channel-bucket partition. Because quorum reads involved the replicas serving that partition, a hot partition could slow related traffic and create broader latency. The post also describes compaction backlog and operational work to remove nodes from traffic while they caught up.

The lesson is not simply “choose smaller time buckets.” Smaller buckets bound partition size but increase the number of partitions and fanout for long history reads. Larger buckets reduce partition count but increase skew and storage maintenance. The access pattern should include hot guilds, channel history, search, retention, and cold-history behavior. Message IDs and partition keys need to support the dominant page query without allowing one channel to monopolize a shard.

## Migration as a multi-stage operation

Discord experimented with ScyllaDB and migrated most databases by 2020, leaving the message cluster for later because of its size and operational risk. The engineering post then describes changing architecture and building data services to serve the new store, followed by a large migration. A migration of trillions of records cannot be treated as a one-time copy: it needs a consistent snapshot or dual-write/change stream, backfill progress tracking, validation, read-path readiness, and a cutover plan that keeps old and new data aligned. The post's detailed implementation should be consulted for exact steps; this summary generalizes the design requirements.

Discord later reported splitting message workloads into data-service cells and using ScyllaDB to improve operations and latency. These are documented outcomes from its post, while the recommendation to evaluate hot-key distributions and migration checkpoints is a general engineering inference. A database change is successful when it reduces toil as well as meeting throughput, and when common queries remain efficient after sharding.

## Lessons and limits

Measure query shape and skew, not only total rows. Model hot partitions and maintenance operations before choosing a NoSQL store. Keep the database layer behind a data service so storage changes do not force every application client to change. Build migration tooling before a multi-trillion-record move becomes urgent. Track p99 by partition, compaction lag, repair backlog, migration parity, and on-call pages. The right key is workload-specific; channel, user, time, and search use cases may need separate layouts.
