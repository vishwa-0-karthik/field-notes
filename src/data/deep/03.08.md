A write-ahead log (WAL) records changes before modified data pages are written to their final locations. It is central to crash recovery: after a process or machine failure, the database can replay durable log records to restore changes that had not yet reached table and index files. WAL also supports replication and point-in-time recovery, but each use has separate retention and failure considerations.

## Trace one commit

Suppose a transaction inserts an order and updates inventory. The database changes in-memory pages and appends log records describing the modifications. Before it acknowledges a durable commit, the relevant log must be flushed according to its commit policy. The data pages can be written later. If the process crashes after acknowledgment but before those pages are flushed, recovery starts from a checkpoint and replays the log to restore the committed state.

The ordering rule matters: if a data page reached disk before its log record was durable, a crash could leave a change the recovery process cannot reason about. PostgreSQL's WAL documentation states that data-file changes are written only after the describing log records are flushed. Sequential log writes and group commit make this cheaper than forcing every modified table page to disk at each commit.

| Component | Role | Failure question |
| --- | --- | --- |
| WAL record | Describes a change | Was it flushed before success? |
| Checkpoint | Limits redo starting point | How much log must replay? |
| Data page | Holds table/index state | Was it written before crash? |
| WAL archive | Preserves history beyond local segments | Can a backup replay to desired time? |

## Separate local durability from disaster recovery

A local WAL flush protects against a process crash and some host failures, depending on storage guarantees. It is not a substitute for backups: accidental deletion, storage loss, or corruption can affect both data and local WAL. A physical backup plus archived WAL can restore to a selected time within the retained log range. Test restore, including the target time, rather than assuming archived files are sufficient.

Replication often streams WAL or related change records to followers. If acknowledgment does not wait for a follower, a primary failure may lose its most recent acknowledged writes when the lagging follower is promoted. If acknowledgment waits for remote durability, write latency and availability depend on that follower. State the exact durability promise and promotion policy.

## Plan for log growth and lag

WAL is not an unlimited queue. A slow replica or broken archive destination can cause old segments to be retained, filling disk. Large bulk updates, index builds, and schema changes can generate substantial log volume. Monitor WAL generation rate, archive failures, replication lag, and available space. Set alarms early enough to intervene without an emergency deletion that destroys recovery options.

Recovery time also matters. Long intervals between checkpoints can mean more replay work after a crash; very frequent checkpoints can increase write pressure. The right settings depend on workload and recovery objective. A design should estimate both data-loss bound and time-to-restore, then verify them in drills.

## Design review

When does the client receive success relative to WAL flush and replica acknowledgment? What can be lost after a process, host, or region failure? Can backups plus retained WAL actually restore to the required point, and how long does replay take?
