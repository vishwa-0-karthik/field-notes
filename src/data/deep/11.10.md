Live commentary combines a durable message timeline with low-latency delivery to people watching the same event. The core challenge is keeping the timeline authoritative while sending updates to many connected clients. A live socket is a delivery path, not the storage layer: viewers who reconnect must still be able to fetch missed comments in the correct order.

## Accept and order messages

Each comment needs an event ID, author, room or event ID, body, server timestamp, and moderation state. A client-generated idempotency key prevents a timeout retry from creating a second comment. Assign a sequence number within the event or room if the UI needs a stable order; wall-clock timestamps from different clients can be skewed. If one room's write rate is too high for a single sequence allocator, partition by subroom or accept a best-effort order with a deterministic tie-breaker.

Persist the comment before broadcasting it. A transaction can insert the message and an outbox event together; a relay publishes after commit. This avoids a client seeing a comment that disappears after a database rollback, and it avoids losing an accepted comment if the broker is temporarily unavailable. Redis Streams or another retained log can also provide ordered IDs and cursor-based replay, subject to its persistence and retention configuration.

## Fan out without overwhelming viewers

Organize connected clients into event subscriptions. A gateway receives each new comment once and sends it to local viewers; a broker or partitioned stream routes it to the gateways that have subscribers. For a huge live event, naive global broadcast multiplies each comment by every connected viewer. Apply room partitioning, regional gateways, and bounded message rates. If the interface can batch comments or briefly coalesce updates, do so during bursts while preserving every durable message in the history.

Send a cursor or sequence with every update. On reconnect, the viewer supplies the last applied cursor and the server replays a bounded range or returns a fresh page with a reset cursor. If the client is too far behind, do not queue hours of stale socket data; give it the latest page and a clear resync point. Slow clients need a bounded buffer and a disconnect path rather than unbounded memory growth.

## Moderate and protect the room

Apply room membership and event visibility on both message submission and subscription. Rate limit per account and per room, detect repeated spam, and allow moderators to hide a comment without rewriting history invisibly. Separate pending moderation from visible messages if the event requires review. Deleted or hidden comments must stop appearing in cached pages and downstream search. A user joining late may see only a time-bounded history window, so define retention and cursor behavior together.

Measure accepted comments per second, write-to-visible delay, replay volume, broker lag, dropped socket updates, moderation queue age, and reconnect rate. Test one extremely popular event, a gateway restart, a broker outage, and a client reconnecting with a stale cursor. The system is correct when durable history remains complete, visible ordering is understandable, and temporary delivery failure can be repaired.

## Design review

What component assigns message order? Is the comment durable before it is broadcast? How does a viewer resume after disconnect? What is the per-room fanout ceiling? How are moderation changes applied to replayed and cached history?
