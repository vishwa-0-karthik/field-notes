A monolith is one deployable application; microservices are independently deployable services communicating across process boundaries. Neither label tells you whether the code is well organized. The central question is where a boundary should live and whether the benefits of remote ownership outweigh the cost of distributed operation.

## Start from domain boundaries

Imagine a commerce product with catalog, checkout, payments, and support. A modular monolith can keep these as packages with explicit APIs and separate data access rules while shipping one artifact. This makes local transactions, debugging, and deployment relatively simple. If several teams later need independent release cycles or the payments workload needs different security and scaling, a service boundary may become valuable.

Splitting by controller or database table is usually weak. A useful boundary contains a coherent business capability and owns the data needed to make its decisions. If every checkout request synchronously calls five services to assemble one transaction, the system may have distributed coupling without meaningful autonomy. Network calls introduce latency, timeouts, partial failures, versioned contracts, and tracing needs that in-process calls do not have.

| Question | Modular monolith tends to help | Separate service tends to help |
| --- | --- | --- |
| Domain still changing? | Refactoring boundaries is cheap | Contract changes become coordinated |
| Teams deploy independently? | Shared release may be acceptable | Independent releases have value |
| Data transaction spans features? | One database transaction is possible | Workflow needs saga or redesign |
| Load profile differs strongly? | Scale whole process | Scale one capability separately |

## Count the operational premium

Each service needs a build, deployment, monitoring, alerting, authentication, capacity plan, and on-call understanding. Cross-service behavior needs correlation IDs, timeouts, retries, and an answer to partial failure. A shared database can erase much of the intended autonomy because every schema change still coordinates teams. Fowler calls this the microservice premium: it can be justified by enough domain and organizational complexity, but it is a real expense.

A monolith can also become painful: long builds, unstable modules, shared database tables, or deployments held hostage by unrelated changes. The remedy may be better internal boundaries before a network split. Enforce module APIs, prevent direct cross-module table reads, and publish domain events within the application if appropriate. This makes a later extraction smaller and helps reveal whether the boundary is real.

## Extract with a migration path

Choose one capability with clear data ownership and a measurable reason for separation. Put an internal interface around it, move callers to that interface, and capture the behavior with contract tests. Decide how data is migrated and how writes are routed during cutover. Avoid simultaneous dual writes without a reconciliation plan; a crash between writes creates divergence. Run the extracted service behind a feature flag or staged traffic shift, then retire the old path when metrics and data checks agree.

The goal is not a predetermined service count. It is to keep change and failure understandable. A small team with a stable product may do better with a modular monolith for years. A large organization with clearly separate capabilities may benefit from services sooner. Fowler's monolith-first essay and his tradeoff analysis present these as context-dependent decisions rather than a universal mandate.

## Design review

Which team owns each data invariant? Which user action spans boundaries? If one service is unavailable, can the others fulfill a useful promise? What measurable pain would a split remove, and what new operations must the team support?
