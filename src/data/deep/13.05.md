# Video transcoding pipeline

Transcoding converts one uploaded source into renditions that fit supported codecs, resolutions, bitrates, and playback protocols. It is an asynchronous workload with expensive CPU or accelerator use, so the design should separate durable job intent from worker execution. Once upload validation succeeds, persist a media record and enqueue a job keyed by media ID and source version. Workers fetch the private source, probe streams, generate outputs, validate artifacts, and publish a manifest only after all required renditions are available.

## Make processing reproducible

Store the source object version or immutable key, detected codecs, duration, dimensions, audio tracks, and a versioned encoding profile. A profile defines codec settings, target ladder, segment format and duration, audio treatment, and output protocol. Pinning profile versions makes a retry reproducible and allows a deliberate re-encode later. The queue message should carry identifiers, not large metadata or signed URLs that expire before a delayed job runs. The worker obtains fresh credentials through a service identity and checks that the source version still matches the job.

Each output should have a deterministic path incorporating source revision and profile version. Write to a temporary namespace first; verify that segments and manifests exist, are decodable, have aligned timelines, and match expected dimensions and durations. Then atomically update the media record to a ready manifest pointer. This prevents a player from seeing half a package. If transcoding fails after some outputs were written, retries can reuse valid immutable outputs or delete them using a bounded cleanup process. Job execution is usually at least once, so workers must be idempotent.

## Control expensive work and noisy media

Probe before allocating a large transcode. Reject unreasonable duration, pixel count, stream count, malformed containers, or decompression behavior according to product policy. Run decoders in isolated workers with CPU, memory, disk, and wall-clock limits. Capacity planning uses source duration and codec complexity, not merely number of jobs; a ten-minute high-resolution source can consume far more compute than a short clip. Use separate queues or priorities for user-facing short clips and bulk reprocessing. Apply admission control when backlog exceeds a latency or budget threshold rather than accepting unlimited work.

A scheduler may split independent renditions across workers, but packaging requires consistent timestamps, keyframe boundaries, and shared audio/video timing. If the pipeline parallelizes, define a barrier that publishes only when all required tasks have completed. Optional renditions can be marked unavailable without blocking playback if the product tolerates fallback to a base rendition. Record the exact toolchain and profile version in job metadata for debugging and compliance.

Track queue wait, processing time per media minute, cost per output minute, worker failures by stage, retry count, invalid source ratio, ready latency, and orphaned bytes. Test corrupt containers, missing audio, variable frame rates, very long videos, worker loss, duplicate queue delivery, and a profile rollout. A dead-letter queue needs an operator path for replay after fixing the cause; simply retrying poison input forever hides failures and burns capacity.

## Design review

Is the input validated before expensive work? Can a retried job overwrite a published package? Are profile and source versions explicit? How is readiness committed atomically? What limits prevent a malformed video from monopolizing a worker pool?
