Counting sounds like a single integer increment, but high write rate, retries, time windows, and distinct-user semantics make it a system-design problem. Start by naming the thing being counted. Total accepted events, unique users, billable actions, and a number displayed on a page can require different guarantees. A financial or quota counter may need exact, transactional accounting; a public popularity badge may tolerate lag and small approximation.

## Define an event and its identity

For exact counting, give each accepted action a stable event ID. A request retry or broker redelivery should not add twice. One approach stores an event row with a unique ID and increments an aggregate in the same transaction. Another keeps the event log authoritative and derives a materialized count asynchronously. The first offers immediate exactness at the database boundary but can create contention; the second scales writes and enables replay but shows a lagging view.

Define the dimensions before building the key: `item_id`, event type, tenant, and bucket time might all matter. A counter labeled “today” needs a time zone and a rule for late events. If the event's timestamp comes from an untrusted client, it can put counts in the wrong window; use a server timestamp or a validated event-time policy. Store enough raw evidence to reconcile a derived count after a bug.

## Avoid one hot row

An atomic database increment serializes updates on one row. At modest throughput that simplicity is valuable. At high throughput, partition events or use counter shards keyed by `(item_id, shard_id)` and sum them for reads. A popular item's writes spread across shards, but reading the exact total becomes more expensive and a shard failure may make the total temporarily incomplete. Batch increments from workers to reduce write frequency; then quantify how many increments could be lost if a worker crashes before flushing.

Redis `INCR` is atomic on one key and can serve a fast approximate display counter, but durability and reconciliation depend on Redis configuration and the write path. Do not use a cache number as the sole authority for billable actions. A stream processor can aggregate events by key into a state store and publish updates to a read model; Kafka Streams documents keyed `count` and stateful aggregation. If processing is replayable, rebuild the read model from the source log.

## Make accuracy visible

State whether the count is exact, eventually exact, or estimated. A UI can show a rounded count while a back-office report uses reconciled exact totals. Measure accepted events, deduplicated events, aggregation lag, missing partitions, count drift against raw events, and read latency. A counter that looks smooth while its event consumer is stopped is not healthy.

For very large distinct counts, a HyperLogLog sketch trades exactness for bounded memory. That is a different question from counting every event: one user producing ten events increases total events by ten but unique users by one. Keep the two measures separate in names, schema, and dashboards. Choose the simplest counter that meets the actual accuracy and freshness requirements.

## Design review

What exactly increments the count? Which ID makes retries safe? Is the displayed number allowed to lag? Where is the authoritative event record? What contention or hot key appears under the most popular item, and how is drift detected?
