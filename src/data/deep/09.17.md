Recent searches help a user repeat or continue their own queries. The feature is a small history store with product and privacy semantics, not merely a list in a search box. Decide whether history is per device, per account, or both; how long it persists; which queries are excluded; and whether deleting an entry removes it from every device. A local-only implementation is simpler, while account sync requires server storage and conflict handling.

## Define the stored record

Store normalized query text for deduplication, original display text, time, optional filters, and an opaque account or device scope. A user who searches `boots` with category `hiking` may expect that filter to return when reopening the query; include only filters that can be restored safely. Keep a bounded list, such as the most recent N entries, and update an existing query's timestamp rather than creating many duplicates. Exact query history can reveal health, finances, or identity, so collect less than a general analytics log might collect.

For device-only history, browser storage can retain a bounded list without a backend. MDN documents that `localStorage` persists across browsing sessions for an origin; that also means another person using the same browser profile may see it. Offer a clear delete action and consider session-only storage for a privacy-sensitive surface. For signed-in history, store server-side with authorization on every read and write, encryption and retention appropriate to the data, and a deletion path that reaches replicas and caches.

## Resolve synchronization and identity changes

When a user signs in, decide whether anonymous device history merges into the account or remains local. A shared device can make automatic merge surprising, so treat it as a product decision. When signed in on two devices, merge by query key and latest timestamp, then cap the list. Use server time or tolerate clock skew so one bad device clock does not pin an entry forever. Signing out should stop showing account history to the next user, even if a local UI cache remains.

Deletion must be specific. Removing one entry should not reappear after an offline device syncs an older copy. A tombstone or versioned deletion can prevent resurrection until all clients have converged; a short-lived local-only store can simply clear itself. A “clear all” action should explain its scope, for example this device or all devices. Do not rely on a front-end hide operation if the backend continues to return the data.

## Make the feature useful and measurable

Show recent searches only when the input is empty or when they are clearly distinguished from live autocomplete. Preserve keyboard navigation and a remove control that is accessible. Do not place a private history item in a global suggestion index. If an old query now has no results, normal search should still handle it; recent history is a shortcut, not a result guarantee.

Measure use of recent entries, delete actions, sync failures, and stale entries without logging more sensitive text than necessary. Test multiple devices, sign-out, browser storage limits, private browsing, and deletion while offline. The feature should degrade gracefully when history storage is unavailable: searching must still work.

## Design review

Is history scoped to a device or account? Which query details are stored, and for how long? What happens on sign-in and sign-out? Can an offline client resurrect a deleted query? Does the UI distinguish private history from public suggestions?
