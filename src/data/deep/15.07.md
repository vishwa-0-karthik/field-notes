# Design: a Kafka-style log

A distributed event log stores ordered records across partitions and lets consumers read them at their own pace. It is not simply a queue that deletes each message after one consumer reads it. Producers append records; brokers persist and replicate partition logs; consumers track offsets and can replay retained data. The architecture must define ordering scope, durability, retention, consumer progress, and what “exactly once” means for the application.

## Partitioned append path

Each topic is split into partitions. A partition is an append-only sequence with offsets increasing within that partition. A record key can route related events to the same partition, preserving per-key order, but a hot key can create a hot partition. There is no single total order across all partitions unless the system adds a coordinating bottleneck. Producers batch records, compress them, and append to the partition leader. The broker can acknowledge after local write, after replica replication, or after quorum confirmation; stronger acknowledgment usually costs latency but narrows data-loss risk. Configure minimum in-sync replicas and producer retry/idempotence behavior around the chosen guarantee.

Replicas follow the leader and maintain a replicated log. If a leader fails, the controller elects an eligible replica and clients refresh metadata. Unclean leader election may restore availability by choosing a stale replica but can lose acknowledged records; clean election preserves stronger durability at the cost of waiting for an in-sync copy. Cluster membership and metadata control plane need their own availability and recovery plan. Segment files are rolled and indexed for sequential append and offset lookup; retention removes old segments based on time, size, or compaction policy.

## Consumer model and replay

Consumers fetch records and maintain offsets. Consumer groups assign each partition to one active member in a group, allowing parallel processing up to partition count. Rebalancing pauses or moves assignments and can duplicate work if the process fails after applying a record but before committing its offset. At-least-once delivery is common: commit after side effects, and make the consumer operation idempotent. Committing before side effects risks loss. Exactly-once processing requires atomic coordination between input offsets and output state or a transactional sink; the phrase should name the boundaries covered.

Retention allows independent consumers to replay history while storage remains available. Log compaction retains the latest value per key and is useful for changelog-like topics, but it is not the same as preserving every event. Consumer lag measures how far a group is behind; lag age is often more actionable than raw offsets when production rate changes. Schema compatibility matters because historical records may be consumed by new code years later. Use versioned schemas and compatibility checks before producers emit new fields or semantics.

## Capacity and failure handling

Plan disk by retention, replication factor, compression, and throughput; network capacity includes replication traffic as well as consumer fetches. Quotas and admission controls prevent one producer or group from exhausting brokers. Monitor under-replicated partitions, leader imbalance, disk watermark, request latency, producer retries, consumer lag, and rebalance churn. Test broker loss during append, network partition, full disk, consumer side-effect retry, schema rollback, and a burst that exceeds retention assumptions. A log design is dependable when producers know when data is durable and consumers know how to resume without silently skipping or corrupting effects.

## Design review

What is the ordering key and partition count? At what point is an append acknowledged? How does failover trade availability against acknowledged data? Are consumer side effects idempotent with offset commits? What retention and schema rules allow safe replay?
