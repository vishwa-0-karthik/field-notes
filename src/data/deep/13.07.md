# Signed URLs, DRM, and video security

Video security combines entitlement checks, short-lived delivery authorization, encryption, and operational controls. It helps to separate three goals: stop casual unauthorized access, limit sharing of account credentials or links, and protect high-value media against copying. A signed URL or cookie can address the first two to a degree; DRM may be required for the third. No browser delivery mechanism can guarantee that a viewer cannot capture content that they are authorized to watch.

## Authorize the playback session

The client asks the application to start playback for an asset. The service checks account entitlement, geographic or device policy, concurrent session limits, and any subscription state. It returns a short-lived token scoped to the asset and playback path. Tokens should have an expiry, audience, and signature; validate them at an edge or gateway that protects both the manifest and every segment, subtitle, and encryption key endpoint. A URL containing a bearer token can leak through browser history, analytics, referrer headers, support screenshots, or logs. Prefer short expiry, path restriction, careful redaction, and signed cookies or headers when they fit the client and CDN model.

Authorization and cache identity are related but distinct. If every viewer's token becomes part of the CDN cache key, the same segment may be stored many times and hit ratio can collapse. The edge can validate a token while caching the object by its immutable media path, provided authorization occurs before returning the cached bytes. Test this behavior explicitly: a valid token must not allow a later request without authorization to reuse a cached response. CloudFront cache and origin request policies distinguish cache-key values from values simply sent to origin; similar distinctions exist at other CDNs.

## Add encryption and DRM deliberately

For encrypted media, packaging encrypts segments and publishes key identifiers; an entitled player obtains a license from a license service. W3C Encrypted Media Extensions defines browser APIs for encrypted playback and application-controlled license exchange, but does not itself define a DRM system or guarantee a particular protection level. A license request should bind to the asset, account, device or session policy, and a short validity window as needed. Keep content keys out of application logs and general-purpose data stores; use a dedicated key-management boundary and audited key rotation. Encryption at rest and TLS in transit protect storage and transport, while DRM controls key release to supported playback environments. These are different layers.

Design for platform diversity: browsers and devices may support different key systems, codecs, and robustness modes. Decide whether the product falls back to clear or lower-protection media on unsupported devices; make that policy explicit. Protect license endpoints from replay and abuse with authenticated requests, rate limits, nonce or session binding where supported, and monitoring. Revocation is limited once a client already has a usable key, so short license duration and key rotation windows matter.

Monitor authorization denials, token validation latency, license failures by platform, suspicious session fanout, and playback start failures. Test expired tokens against cached segments, cross-title token reuse, path traversal, clock skew, account cancellation, and license-service outage. Fail closed for protected assets, but provide clear client errors and an operational recovery path. Security quality depends on the full chain—entitlement, edge validation, manifest, segment, and key—not just on signing one playback URL.

## Design review

Is every media object protected by the same entitlement decision? Does edge authorization happen before a cache hit is returned? What leaks bearer tokens through logs or referrers? Which threat requires DRM, and what happens on unsupported devices or license-service failure?
