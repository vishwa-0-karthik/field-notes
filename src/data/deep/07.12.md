Compaction rewrites immutable files to remove obsolete versions and improve lookup layout. It is the maintenance engine behind LSM performance. Delaying it makes writes look cheap for a while, but raises read and space cost; running it aggressively consumes storage bandwidth and can hurt foreground latency. Design for the sustained workload after compaction has reached steady state.

## See the three amplifications

Write amplification is total storage bytes written divided by logical bytes written. Read amplification describes extra files or blocks consulted for one read. Space amplification is physical bytes occupied relative to live logical data. Different definitions may include or exclude temporary files or cache reads, so compare measurements with the same accounting. RocksDB uses these factors in its tuning guide because a compaction setting can improve one while worsening another.

An update may appear in a new memtable, be flushed to level 0, then be rewritten into several lower levels. Leveled compaction reduces overlap and stale data, often improving reads and space use while rewriting more bytes. Tiered or universal compaction keeps more sorted runs and merges them less often, reducing some write work but increasing read and temporary-space cost. The workload's update skew and key order can change which strategy wins.

## Budget the background work

If clients ingest 20 MB/s and the measured write amplification is 8, the storage device may need roughly 160 MB/s of sustained write capacity before accounting for reads, replication, and filesystem overhead. A device that can briefly absorb a burst may still fall behind over hours. Pending compaction bytes and level-0 file count reveal the debt. When debt exceeds safe bounds, RocksDB can slow or stop writes to prevent runaway space and read amplification.

Compaction also needs free space for output files while inputs remain live. Snapshots and long-running readers may pin old files. A full disk can make it impossible to reclaim space because the engine cannot write the replacement file. Alert on projected headroom, not only current used percentage. Rate-limit background I/O to protect p99 reads, but reserve enough throughput that the backlog can actually drain.

## Preserve deletion semantics

Compaction can drop an old version only when no active snapshot needs it and no older copy can reappear from another level. A tombstone must survive until all older values it hides are no longer reachable. TTL-driven cleanup similarly needs a precise cutoff and must account for snapshots, replicas, and backups. Physical deletion can lag logical deletion, which affects privacy obligations and storage cost.

Benchmark a populated store with representative overwrites, deletes, scans, and cold reads. Run long enough to observe at least several compaction cycles. Record user-visible p95/p99 latency while compaction is active, not just engine throughput. If a policy change improves average speed but causes multi-second stalls, it may fail the product's service objective.

## Design review

What are measured write, read, and space amplification under the real workload? Can compaction keep up indefinitely? How much temporary space is needed? When can tombstones and old versions be removed safely?
