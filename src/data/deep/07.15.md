Range partitioning and consistent hashing divide a keyspace for different reasons. Ranges keep neighboring keys together, making ordered scans and locality natural. Consistent hashing distributes keys by a hash ring and limits movement when nodes change, making point lookup balancing easier. Neither prevents a single hot key from overloading its owner, and either needs an ownership protocol during movement.

## Keep order when scans matter

A range partition owns keys from a start boundary to an end boundary. A query for keys between `customer:100` and `customer:200` can contact only the ranges covering that interval. Related rows may stay near each other. A range can split when it grows or becomes busy, then move independently. Google Spanner documents splits as contiguous primary-key ranges and describes automatic boundary changes based on size and load.

Ordered identifiers can create a write hotspot at the newest range. If every new event uses a rising timestamp key, writes concentrate at the right edge until the system splits or disperses that area. Salting or hashing a prefix spreads writes but makes a time-range query contact more partitions. Choose the degree of locality the application actually needs.

## Spread opaque keys with a hash

Consistent hashing maps keys and nodes into a ring and assigns a key to a following node or virtual node. Adding or removing a node moves only some ranges of the hash space rather than reshuffling every key under a simple modulo rule. Amazon's Dynamo paper uses virtual nodes to distribute responsibility and manage heterogeneous capacity. Hashing works well for independent point lookups, but adjacent business keys land far apart and a range scan becomes a fan-out operation.

A stable ring does not guarantee even load. Key popularity may be skewed, value sizes may differ, and random placement has variance. Virtual nodes or capacity weights can help distribute ranges, while a hot individual key may need replication or application-level caching. The ring's membership must be versioned so clients do not disagree indefinitely about the owner during a topology change.

## Move ownership without losing writes

Whether moving a range or a virtual-node slice, define a handoff protocol: copy existing data, stream new writes or freeze a short window, validate catch-up, publish a new owner epoch, then retire the old owner. A stale client may still route to the old node. It should be redirected or receive an ownership error, not silently write into an obsolete copy. Keep replicas and failure domains in the plan; partitioning alone is not durability.

Compare both schemes using real queries. Count how many partitions each query touches, the maximum traffic on one owner, bytes moved during scaling, and time to rebalance. A mixed workload may use a hashed tenant prefix followed by an ordered time suffix, preserving local scans within a tenant while spreading tenants. The key design is a product and query decision, not only a cluster implementation detail.

## Design review

Which queries require ordered scans? Does an increasing key create a hot edge? How much data moves when nodes change? What prevents an old owner from accepting writes after a handoff?
