# Sliding window rate limiter

A sliding window limiter enforces a maximum number of requests over a rolling interval, such as at most 100 operations during any 60 seconds. It avoids the boundary burst of a fixed window, where a client can spend the full quota just before a window resets and again immediately after. Exact rolling windows give a precise decision but require more state and work; approximations trade precision for lower memory and latency.

## Exact log and approximate counter

An exact implementation stores a timestamp for each admitted request per key. On a request, remove timestamps older than the window, count the remaining events, and admit only if the count is below the limit. The decision and insertion must be atomic, or simultaneous requests can all observe the same count and exceed the cap. This is straightforward conceptually but stores O(requests) events and makes cleanup important. It is appropriate for lower-volume or security-sensitive quotas where exactness matters.

A sliding-window counter uses two fixed buckets: the current window and the previous one. It estimates recent usage as current count plus a weighted portion of the previous count based on how far the current interval has progressed. This needs only a small number of counters and can be atomic in a shared store. The estimate is not exact because it assumes requests in the previous bucket were spread uniformly. For a high-volume API quota, that error may be acceptable; for strict financial or safety limits, choose a stronger consistency model or use a token bucket with carefully defined semantics.

Token buckets solve a related but different problem: they allow a configured burst and replenish at a steady rate. A sliding window constrains the total during each rolling period. Product language should say whether a short burst is allowed, since “100 requests per minute” does not fully define behavior. Some systems combine an instantaneous concurrency limit, a burst bucket, and a longer rolling usage budget.

## Distributed atomicity and time

For multiple API instances, state must be shared or overshoot must be bounded. A Redis sorted set can hold exact event times with an atomic script that prunes, counts, and inserts. A two-counter approximation can use atomic increments and expirations. Partition limiter keys to distribute load, but a very hot tenant key can still become a bottleneck. Regional replicas introduce consistency delay: if two regions accept against independent counters, the quota may be exceeded by the sum. Decide whether a limit is global, per-region, or intentionally approximate. Use a single authority or coordinated allocation of quota when hard global enforcement matters.

Use server-side time from a consistent clock source, and store timestamps at adequate precision. Cleanup keys or events after their useful window to bound memory. When a key has no traffic, it should expire naturally. Avoid deleting a current counter early during a policy update, which can reset quota unexpectedly. Version keys or policies deliberately and specify whether the new policy takes effect immediately or at the next window boundary.

Return remaining quota and reset information only if those values are meaningful under the algorithm. A retry-after estimate is useful but not a promise that the exact next request will succeed under concurrent traffic. Test requests clustered at bucket boundaries, parallel admission races, clock movement, store failover, and hot keys. Measure denied requests, overshoot, decision latency, key count, and store load.

## Design review

Is an exact rolling decision required, or is weighted approximation adequate? Are prune/count/insert atomic? What burst semantics does the API promise? How does quota behave across regions? Are state expiry and policy changes safe for active windows?
