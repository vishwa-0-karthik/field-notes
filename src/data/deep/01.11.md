An extensible data model lets a product add attributes and features without turning every change into a migration emergency. “Flexible” does not mean “schemaless.” The model still needs identity, validation, query paths, ownership, and a plan for old data when new fields appear.

## Keep stable facts structured

Imagine a marketplace listing. Every listing has an ID, owner, price, currency, creation time, and publication state. These fields participate in constraints, joins, sorting, and common filters, so ordinary typed columns are a good default. Category-specific details—shoe size, phone storage, furniture material—may change often. A structured extension field such as `jsonb` can hold less universal attributes while the core stays relational.

PostgreSQL's documentation notes that `jsonb` supports indexing and efficient processing, but also recommends a reasonably predictable document structure. A large JSON document is not free-form magic: updates lock the row, nested fields can be hard to validate, and indexes need to match real queries. Keep each document aligned with an atomic business object rather than stuffing unrelated entities into one blob.

| Data shape | Good fit | Warning sign |
| --- | --- | --- |
| Typed columns | Universal, constrained, frequently queried fields | Hundreds of mostly-null category columns |
| Extension JSON | Evolving category-specific attributes | Critical invariants exist only in app code |
| Child table | Repeating structured values | Excess joins for a truly atomic blob |
| Separate service/store | Different ownership or access pattern | Premature operational complexity |

## Version the meaning, not just the bytes

Suppose the API first stores `size: "M"` and later adds regional sizing. A new field alone is insufficient if old records are ambiguous. Introduce a versioned meaning, such as `size_system: "US"`, and define a migration or default for existing rows. For APIs and events, support a transition period: write the new representation, read both when safe, migrate old data, then remove the old field. Avoid changing the meaning of a field in place while older producers or consumers still exist.

Validation belongs at several boundaries. The API rejects malformed input, the domain layer enforces business rules, and the database protects essential invariants such as uniqueness or non-null ownership. If a listing must always have a positive price, a typed column plus constraint is stronger than a string inside arbitrary JSON. Flexible fields still need a documented schema per category and a policy for unknown keys.

## Design for the queries you expect

List the highest-value filters before choosing storage. If users frequently search listings by category, price range, and a category attribute, determine which indexes can support that combination. A generic JSON index can help containment queries, but it may not be the best answer for sorting by a numeric extracted value. A generated column or expression index may be justified for a hot attribute. Measure query plans against representative cardinality; an index that looks right on ten rows may fail at ten million.

Avoid an entity-attribute-value table as an automatic answer to extensibility. It can represent arbitrary keys, but enforcing types and querying several attributes together becomes difficult. It is appropriate for some metadata systems, not a default replacement for a clear domain schema.

## Design review

Which fields have stable meaning and strong constraints? Which attributes are genuinely variable? How will an old record be read after the next schema version? Can the primary user queries use indexes without scanning every flexible document?
