# Observability for distributed systems

Observability is the ability to explain system behavior from emitted evidence, including situations the team did not predict in advance. In a distributed system, a single user action crosses processes, queues, databases, and networks. No one host log can tell the whole story. A useful design combines metrics for aggregate shape, traces for request paths, and logs or events for detailed facts, with shared resource and request context that lets an operator move between them.

## Instrument the user journey

Start from important user-visible operations and define what success, latency, and failure mean for each. Record request counts and outcomes, latency distributions, saturation, and queue depth at service boundaries. Histograms are usually more useful than averages because they preserve tail behavior; alerting on p95 or p99 latency can show pain hidden by a healthy mean. Metrics need bounded dimensions. Service, operation, region, and status class are often useful; raw user IDs, request IDs, or arbitrary URLs can create unbounded time series and high cost. Put unique identifiers in trace or log fields instead.

Trace context should propagate across RPC and asynchronous boundaries. A trace can show that the API returned quickly while the queue waited ten minutes, or that one database dependency dominated a request. For queues, record producer and consumer spans with message correlation, and preserve the causal link even when the work runs later. Sampling keeps telemetry volume manageable, but head sampling may drop the exact rare slow request that matters. Tail sampling can retain traces based on duration or error, at additional collector state and cost. Keep a controlled path for high-severity traces and record sampling decisions.

Logs capture discrete events and context that do not fit a metric. Use stable structured fields and include trace and span identifiers where available. Do not log secrets, credentials, full payment data, or unnecessary personal information. A syntactically JSON record is not automatically a stable schema; field names and types need conventions. Include enough context to diagnose an event without turning logs into an unbounded copy of every request body.

## Make telemetry reliable and affordable

Telemetry export must not become a synchronous dependency on the user request. Buffer locally with bounded queues, batch exports, and define what happens when the collector or backend is unavailable. Under pressure, drop low-value debug data before blocking application work. Monitor the observability pipeline itself: dropped spans, collector queue utilization, scrape failures, ingest delay, cardinality, and cost. A dashboard that is stale or silently missing one region is an operational hazard.

Dashboards should answer a small set of questions quickly: is the service serving users, where is latency coming from, and is the system approaching capacity? Alert on symptoms and actionable conditions, not every internal metric crossing an arbitrary threshold. The four golden signals—latency, traffic, errors, and saturation—are a useful starting point, but asynchronous systems also need queue age and consumer lag; storage systems need replication and disk health; control planes need convergence and reconciliation status.

Exercise the path by injecting an error or a slow dependency and confirming that the event appears in a dashboard, alert, trace, and log with consistent context. Track time to detect and diagnose, not just telemetry volume. Observability is a product capability: teams should be able to ask a new diagnostic question without deploying emergency instrumentation during an incident.

## Design review

Can an operator follow a request across services and queues? Which metric dimensions are bounded? How are traces sampled without hiding rare failures? What happens when telemetry export is down? Are sensitive values excluded, and is the telemetry pipeline monitored like production infrastructure?
