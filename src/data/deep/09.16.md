Related searches offer alternative queries after a user has searched. They can broaden a topic, narrow an intent, or help recover from poor results. They are different from autocomplete, which starts with a prefix, and from spelling correction, which tries to repair a likely error. A useful related query should lead to a distinct, relevant result set rather than repeat the same words in another order.

## Generate several kinds of candidates

Query-session transitions can reveal refinements: users who searched `running shoes` may next search `trail running shoes`. Co-occurrence is evidence, not proof of a good suggestion; a frequent transition can reflect frustration. Content-based generation can find nearby terms from documents retrieved for the original query. A curated taxonomy can add predictable refinements such as category, brand, or location. Embedding similarity can find paraphrases, but paraphrases that return nearly identical results add little value.

Store each candidate's normalized text, source, query class, locale, and supporting counts or confidence. Exclude sensitive or personally identifying queries from mined suggestions. Apply a minimum support threshold and moderation policy before showing log-derived phrases. A new topic may have no log history, so fall back to taxonomy or corpus-driven candidates rather than returning an empty box.

## Rank for usefulness and diversity

Score candidates for topical relation, evidence quality, and expected result quality. Then diversify: one broadening, one narrowing, and one adjacent intent may be more useful than five near duplicates. Check each candidate against the current index so it does not lead to zero results or only unavailable items. For an exact-ID query, related searches may be inappropriate; show similar products or documentation links under a different label instead of implying the ID was wrong.

Keep a clear boundary between personalization and global suggestions. A user's recent search may improve their own suggestions, but it should not leak into another user's page. For multi-tenant products, filter candidate sources and result checks by tenant and permissions. Cache only when the context key includes the constraints that affect validity. Invalidate or expire suggestions when the underlying corpus changes substantially.

## Evaluate the destination, not the click

Measure suggestion selection, subsequent search success, reformulation loops, and the quality of destination results. A related phrase can earn clicks because it looks interesting while leading to an irrelevant page. Offline review should include candidate diversity and result-set overlap. Test popular and long-tail queries, new content, sensitive query classes, and locales. Stanford's query-expansion discussion provides the retrieval foundation; a product-facing related-search system adds session evidence, filtering, and presentation decisions.

Log why a suggestion was shown: taxonomy edge, aggregate transition, or content similarity. This supports debugging and moderation. Limit the number shown and the computation budget; a slow suggestion panel should never delay the main results. If the recommendation pipeline is unavailable, omit the panel and keep search functional.

## Design review

What relationship should each suggestion express? Are mined queries frequent and safe enough to show? Does the destination have useful results? Are tenant and personal contexts isolated? How will repeated reformulation loops be detected?
