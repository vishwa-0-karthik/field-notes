A distributed lock asks several machines to treat one worker as the temporary owner of a resource. A lease adds an expiry so work can resume after that worker dies. These mechanisms reduce duplicate work, but their safety depends on what the protected resource accepts after the lease expires. Specify the invariant before choosing a lock service.

## Distinguish efficiency from correctness

If two workers generate the same thumbnail, duplicate work wastes CPU but usually does not corrupt data. A short lock can be a useful efficiency measure, and an occasional overlap may be tolerable. If two workers both debit an account or overwrite the same authoritative file, overlap is a correctness failure. That job needs a transactional invariant, compare-and-set, or fencing at the destination; a lease alone is insufficient.

The basic race is simple: worker A acquires a 30-second lease, pauses for 40 seconds, and loses it. Worker B acquires the lease and starts. A resumes and still believes it owns the resource. The lock service may be perfectly correct about who owns the current lease, but it cannot stop A from sending an old write to an unrelated storage system.

## Fence stale owners at the resource

Give each successful ownership period a monotonically increasing token. A resource records the largest token it has accepted and rejects writes with older tokens. If B has token 42 and A later sends token 41, A cannot overwrite B's work. The comparison must occur atomically at the side-effect destination. If the destination lacks this feature, put a transactional publication step in front of it or redesign the operation to be idempotent.

A random lock token is useful for proving that a client may release the lock it acquired; it is not a fencing token because random values do not express newer versus older ownership. A TTL is also not a fencing token. The distinction becomes important when a distributed lock library advertises mutual exclusion but does not control delayed clients.

## Operate the lease under failures

Lease duration should exceed ordinary work and renewal latency, yet a very long lease delays recovery after a crash. Renew before expiry with enough margin for network variation. Stop initiating new work if renewal fails, but assume already issued I/O may still complete. Use a stable job ID so a new owner can identify attempts from an earlier owner and safely resume or replace them.

Do not turn a lock into the source of truth for completed work. Persist a final state in an authoritative store. A worker may finish the action and crash before marking the job done, so the next owner needs an idempotent way to discover the outcome. Monitor lease renewals, overlapping attempts, rejected stale tokens, and time spent without an owner. Exercise long process pauses and delayed network responses rather than only clean worker crashes.

## Design review

Is duplicate execution merely expensive or actually unsafe? Can the side-effect destination reject stale epochs? What happens when a client pauses longer than the lease? How does the next owner discover work completed before a lost acknowledgement?
