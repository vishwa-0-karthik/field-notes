A t-digest is a compact, mergeable summary for estimating quantiles of numeric data. It is attractive for latency distributions because it aims for good accuracy near the tails, where p99 and p99.9 live. It does not store every observation, so a percentile is an estimate whose quality depends on compression settings, implementation, sample distribution, and merge order. For a small dataset or a high-stakes exact report, sort the raw values instead.

## Keep weighted centroids

A t-digest groups nearby values into centroids with a mean and weight. It keeps tighter groups near the extremes of the distribution and allows larger groups near the middle. New values are inserted or buffered and centroids are periodically compressed. To estimate a quantile, the digest walks cumulative weights and interpolates. The reference implementation by Ted Dunning documents online updates, merging, and tuning through a compression parameter.

The number of retained centroids is much smaller than the number of observations, which bounds memory in a stream processor. That saving comes with approximation. Two latency distributions can have similar median and very different p99; preserve enough tail detail for the alerting threshold. Test repeated identical values, long-tailed values, and sudden distribution shifts, because these are common in real latency data.

## Merge without averaging percentiles

Each service instance can build a t-digest for a time bucket and send it to an aggregator. The aggregator merges digests to estimate a fleet-wide percentile. Averaging instance p99 values is wrong: percentiles are not additive, and instances may have different request volumes. A digest merge carries weights and approximates the union distribution. All inputs need the same units, event definition, and compatible serialization. A digest of milliseconds and one of seconds can merge into nonsense while still producing a number.

Keep the bucket ID and input range with each digest. If a worker retransmits the same snapshot and the reducer merges it twice, the distribution becomes weighted twice. Use versioned replacement or deduplicate by partition and offset range. If a late event arrives after a bucket is published, merge a correction digest or republish the entire bucket with a higher version. State whether the report is provisional.

## Compare error where decisions happen

Benchmark the chosen implementation against exact sorted samples at p50, p95, p99, and p99.9 over representative traffic. Report both rank error and value error; a small rank difference can mean a large latency difference in a heavy tail. Apache DataSketches compares t-digest with KLL and emphasizes that their error profiles differ. Choose the sketch for the percentile and accuracy target, not because one name is familiar.

Monitor update throughput, digest size, merge time, input count, and discrepancies against exact sampled windows. A t-digest does not identify which request caused an outlier, so keep sampled traces or raw exemplars alongside the aggregate. Percentile alerts also need a minimum sample count; p99 of a handful of requests is unstable regardless of sketch quality.

## Design review

Which quantiles and units matter? What error at the tail is acceptable? Are digests merged with correct weights and without duplicate snapshots? How are late events handled? What exact sample validates the chosen compression and implementation?
