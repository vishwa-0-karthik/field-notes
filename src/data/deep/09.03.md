Boolean search selects documents through exact logical conditions: `AND`, `OR`, and `NOT`. Ranked search instead orders partial matches and usually returns a top-K page. Both are useful. A compliance filter may require exact membership, while a shopping query like `waterproof hiking bag` should rank helpful partial matches rather than demand that every word appear. Tiered retrieval spends more work only when the first, cheaper candidate set is insufficient.

## Evaluate Boolean expressions deliberately

Represent a parsed query as a tree rather than relying on string substitution. For `red AND (bike OR helmet)`, retrieve postings for `bike` and `helmet`, form their union, then intersect with `red`. With sorted postings, merging and intersection avoid scanning every document. For several AND terms, start with the rarest postings list. A standalone `NOT` can mean nearly the whole corpus, so require a positive anchor or a bounded filter context for expensive negation queries.

Field and permission filters often behave like Boolean conditions. A search for `bike` in `category = cycling` by a user allowed to see only public items should apply those restrictions before presenting results. Never count on a client-side filter to hide private hits after retrieval. Phrase search adds positional checks after a term-level candidate set; a document containing both words in unrelated places should not satisfy the phrase.

## Build retrieval tiers around a budget

A simple tiered plan first searches high-value fields, recent documents, or a precomputed top-doc list. If it finds enough credible candidates, it ranks those and returns quickly. If not, it expands to the full index. Another plan collects broad lexical candidates with a cheap scorer, then applies a costly semantic or personalization model to a smaller pool. The important property is a measured recall/latency tradeoff: the fast tier must not systematically omit relevant results for rare or long-tail queries.

Set a candidate budget and a deadline for each stage. If a query matches millions of documents, scoring all of them is wasteful; use top-K algorithms or bounded traversals supported by the index. If the first tier returns too few results, fall back rather than showing a false zero-result page. Track which tier supplied each result and how often fallbacks run. Stanford describes tiered indexes and champion lists as ways to avoid scoring every posting, with the risk of missing high-quality results.

## Make semantics visible to users

Different product surfaces may need different behavior. An advanced search form can expose exact Boolean operators, while the main search box may treat words as soft evidence with filters as hard constraints. Quoted terms, minus signs, and `OR` should have documented precedence and escaping. If a parser silently changes `A OR B AND C` into the wrong grouping, relevance debugging becomes confusing. Show active filters and a clear explanation when a query returns no results.

Measure p95 latency by query class, number of postings visited, candidate-set size, fallback frequency, zero-result rate, and relevance on queries that use the fast tier. A tier that improves the median while making rare queries wrong may not meet the product goal. Keep evaluation queries for short common terms, long multiword queries, quoted phrases, and permission-heavy filters.

## Design review

Which clauses are hard filters and which are ranking hints? How is operator precedence parsed? What recall is lost by the fast tier? When does the system expand the search, and can a permission filter ever be bypassed during fallback?
