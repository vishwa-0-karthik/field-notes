An API contract is the set of promises a caller can rely on: operations, data shapes, meanings, errors, authorization, and how those promises change over time. A URL list is only part of it. The contract should let a client predict what happens when a request is repeated, times out, or contains an unknown field.

## Begin with the caller's task

For a reservation service, the client wants to create a reservation, read its state, and cancel it. A possible HTTP surface is `POST /reservations`, `GET /reservations/{id}`, and `POST /reservations/{id}/cancellations`. Choose resource names from domain concepts rather than database table names. The create request might include `slot_id`, `customer_id`, and an idempotency key. The response needs a stable reservation ID and state such as `PENDING` or `CONFIRMED`.

Specify what success means. Does `201 Created` mean the slot is held durably, payment is complete, or only that processing was accepted? If work continues after the response, a `202 Accepted` with a status resource may express the promise more clearly. Error responses should be actionable: `SLOT_TAKEN` should be distinguishable from `PAYMENT_UNAVAILABLE` and invalid input. HTTP status classes provide a standard outer meaning, while a stable application error code gives finer detail.

| Contract item | Example decision | Why it matters |
| --- | --- | --- |
| Identifier | Opaque reservation ID | Clients do not infer storage layout |
| Retry behavior | Idempotency key retained for 24 hours | Network timeout can be retried safely |
| Pagination | Cursor with stable ordering | Large collections stay bounded |
| Error body | Code, message, request ID | Client behavior and incident diagnosis |
| Unknown fields | Documented acceptance or rejection | Safe schema evolution |

## Specify validation and authorization

Define required and optional fields, ranges, defaults, and the meaning of `null`. A missing `expires_at` might mean “use server default”; an explicit null might mean “never expire,” which is a very different promise. For every operation, state who may invoke it and whether ownership is checked at the resource level. Authentication tells you who called; authorization decides whether that caller may cancel this reservation.

Do not leak internal implementation details in public errors. A response can identify a conflict without exposing SQL, provider tokens, or stack traces. Include a request or trace ID so support can locate the corresponding server event. Document rate limits and what clients should do after throttling, including a retry delay where applicable.

## Make change deliberate

Additive response fields are usually easier for tolerant readers than deleting or changing an existing field's meaning. A new enum value can still break a client with an exhaustive switch, so document how consumers should handle unknown values. For a breaking change, choose a migration plan: new endpoint or version, parallel support window, client adoption telemetry, and removal date. Contract tests should verify examples and error shapes, not merely that the server returns a 2xx status.

OpenAPI provides a machine-readable description for HTTP interfaces, including paths, operations, request bodies, parameters, and responses. It helps generate docs and validate compatibility, but prose is still needed for semantics such as “exactly when is a reservation confirmed?” RFC 9110 defines the HTTP method and status semantics that the API should respect.

## Design review

If a client sends `POST /reservations`, loses the response, and retries, what happens? Can it distinguish a conflict from a temporary failure? Can a new server safely serve an old client? If those answers are absent, the API contract is incomplete.
