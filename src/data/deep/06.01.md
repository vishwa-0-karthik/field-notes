A distributed system is a set of processes that cooperate through messages while each has only a partial view of the world. A process can fail, a message can be delayed or duplicated, and a reply can disappear after the requested action succeeded. These ordinary events create the central design problem: a caller cannot always tell whether remote work happened. Start by naming the operation's required outcome and the failures it must tolerate.

## Replace local assumptions with explicit messages

Inside one process, a function call returns or throws under one memory model. Across a network, a request may time out even though the server committed the write. Retrying a payment creation can then create a second payment unless the operation has an idempotency key or a naturally unique business identity. Acknowledgements need a precise meaning: received in memory, persisted on one node, replicated to a quorum, or applied by a downstream service are different milestones.

The same ambiguity affects reads. A replica can answer quickly with an older value. A client may have written to one region and read from another before replication catches up. The system should state which order or freshness it promises rather than using “distributed” as an explanation for surprising results.

## Plan for independent failures

A useful failure inventory includes process crash, host loss, network partition, asymmetric connectivity, disk failure, slow dependency, clock skew, and operator error. Retries help with some transient faults but can amplify load or duplicate side effects. Timeouts bound how long a caller waits; they do not cancel work that already reached the server. A circuit breaker can reduce repeated calls to a sick dependency, but it changes availability and recovery timing.

Use failure domains deliberately. Three replicas in one rack do not protect against that rack's power loss. Three replicas spread across regions may survive a regional failure but incur greater write latency and network cost. Define a recovery point objective and recovery time objective for the data and workflow before selecting the topology.

## Give every operation an authority

For each important fact, identify the component allowed to commit it. A database row can be the authority for an order's status; an event stream may distribute that status to search or analytics projections. If two services can independently finalize the same order, conflict resolution becomes part of the business rule. A replicated state machine uses an agreed log order so replicas apply commands consistently; Raft is one way to coordinate that order under its assumptions.

Avoid distributed coordination when the invariant can stay within one transactional boundary. A workflow can often use a single owner for a record plus asynchronous events for secondary views. When cross-service atomicity is unavoidable, define compensation, pending states, or a durable coordinator explicitly. The goal is not to eliminate every temporary disagreement; it is to keep the product's invariants true despite it.

## Observe the system as a chain

Trace a request across hops with a stable operation ID. Record attempt number, authoritative commit ID, queue offset, and outcome. Metrics should expose dependency latency, timeout rate, retry amplification, replication lag, and the number of operations stuck in an intermediate state. Test by delaying and dropping messages, restarting nodes, and repeating commands after lost acknowledgements. The recovery behavior is part of the design, not an appendix.

## Design review

What does success mean for this operation? Which failures can happen after a commit but before a reply? Who owns each invariant? How is a duplicate request recognized? What must remain available during a partition?
