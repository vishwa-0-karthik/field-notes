H3, S2, and geohash map latitude/longitude into discrete cells. A cell ID supports partitioning, aggregation, joins, and approximate neighborhood lookup. These systems differ in cell shape, hierarchy, distortion, and boundary behavior. Pick one based on the operation: a grid can make city-level aggregation easy, but it does not replace an exact point-in-polygon or distance test.

## Geohash: simple prefixes and rectangles

Geohash repeatedly bisects latitude and longitude intervals and interleaves the bits into a base-32 string. Prefixes identify parent rectangular regions and are easy to index lexicographically. Neighbor lookup and cell width require care: cells are not square everywhere, nearby coordinates can have unrelated prefixes at a boundary, and longitude wraps at the dateline. Geohash works well for coarse prefix partitioning and common database key patterns, provided queries enumerate every intersecting cell and refine candidates exactly.

## H3: hierarchical hexagons

Uber's H3 indexes the sphere with mostly hexagonal cells plus twelve pentagons at each resolution. Each hexagon has seven finer child cells. This makes local neighborhood and aggregation operations convenient, especially when comparing neighboring areas or aggregating trips. H3's documentation distinguishes exact logical containment in its hierarchy from approximate geometric containment: a point in an H3 cell's geometric shape and a child cell's parent relation are not identical in every boundary case. Resolution is discrete; choose it for the analysis scale, not as an exact meter radius.

## S2: hierarchical spherical cells

S2 projects the sphere onto six cube faces and subdivides them with a hierarchical Hilbert curve. Its cell IDs cover a sphere-aware hierarchy, and an `S2RegionCoverer` approximates arbitrary regions with a union of cells. This is useful for covering a polygon or cap with a bounded number of index keys. The cover may include extra area, so exact geometry checks remain necessary. S2's cell hierarchy is not the same as a regular latitude/longitude grid.

## Select by query and operational fit

Use a grid for spatial joins and pre-aggregation when neighboring cell IDs are practical. Compare cell area variation, neighbor enumeration, hierarchy depth, polygon covering quality, language support, and library maturity. H3's hex layout can reduce directional artifacts in some neighborhood analyses, while S2's spherical hierarchy offers flexible region coverings. Geohash's prefix strings are convenient in simple key-value indexes. None guarantees that all nearby points share a prefix or cell.

Store canonical coordinates and the grid version alongside cell ID. If the resolution or library version changes, reindex explicitly. Query a covering cell set, gather candidates, then apply the exact distance, geometry, and visibility predicate. Test poles, antimeridian crossings, cells around pentagons, and points exactly on boundaries. Compare candidate volume against true matches for real density distributions before committing to a grid.

The same location may be encoded at several resolutions for different consumers. A dispatch service can need fine cells while a city analytics job uses coarse cells. Keep these identifiers as separate derived fields; do not overwrite the canonical point with whichever grid the current query happens to use.

## Design review

Is the main operation neighborhood lookup, aggregation, or polygon covering? Which cell hierarchy and shape fit it? What boundary or distortion error is acceptable? Are exact predicates applied after cell retrieval? How will changes in resolution or grid version be migrated?
