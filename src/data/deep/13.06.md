# Adaptive bitrate and the CDN decider

Adaptive bitrate playback packages a title into several quality representations and lets the player choose which segment to fetch next. A manifest describes available renditions and where their segments live. The player estimates throughput, buffer health, decode capability, and sometimes viewport size, then selects a representation. This moves adaptation to the edge closest to user experience: the player sees local stalls and device constraints that a server cannot directly observe.

## Build an aligned rendition ladder

Encode several resolutions and bitrates, but avoid making every rung a separate unrelated video. Align segment boundaries and keyframes so a player can switch representations without visible gaps or timestamp discontinuities. The ladder should reflect source quality and likely device/network classes; upscaling a low-resolution source wastes bytes. Audio may be a shared rendition or paired tracks depending on language and packaging. Package HLS or MPEG-DASH manifests and segments as ordinary HTTP objects, which makes a CDN a natural delivery layer. Browser support and player choice influence whether one protocol or both are needed.

The player's decision can use an estimated bandwidth safety margin rather than chasing every short-lived throughput spike. A rule such as “choose a bitrate below a conservative fraction of recent goodput, unless buffer is critically low” trades sharpness for fewer stalls. Startup often favors a conservative representation to begin quickly; later choices can rise as the buffer grows. A player should avoid switching too often because oscillation is distracting, and should reduce quality promptly when buffer drains. Device decode limits and data-saving preferences can impose a cap even when bandwidth is ample.

## What the CDN decides

The CDN usually does not choose each viewer's quality. It caches the manifest and media segments and serves them from nearby edge locations. The player selects segment URLs and therefore indirectly drives which objects the CDN sees. A manifest may be personalized or signed, while the media segments can be shared cache objects. Keep cache keys stable and include only request dimensions that change the object. A per-viewer token in every segment query can fragment caches; authorization can instead be enforced with signed cookies, path-scoped tokens, or edge validation designed to preserve cache sharing. Ensure the authorization boundary is consistent across manifests, segments, subtitles, and keys.

Cache immutable segments for long periods using versioned paths. Manifests for VOD can also be immutable after publication. Live manifests change frequently and need short freshness or revalidation policies. Origin shielding and request coalescing can reduce a surge against origin when a popular segment is first requested, but they do not replace correct cache headers. If a segment is missing at origin, return a clear failure rather than caching an accidental error as a successful object.

Measure startup delay, rebuffer ratio, average bitrate, quality switches, segment fetch latency, CDN hit ratio, origin bandwidth, and errors by device and geography. Test low bandwidth, sudden bandwidth drop, high RTT, cache cold starts, expired authorization, and missing segments. The central separation is useful: player adaptation optimizes each viewing session; CDN placement and caching reduce delivery cost and latency across sessions.

## Design review

Are segment boundaries aligned across representations? What signals drive the client's bitrate choice? Which objects are immutable? Can the CDN cache media across viewers while still enforcing entitlement? How are live manifests kept fresh without making every segment a miss?
