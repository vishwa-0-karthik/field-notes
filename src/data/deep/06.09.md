Redis Redlock is an algorithm for acquiring a time-bounded lock across several independent Redis instances. Fencing tokens solve a different problem: stopping an old lock holder from making a later side effect. Understand both before using a Redis lock around important work. The precise safety claim depends on timing, persistence, and the resource being protected.

## Follow the Redlock acquisition path

The Redis design describes five independent masters as an example. A client writes the same unique random value under a lock key on each, with a short per-node timeout and an expiry. It succeeds only if a majority grants the lock and the elapsed acquisition time is less than the lease lifetime. The effective validity window is shortened by elapsed time and a margin for clock drift. On failure, the client releases any partial acquisitions promptly. On completion, it releases only locks still containing its random value.

The random value prevents A from deleting a lock that expired and was later acquired by B. It does not tell an external database or file server that B's work is newer. Redis's own documentation describes assumptions around clock drift, node restarts, and lock persistence. Treat those as part of the design, not invisible implementation details.

## See the paused-client hazard

Worker A can acquire a valid lock, read input, and pause for longer than its lease. Worker B then acquires the lock and writes a new result. A resumes and sends its older result. A's lock has expired, but the external resource may still accept the write. A local timeout check before writing can reduce risk, yet A can pause after the check and before the write arrives. A fencing token checked by the destination closes this specific race because A's older token is rejected.

Martin Kleppmann's analysis argues that lease-based locks without fencing are a poor correctness mechanism for arbitrary pauses. Redis's Redlock proposal focuses on a different set of assumptions and a time-bounded lock protocol. The useful engineering response is to state the failure model and choose the mechanism for the job, rather than treating either document as a universal yes or no.

## Choose a safer shape for the invariant

For cache stampede control, occasional duplicate refill may be acceptable; a Redis lock can lower database load without becoming the final authority. For exactly one published artifact, store a job generation in a transactional database and conditionally publish only the current generation. For a financial state change, use the database's transaction and uniqueness constraints directly. A lock can coordinate workers, but the authoritative store must still reject invalid state transitions.

If a fencing token is required, obtain a monotonically increasing number from a system that can safely allocate it, then pass it through to every protected write. Do not manufacture one from a random Redlock value or an unsynchronized timestamp. Measure lock acquisition time, failure rate, remaining validity, and stale write rejections. Test Redis node restarts, delayed clients, and network partitions against the chosen guarantee.

## Design review

Which specific overlap would damage correctness? What timing and restart assumptions does the lock rely on? Can an old holder still reach the resource after expiry? Where is the monotonic fencing token issued and enforced?
