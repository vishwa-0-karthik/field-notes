A cache stores a copy of data closer to a reader or in a form that is cheaper to serve. “Closer” may mean a browser, CDN, application process, distributed memory service, or precomputed database view. Each layer has a different owner, scope, latency, and invalidation path. Start with the slow read and its freshness requirement, then choose the narrowest layer that fixes it.

## Place copies along the request path

A public product image can be cached by a browser and CDN because many users request identical bytes. A personalized account balance may belong only in a short-lived application cache, or may be uncached if stale data would mislead the user. A database buffer pool already caches disk pages; adding Redis in front of a query that is fast and rare may only add a network hop and an outage mode.

| Layer | Good fit | Main constraint |
| --- | --- | --- |
| Browser | Static assets, safe private responses | User controls the copy and its lifetime |
| CDN or shared HTTP cache | Public, reusable responses | Cache key and privacy must be correct |
| Process memory | Tiny, frequently reused local state | Each process has a separate view |
| Distributed cache | Shared high-volume reads | Network, capacity, and invalidation cost |
| Materialized view | Repeated expensive aggregation | Refresh lag and write maintenance |

The request path may contain several layers. On a miss, each layer passes to the next until the authoritative store answers. Measure latency by hit and miss separately. An overall average can hide a small number of very slow misses or cache warmups.

## Match the copy to its identity

An HTTP cache key usually begins with the request target and relevant request headers, but applications often have hidden dimensions: tenant, language, authorization, feature flag, or output format. Accidentally sharing a personalized response is a data leak, not merely a stale result. RFC 9111 defines the semantics of shared and private HTTP caches, freshness, and validation. Use explicit cache controls, vary responses only on intended dimensions, and test authenticated requests through every intermediary.

Inside an application, a cache key should encode the data identity and the representation version. For example, `tenant:42:product:91:v3` prevents one tenant's data from colliding with another's and allows a schema transition without misreading old serialized values. Do not rely on a TTL to correct a broken key design. Keep high-cardinality variants in mind: caching every unique search query can fill memory while producing few hits.

## Decide how each layer becomes fresh

TTL bounds how long a copy can remain without renewal, but it is not an exact invalidation guarantee. A write can invalidate a cache entry, update it, or let it age out. Event-driven invalidation adds delivery and ordering problems. HTTP validators such as ETag can revalidate a stored response without transferring its full body when unchanged. The right approach depends on how stale the product can be and how often the source changes.

Work from a quantitative example. If a read endpoint receives 10,000 requests per second and the database can safely handle 1,000, a 95% cache hit rate leaves about 500 requests per second at the database. But a cold start or outage can suddenly send all 10,000 there. Capacity and fallback must account for the miss path, not just steady-state savings.

## Design review

Which requests share an identical answer? Where is the authoritative copy? What freshness error can users tolerate? How do keys include tenant and representation scope? Can the source survive a cold cache?
