A view counter measures how often content is viewed, but “view” needs a product definition. A page request, a rendered page, a visible item for a minimum duration, and a unique person per day produce different numbers. Bots, reloads, prefetching, and retries can inflate raw requests. Define the event at the client and server boundary before scaling the counter; otherwise a highly available pipeline only computes a misleading value quickly.

## Capture a defensible view event

For a video, a view might require playback beyond a threshold; for an article, meaningful visibility or dwell may matter. Give the client an event ID and include content ID, session or anonymous viewer scope, event time, and a version of the view rule. Validate the event on the server. Do not trust an arbitrary client count or timestamp for a billable metric. Apply bot and abuse filters with documented limits; those filters may change, so retain enough raw data to recompute affected periods.

Duplicates arise when a client retries, a queue redelivers, or a user reloads. Decide whether each reload is a new view or whether a session/time-window rule deduplicates it. A bounded deduplication table keyed by event ID prevents transport duplicates. A separate `(viewer, content, window)` key can enforce a product-level unique-view rule. These keys serve different purposes and should not be conflated.

## Absorb hot content traffic

Writing every view into one content row creates a hotspot for a viral item. Append validated events to a durable stream, partition by content ID or a salted variant, and aggregate in short intervals. If one content ID is still too hot, salt the key into several subcounters and sum them. The read path can show the latest aggregate plus recent increments, or accept a short delay. Make the freshness window visible in internal metrics even if the public display rounds the number.

Bucket events by a defined clock. Event time reflects when the view happened; processing time reflects when the system received it. Mobile clients may send late events after reconnecting. Apache Beam's windowing documentation describes watermarks and allowed lateness: decide when a daily count becomes final and how late corrections are applied. If a public count must never move backward, keep that as a display policy rather than corrupting the accurate underlying count.

## Separate display, reporting, and billing

A public “1.2M views” badge can be cached and rounded. An analytics dashboard may need hourly breakdowns with a revision marker. An advertising report requires stronger event validation, deduplication, auditability, and reconciliation. Do not assume one materialized integer satisfies all three. Retain raw events under a bounded policy and derive multiple views from the same definition version.

Measure ingestion loss, duplicate rate, bot-filter rate, per-content skew, aggregation lag, and drift between raw accepted events and aggregates. Load-test a single viral content ID as well as total traffic. If a stream partition is unavailable, the system should have a clear choice between delaying the view count and dropping a noncritical event; silently claiming exactness after loss is worse than admitting approximation.

## Design review

What user action counts as a view? How are transport duplicates and repeated genuine views distinguished? What happens for one viral item? When does a time bucket become final? Which count is safe for billing versus display?
