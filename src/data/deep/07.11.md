An LSM point read can encounter several generations of sorted files before finding a key. Bloom filters and sparse indexes reduce unnecessary disk work in different ways. A Bloom filter asks whether a particular file might contain the key; a sparse index finds the data block within a file. Neither substitutes for checking the actual record and its version.

## Narrow the candidate files

First check the active and immutable memtables. Then use file-level metadata, such as smallest and largest key, to skip SSTables whose ranges cannot contain the key. Level 0 files may overlap, so several can remain candidates. Lower leveled runs often have less overlap, but compaction policy determines the actual layout. Search candidates in version-aware order so a newer tombstone hides an older value.

A Bloom filter stored with an SSTable can answer “definitely absent” for a key when the filter is correctly built; a positive answer means “possibly present.” False positives cost extra reads but should not produce wrong results. RocksDB's filter documentation describes filters for newly created SST files. Filters consume memory or cache space, so size them for the miss rate and file count. A filter is especially valuable for random lookups of absent keys that would otherwise touch many files.

## Seek inside one sorted file

An SSTable's data blocks contain sorted keys. Its index holds separator keys and block handles with offsets and sizes. Binary-search the index to locate a candidate block, read and decompress that block, then search inside it. The index is sparse relative to individual records: one entry can cover many keys. RocksDB's block-based table format places data blocks, filter and index metadata, and a fixed footer in one immutable file.

If the index is cached, a point read may need only one data-block I/O after filtering. If the index is not cached, the lookup may first fetch index blocks. Larger blocks reduce index size and favor scans, but read more irrelevant bytes for a point query. Smaller blocks improve selective reads while increasing metadata and request counts. A remote object store makes each extra block fetch particularly expensive because network round trips dominate.

## Measure the real miss path

The worst case is often an absent key: it may be tested against many files and levels. Bloom filters reduce this cost but require CPU and memory. A positive filter is not proof of presence, so the engine must inspect the block. For a range scan, filters built for full keys may help less; ordered iterators and block prefetch are more important. Prefix filters can help some scans only when the prefix extractor and query shape agree.

Track filter checks, useful negatives, false positives, index cache misses, data-block reads, and p99 latency by hit versus miss. A low hit rate can signal a poor working set, but a filter may still be saving most negative lookups. Rebuild filters only with the immutable file they describe; pairing a stale filter with new file contents could create false negatives and lose data.

## Design review

How many files can overlap a key? Which metadata is cached? What fraction of lookups are misses? Does block size suit point reads or scans? Can any stale filter or index be paired with a different file generation?
