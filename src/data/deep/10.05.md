A mergeable sketch is a compact summary that can be combined with another compatible summary to approximate a result over their union. This property lets workers analyze partitions independently and then reduce their summaries, without shipping every raw event to one machine. The merge operation must have a defined mathematical meaning; simply adding two estimates is often wrong, especially for distinct counts and percentiles.

## Match the sketch to the question

HyperLogLog estimates distinct identifiers and can merge registers for a union. A count-min sketch estimates per-key frequencies and can combine compatible counter tables. Quantile sketches summarize a value distribution so percentiles can be queried after merging. Frequent-items sketches seek likely heavy hitters. These are different contracts: a distinct-count sketch cannot answer “which users?” and a quantile sketch cannot provide an exact sum. Apache DataSketches documents several sketch families and a feature matrix for union, intersection, and merge support.

Before selecting one, state the error bound or empirical accuracy target, memory per partition, update rate, merge frequency, and needed operations. Some sketches support only union, while others support set intersections or differences. Some accept weighted updates or deletions; many do not. A design that requires retracting fraudulent events may need raw replay or a different summary.

## Keep versions and dimensions compatible

Suppose each region maintains a daily unique-viewer sketch. A global daily estimate comes from merging sketches built with the same identifier normalization, hash function, precision, and bucket definition. If one region hashes account IDs and another hashes device IDs, the merge is technically possible but semantically invalid. Store sketch type, parameters, schema version, time window, and input definition with each serialized value. Reject incompatible merges rather than returning a plausible but wrong number.

Sketches can be merged hierarchically: worker → region → global. This reduces network transfer and spreads CPU work. Merging should be associative enough for the implementation's documented guarantee, so a retry or different merge tree does not materially change the result beyond expected error. Deduplicate partition snapshots or use versioned replacements; merging the same sketch twice can double frequency estimates for additive sketches, even if a distinct-count union is insensitive to repeated identical members.

## Publish estimates responsibly

Expose an estimate and its uncertainty or expected error, not a falsely precise integer. Validate against exact calculations on sampled or smaller buckets. Check low-cardinality behavior, skew, serialization compatibility, and memory growth. Keep raw events for a bounded period when exact audit or rebuilding matters. A sketch reduces the cost of a question, but it does not repair lost input events or a wrong event definition.

Plan time windows explicitly. A daily sketch cannot answer an arbitrary rolling 24-hour query exactly unless the system keeps finer buckets or accepts boundary error. Merging monthly and daily sketches with overlapping intervals double counts frequency metrics. Track provenance and window IDs so the query planner merges disjoint, compatible inputs. The power of mergeability is parallelism with a known approximation contract.

## Design review

Which exact question and operation must the sketch support? What error is acceptable? Are input identities and parameters identical across partitions? Can duplicate merges or overlapping windows corrupt the answer? How will an old sketch be rebuilt after a bug?
