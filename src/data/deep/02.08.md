An event contract tells consumers what happened, how to identify that occurrence, and how to interpret its data. A topic name and an arbitrary JSON blob are insufficient when several independently deployed services depend on the event. The contract includes semantics, envelope fields, payload schema, ordering, delivery expectations, and evolution rules.

## Name a fact that has already occurred

An event such as `OrderPlaced` should mean the order reached a defined durable state. If it can later be rejected by payment, perhaps `OrderSubmitted` is more honest. Consumers may take irreversible actions based on the name, so distinguish a fact from a command or tentative workflow step. The producer owns the meaning and should publish only after the underlying state transition is committed.

A useful envelope includes an event ID, source, type, occurrence time, schema version or reference, and trace or correlation ID. The payload carries domain facts such as order ID, customer ID, currency, and total. CloudEvents standardizes several envelope attributes, including `id`, `source`, `type`, and `specversion`; the `source` plus `id` combination identifies a distinct event. Your product still defines what `OrderPlaced` means and what its fields mean.

| Field | Purpose | Example question |
| --- | --- | --- |
| Event ID | Deduplication and tracing | Is it stable across delivery retries? |
| Entity ID | Associate related events | Can consumers key state by order? |
| Occurred time | Business timeline | Is it source time or broker time? |
| Schema version | Decode payload | How are old versions retained? |
| Correlation ID | Follow a workflow | Which request caused the event? |

## Define delivery and ordering

Many brokers can redeliver after a consumer crash. Treat consumers as at-least-once unless the entire end-to-end contract proves otherwise. A consumer should store a processed-event ID or make its side effect naturally idempotent. Ordering may exist only within a partition keyed by entity ID. If order events are keyed differently, `OrderCancelled` could be observed before `OrderPlaced` by one consumer. State the ordering scope and how consumers handle gaps or replays.

Payloads should contain enough facts for the intended consumers without exposing unnecessary private data. If a consumer needs a current snapshot, a small event with only an ID forces a synchronous fetch and reintroduces coupling. If the event copies every internal field, it becomes a privacy and compatibility burden. Choose the event's public facts deliberately and document who may subscribe.

## Evolve schemas without breaking consumers

Adding an optional field is usually easier than removing a required one. A new enum value may still surprise a consumer. Establish compatibility rules and test old consumers against new producer examples. For a breaking semantic change, publish a new event type or version, run both during migration, then retire the old form after consumer adoption is measured. Avoid silently changing the unit of an existing field, such as cents to dollars.

Keep example events in the contract and validate them in CI. Include duplicate, missing optional field, old schema, and out-of-order cases in consumer tests. When a producer changes, check not only that JSON parses but also that the event is emitted at the same point in the business workflow.

## Design review

What exact committed fact does this event assert? Can a consumer deduplicate it after a crash? Which events are ordered relative to it? Can a consumer using last month's schema still understand the new payload?
