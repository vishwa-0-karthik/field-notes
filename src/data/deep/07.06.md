Immutable versioned data files make a storage system easier to read concurrently and recover after failure. A writer creates a new complete file instead of changing an existing one. A manifest then names the set of files that forms the current logical database. Readers can keep using an older manifest while a new version is published. The hard parts move to publication, garbage collection, and version retention.

## Publish a new generation safely

Suppose files A and B form the current dataset. A compaction merges them into file C. Writing C does not yet make it visible. After C is complete and durable, the engine records a manifest edit saying “add C, remove A and B.” A reader that pinned the old version keeps reading A and B; a new reader sees C. RocksDB's MANIFEST records these version edits because filesystem operations alone are not an atomic multi-file transaction.

The publication order protects crash recovery. If the process crashes while writing C, the old manifest still points to A and B. If it crashes after committing the manifest edit, C must already be readable. Sync and ordering details depend on the filesystem and storage API, so test them rather than assuming a rename always makes every related file durable. A recovery path replays manifest edits to the latest consistent version.

## Let readers pin their view

Immutable files are safe for concurrent reads because their bytes do not change. A reader can hold a snapshot or version handle while compaction proceeds. It may see an older logical state, but it sees a coherent one. RocksDB tracks live SST files and delays deletion while readers still reference an old version. A remote object-store design can use generation IDs and retention windows for the same purpose, though without local reference counts it needs a conservative deletion policy.

The cost is temporary duplication. During compaction, input and output files coexist. Long-lived readers or snapshots can keep obsolete files alive much longer, increasing space amplification. Monitor oldest pinned version, obsolete bytes, and free-space margin. If disk becomes too full to write the output, compaction may stall, eventually stopping new writes even though the live logical dataset would fit.

## Separate logical and physical deletion

Removing a file from the current manifest is not the same as deleting its bytes. Physical cleanup should occur only after every reader and rollback window releases it. In object storage, versioning may retain prior object versions even after a delete marker is created. That improves recovery from accidental changes but affects cost and privacy deletion. Define lifecycle rules and audit them against retention requirements.

Use unique file IDs so a cache never confuses a newly created file with an old file at the same path. A checksum or content hash can detect corruption and help deduplicate identical data, but content-addressed names require careful handling of encryption and access scope. Keep the manifest small and recoverable; it is the map that makes all immutable pieces meaningful.

## Design review

What exact step publishes a generation? Can a reader finish on the old version during compaction? When are old bytes safe to delete? How much temporary space is needed, and how is the manifest restored after a crash?
