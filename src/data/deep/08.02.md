A task queue and an event stream both move messages between processes, but they represent different contracts. A task says “someone should perform this work.” An event says “this fact happened,” often for several independent consumers. The choice affects retention, replay, ordering, acknowledgements, and who owns the business outcome.

## Match the message to its owner

A thumbnail-generation task usually has one logical owner. Any capable worker may claim it, produce the image, and acknowledge completion. A broker can requeue after worker failure and dead-letter an unprocessable task. RabbitMQ documents consumer acknowledgements and negative acknowledgements for that handoff. The task message may be deleted once responsibility is completed, subject to the broker's persistence and queue policy.

An `OrderPlaced` event can feed billing, analytics, search, and customer notification independently. One consumer finishing should not remove the record for the others. A retained log lets each consumer group track its own offset and replay within retention. Kafka's consumer group model stores committed offsets per partition; the event remains until the topic's retention or compaction policy removes it. The producer should not need to know every future consumer.

| Decision | Task queue | Event stream |
| --- | --- | --- |
| Main meaning | Command to perform work | Fact for subscribers to interpret |
| Consumption | One worker from a competing group | Multiple independent groups |
| Replay | Usually retry or dead-letter | First-class within retention |
| Ordering | Queue-specific and concurrency-dependent | Per-partition offset order |
| Completion | Task outcome and acknowledgement | Each consumer's own progress |

These are common patterns, not hard walls. A stream consumer can execute work, and a broker exchange can fan an event into multiple queues. The important question is what the application promises and how it recovers when a subscriber is down.

## Define failure and replay semantics

A queue worker may complete a side effect and crash before acknowledgement, producing a duplicate delivery. A stream consumer may update a database and crash before committing its offset, then replay the event. Both need idempotent effects or a transaction that combines effect and progress in one authority. In a stream, a consumer that lags beyond retention cannot replay the missing range and needs a snapshot or backfill. In a queue, long-lived unacknowledged messages can exhaust broker resources or create repeated redelivery.

Do not publish a business event before its database transaction commits. An outbox row written in the same transaction can be relayed to a queue or stream afterward, with duplicate handling. Also avoid treating a task command as a historical fact. `SendEmail` means work was requested; `EmailSent` means a later outcome occurred. Naming the message by its actual meaning helps consumers avoid false assumptions.

## Choose from the access pattern

Use a queue when bounded work needs one processor, direct retry, and a terminal job state. Use a stream when several consumers need the same ordered history, replay, or independent offset management. If both are needed, a stream can record domain events and a consumer can create durable tasks. This adds a boundary, so measure end-to-end delay and failure states across it.

## Design review

Is this message an instruction or a fact? How many independent consumers need it? How long must replay remain possible? Who owns the final outcome, and how is duplicate processing made safe?
