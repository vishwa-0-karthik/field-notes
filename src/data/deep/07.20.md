An end-to-end checksum lets a reader verify that bytes received later match the bytes the writer intended to store. Storage replicas and transport checks catch many errors, but a checksum computed and checked at the application boundary can detect corruption introduced between those layers. Define what bytes are hashed, when the checksum is recorded, and which version it identifies.

## Follow the data across boundaries

A client computes a checksum over the exact object bytes before upload. The server validates the received bytes and stores the checksum with the object version. On download, a client recomputes and compares it after the full transfer. If data is transformed, such as compression or transcoding, the input and output are different objects and need separate checksums. Hashing compressed bytes on upload but decompressed bytes on read will produce a mismatch even when storage is correct.

Amazon S3 documents several checksum algorithms and both full-object and multipart-related checksum behavior. An ETag is not a universal full-object MD5 checksum, especially for multipart or other upload modes, so clients should use an explicit checksum field when integrity matters. A checksum proves equality of bytes under the chosen algorithm; it does not prove who authored them. For adversarial tampering, use an authenticated signature or MAC with protected keys.

## Check parts and the whole

Large objects upload in parts. A per-part checksum catches corruption before the entire transfer completes and supports retry of just the damaged part. A full-object checksum confirms the assembled sequence, including part order, if the service supports that contract. Record algorithm, checksum value, byte length, object version, and part layout so future readers can validate exactly what was stored. A checksum without a stable version reference can validate the wrong generation after overwrite.

For ranged reads, a full-object checksum cannot be recomputed from one range. Store block or chunk checksums, or verify the whole object when it is eventually assembled. A Merkle tree can authenticate individual chunks against a root digest, at the cost of proof metadata. Choose the simplest scheme that matches the read pattern and threat model.

## Repair and respond to mismatch

On mismatch, do not return silent success. Retry from a different replica or location if available, quarantine the suspect copy, and compare against another known-good checksum. Record the object version, range, source, and checksum algorithm in a corruption event. Scrub cold data periodically, because an object that is never read can otherwise harbor latent damage until a restore is needed.

Checksums have cost: CPU to compute, metadata storage, and additional I/O for scrubbing. Hardware acceleration and streaming calculation usually make them affordable for important durable data, but measure the pipeline. Test deliberate bit flips, truncated uploads, swapped parts, and stale caches. An end-to-end check is strongest when the writer and final reader independently verify the same immutable byte sequence.

## Design review

Which exact bytes are checksummed? Is the checksum tied to an immutable object version? How are multipart and range reads verified? What happens operationally after a mismatch, and how are cold objects scrubbed?
