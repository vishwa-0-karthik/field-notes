Distributed ID generation gives independent writers a way to assign unique names to records before a central database commit. The design choice affects availability, index locality, information exposed to clients, and what ordering can be inferred. Start by separating the requirements: uniqueness, size, approximate time order, unguessability, and whether an ID must be created while disconnected.

## Compare coordination with local generation

A single database sequence is simple and can produce compact integers, but every issuer depends on that database. A ticket server centralizes only ID allocation, which may be cheaper than centralizing all writes, yet still adds a network hop. Range allocation lets an application node lease a block of IDs and issue them locally; unused values are lost on crash, which is usually acceptable. UUIDs can be generated without shared coordination, with a collision probability designed to be negligible when the generator follows the specification.

Time-based IDs combine a timestamp, worker identity, and per-time-unit sequence. Twitter's Snowflake design used that composition to obtain roughly sortable 64-bit IDs without a coordinated call for every ID. It still needed unique worker numbers at startup. The distinction is subtle: the hot path can be uncoordinated while worker assignment remains coordinated.

| Requirement | Candidate approach | Hidden obligation |
| --- | --- | --- |
| Compact integer | Sequence or Snowflake-style | Issuer availability or clock/worker IDs |
| Offline generation | UUID | Entropy and format handling |
| Rough time order | UUIDv7 or Snowflake-style | Clock rollback policy |
| Unpredictable public token | Random identifier | Enough entropy and abuse controls |
| Strict total order | Coordinated sequencer | Availability and throughput ceiling |

## Define the uniqueness scope

An ID may be unique per table, per tenant, per entity type, or across the entire product. Two services can safely use `42` if every reference includes entity type; they cannot if a public API accepts only one bare numeric ID for all objects. Worker identifiers must be unique among concurrently active generators. Reusing a worker ID while an old process is still alive can create collisions at the same timestamp and sequence value.

Do not confuse uniqueness with commit order. A writer can allocate ID 101, pause, while another writer allocates 102 and commits first. A client sorting by ID may then see records out of real creation order. Even a time-embedded ID is only as accurate as the generating clocks and timestamp granularity. If strict order matters, use an authoritative commit timestamp or sequence designed for that guarantee.

## Fit the identifier to storage and APIs

Random keys can scatter B-tree inserts, affecting locality; roughly increasing keys may append more predictably but can concentrate writes in a particular range or expose traffic timing. Wider IDs increase index and foreign-key storage. For JavaScript clients, a 64-bit integer may exceed exact numeric representation, so send it as a string. Do not expose an internal incremental ID if it reveals sensitive business volume or makes enumeration easy; authorization remains necessary regardless of ID format.

Test restart, clock rollback, same-millisecond bursts, worker reassignment, and sequence exhaustion. Keep a unique database constraint as a final guard where possible. The chosen generator should fail closed rather than knowingly issuing duplicates when its assumptions break.

## Design review

Which guarantees are required: uniqueness, order, compactness, or secrecy? Can two live workers share an identity? What happens when the clock moves backward or a local range is exhausted? Can a client safely handle the ID's numeric width?
