# Direct-to-object-storage upload

Direct uploads let a client send large bytes to object storage without making an application server proxy every byte. The application still owns authorization, object identity, policy, and the transition from an untrusted upload to a usable asset. A safe flow is: client asks for an upload, API authenticates and checks quota, API creates an opaque upload record and a short-lived signed request for one staging key, client uploads, then client reports completion and the backend verifies the stored object before publishing it.

## Keep control and data planes separate

The API should return a generated object key, allowed method, required headers, expiry, and constraints such as maximum size and accepted content type. Do not let the client choose an arbitrary bucket key: an attacker could overwrite another user's object or place content in a public path. Scope the credential to one key and one operation. A presigned URL is a bearer capability: anyone who obtains it can use it until expiry, within the signer's permissions. Store it only in memory, avoid logging query strings, and use a short lifetime appropriate to expected upload duration. AWS documents that a presigned URL can be reused until expiration and that writing the same key replaces that object, so unique keys and one-time application state matter.

The browser sends bytes directly to storage. Configure CORS narrowly for the app origins and required methods and headers; CORS is a browser rule, not authorization. The API remains the authority for who may create an upload and whether it can become visible. For small files a single PUT is simple. For large or unreliable transfers, multipart upload allows independent parts and retries; the application needs an upload identifier, part numbers, and completion or abort semantics.

## Verify before accepting

A successful HTTP response proves storage accepted bytes, not that the object is safe or valid. On completion, the backend should `HEAD` the exact key, compare expected and observed size, record an ETag only as a storage-specific validator rather than assuming it is always a content MD5, and enqueue malware scanning or media inspection. Verify ownership against the upload record. Content type supplied by a browser is untrusted; detect type from bytes and apply format-specific parsers with resource limits. Keep staged objects private until processing succeeds. A state machine such as `created → uploading → received → scanning → ready` makes duplicate callbacks and retries manageable.

## Failures and cleanup

Clients can close the tab after storage succeeds but before notifying the API. A reconciler can find old upload records and inspect their keys. Conversely, a completion request can race a retry; make completion idempotent by persisting the verified object version and returning the same result. Delete abandoned staging objects after a retention window. For multipart uploads, explicitly abort failed sessions or configure storage lifecycle cleanup for incomplete parts, which otherwise consume space. Make retry policy bounded, with jitter, and avoid issuing a new key for every retry unless the old object is also cleaned up.

Track issued upload intents, successful bytes, failed requests by status, completion lag, abandoned bytes, scan rejection rate, and quota denials. Alert on growing staging age and storage errors. Test expired signatures, overwritten keys, forged completion events, oversized files, CORS preflight, and duplicate completion. The design should make the boundary obvious: a URL grants temporary byte-write access; it does not grant permission to publish the resulting asset.

## Design review

Does each signed request target one generated key and one operation? What limits size, type, and user quota? How does the server confirm bytes landed before accepting completion? Are staged objects private pending scanning? How are abandoned multipart parts and duplicate callbacks handled?
