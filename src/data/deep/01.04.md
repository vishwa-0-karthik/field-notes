A system design choice is a tradeoff when improving one property changes another property or transfers work to another part of the system. “Use a cache for speed” is incomplete: the cache adds invalidation, memory cost, and a failure path. Good design records both the gain and the new obligation.

## Compare choices against a workload

Suppose a product catalog serves 2,000 reads per second and 20 updates per second. A cache may reduce database load, but its value depends on whether reads repeatedly request the same products and how quickly price changes must appear. If 80% of reads hit a few thousand items, caching can be effective. If every read is unique, the cache may have low hit rate and consume memory without reducing much load.

Start with the *decision driver*: a measured symptom, an expected scale, or an explicit product promise. Then list viable options. For a slow catalog read, options include a better index, a denormalized read model, a cache, or a looser freshness requirement. Compare them using the same workload and target. A cache should not be chosen merely because it is familiar.

| Choice | Likely benefit | New cost or risk | When it fits |
| --- | --- | --- | --- |
| Add an index | Faster selective queries | Write amplification and storage | Stable query predicate |
| Cache responses | Lower repeated read cost | Staleness and invalidation | Repeated hot keys |
| Materialize a view | Fast complex reads | Pipeline lag and repair work | Expensive aggregation |
| Stronger consistency | Fewer stale reads | Higher latency or lower availability | Correctness-sensitive action |

## State the invariant before optimizing

Some tradeoffs are constrained. A stale product description might be harmless; a stale tax amount or inventory promise might not be. Identify what must remain true and where it is enforced. The catalog page can use a cache, while checkout revalidates the price and stock against the authoritative store. This yields two consistency levels for two different user actions. It is often more effective than applying the strictest requirement everywhere.

Also include operational effects. A new queue can protect the request path from downstream latency, but introduces retries, poison messages, monitoring, and a backlog recovery plan. A second region can improve availability, but complicates data residency, replication, and failover tests. The AWS Well-Architected framework makes these dimensions explicit through reliability, performance, operations, security, cost, and sustainability; the dimensions interact in real systems.

## Make the decision reversible when possible

Prefer a small experiment when data is missing. Add query instrumentation, run a representative load test, or enable a cache for a subset of traffic. Define a rollback condition before rollout: for example, “disable the cache if p99 checkout mismatch exceeds 0.01% or hit rate remains below 30% after warmup.” Keep interfaces that allow a later implementation to change without rewriting callers. Reversibility reduces the cost of a wrong assumption.

Document a design decision in a few sentences: context, chosen option, alternatives, expected benefit, known costs, and the signal that would trigger reconsideration. This is more useful than an architecture diagram alone. It tells the next engineer why a component exists and when it should be removed.

## Design review

For every new box in a diagram, ask: Which measurable problem does it solve? Which invariant does it preserve? What failure modes and recurring work does it add? What observation would prove this choice was wrong? If the answers are absent, the tradeoff has not been made explicit.
