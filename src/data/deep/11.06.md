A newly-unread indicator tells a user that content arrived after the point they last viewed. It can be a dot, a number, or a per-conversation badge. The design needs a precise boundary: “unread” may mean created since last open, delivered since last acknowledged, or not yet rendered. A dot often needs only a Boolean; an exact count needs more state and more updates.

## Use a cursor when the timeline is ordered

For a simple ordered inbox, store a per-user read cursor such as the highest seen message sequence. New items with a higher sequence make the indicator true. The client marks seen up to a chosen sequence only after it has displayed or acknowledged those items according to the product rule. A monotonically increasing server sequence is safer than client wall-clock time, which can be skewed. The update to the cursor should be monotonic so an old device cannot move it backward.

One global cursor does not cover every feed. Items may be filtered, deleted, or delivered out of order; a user can read a newer item but not an older one. For a conversation list, store per-conversation cursors or last-read IDs. For a feed, a “new posts since last visit” dot can compare the latest eligible post sequence with a visit watermark, while an exact count may require querying or maintaining a per-user unread set. State the product semantics before using the simplest cursor.

## Deliver a hint, then reconcile

A WebSocket or SSE event can tell an open client that a new item exists. The event is only a hint; after reconnect, the client should fetch current unread state from the authoritative service. Give updates a version so a delayed `unread = true` does not replace a later `unread = false` after the user opens the inbox. If a user reads on one device, publish the new cursor to other devices and let them refresh. A dropped live event should not permanently hide unread content.

The count may be cached or aggregated, but it must not become negative after concurrent read and arrival events. A transaction or compare-and-set can advance the read cursor and derive the count from item sequences. If maintaining a materialized count, reconcile it periodically against the underlying items and cursor. Redis Streams documents per-consumer cursors and ordered IDs, which illustrate the cursor idea, though a product's per-user read semantics still need their own model.

## Respect visibility and scale

Only eligible, visible items should trigger unread state. A blocked author's post, a deleted notification, or a message in a muted conversation may follow different rules. Recheck visibility when computing the badge, especially if fanout projections lag. Avoid sending every new item to every device as a separate badge update; coalesce high-rate changes and send the latest version. For a huge inbox, query by indexed sequence and user rather than scanning all historical entries.

Measure unread-state update lag, cross-device convergence time, cursor regression attempts, count drift, and reconnect snapshot rate. Test simultaneous reading on two devices, an item arriving during a read, deletion, and a long offline interval. A trustworthy dot is better than an “exact” number that is often wrong.

## Design review

What user action marks content read? Is unread a Boolean or an exact count? Which monotonic sequence defines newness? Can an old device regress the cursor? How does a reconnect repair missed live hints and stale cached counts?
