# Design: a search service

A search service turns user queries into ranked documents under a latency budget. It needs an indexing pipeline that keeps a searchable projection fresh, a query path that handles text, filters, and permissions, and relevance evaluation that reflects user intent. Search results are usually a derived view; canonical records remain in their source systems. The service should tolerate index lag while preventing deleted or unauthorized documents from being exposed.

## Ingestion and index model

Sources publish create, update, and delete events through an outbox or change stream. A normalizer extracts text, language, timestamps, structured fields, and access-control metadata, then sends versioned documents to the index. Use monotonically increasing source versions so delayed events cannot overwrite newer documents. If an index write fails, retry from a durable queue; dead-letter poison documents and expose index lag. Periodic reconciliation or rebuilds compare the search projection with canonical data. Deletions need tombstones or version checks because a late update can resurrect a removed record.

An inverted index maps terms to documents and supports tokenization, stemming, phrase matching, and relevance scoring. Field mapping is a product decision: exact keyword fields support filters and facets; analyzed fields support full text. Store document IDs and only enough fields to render result snippets. Hydrate critical or highly dynamic fields from the source service when necessary, but avoid a serial per-result fanout that destroys latency. Permission filters should be applied before returning results; post-filtering a small top-N list can hide valid items and leak unauthorized result counts or snippets.

## Query and relevance

Parse queries into bounded terms and filters. Support typo tolerance or synonyms where useful, but measure their effect on relevance and cost. Ranking can combine text score, recency, popularity, and business rules. Keep each factor observable so a result can be explained. Use facets to help users narrow results; compute them over the intended candidate set and be aware that distributed shard aggregations can be approximate. Deep pagination with offsets becomes expensive; use a search-after cursor or a point-in-time snapshot when stable traversal is needed.

Search nodes are partitioned into shards and replicas. A coordinating node fans a query to shard copies, merges candidates, and returns the top results. More shards increase parallelism but add fanout and coordination overhead; replicas improve read capacity and availability. Route repeated queries consistently when caches help, and avoid unbounded user-specific query caching. Apply per-query timeouts and cancellation to protect the cluster from expensive wildcard or aggregation requests.

## Quality and operations

Measure end-to-end latency, index freshness, zero-result rate, click or task completion, and relevance using judged query sets. A/B tests need guardrails for latency and business outcomes; click-through alone has position bias. Monitor shard health, rejected queries, merge pressure, queue depth, and document count. Test updates arriving out of order, permission revocation, index rebuild, a query with many filters, and one shard unavailable. Search quality and index correctness are both product reliability.

## Design review

How do source changes reach the index and how is lag measured? Are permissions enforced before results leave the service? Which fields are analyzed versus exact? What prevents a costly query from exhausting the cluster? How is relevance regression detected beyond raw clicks?
