An index is an extra data structure that helps a database find or order rows without scanning every row. It is valuable when a query selects a small or useful subset, but it consumes storage and makes writes do more work. Design indexes from actual predicates, sorting, and data distribution, then confirm that the planner uses them at realistic scale.

## Begin with one query

Suppose a booking page runs `SELECT id, starts_at FROM reservations WHERE customer_id = ? AND status = 'CONFIRMED' ORDER BY starts_at DESC LIMIT 20`. An index beginning with `customer_id`, then `status`, then `starts_at DESC` can support filtering and ordering for that shape. An index on `starts_at` alone may not help much if the database still must examine many other customers' rows. A primary-key index on `id` helps a different query: fetching one reservation by ID.

The order of columns in a composite index matters. Equality conditions on leading columns often narrow the search, while a following range or sort column helps traverse the matching slice. The exact planner behavior depends on the database and query; do not apply a memorized ordering rule without checking `EXPLAIN`. PostgreSQL documents B-tree indexes for equality and range comparisons and has detailed guidance for multicolumn indexes.

| Query pattern | Candidate index | Caveat |
| --- | --- | --- |
| `WHERE id = ?` | Primary key | Usually already exists |
| `WHERE customer_id = ? ORDER BY created_at` | `(customer_id, created_at)` | Direction and limit affect plan |
| `WHERE lower(email) = ?` | Expression index on `lower(email)` | Must match query expression |
| Search inside JSON | GIN or targeted expression index | Depends on operator and selectivity |

## Understand selectivity and cost

If a condition matches 90% of a table, an index may be slower than a sequential scan because it creates many scattered heap reads. If it matches ten rows among millions, an index is often valuable. Statistics help the query planner estimate row counts and choose a path. Stale statistics or skewed values can lead to poor plans. Use `EXPLAIN` to see estimates and `EXPLAIN ANALYZE` carefully to see actual behavior; remember that the latter executes the query, which matters for writes.

An index can sometimes satisfy a query's selected columns without reading the main table, but this depends on visibility and database-specific behavior. Covering indexes may improve a hot read at the cost of a larger index. Partial indexes can index only rows matching a stable predicate such as `status = 'ACTIVE'`, reducing size when most rows are inactive. These are targeted tools, not default additions.

## Account for the write path

Each inserted or updated row may require work in every affected index. A table with many indexes can have slower writes, more log volume, longer migrations, and higher storage cost. Update-heavy columns in indexes are especially expensive. Drop unused indexes only after measuring their real usage and accounting for infrequent jobs. When building an index on a large live table, use the database's online/concurrent option and understand its lock and failure behavior.

The index also cannot fix a query whose predicate prevents its use, such as wrapping an indexed column in an unindexed expression or requesting an unanchored substring search with a plain B-tree. Sometimes the better fix is a query rewrite, a different index type, or a dedicated search index.

## Design review

Which exact query is this index for? How many rows does its predicate match at production scale? Does the plan use the index and avoid an expensive sort? What write cost and migration time does it add?
