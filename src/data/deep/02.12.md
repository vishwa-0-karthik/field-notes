Tail latency is the slow end of a response-time distribution: p95, p99, or p99.9 rather than the average. It matters because real users experience individual requests, and a request that fans out to many components is more likely to encounter at least one unusually slow one. A design that looks fast at the median can still feel unreliable.

## See how fanout amplifies slow parts

Suppose a search request calls 20 independent shards and waits for all results. If each shard is slower than 200 ms on 1% of calls, the chance that at least one shard is slow is `1 - 0.99^20`, about 18%. Independence is a simplifying assumption, but the example shows why a small per-shard tail becomes a common end-to-end event. Google's “The Tail at Scale” describes this problem for large interactive systems.

Measure latency at the user-facing boundary and at each major stage. A 500 ms p99 could come from queue wait, garbage collection, a database lock, a cold cache, a network retransmission, or a slow shard. Aggregate histograms by endpoint and workload class. Mixing a cheap health check with a complex report query hides both experiences in one percentile. Compare peak and quiet periods separately.

| Technique | Helps when | Cost or caution |
| --- | --- | --- |
| Remove slow work from critical path | Work can finish later | Requires eventual-status contract |
| Bound fanout | Too many dependencies per request | May reduce completeness |
| Hedged request | Rare replica straggler | Extra load; must be safe to duplicate |
| Timeout and partial result | Some shards may be skipped | User sees incomplete result |
| Reduce utilization | Queueing dominates tail | More capacity cost |

## Treat queues as part of latency

When utilization approaches capacity, waiting time can rise sharply even if service time changes little. A worker that processes 100 requests/s cannot sustainably accept 110 requests/s; the queue grows. At a lower but bursty rate, a short peak can still create a long tail. Capacity planning should include headroom and workload variance, not just average CPU. Record queue wait separately from execution time so the fix targets the right stage.

Hedging a request to another replica after a delay can reduce stragglers, but it must have a limit and should generally be used for safe reads. Hedging writes without idempotency can duplicate effects. If every client hedges during overload, the additional traffic can make the tail worse. Choose a threshold based on measured latency distribution and use a global extra-work budget.

Partial results are a product decision. Search may return 95% of shard results with a visible indication if one shard times out; a financial balance cannot usually do that. Decide which components are required and which can be omitted. A deadline shared across the full request prevents one slow dependency from using all remaining time.

## Design review

What is the p99 of the user action, not just one service? How many independent dependencies does it wait for? Can a slow dependency be skipped, retried elsewhere, or moved out of the critical path? What extra load would the mitigation create during an incident?
