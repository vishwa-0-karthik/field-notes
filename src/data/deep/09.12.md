A crawler discovers documents, fetches them, extracts useful content, and schedules them for indexing. Its hardest work is often not downloading pages but deciding what to visit again, respecting site boundaries, and turning many URLs for the same content into one searchable document. A web crawler and a connector for a private document store share a pipeline shape, but their access rules and discovery mechanisms differ.

## Build a controlled frontier

Seed the frontier from known URLs, sitemaps, and discovered links. Store normalized URL, host, discovery source, next eligible fetch time, fetch state, and content version or fingerprint. Deduplicate URLs before enqueueing: fragments, tracking parameters, redirects, and alternate hostnames can produce many addresses for the same page. Canonicalization is partly a content decision; a site's canonical hint is useful evidence but should be validated against the actual fetched page.

Use per-host concurrency and pacing so the crawler does not overload a site. Honor the Robots Exclusion Protocol for eligible public crawling; RFC 9309 defines its parsing and caching behavior and notes that robots rules are not access authorization. Handle redirects, timeouts, HTTP errors, and `Retry-After` with bounded retries. Do not treat every 404 as a permanent delete without checking whether the source is temporarily unhealthy.

## Extract and index a stable document

Fetch bytes, detect content type and encoding, parse safely, remove navigation and boilerplate, and extract title, body, links, language, and metadata. Some pages need rendering to expose their content, which is more expensive and should be used deliberately. Google Search's public documentation describes discovery, crawling, rendering, canonical selection, and indexing as separate stages. For private connectors, use the source system's API and preserve document ACLs rather than crawling links that bypass permission metadata.

Compute a content hash or version to avoid reindexing unchanged documents. Deduplicate near-identical pages so query results do not fill with copies. Store the original URL and a canonical document ID; redirects and canonical changes should update that mapping. A parser change may require reprocessing stored raw content or refetching, so decide whether to retain raw snapshots and for how long.

## Schedule recrawls and recover gaps

Frequently changing pages need shorter recrawl intervals than static archives. Use sitemaps and source update timestamps as hints, not guarantees. A priority function can combine observed change rate, last fetch, importance, and host budget. Track HTTP cache validators such as ETag or Last-Modified when supported to avoid full downloads. Revisit failed pages with backoff, and keep a finite retry or manual inspection path for persistent errors.

Measure discovered-to-indexed delay, frontier size by host, fetch error rate, duplicate rate, parse failures, index acceptance, and deleted-page lag. Keep durable checkpoints so workers can retry a fetch without losing or double-counting a document. A crawl-complete claim should include coverage evidence: how many expected URLs were discovered, fetched, parsed, and searchable? Sites can block or omit pages, so a crawler should report gaps rather than assume full coverage.

## Design review

How are URLs discovered and deduplicated? What rules govern host pacing and robots handling? Which pages need rendering? How are ACLs and deletes propagated? What evidence shows the corpus is fresh and complete enough for the product?
