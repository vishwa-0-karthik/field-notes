# Design: rate limiting and abuse prevention

Consider a public API that serves reads, creates expensive objects, and triggers downstream work. A single per-IP limit will not protect every cost or offer fair quotas. Build admission around distinct identities and resource budgets: anonymous traffic needs broad edge protection, authenticated users need account-level quotas, organizations need tenant budgets, and costly operations need stricter operation-specific limits. The service that owns each resource should enforce its own hard limit even when the gateway rejects most excess traffic earlier.

## Threat model and policy

Abuse ranges from credential stuffing and scraping to accidental retry storms and a customer integration with a bug. Identify the constrained resources: CPU, database reads, outbound API spend, queue depth, storage, and human review capacity. For each, set limits on rate, concurrency, payload size, and total allocation. Separate a burst allowance from a sustained rate. A token bucket lets a client use a limited burst while replenishing at a steady rate; a sliding window caps total actions in a rolling interval. Pick semantics that fit the product, then publish stable error responses and retry behavior.

Use several keys. The edge can count IP or network prefix before authentication, with generous thresholds for carrier NAT. After login, key by verified account or API credential. For SaaS, enforce a tenant ceiling so one organization cannot monopolize shared capacity. Add endpoint-class limits for high-cost operations and global circuit breakers for dependencies. Never derive identity from a caller-controlled header unless a trusted proxy strips and replaces it. Use a random API key identifier rather than the secret itself as a limiter key.

## Enforcement architecture

An API gateway performs cheap early rejection, coarse bot rules, payload-size limits, and global rate shaping. Application services enforce authorization-aware quotas and specific business limits. Workers enforce bounded concurrency and queue admission before expensive processing. Central shared state provides consistent counters across application replicas but adds network latency and failure modes. Atomic scripts or transactions prevent concurrent requests from double-spending quota. Local token buckets can protect the service during a shared-store outage, but the allowed fallback must be explicit; otherwise N local instances multiply the global limit by N.

Return `429 Too Many Requests` for caller quota exhaustion, with `Retry-After` when a safe estimate exists. Distinguish temporary overload from plan quota exhaustion if clients need different remediation. Do not expose whether a sensitive account exists through the limiter response. For internal overload, shed low-priority work, use deadlines, and bound retries. A queue only delays overload; cap its age and depth. Protect critical operations with reserved capacity so bulk jobs cannot starve login, checkout, or control-plane recovery.

## Abuse response and metrics

Use risk signals such as high failure rates, rapid account creation, unusual geography, repeated token guesses, or expensive request patterns. Automated blocking should include a recovery path for false positives. Rate limiting is not a substitute for authentication, input validation, fraud detection, or DDoS mitigation. Keep limit policy versioned, auditable, and adjustable without a code deploy where operationally useful.

Track admitted and denied traffic by operation, key class, tenant tier, and region; limiter latency and errors; queue age; downstream spend; and fallback mode. Test spoofed identity headers, many app instances, NAT users, account rotation, limiter store failure, and a sudden high-cost workload. Abuse prevention should protect shared service health while making fair, explainable decisions for legitimate users.

## Design review

Which resource does each limit protect? Where is identity verified? Are global, per-tenant, and per-operation budgets composed atomically? What happens during limiter-store failure? Can the response distinguish retryable load shedding from a durable quota limit?
