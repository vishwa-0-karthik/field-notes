# Blocklist versioned file metadata

Block-based file storage separates file bytes from the metadata that says how to reconstruct a particular version. A blocklist is the ordered sequence of block identities and lengths for one file revision. The version metadata also carries the file's logical ID, parent or path, size, modification information, and previous revision or lineage. Treat each version's blocklist as immutable: edits create a new version record that reuses unchanged blocks and points to new blocks for changed data.

## Version metadata is the commit record

The upload client first ensures all newly needed blocks exist and are verified. It then submits a new blocklist with the base revision it edited. The metadata service checks authorization, validates that each block is available to the account or permitted namespace, verifies aggregate size and block count, and conditionally commits against the base revision. If another device has already advanced the file, the commit conflicts rather than silently replacing newer metadata. The service can preserve both versions or create a conflict copy according to product policy. A successful commit assigns a server revision and updates the folder's change feed.

This ordering means bytes may exist without being referenced; that is a harmless temporary orphan. The inverse is dangerous: metadata must never point at missing or unverified blocks. The metadata transaction should therefore publish only after storage acknowledgements and validation. If the metadata database update times out, the client queries by an idempotency key or proposed revision ID before retrying; otherwise it may create duplicate versions. Use server time for ordering and a logical revision or sequence rather than trusting client modification timestamps as concurrency control.

## Paths, tombstones, and history

Keep file identity separate from paths so rename and move operations can update directory metadata without rewriting the content blocklist. A folder listing can return a stable revision token and paginated entries. Sync clients consume a change log of creates, updates, moves, and tombstones. Tombstones must remain long enough for offline devices to learn about deletion; purging a tombstone too soon can cause an old client to resurrect the file. Version history policy determines which old blocklists remain roots for garbage collection. Retention and user-visible restore windows should be explicit.

Block references create a reachability graph: current file versions, retained history, shared folders, snapshots, and active upload intents can all keep a block alive. Garbage collection should remove a block only after it is unreachable from every protected root for a grace period. Reference counts can accelerate this but require repair after partial transaction failures; periodic mark-and-sweep provides a correctness check. When deleting a file, first commit a tombstone and remove it from the current namespace, then retire old versions according to retention policy, then allow block reclamation.

Index metadata for files, folders, and revisions by account and parent to serve listings and access checks. Avoid storing one gigantic blocklist in a hot relational row if files can have millions of blocks; use bounded manifests or paged structures with a stable root hash. Measure metadata commit latency, conflict frequency, blocklist size, orphan bytes, GC lag, and stale-client resyncs. Test concurrent upload, move during content update, deletion while offline, metadata timeout after commit, and garbage collection during a pending upload.

## Design review

Can a version commit only after all referenced bytes are durable? What compare-and-set prevents lost updates? How do renames and deletions propagate to offline devices? Which old versions remain GC roots? How does retry after a timed-out metadata commit avoid duplicate revisions?
