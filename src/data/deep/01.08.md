Vertical scaling gives one node more resources. Horizontal scaling adds nodes and spreads work among them. Both can help, but neither removes a bottleneck that sits elsewhere. Choose the scaling axis only after identifying the limiting resource and the shape of the work.

## Start with the current bottleneck

Suppose an API instance reaches 90% CPU at 400 requests/s while its database is at 25% CPU. A larger instance or more API replicas may increase capacity. If the database is already saturated by one costly query, more API replicas may make the outage worse. First profile CPU, memory, I/O, network, pool wait, and p99 latency. An architectural change without a bottleneck diagnosis is a bet.

Vertical scaling is operationally simple: a larger machine can run the same process and preserve local assumptions. Its limits include maximum available instance size, restart or migration time, and a larger single-node failure domain. Horizontal scaling offers more aggregate capacity and fault tolerance, but requires request routing, health checks, deployment coordination, and a plan for state held in memory.

| Dimension | Scale up | Scale out |
| --- | --- | --- |
| First implementation | Usually simple | Load balancer and replica management |
| Failure domain | One larger node still fails | Other replicas may continue |
| Application state | Local state may remain | Shared or partitioned state needed |
| Limit | Largest practical node | Coordination and data bottlenecks |

## Make request handling replica-safe

If requests may land on any application replica, a session stored only in one process can disappear on the next request. Use signed client state, a shared session store, or intentionally sticky routing with an understood failover cost. Background jobs need ownership: several replicas must not all run the same periodic task unless the work is idempotent. Uploads need shared durable storage rather than a local disk path visible to only one replica.

Stateless application replicas are relatively easy to scale. Databases are harder. Read replicas can add read capacity when stale reads are acceptable, but writes still need an authoritative path. Partitioning spreads writes by key, but queries across partitions become more expensive and hot keys can remain hot. Scaling the frontend fleet is not the same as scaling the whole system.

## Plan for transitions, not only steady state

An autoscaler reacts after a metric crosses a threshold, and new capacity takes time to start and warm. Keep headroom for bursts and for the loss of a node. Scale-up operations may also involve downtime or replica promotion. Test a sudden traffic spike and a single-node failure while measuring user-facing latency, not just CPU utilization. AWS reliability guidance recommends metrics that correlate with demand and explicitly calls out headroom during scale-out delay.

Set a practical progression: optimize a bad query or inefficient code, scale the limiting resource vertically when cheap, add replicas for independent work, then partition state only when measured limits justify it. This is not a universal order—availability requirements can justify replicas early—but it keeps each step tied to a reason.

## Design review

If traffic doubles tomorrow, which component reaches its limit first? If one replica disappears at peak, can the remainder meet the SLO? What state currently lives on a node, and how will another node find it? What metric triggers adding capacity early enough?
