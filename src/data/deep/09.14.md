Autocomplete suggests completions while a user types. It reduces effort and can guide users toward searchable entities or common queries, but it operates under a very short latency budget and sees incomplete intent. A suggestion is not a spell correction: `san` might complete to `San Francisco`, while a misspelled full query needs a different candidate process. Choose whether the product suggests query strings, documents, categories, or a clearly labeled mixture.

## Build a prefix-friendly index

A completion index can store normalized phrases with weights for fast prefix lookup. A trie or finite-state structure shares prefixes and can return top suggestions without scanning every phrase. Elasticsearch's completion suggester is designed for this fast lookup and documents its memory and index-build tradeoffs. Another approach indexes edge n-grams such as `b`, `bi`, `bik` for `bike`, then uses normal search machinery. Edge n-grams are flexible for fields and filtering but increase token count and index size. Test the chosen structure with realistic vocabulary and update rates.

Store a stable suggestion ID, display text, normalized form, type, locale, visibility scope, and weight. A product title that is deleted or becomes private must disappear within the required freshness window. A popularity weight can help, but a query-log suggestion may expose a rare private search. Require frequency thresholds or curated suggestions, and avoid surfacing sensitive or abusive text from raw logs.

## Rank for the current prefix

Filter by prefix, locale, tenant, and permission first. Rank candidates using exact prefix strength, popularity, freshness, and context. A suggestion beginning with the entire typed prefix usually deserves priority over a weak match deep inside a phrase. Dedupe equivalent spellings and avoid filling the list with near-identical variants. If the user typed a known SKU, show an exact product result rather than only a popular phrase completion.

Short prefixes can match an enormous vocabulary. Require a minimum number of characters where useful, cap results, and precompute top completions for very popular prefixes. Cache by normalized prefix plus relevant context, never by prefix alone if tenants or permissions differ. Debounce client requests and cancel stale responses so suggestions for `bi` do not replace newer results for `bike`. Keep keyboard navigation and screen-reader announcements coherent when results change rapidly.

## Observe the interaction

Measure time from keypress to visible suggestions, request rate per user, empty-prefix rate, selection rate, and the success of the search after a suggestion is chosen. A high selection rate can reflect attractive but misleading suggestions; inspect downstream results and reformulations. Run separate evaluation for head and rare prefixes, multilingual input, and rapidly changing catalog entries. If the suggestion service times out, let normal search submission work rather than blocking the whole search box.

Autocomplete can generate substantial traffic because one user action produces many requests. Budget QPS from keystrokes, not only searches, and enforce server-side limits. Maintain a clear source and rebuild path for suggestions so corrupted popularity weights or a bad analyzer can be rolled back.

## Design review

Are suggestions queries, entities, or both? What index supports prefix lookup at the target latency? How are private or deleted suggestions removed? Can stale responses overtake newer typing? What does the UI do when suggestions fail?
