Soft delete marks a record as deleted without immediately removing its row. It can support recovery, audit, and asynchronous cleanup, but it changes the meaning of every query and uniqueness rule. The core question is what “deleted” promises to users: hidden from normal views, restorable for a period, or eventually erased from all systems.

## Define the lifecycle

For a project-management app, a task might move from `ACTIVE` to `TRASHED`, remain restorable for 30 days, then be permanently deleted. A `deleted_at` timestamp can represent the transition and support a cleanup job. But a task also has comments, attachments, search documents, cache entries, and analytics events. Decide which derived views hide it immediately, which retain it for recovery, and what physical deletion entails.

Normal reads must consistently filter `deleted_at IS NULL`. One forgotten query can expose trashed data. Centralizing common query scopes can help, but test every path, including joins, exports, administrative tools, and search. A soft-deleted parent with live children needs a rule: hide children, cascade the soft delete, or allow them to remain independently visible. The rule should be expressed in domain behavior, not inferred from a database flag.

| Concern | Design question | Typical mechanism |
| --- | --- | --- |
| User visibility | When does the record disappear? | Filter and cache invalidation |
| Uniqueness | Can a new record reuse its name? | Partial unique index on active rows |
| Restore | What if the name was reused? | Conflict resolution or new name |
| Retention | When is physical cleanup allowed? | Bounded purge job |
| Privacy deletion | Must all copies be erased? | Data inventory and verified deletion |

## Revisit constraints and indexes

Suppose usernames are unique while active. A global unique index on `username` prevents reuse after soft delete. A partial unique index such as `UNIQUE(username) WHERE deleted_at IS NULL` can express active-only uniqueness in PostgreSQL. Restoring an old user may then fail if another active user claimed the name. That is a valid conflict requiring a product decision, not a database bug.

An index on active rows can also keep common reads efficient when most historical rows are deleted. But the planner uses a partial index only when it can prove a query implies its predicate. Keep query conditions explicit and inspect plans. Soft delete is an update, so it creates normal write and WAL work; a large mass-delete operation can still be expensive.

## Do not substitute soft delete for backup or erasure

Soft delete helps undo accidental user actions within a defined window. It does not protect against database loss or malicious changes, so backups remain necessary. Conversely, retaining a row indefinitely may violate a product's promised deletion or a legal retention rule. Physical purge must include derived stores, object storage, replicas, and backups according to the relevant policy. Avoid promising instant erasure if backup expiry is the actual limit.

Operationally, monitor the number and age of trashed records, purge failures, storage growth, and restore conflicts. Make purge idempotent, since retries may happen after a partial cleanup. Keep audit records only as long as policy permits and avoid copying sensitive payloads into logs that escape the deletion process.

## Design review

What exactly does a user see after delete? Which queries and derived views must change? Can a deleted unique value be reused, and what happens on restore? When and how is the row physically removed from every required location?
