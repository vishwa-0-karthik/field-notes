# Image CDN and resizing

An image delivery service turns an original upload into cacheable renditions suited to a device and placement. The central choice is whether transformations happen eagerly at ingest or lazily on demand. Eager generation makes serving predictable and avoids first-view work, but can produce many unused variants. Lazy resizing saves work for long-tail sizes, but needs abuse limits, cache design, and a strategy for cold transformations. Most systems combine a small standard rendition set with bounded on-demand variants.

## Define a canonical rendition identity

Represent a rendition as a deterministic tuple: source asset version, width, height or fit mode, output format, quality policy, and any crop parameters. Resolve that tuple to a canonical URL or internal cache key. A content version in the path makes updates safe: `/asset/abc/v7/w640/cover.webp` can have a long immutable cache lifetime, while a mutable alias needs revalidation or purge. Validate requested dimensions against a policy rather than allowing arbitrary width and height. Otherwise a client can request millions of distinct variants and turn the image service into an unbounded compute and cache workload.

The edge can serve an existing rendition or route a cache miss to a transformation service. That worker fetches the private original, decodes it with limits, transforms, writes an immutable result, and returns it. Keep the origin protected from direct public listing and use service credentials for the transform path. Normalize equivalent requests before caching: `?w=640&h=480` and reordered query parameters should not accidentally create separate objects. If format negotiation depends on `Accept`, include only a normalized supported format in the cache key or emit stable format-specific URLs. CloudFront's cache key documentation emphasizes that each additional header, cookie, or query variation can create another cache object; include only values that change the response.

## Protect decoders and control cost

Image parsers process attacker-controlled binary input. Apply byte-size, pixel-count, frame-count, CPU, and wall-time limits; reject malformed or decompression-bomb inputs. Decode in isolated workers with bounded memory. Strip EXIF metadata by default to reduce privacy leakage and avoid orientation inconsistencies. Preserve color profiles deliberately, and define how animated formats are handled. A thumbnail path should not silently decode a huge animation into memory. Validate that output dimensions and format match the canonical request before writing it.

On a miss, concurrent requests for the same rendition can stampede. Use a single-flight lock or idempotent conditional object creation keyed by the rendition identity. Locks need expiry and recovery if a worker dies. The CDN can coalesce some misses but should not be your only coordination guarantee. Set cache TTLs based on immutability: content-addressed or versioned paths can be cached for a long time; mutable endpoints should have short TTLs and a reliable invalidation plan. Purging every edge on every edit is expensive, so immutable versioned URLs are often simpler.

Measure hit ratio, transformation latency, queue depth, decode failures, origin bytes, rendition cardinality, and cost per source asset. Test odd aspect ratios, transparent images, animated files, extreme dimensions, query normalization, stale source versions, and simultaneous cold requests. The product contract should state crop behavior and whether a requested size is exact or a maximum box; that decision affects both UX and cache identity.

## Design review

Can every rendition be represented by a bounded, canonical key? Are originals private and immutable versions addressable? What limits defend image decoders? Which inputs change the CDN cache key? How do format negotiation, invalidation, and cold-miss stampedes behave?
