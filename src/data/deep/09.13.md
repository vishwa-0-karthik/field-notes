Vector search retrieves documents whose embeddings are close to a query embedding. It can find semantically related text even when exact words differ. Lexical search still excels at names, codes, rare terms, and precise phrases. Hybrid retrieval runs both and combines their candidates. The design challenge is not simply storing vectors; it is maintaining comparable document versions, enforcing filters, and measuring whether semantic recall improves the user's task.

## Build compatible vectors

Choose an embedding model, dimensionality, chunking policy, and normalization. A long article may be split into passages so a specific section can match a query. Store the parent document ID, chunk ID, model version, source version, and access metadata with each vector. Query embeddings must use a compatible model version. When the model changes, plan a backfill or dual-index period; mixing incompatible vector spaces can produce meaningless distances.

Exact nearest-neighbor search compares the query with every vector and becomes costly at scale. Approximate nearest-neighbor structures trade some recall for lower latency and resource use. A graph index such as HNSW needs memory and update capacity; its search parameters affect recall and latency. Always benchmark recall against an exact baseline on representative queries, especially after heavy insertions and deletions. A distance value has meaning within one embedding space and metric, not as a universal relevance score.

## Combine lexical and semantic candidates

Run BM25 and vector retrieval in parallel under one deadline, take a bounded candidate set from each, deduplicate by document or passage, then merge. Raw BM25 and cosine scores have different scales, so adding them naively can let one side dominate. Reciprocal rank fusion combines result ranks instead and is documented by Elastic for hybrid search. A learned reranker can score the merged candidates, but it cannot recover documents missing from both pools.

Apply tenant and permission filters during retrieval or before display with enough candidate oversampling. If filtering removes most vector neighbors after the approximate search, recall can collapse. Exact IDs and quoted phrases should retain a lexical route even when semantic search is enabled. Group passage hits back to documents and diversify results when many chunks from the same page occupy the top slots.

## Maintain and evaluate the hybrid index

An update to source text must update both the lexical record and its embeddings. Use versioned jobs and reject late embedding results generated from old content. Deletes and ACL changes must affect both indexes promptly. Embedding generation may be slow or expensive, so state the semantic freshness target separately from lexical freshness. Monitor model failures, backlog, vector-index size, ANN recall, and per-stage latency.

Evaluate on queries that require synonyms or paraphrase, and on exact names and identifiers where vectors may hurt. Compare lexical-only, vector-only, and hybrid top-K with human judgments. Track zero results, duplicate chunks, and irrelevant semantic matches. Semantic similarity is not proof of factual correctness or authority; the original source and its permissions remain decisive.

## Design review

What document or passage gets embedded? Which model version produced each vector? How is approximate recall measured? How are lexical and vector rankings merged? Can stale vectors or ACLs expose deleted or private content?
