Log-structured storage turns updates into new records appended to a log instead of overwriting old bytes in place. It makes the foreground write path simple and sequential, but it creates a background obligation: find the newest value, remove obsolete versions, and keep recovery time bounded. The design is a trade between immediate write cost and later merge work.

## Append first, reorganize later

For each `put`, write a framed record containing a key, value, and checksum to the active segment. For a delete, append a tombstone. A read needs an index or search structure to find the newest record among segments. In a hash-log design, an in-memory key directory points directly to the latest offset. In an LSM design, a memtable and sorted disk files let the reader search by key order. Both append changes, but their read and scan behavior differs.

An append can be acknowledged after it reaches process memory, the operating system, synchronized disk, or a replicated log. These are distinct durability promises. RocksDB documents the difference between non-sync and sync writes, and its write-ahead log protects in-memory state under the configured recovery model. Choose an acknowledgement level from the product's loss tolerance; do not equate an append call returning with stable storage.

## Recover the latest logical state

On restart, replay committed log records in order to rebuild an index or memtable. A checksum and length let recovery detect a torn final record. A batch update needs a commit marker or atomic framing so a crash after only part of the batch does not expose half a logical transaction. If the log becomes huge, startup replay becomes slow; periodically checkpoint the index or flush a sorted table, retaining only the log range newer than that checkpoint.

The log must also represent deletion correctly. A tombstone can be discarded only after the system knows that no older value can reappear from a lower level, replica, backup replay, or delayed file. Removing a tombstone too early can resurrect data. Retention and privacy deletion therefore need a documented path through compaction and old versions, not just a new delete record.

## Pay the merge debt

An append-only log fills with old values. Compaction reads segments and writes a new segment containing current data. This reclaims space and can improve reads, but consumes I/O and temporary disk space. If writes arrive faster than compaction can process them for long enough, the engine must slow writers, let read and space amplification grow, or run out of storage. RocksDB's write-stall documentation treats backpressure as protection against unbounded debt.

Measure foreground write latency together with compaction bandwidth, bytes rewritten per logical write, obsolete bytes, and p99 read latency. Test a sustained workload after the store is full. A short burst benchmark can make an engine look exceptionally fast while merely deferring work into a growing backlog.

## Design review

How does a read identify the newest version? At what point is an append durable? How is a partial final record recovered? What bounds log replay and compaction debt? When can a tombstone safely disappear?
