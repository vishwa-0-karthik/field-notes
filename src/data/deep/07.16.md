A partition manager decides which nodes own each slice of a keyspace. Its map table turns a logical partition ID or key range into current replicas, a leader or leaseholder, and an ownership generation. The map is control-plane data: small in bytes, large in consequence. A safe manager must publish changes atomically and make stale clients harmless.

## Give the map an explicit shape

For range partitioning, a map entry might contain `[start_key, end_key)`, range ID, replica set, leaseholder, and epoch. For hash partitioning, it might contain a token interval or fixed hash slot. Include status such as creating, copying, serving, or retiring. A client can cache a versioned snapshot and route requests locally. A server checks the epoch and either serves, redirects, or rejects a stale request. This avoids requiring a metadata-service lookup on every read while preserving an authoritative source for changes.

Redis Cluster demonstrates one concrete map: keys hash to 16,384 slots, and nodes own subsets of those slots. Moving slots changes ownership without changing the hash function. Spanner's range splits show the alternative: ranges can be split and assigned independently as size and load change. The manager can use either model, but its map and handoff rules must match the storage layout.

## Move a partition in stages

Suppose partition P moves from A to B. The manager first ensures B has the required data, perhaps by snapshot plus a stream of later writes. During catch-up, A remains authoritative. After B reaches a known commit position, the manager publishes a higher ownership epoch and B begins serving. A refuses new writes under its old epoch and may redirect clients. Finally, remove A's copy after retention and recovery conditions are met. If A and B both accept writes during the cutover without a conflict rule, the map has failed its purpose.

Faults can occur at each step. B may crash during copying; A may fail before cutover; the manager may publish an epoch while some clients hold the old map. Make steps idempotent and persist progress so the manager can resume. A retry with a stale epoch should not turn into a successful write on A. Use a quorum-backed metadata authority or transactional store for map changes that affect correctness.

## Balance without thrashing

The manager can split a range that is too large, move a hot partition to a less busy node, or add replicas for read load. Moving data consumes network and disk bandwidth and can worsen latency while in progress. Use hysteresis and rate limits so a short traffic spike does not cause repeated moves. A single hot key may remain hot after moving and require a different solution.

Monitor map version age at clients, redirects, ownership conflicts, bytes in flight, replica lag, and movement completion time. Keep a manual freeze or rollback path for a bad rebalance. A metadata outage may pause new moves while cached maps keep existing partitions serving; define that degraded mode explicitly.

## Design review

Who is the authority for the map? What generation does each server enforce? How are writes handled during copy and cutover? Can a stale client corrupt the former owner? What prevents rebalancing from overwhelming the cluster?
