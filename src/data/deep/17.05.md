# Design: a database migration

Treat a database migration as a multi-release protocol between application versions and data. The aim is to change schema or ownership while production traffic continues and while rollback remains understandable. Before writing DDL, identify every reader and writer: web binaries, background jobs, analytics, admin tools, old mobile clients, and delayed events. A migration is unsafe if one of these can still use a representation that a new release removes.

## Expand the schema compatibly

Suppose a large `display_name` field must be split into `given_name` and `family_name`. First add the new nullable fields without removing the old field. Deploy a version that can read both layouts and continues to write the old field, or dual-writes under a defined transaction. Deploy to all web and worker pools and wait for old binaries to drain. If the deployment can be rolled back, the prior version must still understand the expanded schema.

Backfill old rows in bounded primary-key ranges. Checkpoint progress, throttle by database load and replica lag, and make each batch idempotent. A concurrent user update can race the backfill, so update only rows whose source version has not changed, or use a change stream to replay writes after the snapshot. Compare counts and values using sampled checks and aggregate invariants. Only after parity is confirmed should reads switch to the new fields. Keep a short period of dual-read comparison to catch semantic differences such as nulls, whitespace, or legacy values.

## Contract with evidence

The contract phase removes old writes, then old reads, then drops the legacy field in a later release after all old clients and jobs are gone. DDL behavior depends on the database and version. Adding an index, constraint, or column may lock, scan, or rewrite data. Use online or concurrent operations only after understanding their failure modes; they may need multiple scans or leave an invalid object. Set lock timeouts so a migration does not wait behind a long transaction and create a queue of blocked requests. Monitor lock waits, transaction age, CPU, I/O, disk headroom, and replication lag.

For a data-store move, keep the old store authoritative initially, copy a snapshot, replay changes, compare reads, and shift traffic gradually. Dual writes across two databases are not atomic without a coordination protocol. Prefer an outbox or change-data capture from one source of truth. Define a rollback point and how to reconcile writes created after cutover; simply routing back can lose them.

Rehearse on production-shaped data, record expected time, and have an operator stop condition. A partial migration should remain safe and resumable. Track backfill lag, parity difference, failed batches, lock duration, and traffic version. Test interrupted deployment, a write racing the backfill, a stale worker, a failed concurrent index, and rollback after new-format writes have begun. The migration is done only when data, code, and every hidden consumer have moved together.

## Design review

Can old and new binaries coexist? How are concurrent writes preserved during backfill? Which database locks or rewrites occur? What evidence permits the read cutover? How can rollback work after new-format writes exist?
