# Design: a file sync service

A file sync service keeps folders and files consistent across devices with different connectivity and local edits. It stores immutable content blocks separately from versioned file and folder metadata. Clients exchange change cursors and manifests, transfer only missing blocks, verify content hashes, and publish new versions through conditional metadata updates. Conflict handling and deletion propagation are correctness requirements; bandwidth optimization is secondary.

## Metadata and content plane

Each file has a stable identity, independent of path, and a sequence of immutable revisions. A revision contains size, content hash, ordered blocklist, and parent revision. Folder membership maps names to file identities. The metadata service owns revision order, paths, permissions, tombstones, and sync cursors. The block service stores immutable content-addressed blocks and serves authorized uploads/downloads. This separation lets identical data deduplicate while the metadata layer preserves user-visible identity and history.

When a device edits locally, it records the base revision and computes changed blocks. It requests missing block uploads, sends those bytes, and commits a new manifest only after every block is durably present and verified. The commit compares the base revision to the current one. If unchanged, publish the new version; if another device has advanced it, preserve a conflict copy or invoke a domain-specific merge. Do not use client clocks as the sole last-writer-wins rule. Clients can resume uploads and downloads by block identity after reconnecting.

## Change feed, deletion, and offline behavior

Devices keep an acknowledged server cursor and request ordered changes after it. The feed includes updates, moves, and tombstones. If a cursor is too old for retained history, require a full rescan or snapshot instead of returning an incomplete delta. Tombstones must remain long enough for offline devices to learn about deletion; otherwise they may resurrect an old file. Account deletion and shared-folder membership changes should revoke access before cleanup proceeds. A local edit made after a remote delete should enter a conflict or recovery area, not silently recreate the shared file.

Content-defined chunking can preserve boundaries after insertions, while fixed blocks are simpler and may be sufficient for many workloads. Deduplication affects privacy: global equality leakage can reveal that two accounts share a block, so scope block namespaces or encryption policy appropriately. Garbage collection traces current revisions, retained history, shared copies, and active upload sessions. Mark-and-sweep with a grace period is easier to audit than immediate reference-count deletion.

## Operations

Measure convergence delay, bytes transferred per changed byte, conflict rate, cursor resets, hash failures, abandoned uploads, and GC lag. Test concurrent offline edits, rename and edit races, deleted file resurrection, partial block arrival, permission revocation, restore from an older snapshot, and an interrupted manifest commit. The client should show whether content is local, syncing, conflicted, or fully saved so users are not misled by a stale icon.

## Design review

Which service owns paths, revisions, and blocks? How is a manifest committed atomically after data verification? What happens when the base revision is stale? How are tombstones retained for offline devices and removed after a safe interval? Does deduplication reveal cross-user equality?
