A file-backed dictionary is the smallest useful storage engine: map a key to a value, keep enough information to find the latest value, and recover after restart. Building one clarifies why logs, indexes, checksums, and compaction appear in larger databases. The example can stay simple, but its write acknowledgement must be honest.

## Start with an append-only record

Write records such as `length | checksum | key length | key | value | version` to the end of a data file. After a successful append, update an in-memory map from key to file offset. A lookup checks the map, seeks to the offset, reads the record, and validates its checksum and key. An update appends a new record and changes the map; a delete appends a tombstone. Old records remain until compaction. This design avoids in-place modification and makes the write path easy to reason about.

The order of operations matters. If the map changes before the record is safely written, a crash can leave the map pointing at missing data. Since the map is memory-only, rebuild it by scanning valid records on startup. A partial final record should be ignored or truncated according to a documented recovery rule; a corrupt record in the middle should raise an error rather than silently skipping unknown data. Include an offset and version in diagnostics.

## Decide when a write is durable

An operating-system write can return before data reaches stable media. If the API promises survival of machine crash, synchronize the file and handle the sync result before returning success. If it promises only process-crash survival, state that weaker contract. Grouping multiple writes into one sync can improve throughput but changes which acknowledgements are safe. RocksDB exposes this distinction through its `sync` write option and explains the potential loss of recent non-sync writes after machine failure.

Use one writer or serialize appends so two records cannot interleave. Readers can use offsets from a consistent snapshot of the in-memory map; a record already appended is immutable. For multi-key atomic updates, this simple dictionary is insufficient without a transaction record or batch framing that recovery can recognize as all-or-nothing.

## Reclaim old records safely

Compaction writes only the latest live value for each key into a new file. Do not replace the old file until the new file is complete, synchronized, and published through an atomic manifest or rename sequence appropriate to the filesystem. Readers may hold offsets into the old file, so delay deletion until they are done or switch generations atomically. Keep enough spare disk space for the new copy during the merge.

An in-memory map uses space per key. At millions of keys, that overhead may become the limiting resource, pushing the design toward a sparse disk index or sharded files. Startup scan time also grows with the log. A compact hint file can accelerate rebuild, but recovery must still verify it against the durable data and handle a crash during hint creation.

## Design review

What does success from `put` guarantee? How does startup handle a torn final record? Can a reader use an offset while compaction switches files? How large can the key directory grow, and how long does restart take?
