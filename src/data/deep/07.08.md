Bitcask is a log-structured hash table designed for fast point lookups. It appends key-value records to data files and keeps an in-memory directory, called keydir, mapping each key to its newest file and offset. That layout avoids a disk index lookup for an existing key. Its main boundary is that metadata for every key must fit in memory.

## Follow one write and read

Only one file is active for appends. A write records key, value, timestamp or version information, and framing metadata, then updates keydir to the new location. A read consults keydir and fetches the value directly from the referenced file offset. Older records remain on disk until a merge. A delete writes a tombstone so a later recovery scan knows that an older value must stay hidden.

The keydir points to a fixed-size descriptor for each key, not to the full value. That makes values larger than the index entries affordable, but a very high key count still consumes significant RAM. If one billion keys each required even a few dozen bytes of directory state, the index would need tens of gigabytes before process overhead. Bitcask fits workloads with enough memory per key and point reads; ordered range scans are not its strength because the on-disk log is not sorted by key.

## Rebuild and merge safely

At startup, the engine needs to reconstruct keydir from data files. Scanning every value file is possible but slow at scale. Bitcask's design uses hint files that summarize key locations in merged segments, so startup can build the directory without reading all values. The active or recently written segment still needs careful replay. A corrupt or incomplete tail must be recognized and handled according to the file format, rather than accepted as an arbitrary key mapping.

Merge compaction scans closed segments, keeps only the newest live value for each key, writes new segments, and emits hint files. The active segment is not merged while it is being written. Readers may still hold offsets into old files, so the engine must publish the new file set and delay deletion until those readers are safe. Temporary duplication means enough free disk space is required during merge.

## Decide the durability boundary

Append-only does not automatically mean every acknowledged write survives power loss. The process may update keydir after the operating system has buffered a record but before stable storage. Configure synchronization or group commit for the desired loss window, then test crash recovery. A keydir built from durable files after restart must not claim a record that never made it to storage. Likewise, a write that returned success but was not synchronized may be lost under a weaker contract.

Bitcask also illustrates a broader lesson: trading disk-index work for RAM is effective only while the index fits. Monitor keydir size, startup reconstruction time, merge backlog, obsolete-data ratio, and point-read latency under cold file cache. If range queries or key cardinality grow beyond the original workload, another engine shape may be a better fit than trying to bolt sorted scans onto a hash log.

## Design review

How many distinct keys must keydir hold? What is the required durability point for a write? How are tombstones and old segments merged? Can the service tolerate startup rebuilding and does it need range scans?
