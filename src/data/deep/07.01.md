A storage engine turns a logical operation such as `put(key, value)` into durable bytes and an efficient path to find them again. Its design starts with constraints: record size, read shape, write rate, durability promise, device behavior, and available memory. A file format or index is only useful when it matches those constraints and survives crashes and upgrades.

## Write the workload before the structure

Estimate how many keys exist, their key and value sizes, update frequency, and retention period. Separate point lookups from range scans. A workload that reads adjacent keys benefits from sorted blocks; one that only looks up opaque IDs may favor a hash index. Large values can dominate cache space, so an engine might store metadata and data separately. Decide whether reads must see a just-acknowledged write and whether multiple keys must change atomically.

Device assumptions matter. Sequential writes were especially attractive on spinning disks, while SSDs reduce seek cost but still have finite write endurance and bandwidth. The operating system page cache, filesystem, and drive's own cache sit between an application write and stable media. RocksDB's documentation distinguishes a write returned after the OS accepts it from one synchronized to persistent storage. Define “durable” at the API boundary, then select sync and replication policies to meet it.

## Bound memory and disk amplification

An in-memory index can make point reads fast, but its cost grows with key count. A billion keys cannot be assumed to fit in RAM. A disk index trades more reads for a smaller working set. Measure read amplification as extra reads per query, write amplification as storage bytes written per logical byte, and space amplification as physical size versus live logical data. RocksDB's tuning guide makes these three dimensions explicit because improving one can worsen another.

Compaction is part of capacity planning. An append-only format writes fast but accumulates obsolete versions. Reclaiming space may need to rewrite large segments while serving foreground requests. Reserve disk headroom for temporary outputs and rate-limit background I/O so p99 reads do not collapse. A system that performs well only with an empty database or no compaction has not met its workload constraints.

## Define corruption and recovery behavior

Choose a record checksum, framing format, and recovery rule for a partial final write. A write-ahead log can replay committed updates after a crash, while a snapshot can shorten recovery. Keep the distinction between crash recovery and backup: a valid but accidentally deleted record can be propagated and compacted away. Test power-loss-like interruption at each write boundary, not just a clean process restart.

Version the on-disk format. Readers must recognize old versions during rollout or a migration must convert them safely. An engine embedded in several services may need mixed-version compatibility for weeks. Specify byte order, lengths, checksums, and unknown-field behavior, and make the upgrade reversible where practical. Monitor recovery duration as the log and data set grow.

## Design review

What are the dominant read and write shapes? What exactly does an acknowledged write survive? How much RAM may the index consume? What are the amplification and compaction budgets? Can a new binary read an old data file?
