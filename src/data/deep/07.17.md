An object store's metadata database maps names to the bytes and versions that users can retrieve. It also supports listing, ownership, policy, and lifecycle operations. Object payloads may be huge, but metadata entries are small and numerous; their access patterns can become the limiting part of the system. Design point lookup, ordered listing, and update consistency together.

## Separate the metadata questions

A `GET bucket/key` needs the current version's location, size, checksum, and access rules. A `LIST prefix` needs an ordered view of many names. A `DELETE` may create a tombstone or version marker. These operations do not all benefit from the same index. Hashing a full key distributes point lookups, but a prefix listing may require fan-out across every hash partition. Range-partitioning names helps listing but can create hot ranges under sequential key patterns. A system may keep a primary object map plus a secondary bucket index, with a transactional or carefully reconciled update between them.

Ceph's RADOS Gateway documentation provides a concrete public design: it distinguishes metadata, bucket indexes, and object data. A bucket index stores entries used for listing; object data can occupy one or more underlying RADOS objects. That implementation is not a claim about Amazon S3 internals, but it shows why a scalable object API often has several metadata structures.

## Publish an object atomically to readers

An upload must not make a partially written object visible. One approach writes payload chunks first, then commits a head or manifest record that points to complete bytes. Ceph's bucket-index design describes writing the head object last as a visibility commit for reads. Listing also needs to reflect completed updates according to the service's consistency contract. If a crash occurs between payload and metadata commit, a reconciler can later remove orphaned bytes.

Overwrites and deletes need version identity. A reader that resolves version V should fetch V's bytes even if another writer publishes V+1 moments later. Keep old versions as long as active readers, versioning policy, or rollback require them. Apply authorization to the current metadata state rather than trusting a cached pointer from an earlier request.

## Scale a hot bucket index

A bucket with billions of objects can overwhelm a single index shard. Split or shard the index, maintain routing metadata, and bound listing-page work. A listing cursor should carry the last seen key and a consistent or explicitly live traversal rule. Large deletes or lifecycle transitions can produce bursts of metadata writes; schedule them without starving user requests.

Monitor point-lookup latency, listing latency, index-shard size, hot prefixes, orphaned payloads, and time between payload commit and index visibility. Back up the metadata authority and test rebuilding indexes from durable object manifests when possible. Losing the index can make durable bytes effectively inaccessible even when every payload replica survives.

For a listing outage, check whether point reads can remain available from the object map. Keeping those paths separate can reduce the blast radius of one overloaded bucket index.

## Design review

How are GET and prefix LIST indexed? What single record makes an upload visible? Can a reader pin an exact version during overwrite? How are orphaned bytes and missing index entries reconciled?
