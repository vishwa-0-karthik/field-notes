Cost-aware architecture treats money as a design constraint that can be measured per unit of useful work. The objective is not the cheapest monthly bill. It is to meet the product's reliability, performance, security, and growth needs at a sustainable cost, including engineering and operational effort.

## Build a unit-cost model

For a media upload service, estimate cost per uploaded GB and per delivered GB. Storage cost depends on retained bytes and replicas; delivery cost depends on egress and cache hit rate; processing cost depends on transcode minutes and output variants. If 1 TB arrives each month and copies are kept for twelve months, stored data accumulates even when upload traffic stays flat. A bill based only on today's write rate misses the retention curve.

For an API, a useful unit might be cost per thousand successful requests. Include compute, database, cache, queue, logging, and network. The fixed baseline matters too: a low-traffic product can spend more on always-on clusters than on actual requests. Unit costs help compare architectures as traffic grows, while total cost shows whether the business can afford the baseline.

| Cost driver | Question to ask | Common lever |
| --- | --- | --- |
| Compute | Is capacity idle or CPU-bound? | Right-size and scale with demand |
| Storage | What is retained and replicated? | Lifecycle and retention policy |
| Egress | Which bytes leave the provider? | CDN, compression, regional placement |
| Database | Which queries and replicas dominate? | Indexes, query changes, read models |
| Operations | How many systems need on-call care? | Simplify topology and automation |

## Connect cost to user value

A redundant deployment across zones may increase the bill but be necessary to meet a checkout SLO. A multi-region active-active system may be unjustified for an internal report that tolerates a day of recovery. State the requirement first, then find the least costly architecture that meets it with margin. AWS's Cost Optimization pillar frames the task as achieving required outcomes with resources that are actually used, not simply removing every expense.

Beware of local optimizations. Compressing every response can reduce egress while raising CPU cost and latency. A cache can reduce database reads but add memory, invalidation traffic, and stale-result support work. Serverless billing can be efficient for intermittent work but expensive under sustained high-volume execution. Compare the whole request path and the expected workload distribution.

## Observe and revisit

Tag resources by product or environment, set budgets and anomaly alerts, and review cost by service and unit over time. Load tests should produce a capacity curve, not only a pass/fail result: requests per second at the target p99, CPU per request, database work per request, and marginal cost. Revisit estimates after growth, a major feature, or pricing changes. Cloud prices are time dependent, so a design note should state assumptions rather than hard-code a claim that one product is always cheaper.

The largest saving may be avoiding unnecessary retention, duplicate processing, or an unused environment. Deleting a log field can be cheaper than changing instance families if logs dominate storage and ingestion. Conversely, cutting logs so far that incidents cannot be diagnosed may increase operational cost. Cost decisions need feedback from both billing and reliability data.

## Design review

What is the current cost per useful operation and its largest component? What happens to total cost when traffic or stored data grows tenfold? Which reliability promise justifies each expensive redundancy? Which assumption would you measure next?
