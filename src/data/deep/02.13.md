Load shedding deliberately rejects or omits some work before overload causes every request to fail slowly. It is a reliability mechanism for finite capacity. A fast, explicit rejection can preserve useful service for admitted requests and give callers a chance to back off.

## Recognize the overload point

A service has a sustainable throughput at a latency target, not an infinite capacity number. As incoming work approaches that rate, queues and tail latency often rise. If the system keeps accepting work, it may run out of memory or connection slots, time out most requests, and trigger retries that add even more load. Shed before the collapse point, using a signal that correlates with real saturation: in-flight work, queue age, CPU, database pool wait, or a combination.

Suppose a thumbnail service can process 800 images/s while meeting its SLO. A surge sends 1,500/s. If it accepts all jobs into an unbounded in-memory queue, the queue grows by 700/s and the oldest request becomes stale. If it admits only 800/s and returns a retryable rejection for the rest, admitted jobs can complete. The caller may retry later with backoff; if the work is optional, it may skip the thumbnail for now.

| Work class | Example policy | User impact |
| --- | --- | --- |
| Critical write | Reserve capacity or fail explicitly | Caller knows action did not complete |
| Interactive read | Short queue and deadline | Fast error or degraded view |
| Optional enrichment | Omit under pressure | Core response still works |
| Background task | Persist in bounded queue | Later completion with visible lag |

## Make priority and fairness explicit

Do not let a single tenant consume all capacity. Per-tenant limits or weighted fair queues can protect others. Reserve some capacity for health checks and administrative repair, but do not assume every request marked “high priority” can bypass limits. Priority rules should be simple enough to understand during an incident.

At the API boundary, choose an appropriate status such as `429` for client rate limits or `503` for temporary service overload, with documented retry guidance. Internally, the shedder should distinguish a request rejected before work starts from one whose side effect may have committed. If the outcome is ambiguous, the client needs an idempotency key or status query before retrying.

## Prevent a retry storm

Load shedding and client retries must agree. Immediate retry after a rejection recreates the same pressure. Use randomized backoff, cap attempts and elapsed time, and respect a server-provided retry delay where applicable. Consider a retry budget so additional attempts remain a small fraction of normal traffic. Monitor the accepted rate, rejected rate, completed rate, latency of admitted work, and downstream saturation together.

Test the policy with a ramped load test and with one backend missing. The desired outcome is stable latency for a useful fraction of requests, clear rejection for the rest, and rapid recovery when demand falls. Google's SRE guidance discusses shedding as a way to survive overload and avoid cascading failures; the mechanism should be practiced before a real surge.

## Design review

At what measured point does the service stop admitting work? Which work is protected, and which is rejected first? Will clients retry in a way that helps recovery? Can an operator tell whether the system is shedding by design or failing unexpectedly?
